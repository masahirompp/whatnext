# フックで取れない値は会話記録で補う

[ADR-0001](0001-read-state-only-from-agents-json.md) と [ADR-0009](0009-receive-hooks-and-otel-from-launched-sessions.md) を補う。サイクル4の途中で決めた。

セッションの今の様子（一言、待機時間、保留を解く判定、`!` のコマンド）は、フックから取る。
フックで取れないときは、Claude Code がセッションごとに残す会話記録（`~/.claude/projects/*/<sessionId>.jsonl`）から取る。
段は引き続き `--json` だけで決め、会話記録は段の判定に使わない。
CTX の列は OTel だけから取り、会話記録では補わない。

フックで取れないのは、次の2つの場合である。

- whatnext の外で起動したセッションと対話セッション。フックは `n` で起動するときに `--settings` で付けるので、ほかの経路で起動したセッションには届かない。
- whatnext を閉じている間にターンが進んだセッション。受けた値はメモリにだけ持つので、閉じている間に発火したフックは失われる。

会話記録は、whatnext が読むだけで書き込まない。利用者の設定も変えないので、[ADR-0002](0002-no-writes-no-persistent-state.md) は守られる。

## 依存する範囲

会話記録の形式は公開された仕様ではない（フックの入力に `transcript_path` の項目があるだけ）。
版の更新で壊れたときの影響を小さくするため、依存するのは次の項目だけに限る。項目の中身と実測は [claude-code-behavior.md](../claude-code-behavior.md) にある。

- 置き場所：`--json` の `sessionId` を名前に持つファイル。フォルダ名は組み立てず、`sessionId` で探す（worktree の中で動いたセッションは、worktree のパスに対応するフォルダに記録が残る）
- 行の `type`（`user`、`assistant`）と `timestamp`
- `message.content`：`user` の文字列（指示）、`assistant` の `text` と `tool_use`（`name`、`input`）、`tool_result`
- 失敗の印（`isApiErrorMessage`）

形式が変わって読めなくなっても、段と並びは変わらない。
一言が出なくなり、待機時間は観測からの推定に戻るだけである。
形式の変化には、`claude` の更新のたびに checking-claude-cli スキルで見本との差分を確かめて気づく。

## Considered Options

- **attach したあとでフックを仕込む**：動いているセッションに、あとから `--settings` を足す手段がない。`claude respawn` はフラグを取らず、`--resume` に `--settings` を付けると別の ID のコピーが起動する（[ADR-0006](0006-receive-otel-from-launched-sessions.md)）。利用者やプロジェクトの `settings.json` にフックを書くのは ADR-0002 に反し、whatnext と関係ないセッションにも効き、whatnext が異常終了すると設定が残る。
- **tmux の `capture-pane` で attach している画面を読む**：画面ではバッククォートが描画で消えるので、コードとして書かれた `!` と地の文の `!` を区別できない。[ADR-0003](0003-no-input-injection-or-proxy-response.md)（画面を解析しない）にも反する。
- **会話記録に一本化して、フックと OTel の受け口をやめる**：同じ値を作る経路が1本で済み、実装も確かめる手間も減る。しかし、非公開の形式への依存が全面的になる。公式の口であるフックを主にした。その代わり、whatnext が起動したセッションでは補う経路がほとんど動かず、そちらの不具合に気づきにくい。完了条件に、フックのないセッションで補う経路を確かめる項目を置いて補う。
- **CTX を会話記録の `message.usage` で補う**：取れる見込みはあるが、利用者の判断で OTel だけにした。
- **会話記録を `!` のコマンドだけに使う**：最初はこの範囲で検討した。外で起動したセッションの一言と待機時間にも同じ読み取りで足りるので、状況の把握全体に広げた。

## Consequences

- whatnext が起動したかどうかで外から見える違いは、CTX の列（外で起動したセッションと対話セッションでは `-`）だけになる。
- 待機時間は、whatnext の起動直後や開き直した直後から分かる。「起動して最初の更新で見えた行は `-`」は、会話記録もない場合だけになる。
- 保留を解く判定に、会話記録の伸びを使える。外で起動したセッションで、attach したまま作業を終えて戻ると保留が残るという穴が塞がる。OTel のイベント数はこの判定に使わない。（サイクル8で保留は利用者の操作でだけ解くことにし、この判定はなくなった。2026-10-06）
- PRODUCT.md の Out of Scope「一覧に出ない過去のセッションを再開する機能」は引き続き外に置く。会話記録を読むのは `--json` に出ているセッションを補うためだけで、過去のセッションを探す入口にはしない。
