# 本体が依存するコマンドは `claude`、`git`、`tmux` だけにし、外部の出来事はセッションとして拾う（改訂2）

[ADR-0005](0005-dependencies-and-contact-points.md) の改訂版。サイクル3の終わりに、作業台のために tmux を必須にした（[ADR-0010](0010-workbench-lives-inside-whatnext.md)、改訂前は ADR-0007）。また、起動したセッションからフックを受けるようにした（[ADR-0009](0009-receive-hooks-and-otel-from-launched-sessions.md)）。

whatnext 本体が依存するコマンドは `claude`、`git`、`tmux` だけにする。
`git` を許すのは、`claude --bg` が worktree を使うため、whatnext を使う環境には事実上 `git` があるからである。
`tmux` は作業台のために必須にする。サイクル6までは popup（`display-popup`）を使ったので 3.2 以上とした（確かめたのは 3.7c）。サイクル7で popup をやめたので（[ADR-0014](0014-workbench-shows-in-a-screen-the-user-opens.md)）、求める版は使う機能で決め直す。whatnext は専用のサーバで使い、利用者の tmux の設定には触れない。
URL やエディタを開く `open`、端末の設定を保存・復元する `stty`、フックが値を送る `curl`、作業台で動いているもののコマンド行を引く `ps` は、macOS と主な Linux に常にある基本コマンドなので、依存を増やすものとして扱わない。
`!` のコマンドをコピーするときは、`pbcopy` があれば使い、なければ端末のエスケープシーケンス（OSC 52）でコピーする。`pbcopy` は macOS の基本コマンドとして同じ扱いにする。Linux には標準のコピーのコマンドがないので、OSC 52 で依存を増やさずに済ませる。

次の基準のどれかに当たる機能は本体に入れず、別ツールにする。

| 基準 | 本体に入れると崩れるもの |
| --- | --- |
| 状態を持つ | ADR-0002 |
| 常駐が必要 | 本体は常駐しないので、閉じている間の取りこぼしを防げない |
| 人の操作なしに行為をする（セッションを起こすなど） | 「どれに手を付けるかを示す」という役割 |
| `claude`、`git`、`tmux` 以外に依存する | 依存先のない環境でも本体が同じように動くこと |

例外として、無くても同じ手順で動き、在れば便利になるだけのコマンドは、任意の依存として使ってよい。
今は `ghq`（新しいセッションの作業ディレクトリの候補を増やす）と `gh`（行に PR を出す）の2つである。
どちらも無ければ候補や表示が減るだけで、エラーも出さず、ほかの動作も変わらない。
任意の依存は、候補や表示を足すことにだけ使い、段の判定や操作の成否を左右させない。
ただし、任意の依存で足した表示に付く操作（例：`gh` で出した PR を開く）は、その依存がないときは選択肢に出さないだけにしてよい。表示が無ければその操作の対象も無く、ほかの操作は変わらないからである。

別ツールとの接点は、外部 watcher が起こすセッションだけにする。
外部 watcher が `claude --bg` でセッションを起こし、whatnext が `--json` でそれを拾う。
一覧に並ぶのは「CI が落ちた」という通知ではなく、原因を調べて計画を出したセッションになる。

whatnext の入力は、`--json` と、whatnext が起動したセッションから受けるフックと OTel である（ADR-0009）。
段は `--json` だけで決め、フックと OTel の値は行の一言、列の表示、待機時間の推定、保留を解く判断にだけ使う。
フックと OTel は `claude` 自身が送るもので、依存するコマンドは増えない（フックの送信に使う `curl` は基本コマンド）。

## Considered Options

- **tmux を任意の依存にし、あるときだけ作業台を出す**：無いときと有るときで attach と離脱の流れが2通りになる。任意の依存は「候補や表示を足すことにだけ使い、操作の成否を左右させない」という規則にも反する。依存を増やしたくないのはその通りだが、使い勝手を犠牲にするのは本末転倒として、必須にして試す（利用者の判断）。サイクル4の途中で、`!` のコマンドをコピーの機能にして tmux に頼らなくしたのを機に見直したが、attach と離脱の流れが2通りになる理由は残るので、必須のままにした。tmux を入れない利用者の需要が見えたら見直す。
- **外部 watcher を whatnext に同梱する**：処理済みの位置という状態を持ち、常駐し、人の操作なしにセッションを起こすので、基準の複数に当たる。
- **項目プラグインで外部の出来事を一覧に取り込む**：入力が `--json` とプラグインの二系統になり、段の判定規則が二つに分かれる。外部コマンドは関数を返せないため、解決の手段を JSON で表して whatnext が実行することになる。`gh` を本体から呼ぶと依存も増える。セッションを起こすほどではないが一覧には出したい出来事が実際に溜まってきたら、再検討する。
- **属性プラグイン（既存の行に表示用の属性を足す外部コマンド）を接点に置き、外部のメトリクス基盤からコストを読む**：ADR-0004 ではこの口でコストの列を出す予定だった。利用者に、常駐するメトリクス基盤とその設定を求める。whatnext が起動している間だけ OTel を受ければ足りたので、口ごと外した。
- **常駐してコストを集計する仕組みを自作する**：常駐と集計を持つ別ツールが一つ増え、基準に当たる。whatnext が起動している間だけメモリで受けるのは、常駐も永続状態も持たないので採る（ADR-0006）。
- **`ghq` の置き場所を自分で走査する**：`git` だけで済むが、`ghq` の配置の規則を whatnext が抱えることになる。`ghq` を使っていない環境では、どちらの案でも候補は増えない。
- **fzf で作業ディレクトリを選ばせる**：attach と同じく端末を子に渡すことになり、戻ったときの端末の状態という問題をもう一つ抱える。候補は多くて数百件なので、Ink の中の絞り込みで足りる。

## Consequences

- tmux の入っていない環境では whatnext は動かない。起動時に tmux がなければ、そのことを英語で示して終了する。
- PRODUCT.md の Out of Scope「一覧の常時表示」の理由のうち、「tmux を常用しない環境でこの一機能のために導入するのは割に合わない」は失効した。
