# whatnext は何も書き込まず、永続状態を持たない

whatnext はファイルにもどこにも書き込まず、次の起動に持ち越す状態を持たない。
セッションの起動は `claude --bg` を呼ぶだけ、状態の取得は `claude agents --json` を読むだけにし、独自のセッション台帳やプロセス管理も持たない。
状態をすべて Claude Code 側に置くことで、whatnext を閉じてもセッションは動き続け、whatnext を経由せずに起動したセッションも同じように拾え、whatnext を捨てても何も失われない。
利用者の設定（`~/.claude/settings.json` など）も書き換えず、書き換えを求める別ツールも前提にしない。
プロセス内のメモリ（初めて観測した時刻など）は永続状態に当たらない。閉じれば消え、次の起動で観測し直す。

## Considered Options

- **検証用の計測ログだけは追記専用で書く**：成功指標を数値で測るための例外として検討したが、成功指標は利用者が定性的に判断すると決めたため、書く理由がなくなった。
- **外部からの push 型キューを受ける**：常駐していない間の push を取りこぼさないには永続キューが要る。外部の出来事は外部 watcher がセッションとして起こせば `--json` に現れるので、キュー自体が要らない（ADR-0005）。
- **過去の分布から閾値を決めて燃焼率の異常を検知する**：閾値を決めるには2週間以上の蓄積の保存と読み戻しが要る。
- **ACP で起こしたセッションを `session/load` で復元する**：自分が起こした `sessionId` を覚えておく必要がある（ADR-0003）。
- **statusline のコマンドにタップを挟み、セッションの情報（モデル、effort、コンテキスト、PR）を取る**：statusline の JSON は公式に文書化された口で、attach していない `--bg` のセッションにも `refreshInterval` ごとに届く。しかし、設定された statusline のコマンドにしか渡らないので、利用者の `settings.json` を書き換えてタップを挟む必要がある。タップはキャッシュのファイルも書く。利用者の設定を変えないので却下した。whatnext が起動するセッションにだけ `--settings` でタップを付ける案は、whatnext の外で起動したセッションが空欄になり、User Story 12 に反する（OTel については、この空欄を受け入れた。ADR-0006）。

## Consequences

起動した直後は、どのセッションについても待機時間が分からない。
履歴を前提にする機能（使った作業ディレクトリの記憶など）は作れず、候補は今の `--json` から作る。
端末のウィンドウを閉じても whatnext は終了せず、プロセスのメモリは終了まで残る（[ADR-0012](0012-list-runs-inside-the-dedicated-tmux-server.md)）。書き込まず、終了すれば消えるので、永続状態には当たらない。
セッションの停止（`claude stop`）と削除（`claude rm`）は `claude` への操作であり、whatnext 自身は書き込まない。`claude --bg` による起動と同じ扱いにする。
