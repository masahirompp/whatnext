# 作業台は、利用者が端末の別の分割で開く作業台の画面に、専用の tmux の2つ目のクライアントとして映す

Decision の「whatnext は端末のアプリを操作しない」は、Ghostty で押した `ctrl+q ctrl+w` と一覧の `w` に限って [ADR-0015](0015-ghostty-split-for-workbench-on-ctrl-q-ctrl-w.md) で改めた（作業台の画面の分割を作り、そこへ移る）。

[ADR-0010](0010-workbench-lives-inside-whatnext.md) のうち、作業台を claude の画面の上に popup で出す部分を置き換える。作業台の寿命（whatnext を終了すると閉じる、確認を出せずに終わったときは動いているものを残す）と、専用の tmux サーバに置くことは、ADR-0010 のまま変えない。サイクル7の開始時に決めた。

サイクル6の作業台は、`ctrl+q ctrl+q` で claude の画面の上半分に popup で出した。利用者は、作業台を開いたまま claude の画面にも入力したいこと、並べて見比べるときに claude の画面の高さを減らしたくないことから、popup をやめると決めた（サイクル6の終わり）。左右に並べると、端末の選択が左右の文字をまたいでコピーに混ざる。これを解くことが、形を決めるうえでの中心の制約だった。

- 端末の選択は、端末のアプリの分割の中に閉じる。1つの端末の画面を tmux や自前の描画で分けている限り、端末の選択はその境を知らない。選択を閉じ込めるには、マウスを奪って自前で選択を描く（tmux の `mouse on`）しかなく、選択とスクロールの手触りが端末本来から外れる。
- whatnext の操作（`ctrl+q` のキー、メニュー、概要の行とキーの説明のステータス行）は、tmux の上に積んである。維持したい操作感はこちらにある。

そこで次のようにする。

- 作業台は、専用の tmux サーバのセッション `sh-<id>` のまま置く。
- 利用者は、端末の別の分割（左右でも上下でも、別のタブやウィンドウ、別の端末のアプリでもよい）で `whatnext workbench` を実行する。これは専用サーバの2つ目のクライアント（作業台の画面）になる。
- whatnext は、1つ目のクライアント（whatnext の画面。一覧と、`claude attach` の動くセッション `<id>` を映す）の切り替えに合わせて、作業台の画面を `sh-<id>` に切り替える（`switch-client -c`）。一覧を映している間は、カーソルの行のセッションの作業台を映す。
- whatnext は端末のアプリを操作しない。分割を作る、フォーカスを移す、幅を変える、閉じる、は利用者が端末の操作で行う。
- 作業台を作る時機は利用者が決める（`ctrl+q ctrl+w`、一覧の `w`、作業台の画面の案内で `Enter`）。作業台の作業ディレクトリは作った時点のセッションの場所になり、worktree に入る前か後かで変わるため。
- 作業台の画面は同時に1つだけ映す。2つ目が来たら、新しいほうが映す。

こうすると、コピーは端末の分割の中に閉じ、両方に入力でき、claude の画面の高さも減らない。どれも端末の機能のままで成り立つ。作業台の画面も専用サーバのクライアントなので、`ctrl+q` の whatnext の操作も tmux の既定のキー（`ctrl+q c` など）もそのまま効く。作業台の中身は tmux が持つので、作業台の画面を閉じても、一覧に戻っても、端末のウィンドウを閉じても残る。

## Considered Options

サイクル7の開始時に、手元の Ghostty 1.3.1 と tmux 3.7c で確かめたことと、各道具の docs と GitHub を調べたことに基づく（2026-09-30）。

- **popup のまま（サイクル6）**：開いている間は claude の画面に入力できず、claude の画面の上半分が隠れる。popup をやめる動機そのもの。
- **tmux の中で左右のペインに分ける（作業台を常に、または `ctrl+q ctrl+q` で出す）**：コピーの混ざりを避けるには `mouse on` が要り、選択とスクロールが tmux のコピーモードの手触りになる。ホイールで遡ったまま文字を打つと一番下に戻り、トラックパッドの慣性のあるスクロールも1行ずつになる。
- **whatnext が Ghostty の分割を AppleScript で作る**：Ghostty 1.3 には AppleScript の辞書があり（`split`、`focus`、`close`、`input text`。作業ディレクトリ・コマンド・環境変数を渡せる）、ADR-0010 の「端末のアプリには外から操作する口がない」は古い事実になった。ただし、whatnext が分割を作ったり閉じたりすると、Ghostty 専用になり、macOS の自動操作の許可を求め、セッションを移るたびに分割の中身を差し替えることになる。分割を利用者が作り、中身の切り替えを tmux で行えば、これらはすべて要らない。
- **Ghostty の `cmd+d` で開いたただのシェルを作業台にする**：作業台と whatnext のつながりがなくなる。セッションの作業ディレクトリで開かず（左の分割で動くのは tmux のクライアントで、claude のいる場所を Ghostty に伝えない）、セッションを移っても追従せず、ウィンドウを閉じれば止まり、`⚙` も作業台の中の whatnext のキーも失う。
- **セッションごとに Ghostty のタブを開き、whatnext はタブを出し入れする**：作業台は各タブの中の `cmd+d` の分割になり、Ghostty 本来の操作で済む。ただし、attach している間の操作を保つには claude の側を tmux のクライアントのままにする必要があり（Ghostty のキーは外部のコマンドを動かせず、利用者の設定を whatnext は書き換えない）、作業台は上の案と同じくつながりを失う。
- **tmux の control mode（`tmux -CC`）で、tmux のペインを端末の本物の分割として映す**：`cmd+d` がそのまま専用サーバのペインになり、コピーも端末本来になる理想の形。Ghostty は解析部分だけを持ち、利用者が使える形にはなっていない（ghostty-org/ghostty#1935 は open。2026-08 に mitchellh が「予定には残っている」と述べた）。iTerm2 は長く対応しているが、キー入力を iTerm2 が受けて送るので、tmux のキーの表（`ctrl+q` の prefix）、ステータス行、`display-menu` が効かない見込みで、whatnext の操作を作り直すことになる。cmux（Ghostty をもとにした macOS の端末）は ssh 越しの tmux だけを control mode で映す（beta）。
- **WezTerm の mux に置き換える**：分割がサーバのペインなので `cmd+d` の問題は解けるが、tmux の上に積んだフック、メニュー、キーの表、ステータス行を Lua で書き直し、その Lua を利用者の設定に置くことになる（[ADR-0002](0002-no-writes-no-persistent-state.md) とぶつかる）。安定版は 2024-02 から出ていない。
- **kitty、otty**：外から分割を操作する口はある（`kitty @ launch --location=vsplit`、`otty pane split`）。どちらもウィンドウを閉じるとプロセスは止まり（配置の復元だけ）、キーで外部のコマンドを動かせない。otty は AppleScript でタブの `processes` を取れるが、若く（GitHub のタグは v0.1.0）、日本語入力の記述がない。
- **herdr で tmux を置き換える**：背景のサーバ、JSON を返す CLI、ペイン単位の選択を持つ。ただし1つの端末の画面を分ける点は tmux と同じで、選択は herdr のもの（`mouse on` と同じ種類）になり、端末本来の手触りにはならない。tmux の上に積んだ操作も作り直すことになる。
- **Web UI（一覧を Web ページにし、claude の画面と作業台を端末部品で載せる）**：キーと画面の組み合わせをすべて whatnext が握れる唯一の形で、選択は端末部品ごとに閉じる。代わりに、端末部品（xterm.js）の描画と日本語入力の品質に頼り、作業台の寿命を持つサーバを自作し、手元のシェルを動かせるローカルのサーバの安全性（起動ごとのトークン、Origin の検査、DNS rebinding）を引き受け、一覧の描画と tmux の仕組みを捨てる。ブラウザがキー（`cmd+w` など）を先に取り、ウィンドウも1つ増える。作り直す量が大きいので、この ADR の構成を利用者が使って悪いと判断したときの第一候補として残す（PRODUCT.md の Out of Scope）。
- **デスクトップアプリ（Electron、Tauri、または Swift と libghostty）**：Web UI の利点に加えてキーを取られないが、配布（署名と公証）と作り直しの量がさらに大きい。利用者は Web UI のほうを選んだ。
- **作業台の画面を2つ以上同時に映す（tmux のセッショングループで、同じ作業台の別のウィンドウを映す）**：利用者が欲しかったのは、1つの作業台の中を `ctrl+q %` で割って2つのコマンドを並べることで、これは1つの作業台の画面の中で足りる。
- **作業台の画面を開いたときや、セッションを移ったときに、作業台を自動で作る**：worktree に入る前に作ると、リポジトリの根で開いてしまう。

## Consequences

- whatnext は端末のアプリに依存しない。確かめるのは Ghostty で行う。
- claude の画面の幅は、作業台の画面を開いている間、分割の比率の分だけ減る。高さは減らない。作業台の画面は任意なので、要らないときは閉じて全幅に戻す。
- `ctrl+q ctrl+q` は空く。作業台を作るキーを `ctrl+q ctrl+w`（一覧の `w`）にし、待ち先は `f`（`ctrl+q ctrl+f`）に移した（[ADR-0013](0013-whatnext-keys-hold-ctrl-after-ctrl-q.md) の文字の規則は保つ）。
- 起動の口に、サブコマンド `whatnext workbench` が1つ増える。
- whatnext は、作業台の画面のクライアントを見分けて切り替える。一覧のクライアントを1つに限る規則（[ADR-0012](0012-list-runs-inside-the-dedicated-tmux-server.md)）と同じく、作業台の画面のクライアントも1つに限る。
- popup を使わないので、tmux に求める版は `display-menu` などの版で決まる（[ADR-0008](0008-dependencies-and-contact-points-with-tmux.md) は popup のために 3.2 以上としていた）。

## 見直す条件

- Ghostty が tmux の control mode を使える形で統合したとき（#1935）、または Ghostty 独自のマルチプレクサ（mitchellh が進めている）が、端末を閉じても残るペインを外から扱える口を持ったとき。`cmd+d` をそのまま作業台にする形を、端末本来の操作のまま取れる。
- cmux が手元の tmux を control mode で映せるようになったとき。
- 利用者が使って、この ADR の構成の作業台の使い勝手がサイクル6より悪いと判断したとき（PRODUCT.md のサイクル7の完了条件）。Web UI を第一候補にして決め直す。
