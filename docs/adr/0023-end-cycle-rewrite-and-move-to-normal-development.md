# cycle 9 でサイクル型リライトを終え、通常の開発に移る

cycle 1 から cycle 9 までは、`src/` とテストをサイクルの終わりに捨て、docs だけから書き直す方式で開発した。
cycle 9 の終わり（2026-11-21）に、利用者がこの方式を終えると決めた。`src/` とテストは捨てず、以後は今のコードを直しながら育てる。

cycle 9 を最後のサイクルにするかは、cycle 9 の終わりに決めることにしていた（[ADR-0020](0020-rewrite-the-list-in-cycle-9.md)、PRODUCT.md「サイクル9の完了条件」）。
利用者は、cycle 9 の whatnext が cycle 8 より良くなったと判断した（完了条件の 6）。

## 決めたこと

- `src/` とテストを残す。コードを捨てないので、タグ `cycle-9` は作らない（利用者の判断）。
- CLAUDE.md から、サイクル型リライトの決まり（層の定義、使い捨て層の削除の手順、昇格の決まり、旧サイクルのコードを見ない決まり、ADR の基準の「サイクルを跨いでも覆らないか」という読み方）を外す。
- `lib/` と `mod/` は置き場所を変えない。`lib/` の契約の docs（`docs/lib/`）は保ち、`src/` → `lib/` の一方向の依存も保つ。「`src/` は `lib/` の中のコードを読まない」という決まりは、docs だけで書き直せるかを確かめるためのものだったので、外す。
- すべてのコードを本番品質で維持する。挙動を変えるときは、同じ変更の中で docs を直す。
- 学びを issue に起票する決まりは保つ。サイクルのマイルストーンは付けない。
- PRODUCT.md と DESIGN.md に残る「サイクル N」の記述は、経緯の記録として残す。

## Consequences

- docs とコードの食い違いを、書き直しで洗い出す機会（cycle-audit）がなくなる。食い違いは、挙動を変える変更の中で docs を直すことと、受け入れシナリオのテストで防ぐ。
- 過去のサイクルのコードは、タグ `cycle-1` から `cycle-8` で参照できる。
