# 作業台は whatnext 専用の tmux サーバに置き、whatnext を閉じると閉じる

[ADR-0007](0007-workbench-in-a-dedicated-tmux-server.md) の改訂版。サイクル4の開始時に、作業台と `claude attach` の寿命と、作業台のキーを決め直した。

`Enter` で端末を子に明け渡す仕組みと、端末のウィンドウを閉じたときの扱いは、[ADR-0012](0012-list-runs-inside-the-dedicated-tmux-server.md) で置き換えた（サイクル5）。以下の該当箇所は、ADR-0012 の構成が破綻したときの戻り先として残す。

ステータス行は、サイクル5で attach した claude の画面の最下行にだけ出すことにした（PRODUCT.md「作業台」）。以下の「ステータス行も出さない」と、Considered Options の「tmux のステータス行にキーを出す」は、サイクル4の時点の判断である。

利用者は仕事用の PC で Claude Code を sandbox の中で動かし、credential を読めないように設定している。
そのため docker、gcloud、terraform などは sandbox の中では動かせず（`!` で打っても同じ）、人が sandbox の外で手で動かす。
手で動かすときに「どのセッションのための端末か」「その端末がどこに行ったか」で迷う。これが Problem Statement の「ウィンドウが散らばる」の具体例である。

whatnext は、セッションごとに**作業台**（そのセッションの作業ディレクトリで開いたシェル）を持ち、セッションの画面から離れずに開けるようにする。そのために tmux を使う。

- whatnext は専用の tmux サーバ（`tmux -L <名前> -f <whatnext の設定>`）を使い、利用者の tmux サーバや設定には触れない。tmux は作業台のためだけに使うので、利用者から隠す（ステータス行も出さない）。
- `Enter` で、whatnext の子として、専用のサーバのセッション `<id>` に入る。`<id>` の中で `claude attach <id>` を動かす。子が終わることが「attach から戻った」になり、端末を明け渡す仕組みは tmux を使わないときと同じである。
- 作業台は同じサーバの別セッション `sh-<id>` に置き、キーで popup として claude の画面の上に出し入れする。popup の中では分割やウィンドウの追加ができ、それは `sh-<id>` に残る。
- キーの起点は `ctrl+q` の1つだけにする。`ctrl+q ctrl+q` で作業台を出し入れし、`ctrl+q l` で一覧に戻る。作業台の中では `ctrl+q` が tmux の prefix として働く。`ctrl+q` は Claude Code（2.1.283 の既定の割り当て）、tmux の既定、Ghostty のどれも使っておらず、シェルでの意味（zsh の push-line など）も使う頻度が低い。
- `ctrl+q l` で一覧に戻ったときは、tmux のクライアントだけを離し、`claude attach` は畳まずに残す。次の `Enter` では attach し直さず、すぐに元の画面に戻る。
- 空のプロンプトの ← で Agent View に入ったとき（端末のタイトルが `claude agents` に変わる。`pane-title-changed` のフックで拾う）は、`claude attach` を畳んで一覧に戻る。Ctrl+Z は `claude attach` が自分で終わるので、何もしなくても一覧に戻る。どちらも、次の `Enter` で attach し直す。
- 残した `claude attach` は、そのセッションを止めたとき、削除したとき、whatnext を閉じたときに畳む。
- 作業台は whatnext を閉じると閉じる。作業台でシェル以外のものが動いていれば、閉じる前に確認する。
- セッション本体は引き続き `claude --bg` で起動する。whatnext を閉じても、セッションは動き続ける。

whatnext が確認を出せずに終わったとき（端末のウィンドウを閉じた、`kill` した、異常終了した）は、次のように扱う。

- 終わる処理を走らせられる場合（端末が閉じた合図を受けたときなど）は、残した `claude attach` と、何も動いていない作業台を畳み、シェル以外のものが動いている作業台だけを残す。
- 次に whatnext を開いたとき、前の tmux サーバが残っていれば、動いているものがある作業台について、引き継ぐかを確認する（既定は引き継ぐ）。何も動いていない作業台と、残っていた `claude attach` は、確認せずに捨てる。

## Considered Options

- **whatnext を閉じても作業台を残す**（ADR-0007 の決定）：長い e2e を流したまま whatnext を閉じられる。しかし、閉じたあとも見えないところにシェルとプロセスが残る。利用者は「作業台は whatnext の中にある」と受け取っており、閉じれば閉じるほうが直感に合う（利用者の判断）。whatnext は一覧を開いたまま使う道具なので、流したまま閉じる場面は少ないと見込む。
- **確認を出せずに終わったときに、作業台をすべて閉じる**：端末のウィンドウをうっかり閉じると、`terraform apply` などが途中で止まる。止める判断を利用者に委ねるため、動いているものは残して次の起動で聞く。異常終了ではどのみちサーバが残るので、次の起動で拾う処理はいずれにせよ要る。
- **戻るたびに `claude attach` を畳む**（ADR-0007 の決定）：常駐のメモリ（1本あたり約 140MB）を使わないが、入り直すたびに attach し直す待ちが生じる。並行は 3〜8 個の想定で、常駐させても 1GB 程度に収まるので、入り直しの速さを採った。
- **常駐させる `claude attach` を直近 N 本に限る**：どれが畳まれたかが利用者から見えず、入り直しの速さが不規則になる。
- **whatnext を閉じても `claude attach` を残す**：開き直しても速いが、閉じたあとも見えないところでメモリを使い続ける。
- **作業台のキーを `ctrl+q w` にする**：一番よく使う出し入れのたびに、指を離して別のキーを押すことになる。`ctrl+q ctrl+q` は ctrl を押したまま q を2回押せば済む。prefix を2回押すと直前のウィンドウに移るという tmux の慣習とはぶつかる。
- **Option（meta）のキーを使う**：Ghostty では `macos-option-as-alt` の設定が要り、Claude Code も `meta+p` などを使う。
- **tmux のステータス行にキーを出す**：claude の画面が常に1行減る。キーは一覧のキーの説明に載せる（サイクル5で覆した）。
- **利用者の tmux サーバに `whatnext` セッションを置く**：一覧に戻るキーをサーバ全体に割り当てることになり、利用者の設定を書き換える。
- **一覧も tmux の中で動かし、attach を `switch-client` にする**：サイクル4の開始時は、利用者の tmux の中で起動すると入れ子の扱いが増えることを理由に退けた。しかしこれは気持ち悪さだけで、不具合の想定はない（サイクル4の終わりに利用者と確認した）。今の形でも、利用者の tmux の中で起動すれば、専用サーバのクライアントは入れ子になっている。一方、この形なら whatnext が端末を明け渡さずに済むので、Node の内部 API への介入（working-with-ink スキル）と `stty` による保存と復元が要らなくなる見込みがある。次のサイクルで試す（PRODUCT.md の Further Notes「端末の明け渡しを無くす案（構想）」）。
- **tmux を使わず、作業台は一覧の行から全画面で開く**（`/usr/bin/screen` や `dtach` でシェルを生かす）：セッションの画面から離れずに開けない（Ctrl+Z → 一覧 → 行のキーの2手）。← の誤操作も検知できない。会話を読みながらその場で作業台を開けることが、解きたい問題の中心なので採らない。
- **whatnext が端末と `claude attach` の間に入り、画面を合成する**：node-pty と端末エミュレータの自作になる（Out of Scope「一覧の常時表示」と同じ理由で、依存の総量が tmux より重い）。
- **`node-pty` と `@xterm/headless` で tmux を置き換える**（エミュレータを自作しない版）：`node-pty` の子プロセスは whatnext のプロセスが持つので、whatnext が確認を出せずに終わると作業台も失われ、動いている `terraform apply` などが途中で止まる。避けるには常駐のプロセスを別に立てることになり、tmux のサーバを作り直すのと同じになる。`@xterm/headless` は画面の状態を持つだけで、実際の端末への差分の描画、popup の重ね合わせ、キーの振り分け、大きさの変更への追従は whatnext が書く。`node-pty` はネイティブモジュールで、環境によってはビルドが要るので、導入の手間も減るとは限らない。
- **tmux の代わりに Zellij などを使う**（サイクル4の終わりに調べた）：必要なのは、利用者の設定と分離した専用のサーバ、クライアントがいなくても生き続けるセッション、CLI からの切り替え、popup、claude の画面の忠実な中継の5つである。Zellij は、macOS の日本語入力で1文字だけの確定が効かず（zellij-org/zellij#4878）、Claude Code を中で使うと IME の候補窓の位置がずれる（anthropics/claude-code#50650）。`CLAUDE_CODE_NO_FLICKER=1` で描画が崩れ（anthropics/claude-code#42930）、既定のキーが多く `ctrl+b` とぶつかる。tmux 3.7c で実測した罠を作り直すことにもなる。CLI からの切り替え（0.44）、入れ子のセッション（0.45）、WASM のプラグインで一覧を作れることは利点である。日本語入力の不具合が直り、claude の画面が崩れないことを実機で確かめられたうえで、プラグインで一覧を作る利点が欲しくなったら再検討する。WezTerm の多重化と kitty の遠隔操作は端末のアプリに縛られ（次の項と同じ理由）、GNU screen には popup がなく、dtach と abduco にはセッションを生かす機能しかない。
- **端末のアプリの機能**（Ghostty の分割など）：外から操作する口がない。端末のアプリごとに作ることになる。
- **エディタの端末を作業台にする**：ウィンドウを行き来する問題そのもの。
- **作業台を横のペインに出す**：実装の違いは小さい（`split-window` か `display-popup` か）。popup なら claude の画面の大きさが変わらず、フォーカスを移すキーも要らない。popup の中でも分割できるので、popup だけにした。
- **`--bg` をやめて、普通の `claude` を tmux の中で動かす**：← を押すと会話が別の `id` の `--bg` のセッションに移る。`--json` の `id` と `state` を失い、セッションの寿命を whatnext の tmux サーバが握ることになる（[ADR-0002](0002-no-writes-no-persistent-state.md)）。
- **一覧で選んだ行の画面をプレビューする**：読む負荷が attach と変わらない（Out of Scope）。

## Consequences

- tmux が必須の依存になる（[ADR-0008](0008-dependencies-and-contact-points-with-tmux.md)）。
- whatnext を正常に閉じれば、tmux サーバは残らない。確認を出せずに終わったときだけ、動いているものがある作業台を持つサーバが残り、次の起動で扱いを聞く。状態を持つのは tmux であって whatnext ではなく、whatnext は tmux のセッション名（`<id>`、`sh-<id>`）から見つけ直すので、[ADR-0002](0002-no-writes-no-persistent-state.md) は守られる。
- セッションを削除するときは、`sh-<id>` と残した `claude attach` もまとめて閉じる。作業台でシェル以外のものが動いていれば、そのコマンドを示して確認を求める（`terraform apply` の途中で閉じると state のロックが残るなど、取り返しがつかない）。
- 作業台でシェル以外のものが動いていることを一覧に出すため、tmux が返すペインのプロセスから `ps` でコマンド行を引く。
- Agent View から別のセッションに入る操作は、whatnext から入ったセッションでは使えなくなる。
- 作業台の最後のシェルを `exit` で抜けると `sh-<id>` は消える（tmux の既定の動作）。次に出すと新しく作る。
