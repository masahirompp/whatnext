# セッションへの入力の注入や、返信と権限応答の代行はしない

whatnext はセッションの画面を解析せず、入力を注入せず、返信や権限応答を代行しない。
セッションを操作するときは attach で端末を明け渡し、利用者が直接操作する。
whatnext の役割は「どれに手を付けるか」を示すことで、返信を速くすることではない。
画面の解析を誤って `y` や `1` を送ると、承認するつもりのなかった破壊的な操作を承認し、しかもそれは利用者が画面を見ていないときに起きる。

## Considered Options

- **tmux send-keys で入力を注入する**：得られるのは数秒の短縮だけで、誤った承認の危険に見合わない。tmux への依存も生じる。
- **Agent View の peek に当たる返信機能を自前で作る**：peek の劣化コピーになる。順位が正しければ、返信は attach で足りる。
- **ACP（Agent Client Protocol）経由で権限要求に応答する**：権限要求は、エージェントのプロセスからそれを起動したクライアントへの RPC なので、whatnext 自身が起こしたセッションにしか届かない。ACP で起こしたセッションは `id` を持たない `interactive` の行として出て、whatnext が終わると一覧から消える。これは ADR-0002 にも反する。権限待ちが日に数十回に増え、その多くが `permissions.allow` の規則にできない種類になるか、ACP で起こしたセッションに `kind: "background"` と `id` が付くようになったら、再検討する。
- **attach せずに一覧の上で権限を許可する**：`--bg` のセッションの権限要求に答える公式の口はない（`--permission-prompts` は `--print` 専用）。実現するには上の3案のどれかに戻ることになる。

## Consequences

権限待ちの解除には、attach、許可、離脱の往復が要る。
往復の手間を減らしたいときは、権限待ちそのものを `permissions.allow` の規則で減らす方向で考える。

セッションが勧めた `!` のコマンドを、作業台（利用者自身のシェル）の入力欄に貼ることは、セッションへの入力の注入に当たらない。貼るのは利用者がメニューで選んだときだけで、Enter は押さない。claude の入力欄には貼らない。
