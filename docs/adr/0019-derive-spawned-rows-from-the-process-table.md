# 起動された行の起動元を、OS のプロセス表から導く

スキルのスクリプトや stdio の MCP サーバが Bash から起動した `claude -p` は、`--json` に `interactive` の行として出る。しかし、どの行が起動したかは `--json` にない。
起動元が分からないまま行が増えると、利用者には起動した覚えのない行に見える。
そこで、`ps` のプロセス表で行の `pid` の祖先をたどり、最初に当たった `--json` の別の行を起動元とし、一覧では起動元の下に `(sub)` を添えて入れ子で並べる（[PRODUCT.md](../PRODUCT.md)「起動された行」）。
サイクル8の完了条件を満たしたあとに、利用者の依頼で決めた（2026-10-25、PR #236）。

[ADR-0008](0008-dependencies-and-contact-points-with-tmux.md) の次の2点を改める。

- **入力**：`--json`、フック、OTel に、OS のプロセス表を足す。`ps` は作業台の `⚙` ですでに使っている基本コマンドで、依存するコマンドは増えない。
- **段の決め方**：「段は `--json` だけで決める」を、「段は `--json` の値と、行どうしの関係（利用者が結んだ待ち先と、プロセス表から導く起動元）から決める」に改める。関係から導くのは待ちの段だけで、`--json` の値から決める段の規則は変えない。起動元は、待ち先と同じく、自分がレビュー待ちに当たり、起動された行が終わっていなければ待ちの段に入る。

状態は今までどおり `--json` からだけ読む（[ADR-0001](0001-read-state-only-from-agents-json.md)）。プロセス表から読むのは行どうしの関係で、セッションの状態ではない。
起動元の関係は状態のファイルに書かず、更新のたびに導き直す。起動された行は終わるとプロセスごと消えるので、引き継ぐ必要がない。

## Considered Options

- **起動された行を一覧から外す**：行が突然出て混乱することはなくなるが、利用者は「ほかの行がサブエージェントで何かしていると分かること自体は問題ない」とした（2026-10-25）。外すと、起動された行が権限待ちなどで止まっても見えなくなる。
- **利用者が `f` で待ち先として結ぶ**：仕組みを増やさずに済む。しかし起動された行は数秒から数分で消え、スキルによっては次々に起動するので、結ぶ手間が見合わない。結んだ関係を状態のファイルに書くことにもなる。
- **会話記録や環境変数から起動元を引く**：確かめていない。`--json` と同じく、Claude Code が公式に約束した口ではない。プロセスの親子は OS が保証する関係で、Claude Code の版に左右されにくい。

## Consequences

- stdio の MCP サーバは起動元の `claude` の子プロセスなので拾える。HTTP で待ち受ける MCP サーバや、常駐のデーモンを経由する起動は、祖先に起動元が出ないので拾えず、今までどおりトップレベルに `(tty)` で並ぶ。
- `--json` と `ps` は別の時点で読むので、その間に行が終わったり、`ps` が読めなかったりする。そのときは前回の関係をメモリの中で持ち越す（[DESIGN.md](../DESIGN.md)「起動元の引き方」）。その間に pid が再利用されると、無関係な行が起動された行になりうる。確率はとても低いので受け入れた（#245）。
- 今の Claude Code（2.1.310）では、起動元の `--bg` の行は、Bash ツールのバックグラウンドで起動した行が動いている間も `working` のままなので、起動元が待ちの段に入る経路は見つかっていない。規則は `--json` の振る舞いが変わったときの備えとして残した（#237、#242）。

## サイクル9での改め（2026-10-26）

サイクル9の開始時に、依存の規則を組み直した（[ADR-0020](0020-rewrite-the-list-in-cycle-9.md)、[PRODUCT.md](../PRODUCT.md)「依存（待ち先と起動された行）」）。プロセス表から起動元を導くことは変えず、次の3点を改めた。

- **起動元は待ちの段に入らない。** 起動された行は見せるだけの関係にし、起動元の段も `↳ <名前> done` も変えない。上の「段の決め方」のうち、起動元から待ちの段を導く部分を取り消す。関係から導く段は、利用者が結んだ待ち先による待ちの段だけになる。効く経路がなく（上の Consequences の最後の項目）、利用者も `(sub)` の行を動いていることの確認にだけ使っていた。
- **起動された行かどうかは、プロセスの親子だけで決まる。** サイクル8の、利用者が注釈を付けた行を起動された行にしない例外をやめ、起動された行には待ち先もメモも付けられないようにした（#254）。人間が関係を調整するのは人間が始めたセッションだけである（利用者の判断）。
- **起動元が一覧に出ていない間も、起動された行として扱い、トップレベルに `(sub)` を添えて出す。** 上の Consequences の「トップレベルに `(tty)` で並ぶ」は、祖先に `--json` の行が1つもないときだけになる。

HTTP や常駐のサーバを経由する起動（上の Consequences の最初の項目）は、利用者がオーケストレーションに日常的に使っている形だった。別の手がかりがあるかを、サイクル9で調べる（PRODUCT.md「サイクル9の完了条件」の 5）。

## 会話の外の MCP サーバが起動した行（2026-10-26）

HTTP や常駐のサーバを経由して起動された `claude -p` は、プロセスの親子からは起動元が分からない。サイクル9の開始時に調べ（#273）、次の取り決めで起動元を引くことにした（利用者の判断）。

- 利用者の MCP サーバは、`claude -p` を起動するとき、ツールを呼んだ MCP クライアントの pid を、子の環境変数 `MCP_CALLER_PID` に入れる。その pid は、MCP の設定の `headersHelper`（Claude Code が接続のたびに実行する、公式に文書化されたコマンド）がヘッダ `X-MCP-Caller-Pid` に入れて返す `$PPID` から得る。
- whatnext は、祖先から起動元が分からない `interactive` の行について、そのプロセスの `MCP_CALLER_PID` を `ps -E` で読み、`--json` の別の行の `pid` と一致すれば、その行を起動元とする。ほかの規則（見せるだけ、`(sub)`、注釈を付けない）は、プロセスの親子から導いた起動された行と同じである。
- 名前は whatnext 専用にせず、中身を表す汎用の名前にした。whatnext 以外の道具も同じ値を使える。

これは利用者の MCP サーバとの取り決めで、外との接点（[ADR-0008](0008-dependencies-and-contact-points-with-tmux.md)）が1つ増える。値が渡されなければ、今までどおりトップレベルに出るだけで、壊れる経路はない。

### Considered Options

- **`tools/call` の `_meta` の `claudecode/toolUseId`**：MCP サーバの改修だけで済み、呼んだセッションの会話記録から引けた。しかし、公式の文書に載っていない値で、予告なく変わりうる。
- **推定**（ツールを呼んだ時刻と、行が現れた時刻の突き合わせ）：外れうる入れ子は利用者が信用できなくなる。
- **何もしない**：利用者はこの形でオーケストレーションを日常的に行い、起動元から離れた行を探せずに困っていた。
