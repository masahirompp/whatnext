# whatnext

<!-- last updated: cycle 2 -->

## Problem Statement

Claude Code のセッションを同時に 3〜8 個走らせると、`claude agents` の一覧には *Needs input* が複数並ぶ。
どれが待っているかは見えるが、どれから手を付けるべきか（どれが一番止まっていて、どれが一番安く解除できるか）は見えない。
利用者はこの判断を毎回頭の中で組み立て直しており、並行度が上がるほど手間が線形に増える。
セッションごとにエディタ、GitHub、ターミナルのウィンドウも散らばる。

認知負荷の実体はセッションの数ではなく、判断の組み立て直しとウィンドウ間の視線の移動にある。
ボトルネックはエージェントの数ではなく人間のレビューの帯域なので、目的は並行を増やすことではなく、詰まっているセッションが詰まっている時間を短くすることに限る。

## Solution

whatnext は Ink と Node で作る端末アプリで、セッションを優先度ラダーの順に並べた一覧を1画面で示す。
Agent View を置き換えるのではなく、その前段に立つ。

並び順は、タスクの重要度ではなく放置コストを解除コストで割った値で決める。
この値は `claude agents --json` の出力だけで計算でき、人間の入力を必要としない。
重要度はテレメトリに存在せず、人間に入力させればそれ自体が新しい管理作業になる。

各行には順位の根拠（段と待機時間、段から分からないときは待機の理由）と、場所の要約（リポジトリ、ブランチ、PR）を必ず併記する。
一度でも外した推薦は使われなくなるので、この種のツールの寿命は精度より説明可能性で決まる。

利用者は一覧から行を選んで attach し、離脱すると一覧に戻る。
一覧からは新しいセッションの起動と、セッションの停止と削除もできる。

## User Stories

1. As a 並行してセッションを走らせる開発者, I want 手を付けるべきセッションが一番上に来た一覧, so that どれからやるかを毎回自分で組み立て直さずに済む。
2. As a 開発者, I want 各行に段、待機時間、場所（リポジトリ、ブランチ、PR）が出ること、段から分からないときは待機の理由も出ること, so that 推薦を鵜呑みにせず根拠を見て判断できる。
3. As a 開発者, I want 待機時間が分からない行が同じ段の先頭に来ること, so that 長く止まっていたかもしれないセッションを見落とさない。
4. As a 開発者, I want 稼働中のセッションも一覧の末尾に稼働時間の長い順で出ること, so that 全体を一か所で見渡せ、空転していそうなセッションにも気づける。
5. As a 開発者, I want 見ている間は一覧の並びが勝手に動かないこと, so that 選ぼうとした行が直前に入れ替わって別のセッションを操作してしまうことがない。
6. As a 開発者, I want 選んだ行で `Enter` を押すとそのセッションに attach し、離脱すると一覧に戻ること, so that ウィンドウを増やさずにセッションを操作できる。
7. As a 開発者, I want attach できない対話セッションでは、その場所（`cwd` と `pid`）が示されること, so that どの端末で止まっているかを探せる。
8. As a 開発者, I want 作業ディレクトリとモデルを指定して新しいセッションを起動し、そのまま attach して最初の指示を書けること, so that 一覧から離れずに作業を任せられる。
9. As a 開発者, I want 作業ディレクトリを、いま動いているセッションのリポジトリと手元のリポジトリの一覧から、文字を打って絞り込んで選べること, so that パスを毎回入力せずに済む。
10. As a 開発者, I want Agent View と同じ操作でセッションを止め、続けて一覧から消せること, so that 不要になったセッションを一覧から片付けられる。
11. As a 開発者, I want whatnext を閉じてもセッションが動き続けること, so that whatnext を気軽に開いたり閉じたりできる。
12. As a 開発者, I want whatnext を経由せずに起動したセッションも一覧に出ること, so that 起動の経路を気にせずに済む。

## Implementation Decisions

### 技術と依存

- Ink と Node で作る。
- 本体が依存するコマンドは `claude` と `git` だけで、URL やエディタを開くときだけ OS の `open` を使う（[ADR-0004](adr/0004-depend-only-on-claude-and-git.md)）。任意の依存として、作業ディレクトリの候補を増やすためだけに `ghq` を、行に PR を出し、その PR を開くためだけに `gh` を、あれば使う。
- Claude Code の状態は `claude agents --json --all` からだけ読む（[ADR-0001](adr/0001-read-state-only-from-agents-json.md)）。アカウントの Usage はセッションの状態ではないので、別に `claude -p "/usage"` から読む（「Usage の表示」を参照）。
- 何も書き込まず、永続状態を持たない（[ADR-0002](adr/0002-no-writes-no-persistent-state.md)）。
- 画面の文言とキーの説明は英語で書く。設計文書は日本語で書く。

### 優先度ラダー

| 順 | 判定条件 | 段 | 放置コスト | 解除コスト |
| --- | --- | --- | --- | --- |
| 1 | `waitingFor: "permission prompt"` | 権限待ち | 極大（完全停止） | 極小（1キー） |
| 2 | `waitingFor: "input needed"`、およびどの規則にも当たらない行 | 質問待ち | 極大（完全停止） | 小（一文） |
| 3 | `waitingFor: "sandbox request"` | 許可待ち | 極大（完全停止） | 小 |
| 4 | `state: "failed"`、または `pid` のない `state: "blocked"` | 失敗 | 大（停止） | 中（原因の調査） |
| 5 | `state: "done"` | レビュー待ち | 小（既に完了） | 大（読む必要） |
| 6 | `status: "busy"`（`state: "working"` を含む） | 稼働中 | ゼロ（進んでいる） | – |
| – | `stopped`、`interactive` の `idle` | 対象外 | ゼロ | – |

同じ段の中は待機時間の長い順に並べ、稼働中の段では稼働が続いている時間の長い順に並べる。

### `--json` の行から段を決める規則

`claude agents --json --all` の行は `kind` によってフィールドの持ち方が違う（Claude Code 2.1.280 での実測）。

| `kind` | `id` | `state` | `status` | `waitingFor` | `pid` |
| --- | --- | --- | --- | --- | --- |
| `background`（稼働中） | あり | あり | `busy` / `waiting` / `idle` | 待機時のみ | あり |
| `background`（プロセスなし） | あり | あり | null | null | null |
| `interactive` | なし | なし | `busy` / `waiting` / `idle` | 待機時のみ | あり |

- **判定は `waitingFor` を最優先にし、`state` は補助に使う。** 対話セッションは `state` を持たないので、`state` だけで判定すると対話セッションの権限待ちを見落とす。
- **重複は `sessionId` で除く。** 停止済みのセッションを別のプロセスが読み込むと、同じ `sessionId` が `background` と `interactive` の二行に出る。重複したときは、`pid` を持つ（プロセスが生きている）行を採る。止めた `background` のセッションを別の端末で開いているときは `interactive` の行が採られ、段はその端末の今の状態で決まり、`Enter` は attach せずに場所を示す。止めたときの古い `state` で段を決めると、別の端末で権限待ちになっているセッションがレビュー待ちに沈む。どちらも `pid` を持たないときは、`background` の行を採る。
- **`pid` のない `blocked` は失敗の段に置く。** `claude stop` で止めたセッションは `stopped` になるので、`pid` のない `blocked` はプロセスが異常終了して状態だけ残ったものと推測できる。権限待ちの段に置くと、解除できない行が最上位に居座る。
- **`interactive` の `idle` は対象外にする。** 対話セッションでは、ターンを終えて入力を待つ状態も、開いているだけの状態も同じ `idle` になる。レビュー待ちに載せると、開いているだけの端末が一覧を埋める。対話セッションは試行錯誤に使い、任せる作業は `claude --bg` で起動する想定なので、止まったときだけ出せば足りる。
- **どの規則にも当たらない行は質問待ちの段に置き、段の表記に生の値を添える。** 表にない `waitingFor`（`"worker request"`、`"dialog open"` を含む）、`pid` があるのに `waitingFor` がない `blocked`、`status: "waiting"` なのに `waitingFor` がない行、未知の `state` などが当たる。止まっているかもしれない行を対象外にすると、不明を0として沈めるのと同じ失敗になる。段を増やさないので、解除コストが実際より大きい行が許可待ちより上に来ることはある。

`--json` の行の形が変わったときは、この表と規則を合わせて直す。

### 一覧の表示

- 列は TIER / WAITING / SESSION / WHERE の順に並べる。
- **TIER**：段の英語の表記（`Permission` / `Question` / `Sandbox` / `Failed` / `Review` / `Working`）。待機の理由は、段から分からないときだけ括弧で添える（例：`Failed (no process)`、`Question (dialog open)`）。理由のほとんどは段と一対一なので、独立した列にしない。
- **WAITING**：待機時間。原因と経過時間は別の情報なので、TIER とは別の列にし、数字を縦にそろえる。
- **SESSION**：セッション名。`interactive` の行にだけ `(tty)` を添える。
- **WHERE**：場所の要約。リポジトリ名（worktree なら元のリポジトリ名、根より下なら `repo/sub`、git でない場所はパスの末尾）、既定でないブランチ名、worktree なら `(wt)`、PR があれば `#番号 (状態)`（状態は `open` / `draft` / `merged` / `closed` の文字で示し、同じ状態を色でも示す。色だけではどの色が何かをすぐに読めないため）。ブランチと worktree は `git` で取る。PR は `gh` があれば、そのブランチを head に持つ最新の PR を引く。`gh` がない、または認証していないときは PR を出さず、ほかの動作は変えない。一覧は PR を待たずに出し、分かったものから埋める。
- WHERE のブランチは、その `cwd` で今チェックアウトされているブランチであって、セッションが作業したブランチとは限らない。PR も同じ理由でずれうる。`--json` にはセッション固有のブランチを知る口がない。
- `interactive` の行の場所の提示（`Enter`）では、フルパスの `cwd` を出す。

### 更新と待機時間

- 一覧は、最後の更新から60秒たったとき、更新キーを押したとき、attach から戻ったときに更新する。更新と更新の間は `--json` を読まず、一覧の並びも変えない。
- 画面には最後に更新した時刻（経過秒数）を出す。
- `--json` には「いつ今の状態になったか」がなく、`startedAt` は `claude -r` で再開すると更新されるので、待機時間の代わりにならない。待機時間は whatnext の観測から推定する。
- **待機時間は悲観的に数える。** 更新の間に新しく今の段に入った行は、前回の更新時刻から待っていたとみなす。誤差は更新の間隔（attach から戻ったときは attach していた時間）以内で、必ず長いほうに振れる。
- **起動して最初の更新で見えた行の待機時間は `?` と示し、同じ段の先頭に置く。** 不明を0として扱うと、何時間も止まっていたセッションが最下位に沈む。これがこのツールで最悪の失敗である。
- カーソルは選んでいたセッションに付いていく。起動したときは最上位の行を選び、選んでいたセッションが一覧から消えたら最上位の行に戻る。
- ただし attach から戻ったとき（新しく起動したセッションから戻ったときを含む）は、最上位の行を選ぶ。最上位が今離脱したセッションで、段が attach する前と変わっていなければ、その次の行を選ぶ（行が1つしかなければそのまま）。読んだだけで離脱したレビュー待ちの行や、許可した直後でまだ `waiting` を返す行が、先頭に居座るのを防ぐため。User Story 5 の動機は選んでいる最中の入れ替わりなので、attach から戻った瞬間とは衝突しない。
- 対象の行が1件もないときは、そのことをメッセージで示す。
- `--json` の取得に失敗したとき（`claude` が見つからない、出力を解析できないなど）は、エラーの内容を示し、古い一覧は出さない。次の更新で再び読む。

### Usage の表示

- 一覧のヘッダに、アカウントの Usage を出す。`/usage` が示す枠ごとに、使用率とリセットする時刻を並べる（例：`session 42% (resets 2:09pm) · week (all models) 25% (resets Sep 29 9:59am)`）。リセットが今日なら日付を省く。使用率が50%以上なら黄、80%以上なら赤で示す。
- 目的は、rate limit にいつ当たりそうかを見ることと、新しいセッションのモデルを決める材料にすること。
- 取得するのは、whatnext の起動時、attach から戻ったとき（新しく起動したセッションから戻ったときを含む）、更新キーを押したときに限る。60秒ごとの更新では取らない。Usage は数分で大きく動くものではなく、一覧に戻る時点の値があれば判断に足りる。
- 取得は一覧の更新を待たせず、非同期に行う。取得中は前の値を出したままにする。
- 取得には `claude -p "/usage" --no-session-persistence --output-format json` を使う。モデルを呼ばないので rate limit を消費しない。`--no-session-persistence` を付けないと、呼ぶたびに会話ファイルが残る。プロジェクトの設定や hook を拾わないよう、一時ディレクトリで実行する。
- `/usage` の結果は人間向けの文字列なので、`Current <枠>: <N>% used · resets <時刻>` の行を読む。取得に失敗したとき、または読める行が1つもないときは、Usage を出さない。エラーは示さず、一覧のほかの動作は変えない。
- 出る値はアカウント全体のもので、他の端末や claude.ai での利用も含む。セッションごとの内訳は出さない。

### 操作

- **`Enter`（`background` の行）**：`claude attach <id>` に端末を渡す。離脱キーは Ctrl+Z とする（`claude attach` の公式の離脱キー。`←` と `/exit` は Agent View を開いてしまう）。離脱して一覧に戻ったとき、端末に子の設定（代替画面、マウスの追跡など）が残ってはならず、子が異常終了した場合も同じである。attach している間、キー入力が whatnext と子の両方に届いてはならない。`claude attach` が 0 以外の終了コードで終わったときは、子の出したメッセージを画面に残したまま、キーが押されるのを待ってから一覧に戻る。すぐに描き直すと、attach できなかった理由と対処（`claude respawn` など）が読めない。正常に離脱したときは待たずに戻る。画面の解析や入力の注入はしない（[ADR-0003](adr/0003-no-input-injection-or-proxy-response.md)）。
- **`Enter`（`interactive` の行）**：`id` がなく attach できないので、`cwd` と `pid` を示す。
- **`n`**：作業ディレクトリとモデルを指定し、プロンプトなしで `claude --bg` で起動する。最初の指示は attach した先の Claude Code の入力欄で書く。whatnext はプロンプトを受け取らない（入力欄を作ると Claude Code の入力欄の劣化コピーになり、複数行や貼り付けの扱いを抱え込む）。
  - 作業ディレクトリは候補から選ぶか、`Other...` で自由に入力する。候補は、whatnext を起動したディレクトリ、`--json` の各行の `cwd`、`ghq list` のリポジトリの順に、重複を除いて並べる。worktree に移ったセッションの `cwd` は worktree のパスなので、`git` で元のリポジトリのパスに寄せる。
  - 候補はフルパスではなく末尾のディレクトリ名（リポジトリ名）で表示する。同じ名前の候補が複数あるときだけ、互いを区別できるところまで親のディレクトリを足して表示する（例: `a/foo` と `b/foo`）。絞り込みは表示名とフルパスの両方に対して行い、表示名で当たった候補をフルパスだけで当たった候補より上に並べる。表示名は入力の文字が順に含まれていれば当たるが、フルパスは入力がそのまま続けて含まれるときだけ当たる（長いパスでは、とびとびの一致がほぼどの入力にも成り立ってしまうため）。
  - `ghq` がないとき、または失敗したときは、`ghq` の候補を出さずにそのほかの候補だけで続ける。エラーは示さない。
  - 文字を打つと候補を絞り込む。打った文字を順に含む候補だけを残し、連続して一致する候補を上に置く。`Other...` は絞り込みの対象にせず常に末尾に置き、選ぶと打った文字を入力欄に引き継ぐ。
  - worktree を使うかは聞かず、`claude` の設定（`worktree.bgIsolation`）に任せる。
  - モデルは省略でき、省略したら `claude` の既定を使う。入力した値はそのまま `--model` に渡し、選択肢の一覧は持たない（モデルが入れ替わるたびに whatnext を直さずに済む）。
  - 起動したら、そのセッションにそのまま attach する。プロンプトを書かずに離脱すると、そのセッションは指示を待つ行として質問待ちの段に残る。離脱したあとは `Enter` で attach したときと同じく一覧に戻る。
  - `claude --bg` の応答を待つ間は、新しいセッションの画面に留まり、作業ディレクトリとモデルに加えて、起動中であることと経過秒数を示す。この間のキー入力は受け付けない。一覧に戻すと、入力画面が閉じたことが完了か取り消しに見え、起動に失敗したように感じられるため。
  - 起動の出力から `id` を読み取れなかったときは attach しない。`claude --bg` の出力をその画面に残し、キーが押されるのを待ってから一覧に戻る。
  - `--name`、`--permission-mode`、`-w` は指定させない。
- **`Ctrl+X`（`background` の行）**：確認なしで `claude stop <id>` で止める。2秒以内にもう一度 `Ctrl+X` を押すと `claude rm <id>` で削除し、一覧から消す。止める操作が失敗しても2回目で削除する。Agent View の `Ctrl+X` と同じ挙動にする。
  - 削除の待ち受け中に `Esc` を押すか、`Ctrl+X` 以外のキー（カーソル移動など）を押すと、待ち受けを取り消す。カーソルを動かしてから2回目を押して、別の行を消すのを防ぐ。
  - 止めている最中（`claude stop` の応答を待っている間）に押された2回目は、2秒を過ぎていても削除として受け付ける。
  - 止めたプロセスがまだ終わっていないために `claude rm` がロックで断ったときは、プロセスが終わるのを待ってから削除する。利用者から見れば、2回押せば消える挙動のままにする。
  - push していないコミットがあるために `claude rm` が断ったときは、捨ててよいかを英語で聞き（例：`Discard 1 unpushed commit and delete session <id>? [y/N]`）、`y` なら `claude rm` が示した値を `--discard-unpushed` に渡して削除する。コミットは取り消せない形で失われるので、確認を挟む。
  - それ以外の理由で断ったときは、その文言をそのまま示す。
  - Agent View との違い：Agent View の削除は worktree を未コミットの変更ごと消すが、`claude rm` は未コミットの変更がある worktree を残す。
  - `interactive` の行では `id` がないので効かない。
- **`e`**（external）：選んだ行の場所や PR を、whatnext の外のアプリで見るためのメニューを一覧の下に出す（見出しは `Show <セッション名> in:`）。キーの説明に open を使わないのは、`Enter` の attach（セッションを開く）と取り違えるため。`↑↓` と `Enter`、または番号で選び、`Esc` で閉じる。開く先ごとにキーを割り当てると、開く先が増えるたびにキーが尽きるので、入口を1つにする。開く先は次の順に並べる。
  1. **手元の VS Code**：`cwd` が属するチェックアウトの根を開く。worktree で動いているセッションならその worktree、リポジトリ本体ならリポジトリの根、git でない場所なら `cwd` そのもの。`vscode://file/<パス>/` を OS の `open` に渡す（`code` コマンドに依存しない）。`interactive` の行でも出る。
  2. **PR を vscode.dev で**（`https://vscode.dev/github/<owner>/<repo>/pull/<番号>`）。github.com の PR のときだけ出す。
  3. **PR を GitHub で**。
  - PR の選択肢は、WHERE に PR が出ている行でだけ出す。出ていない行（`gh` がない、PR がない、まだ取得中）では、PR がないことをメニューに示す。
  - 開いたら何を開いたかを示し、`open` が失敗したらその出力を示す。
- 更新や終了に使うキーの割り当ては実装で決める。

### Claude Code の外部仕様

`claude` の実測した振る舞いは [claude-code-behavior.md](claude-code-behavior.md) にまとめる。

### 未確定の前提

- **子が異常終了したときの端末の状態。** 正常な離脱（Ctrl+Z）では、端末に設定の残骸が残らず、キー入力の二重配送も起きないことを確かめた。`/exit` と子の異常終了では未確認。
- **`"sandbox request"` が実際に出るか。** 実装中に分かった範囲で capture する。
- **プロンプトなしで起動したセッションの `name`。** `--name` を付けないとき、最初の指示を送るまで SESSION の列に何が出るか。

## Testing Decisions

### 受け入れシナリオ

サイクル2までに確立した振る舞い。各サイクルの完了条件は、cycle-start の grilling でここから選び、足すものを決める。サイクル2の完了条件は、1〜12のすべてである。

1. 状態の違うセッションが並行して動いているとき、whatnext を起動すると、優先度ラダーの順に1画面の一覧が出る。各行には段、待機時間、セッション名、場所の要約が併記され、待機の理由は段から分からないときだけ添えられる。
2. 一覧は、最後の更新から60秒たったとき、更新キーを押したとき、attach から戻ったときに更新される。画面には最後の更新時刻が出る。更新の間に今の段に入った行の待機時間は、前回の更新時刻から数えられる。
3. 起動直後で待機時間が分からない行は `?` と表示され、同じ段の先頭に置かれる。
4. 同じ `sessionId` が二重に出ても1行にまとまり、プロセスが生きている行の状態で段が決まる。`interactive` で `idle` の行は出ない。`pid` のない `blocked` は失敗の段（4位）に置かれる。どの規則にも当たらない行（表にない `waitingFor`、`pid` のある `blocked` など）は、生の値を添えて質問待ちの段に置かれる。
5. 更新で行が並び替わっても、カーソルは選んでいたセッションに付いていく。attach から戻ったときは、カーソルが最上位の行（それが今離脱したセッションで段が変わっていなければ、その次の行）に置かれる。
6. `background` の行で `Enter` を押すと attach する。Ctrl+Z で離脱すると一覧に戻り、whatnext ごと止まることはない。端末に子の設定は残らず、キー入力も二重に届かない。attach が 0 以外の終了コードで終わったときは、子のメッセージが画面に残り、キーを押すと一覧に戻る。
7. `interactive` の行で `Enter` を押すと、attach せずに場所（`cwd`、`pid`）が示される。
8. `n` で作業ディレクトリ（候補を絞り込んで選ぶか `Other...` で自由に入力する）、モデル（省略できる）を指定して起動すると、そのセッションに attach して最初の指示を書け、離脱するとそのセッションが一覧に現れている。起動を待つ間は一覧に戻らず、起動中であることと経過秒数が出ている。`ghq` がない環境でも同じ手順で起動できる。
9. `background` の行で `Ctrl+X` を押すとそのセッションが止まり、2秒以内にもう一度押すと一覧から消える。worktree で動いていたセッションでも、2回押せば消える。push していないコミットがあるときは、捨ててよいかを英語で聞かれ、`y` で消える。
10. 対象の行がないときはメッセージが出る。`--json` の取得に失敗したときはエラーが出て、古い一覧は出ない。
11. 画面の文言はすべて英語である。
12. npm に公開したあと、`npx @masahirompp/whatnext` を実行すると whatnext が起動し、一覧が出る。
13. 一覧のヘッダに、Usage の枠ごとの使用率とリセットする時刻が出る。attach から戻ると、一覧を待たせずに値が新しくなる。Usage を取れないときは、Usage だけが出ず、一覧はふだんどおり使える。
14. `e` を押すと開く先のメニューが出て、手元の VS Code を選ぶと選んだ行の場所（worktree ならその worktree）が開く。PR が出ている行では、PR を vscode.dev で開く選択肢と GitHub で開く選択肢も出る。PR が出ていない行では、PR がないことが示される。

### 確かめ方

- シナリオ 1、3、4（並び順と行の判定）は、`--json` の出力を模した固定データで確かめてよい。並び順は `--json` の行だけで決まる判定なので、固定データでも実機と同じ保証が得られる。`pid` のない `blocked` と `"sandbox request"` は実機で意図して作るのが難しい。`failed` は、存在しないモデル名で `--bg` を起動すれば作れる。
- それ以外のシナリオは実機の `claude` で確かめる。attach は端末の制御そのもので、実機でしか確かめられない。
- シナリオ 12 は、人間が publish したあとに、実機で `npx @masahirompp/whatnext` を実行して確かめる。publish の前には、`npm pack` で作った tarball から起動できることを確かめてよい。
- テストは外から観測できる振る舞いだけを対象にする。

## Out of Scope

- **コストやトークンのダッシュボード**：Grafana 構成の OSS が十数個あり飽和している。
- **事後の振り返りのサマリやレポート**：競合が多く、リアルタイム性という軸から外れる。
- **セッション内容の再構築やデバッグビュー**：JSONL を解析するツール（claude-hindsight など）が先行しており、情報量でも勝てない。
- **一覧の常時表示**：node-pty と ANSI パーサによる端末多重化の自作が要る。node-pty はネイティブアドオンで Node のバージョンごとに再ビルドが要り、バグは特定の端末エミュレータでだけ再現する種類になる。依存を減らす目的に対して、依存の総量が tmux より重い。tmux のペイン移動なら手間はほぼゼロだが、tmux を常用しない環境でこの一機能のために導入するのは割に合わない。
- **セッションへの自動介入や自動承認、返信や権限応答の代行、attach せずに一覧の上で権限を許可すること**：[ADR-0003](adr/0003-no-input-injection-or-proxy-response.md) を参照。
- **完了したセッションへの追加の指示を送るキー（`r`）**：追加の指示は attach して送れば足りる。
- **`claude logs` を開くキー**：出力が画面の再描画の制御コードそのもので読める形にならず、中身を見る手段は attach で足りる。
- **Web UI（ローカルサーバ）**：ブラウザでは対話型の Claude Code セッションを開けないので attach が原理的にできず、別のターミナルを起動することになる。ウィンドウを増やさないという動機と衝突し、ブラウザのタブという常駐アプリも一つ増える。
- **独自のセッション管理、外部からの push 型キュー、常駐デーモン、計測ログ**：[ADR-0002](adr/0002-no-writes-no-persistent-state.md) を参照。
- **外部の出来事（Slack、CI、レビュー依頼など）の監視を本体で行うこと、コストの集計の自作**：[ADR-0004](adr/0004-depend-only-on-claude-and-git.md) を参照。
- **燃焼率の異常の自動検知**：定額プランで空転して失うのは金額ではなく利用枠で、上限に当たらない限り放置コストは小さい。閾値を過去の分布から決めるには蓄積が要り、ADR-0002 に反する。稼働中の行を稼働時間の長い順に末尾へ出せば、長く回り続けている行に気づける。
- **人間の手入力のメモ**：正本がなく、セッションとして起こす根拠もない。保存先が必要になり、個人用 TODO アプリへの変質を招く。
- **並行するセッションの数を増やすための機能**：ボトルネックは人間のレビューの帯域なので、目的を詰まっている時間の短縮に限る。
- **セッションの情報（モデル、effort、コンテキスト使用量）の列、高価なモデルで定型作業を回していることの検知**：利用枠やコストの監視で、「どれに手を付けるか」を示す役割の外にある。取る口は、statusline の JSON（利用者の設定の変更が要る。[ADR-0002](adr/0002-no-writes-no-persistent-state.md)）、OTel（常駐するコレクタが要る）、記録ファイル（内部仕様。[ADR-0001](adr/0001-read-state-only-from-agents-json.md)）のいずれも、本体の原則に反する。別ツールで扱い、一覧の行に出したくなったら属性プラグイン（M3）の口を使う。
- **M1 の評価まで作らないもの**：M2（`e` で作業ディレクトリをエディタで開く、`g` でブランチや PR を GitHub で開く（PR の番号と状態の表示だけはサイクル1で入れた。開く操作は入れない）、行内のリンク、端末のタイトルへの待機件数の表示、blocked が発生したときの OS の通知）と M3（コストの列）。M1 で順位の提示が役に立つと判定されるまで、UI に投資しない。

## Further Notes

### 配布

whatnext を npm に公開し、`npx @masahirompp/whatnext` で呼び出せるようにして、実際に試す（サイクル2で決定）。

- パッケージ名は `@masahirompp/whatnext`、bin の名前は `whatnext` とする。npm の `whatnext` という名前は別人が公開済み（2026-09 時点）なので、スコープ付きの名前にする。`npx` でスコープ付きの名前を呼べば、bin の名前が既存のパッケージと衝突することはない。
- バージョンは `0.1.0` から始める。`0.x` 系で出し、破壊的な変更を入れたら minor を上げる。semver は `0.y.z` を「いつ何が変わってもよい初期開発版」と定めているので、`0.x` であることがアルファ版の表明になる。プレリリース版と dist-tag（`@alpha`）は、安定版の系列が別にあるときの仕組みで、`npx` をタグなしで呼べなくなるので使わない。
- `engines` は `node >=22` とする。Ink 7 の要求に合わせる。
- パッケージに含めるのは、ビルド後のコード（`dist/`）、README、LICENSE だけにする。
- ライセンスは MIT とする。公開すればコードは誰でも取得できるので、許諾しないまま出すと「公開したのに使えない」状態になる。依存先（Ink、React）も MIT である。
- GitHub のリポジトリは private のまま公開し、`package.json` に `repository` を書かない。npm のページから README の相対リンクが切れることは受け入れる。今の目的は撤退判定のために自分で試すことで、リポジトリを public にするかは M1 が撤退判定を通ってから決める。
- publish は取り消せない外部への公開である。公開したバージョン番号は使い直せず、72時間を過ぎると原則として unpublish できない。そのため、`npm login` と `npm publish --access public` は人間が実行する。実装セッションは、その前に `npm pack --dry-run` で同梱物を示して止まり、公開のあとに `npx` で起動できることを確かめる。
- whatnext はデータも設定も持たない（[ADR-0002](adr/0002-no-writes-no-persistent-state.md)）ので、破壊的な変更で利用者に移行を求めるものがない。このため、公開したあともサイクル型の書き直しを続けられる見込みがある。README に「0.x の間は予告なく変わる」と明記する。

### 段階と撤退判定

M1（順位の提示と最小の操作）だけで、順位の提示が実際に役に立つかを判定できる。
役に立たなければ M2 以降は作らない。

撤退判定はサイクルの完了条件とは別に行う。
M1 を1週間使ったあと、利用者本人が定性的に判断する。
提示された順位が自分の直感と一致しない場合、あるいは一致しても結局 `claude agents` を開いている場合は中止する。
順位付けのロジックが機能しない状態で M2 以降の UI に投資すると、完成度に引きずられて使えないツールを使い続けることになる。

目安にする観点は次のとおり。いずれも数値では測らない。

- blocked が発生してから解除するまでの時間が短くなったか。
- 提示された最上位のセッションを実際に選んでいるか。
- `claude agents` を開く回数が減ったか。
- ウィンドウを切り替える回数が減ったか。

### M2 の未確定の前提

- `Notification` フックは Agent View を開いていないときに発火するか。発火しなければ、OS の通知は更新での検知を元に作る。
- 端末のタイトルの変更と行内のリンクが、使う端末で効くか。行内のリンクが効かなければ、`g` キーで開く方式だけにする。

### コストの列（M3、任意）

各行にセッションごとのコストやトークン量を添える。利用者が設定したときだけ有効になり、設定しなければ列は出ず、ほかの動作も変わらない。

- 値の出どころは、利用者が常駐させる既存の OSS（メトリクス基盤）とする。
- whatnext は属性プラグイン経由で値を読み、本体からメトリクス基盤を直接呼ばない。
- 値は表示するだけで、並び順には使わず、異常の自動検知もしない。取得に失敗した行は列を空欄にする。
- メトリクス基盤は、`session.id` ごとに集計した値を問い合わせる API があり、OTLP でメトリクスを受け取れ、単体で常駐できるものから選ぶ。属性プラグインの形式と設定の置き場所は、作るときに決める。
- 未確定の前提：OTel のメトリクスに付く `session.id` が `--json` の `sessionId` と一致するか（一致しなければ行と結合できない）、`--bg` のセッションが OTel を送るか。

### OTel による待機時間の推定（再検討の候補）

OTel には権限要求が表示された時点のイベントはないが、止まる直前の最後のイベント（`api_request` や `assistant_response`）の `event.timestamp` を止まり始めた時刻とみなせば、数秒の誤差で待機時間を推定できる。
これが効くのは、起動した直後に `?` になる行をなくせる点である。
並び順に効くのは分単位の差なので、更新の間の誤差を縮める効果は小さい。
起動した直後の `?` が実際に困るほど多いときに再検討する。
その場合は、`--bg` のセッションが OTel を送るかの確認と、属性プラグインの値を並び順に使うかどうかの決定（上の「値は表示するだけ」の変更）が要る。

### 連続して処理するための候補（M1 の評価のあとで判断する）

- 同じ段の中で、直前と同じリポジトリの行を先にする（頭の切り替えを減らす）。「同じ段の中は待機時間の長い順」を変える。
- 読んだだけのレビュー待ちの行を、段の中で下げる（メモリ上で「見た」を覚える）。

採らなかった案：リポジトリごとのグループ化（「一番上がやるべきもの」という読み方が崩れる）、離脱すると次の候補へ自動で attach する（見ていない間に次へ入る）。

### 起動時の既定のモデルの表示（再検討の候補）

`n` でモデル欄を空にすると `claude` の既定のモデルで起動するので、既定が高価なモデルだと、定型作業を高価なモデルで回す事故の入口になる。
空欄のときに既定のモデル名を画面に出せば、起動の時点で気づける。これは whatnext の範囲に収まる。
M1 の評価のあとで検討する。

### 外部 watcher（別ツール）の設計の要点

外部の出来事を監視し、必要なときにセッションを起こす別ツール。監視先ごとに作ってよい。
whatnext の側で必要な要件は、人間が起動したセッションを前提にしないこと（機械生成の `name` や `cwd` で壊れないこと）だけである。

- **起こす価値があるものだけ起こす。** セッションは利用枠を使う。flaky なテストの失敗や、見ればすぐ分かるレビュー依頼まで起こさない。この選別の良し悪しが外部 watcher の品質になる。
- **出来事が解消したら片付ける。** CI が再実行で通った、別の人がレビューを済ませた、といった場合は、外部 watcher が解消を検知して `claude stop` する。
- **同じ出来事で二度起こさない。** `--name` に出来事の識別子（Slack ならメッセージの `ts`、CI なら `ci-<repo>-<runId>` など）を埋め、起動の前に `--json --all` で同じ名前を探す。セッション一覧そのものが着手済みの台帳になる。`claude -r` でコピーが作られると `--name` が引き継がれず重複排除が崩れるので、新規の起動だけを行う。
- **plan mode で起動する。** セッションは調査だけを行い、計画を出して止まる。承認の対象が「外部の出来事についての推測」から「具体的な変更計画」に変わり、判定を誤って起動してもコードは書かれない。却下は `claude stop` で行う。未確定の前提として、計画の承認待ちで `waitingFor` に何が出るかがある。`"permission prompt"` と出るなら権限待ちの段に入るが、実際には計画を読む必要があり解除コストは大きいので、別の段に置く判定が要る。
- **プロンプトインジェクションを防ぐ。** Slack のメッセージ、PR のコメント、CI のログは信頼できない入力である。本文はデータとして囲み指示として解釈させない、対象を限る（Slack なら DM と特定のチャンネル、送信者のホワイトリスト）、`--permission-mode plan` を強制して `auto` と `bypassPermissions` を使わない、worktree の分離（`--bg` の既定）を切らない、を最低限の防御とする。
