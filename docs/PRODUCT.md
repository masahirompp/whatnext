# whatnext

<!-- last updated: cycle 7 -->

## Problem Statement

Claude Code のセッションを同時に 3〜8 個走らせると、`claude agents` の一覧には *Needs input* が複数並ぶ。
どれが待っているかは見えるが、どれから手を付けるべきか（どれが一番止まっていて、どれが一番安く解除できるか）は見えない。
利用者はこの判断を毎回頭の中で組み立て直しており、並行度が上がるほど手間が線形に増える。
セッションごとにエディタ、GitHub、ターミナルのウィンドウも散らばる。

認知負荷の実体はセッションの数ではなく、判断の組み立て直しとウィンドウ間の視線の移動にある。
ボトルネックはエージェントの数ではなく人間のレビューの帯域なので、目的は並行を増やすことではなく、詰まっているセッションが詰まっている時間を短くすることに限る。

## Solution

whatnext は Node で作る端末アプリで、セッションを優先度ラダーの順に並べた一覧を1画面で示す。
Agent View を置き換えるのではなく、その前段に立つ。

並び順は、タスクの重要度ではなく放置コストを解除コストで割った値で決める。
この値は `claude agents --json` の出力だけで計算でき、人間の入力を必要としない。
重要度はテレメトリに存在せず、人間に入力させればそれ自体が新しい管理作業になる。

各行には順位の根拠（段と待機時間、段から分からないときは待機の理由）と、場所の要約（リポジトリ、ブランチ、PR）を必ず併記する。
一度でも外した推薦は使われなくなるので、この種のツールの寿命は精度より説明可能性で決まる。

利用者は一覧から行を選んで attach し、離脱すると一覧に戻る。
一覧からは新しいセッションの起動と、セッションの停止と削除もできる。

セッションごとに作業台（そのセッションの作業ディレクトリで開いたシェル）を持ち、端末の別の分割で開いた作業台の画面に、セッションの画面と並べて映せる。
作業台の画面は、いま見ているセッションの作業台に追従する。
sandbox の外で人が動かすコマンドを、どのセッションのためのものかで迷わずに動かせる。
作業台で動かしているものは、一覧に戻っても動き続ける。作業台は whatnext の中にあり、whatnext を終了すると閉じる（動いているものがあれば、終了する前に確認する）。
端末のウィンドウを閉じても whatnext は終了せず、次に起動すると同じ一覧に戻る。

利用者は、あるセッションが別のセッションの終わりを待っていること（待ち先）を示せる。
待ち先は待ち元の下に入れ子で並び、組は、組の中で最も手を付けるべき行の位置に出る。
待ち先がすべて終わると、待ち元は元の段に戻る。

## User Stories

1. As a 並行してセッションを走らせる開発者, I want 手を付けるべきセッションが一番上に来た一覧, so that どれからやるかを毎回自分で組み立て直さずに済む。
2. As a 開発者, I want 各行に段、待機時間、場所（リポジトリ、ブランチ、PR）が出ること、段から分からないときは待機の理由も出ること, so that 推薦を鵜呑みにせず根拠を見て判断できる。
3. As a 開発者, I want 待機時間が分からない行が同じ段の先頭に来ること, so that 長く止まっていたかもしれないセッションを見落とさない。
4. As a 開発者, I want 稼働中のセッションも一覧の末尾に稼働時間の長い順で出ること, so that 全体を一か所で見渡せ、空転していそうなセッションにも気づける。
5. As a 開発者, I want 見ている間は一覧の並びが勝手に動かないこと, so that 選ぼうとした行が直前に入れ替わって別のセッションを操作してしまうことがない。
6. As a 開発者, I want 選んだ行で `Enter` を押すとそのセッションに attach し、離脱すると一覧に戻ること, so that ウィンドウを増やさずにセッションを操作できる。
7. As a 開発者, I want attach できない対話セッションでは、その場所（`cwd` と `pid`）が示されること, so that どの端末で止まっているかを探せる。
8. As a 開発者, I want 作業ディレクトリとモデルを指定して新しいセッションを起動し、そのまま attach して最初の指示を書けること, so that 一覧から離れずに作業を任せられる。
9. As a 開発者, I want 作業ディレクトリを、いま動いているセッションのリポジトリと手元のリポジトリの一覧から、文字を打って絞り込んで選べること, so that パスを毎回入力せずに済む。
10. As a 開発者, I want Agent View と同じ操作でセッションを止め、続けて一覧から消せること, so that 不要になったセッションを一覧から片付けられる。
11. As a 開発者, I want whatnext を終了してもセッションが動き続けること, so that whatnext を気軽に起動したり終了したりできる。
12. As a 開発者, I want whatnext を経由せずに起動したセッションも一覧に出ること, so that 起動の経路を気にせずに済む。
13. As a 開発者, I want 優先度が低い、別の関係者の確認が要るなど、今は手を付けないと決めたセッションを、一覧の下に退けておけること, so that 段の上では上位でも今は進められないセッションが、次に手を付けるべきセッションの邪魔をしない。
14. As a 複数のセッションを組み合わせて一つの作業を進める開発者（実装とレビューの往復、大きなタスクの分割、先に直すべき別リポジトリの修正）, I want あるセッションが別のセッションの終わりを待っていることを一覧に示せ、待ち先が終わると待ち元が戻ってくること, so that 組の関係を覚えておかずに済み、待ち先が終わったあとに待ち元を一覧から探し直さずに済む。
15. As a sandbox の中で Claude Code を動かす開発者, I want セッションの画面と並べて、そのセッションの作業ディレクトリで開いた作業台を映し、両方に入力できること, so that sandbox の中で動かせないコマンド（docker、terraform など）を、どのセッションのためのものかで迷わずに手で動かせる。
16. As a 開発者, I want 作業台で動かしているものが、一覧に戻っても動き続け、戻ると元の配置のまま見え、一覧からも何が動いているかが分かること, so that 長い e2e を流しながら別のセッションの作業ができる。
17. （廃止。Out of Scope の「`!` のコマンドのコピー」）
18. As a 開発者, I want 端末のウィンドウを閉じても、次に起動すれば保留や待ち先を含めて同じ一覧に戻ること, so that うっかりウィンドウを閉じても段取りを組み直さずに済み、作業台で動かしているものも止まらない。
19. As a worktree で作業させる開発者, I want 作業台を作る時機を自分で選べること, so that セッションが worktree に入ったあとに、その worktree の場所で作業台を開ける。
20. As a 開発者, I want 作業台の画面を、要るときだけ開き、要らなくなれば閉じられること, so that ふだんは claude の画面を広く使える。

## Implementation Decisions

観測できる振る舞いを書く。仕組み（技術と依存、機能ごとの入力の出どころ、フック・OTel・会話記録の受け方、確かめ方）は [DESIGN.md](DESIGN.md) にある。

### 全体

- 起動時のオプションは `--help` だけである。オプトインの機能を足すときは、起動時のオプションで有効にする。
- サブコマンドは、作業台の画面を開く `whatnext workbench` だけである（「作業台」の節）。
- 知らないオプションを渡されたときは、`whatnext: unknown option <引数>` と使い方を標準エラーに出し、終了コード 2 で終わる。無視して起動すると、オプトインのフラグを打ち間違えたときに、機能が無効のまま黙って起動し、利用者は有効になったと思い込む。
- 何も書き込まず、永続状態を持たない（[ADR-0002](adr/0002-no-writes-no-persistent-state.md)）。例外は、保留と待ち先の関係を書く状態のファイルだけである（[ADR-0016](adr/0016-persist-holds-and-waits-in-a-state-file.md)）。
- 画面の文言とキーの説明は英語で書く。設計文書は日本語で書く。

### 終了と、端末のウィンドウを閉じたとき

仕組みと退けた案は [ADR-0012](adr/0012-list-runs-inside-the-dedicated-tmux-server.md) にある。

- **端末のウィンドウを閉じても、whatnext は終了しない。** 一覧、作業台（動いているものを含む）、保留、待ち先の関係は残り、フックも受け続ける。うっかりウィンドウを閉じて段取りを失わないようにする。
- whatnext を起動したとき、終了していない whatnext があれば、新しく動かさずにその一覧に戻る。セッションの画面を見ていたときにウィンドウを閉じたなら、起動し直すと一覧から始まり、そのセッションから戻ったときと同じに扱う（`Last attached` の組に出し、カーソルをそこに置き、一覧を更新する）。起動すれば必ず一覧から始まるほうが、「まず何に手を付けるか」を見る順序に合う。同じ画面には `Enter` 1回で戻れる。
- 別の端末のウィンドウに whatnext が映っているときに起動すると、一覧は新しいウィンドウに移り、前のウィンドウはシェルに戻る。両方に映すと、tmux が小さいほうのウィンドウに大きさを揃えて大きいほうの表示が欠け、片方で attach するともう片方も同じ画面に切り替わる。
- 起動したとき、動いている whatnext の版が起動した版と違えば、動いている一覧につなぎ、一覧の下に `whatnext <動いている版> is still running. Quit it to start <起動した版>.` と示す。端末のウィンドウを閉じても whatnext は終了しないので、`npm i -g` などで更新してから起動しても、つながるのは更新前の版の一覧である。示さないと、利用者には更新が効いていないことが見えない。新しい版を動かすには、終了の操作で閉じてから起動する。

  ```
    SESSION        STATUS      WHERE          CTX  WAITING
  > fix-login      Review      app            91k       5m
    ...
    whatnext 0.7.0 is still running. Quit it to start 0.8.0.
  ```

- **終了**は、終了のキーで行う。作業台で動いているものがあれば、終了する前に確認する（「作業台」の節）。終了すると、作業台、残した `claude attach`、保留、待ち先の関係がすべて消え、何も残らない。Claude のセッション本体は動き続ける。

### 優先度ラダー

| 順 | 判定条件 | 段 | 放置コスト | 解除コスト |
| --- | --- | --- | --- | --- |
| 1 | `waitingFor: "permission prompt"` | 権限待ち | 極大（完全停止） | 極小（1キー） |
| 2 | `waitingFor: "input needed"`、`state: "working"` かつ `status: "idle"`、およびどの規則にも当たらない行 | 質問待ち | 極大（完全停止） | 小（一文） |
| 3 | `waitingFor: "sandbox request"` | 許可待ち | 極大（完全停止） | 小 |
| 4 | `state: "failed"`、または `pid` のない `state: "blocked"` | 失敗 | 大（停止） | 中（原因の調査） |
| 5 | `state: "done"` | レビュー待ち | 小（既に完了） | 大（読む必要） |
| 6 | `status: "busy"`、または `status` が `idle` でない `state: "working"` | 稼働中 | ゼロ（進んでいる） | – |
| 7 | 行そのものはレビュー待ちに当たり、待ち先のどれかがまだ終わっていない | 待ち | ゼロ（待ち先が進めている） | – |
| 8 | `state: "stopped"` | 停止 | ゼロ（利用者が止めた） | – |
| – | `interactive` の `idle` | 対象外 | ゼロ | – |

同じ段の中は待機時間の長い順に並べ、稼働中の段では稼働が続いている時間の長い順に並べる。

待ちの段だけは `--json` の行だけでは決まらず、利用者が結んだ待ち先の関係と、待ち先の今の段から導く（「待ち先」の節）。

### `--json` の行から段を決める規則

`claude agents --json --all` の行は `kind` によってフィールドの持ち方が違う（Claude Code 2.1.280 での実測）。

| `kind` | `id` | `state` | `status` | `waitingFor` | `pid` |
| --- | --- | --- | --- | --- | --- |
| `background`（稼働中） | あり | あり | `busy` / `waiting` / `idle` | 待機時のみ | あり |
| `background`（プロセスなし） | あり | あり | null | null | null |
| `interactive` | なし | なし | `busy` / `waiting` / `idle` | 待機時のみ | あり |

- **判定は `waitingFor` を最優先にし、`state` は補助に使う。** 対話セッションは `state` を持たないので、`state` だけで判定すると対話セッションの権限待ちを見落とす。
- **重複は `sessionId` で除く。** 停止済みのセッションを別のプロセスが読み込むと、同じ `sessionId` が `background` と `interactive` の二行に出る。重複したときは、`pid` を持つ（プロセスが生きている）行を採る。止めた `background` のセッションを別の端末で開いているときは `interactive` の行が採られ、段はその端末の今の状態で決まり、`Enter` は attach せずに場所を示す。止めたときの古い `state` で段を決めると、別の端末で権限待ちになっているセッションがレビュー待ちに沈む。どちらも `pid` を持たないときは、`background` の行を採る。
- **`pid` のない `blocked` は失敗の段に置く。** `claude stop` で止めたセッションは `stopped` になるので、`pid` のない `blocked` はプロセスが異常終了して状態だけ残ったものと推測できる。権限待ちの段に置くと、解除できない行が最上位に居座る。
- **`state: "working"` かつ `status: "idle"` は質問待ちの段に置く。** 権限の確認で `No` を選ぶとターンが中断され（`Interrupted · What should Claude do instead?`）、この組み合わせのまま次の指示を待つ。`state` だけで稼働中の段に置くと、指示を待っているセッションがラダーの末尾に沈む。
- **`stopped` は停止の段に置き、一覧から除かない。** 止めても `done` と `failed` はそのままの `state` で残るが、`blocked`（権限待ち、質問待ちなど）は `stopped` になる。除くと、止めた結果が行の種類で変わり（レビュー待ちは残り、質問待ちは消える）、`--json` の行がそのまま出るという見込みと食い違う。止めた行が消えてカーソルが別の行に移ると、遅れて押した `Ctrl+X` が別の行を止める（サイクル5で起きた）。一覧から消したいときは、利用者が削除する。会話のないセッション（プロンプトなしで起動し、指示を送っていないもの）は、止めると `--json` から消えることがあり、消えれば一覧にも残らない（サイクル5の終わりに決めた。2.1.283 では、消えた観測と `stopped` で残った観測の両方がある。消える条件は未確定）。停止の段の行は、`Enter` で attach すると起き直る（2.1.283）。権限待ちのまま止めた行は、起き直ると権限の確認が消え、そのツールの呼び出しは中断として扱われて「代わりに何をするか」を待つ。そのため質問待ちの段に移り、`Declined:` は出ない。止める前の状態（権限待ち）には戻らない。
- **`interactive` の `idle` は対象外にする。** 対話セッションでは、ターンを終えて入力を待つ状態も、開いているだけの状態も同じ `idle` になる。レビュー待ちに載せると、開いているだけの端末が一覧を埋める。対話セッションは試行錯誤に使い、任せる作業は `claude --bg` で起動する想定なので、止まったときだけ出せば足りる。
- **どの規則にも当たらない行は質問待ちの段に置き、段の表記に生の値を添える。** 表にない `waitingFor`（`"worker request"`、`"dialog open"` を含む）、`pid` があるのに `waitingFor` がない `blocked`、`status: "waiting"` なのに `waitingFor` がない行、未知の `state` などが当たる。止まっているかもしれない行を対象外にすると、不明を0として沈めるのと同じ失敗になる。段を増やさないので、解除コストが実際より大きい行が許可待ちより上に来ることはある。

`--json` の行の形が変わったときは、この表と規則を合わせて直す。

### 一覧の表示

- 列は SESSION / STATUS / WHERE / CTX / WAITING の順に並べる。SESSION を左端に置くのは、待ち先の入れ子の線をその中に引くため。WHERE の幅は表示中の行の最長に合わせ（端末に収まらなければ切り詰める）、数字の列をその後ろにまとめる。WAITING は右端に置く。
- **STATUS**：段の英語の表記（`Permission` / `Question` / `Sandbox` / `Failed` / `Review` / `Working` / `Waiting` / `Stopped`）。待機の理由は、段から分からないときだけ括弧で添える（例：`Failed (no process)`、`Question (dialog open)`）。理由のほとんどは段と一対一なので、独立した列にしない。入れ子にすると一覧が段の順に並ばなくなるので、「段」を名乗る見出しは実態と合わない。docs の用語は「段」のままにする（`--json` の `status` と紛れるので、docs で列を指すときは「STATUS の列」と書く）。
- **WAITING**：待機時間。原因と経過時間は別の情報なので、STATUS とは別の列にし、数字を縦にそろえる。最小の単位は分とし、1分未満は `<1m` と示す。秒単位で数字が変わり続けると目がちらつき、並び順に効くのも分単位の差だけである。
- **SESSION**：セッション名。`interactive` の行にだけ `(tty)` を添える。
- **CTX**：今のコンテキストの大きさ（token 数。`36k` のように示す）。本体のターンの最新の要求で送った token 数で、statusline のコンテキストの表示と一致する。サブエージェントや補助の要求は含めない。累計の token 数ではない。
- CTX の列は常に出す。
- 待機時間と CTX が分からないときは `-` と示す。`?` は対応が要る印象を与えるため。
- **WHERE**：場所の要約。リポジトリ名（worktree なら元のリポジトリ名、根より下なら `repo/sub`、git でない場所はパスの末尾）、既定でないブランチ名、worktree なら `(wt)`、PR があれば `#番号 (状態)`（状態は `open` / `draft` / `merged` / `closed` の文字で示し、同じ状態を色でも示す。色だけではどの色が何かをすぐに読めないため）。ブランチと worktree は `git` で取る。PR は `gh` があれば、そのブランチを head に持つ最新の PR を引く。`gh` がない、または認証していないときは PR を出さず、ほかの動作は変えない。一覧は PR を待たずに出し、分かったものから埋める。
- WHERE のブランチは、その `cwd` で今チェックアウトされているブランチであって、セッションが作業したブランチとは限らない。PR も同じ理由でずれうる。`--json` にはセッション固有のブランチを知る口がない。
- `interactive` の行の場所の提示（`Enter`）では、フルパスの `cwd` を出す。
- **各行の下に、そのセッションが今どうなっているかを示す一言を1行で出す。** 段と待機時間だけでは各行が何をしていて何を求めているかが分からず、確かめるために attach する手間を減らす。段ごとに出すものは次のとおり。
  - 稼働中：今取り組んでいる指示の冒頭（`→ <指示>`）。スラッシュコマンド（スキルの呼び出し、`/review 12` など）で始めたターンは、`/名前 引数` を指示として出し、待機時間もその時刻から数える。手元で完結してターンを始めないコマンド（`/model`、`/clear` など）は指示に数えない。数えないと、前の指示の一言が残り、稼働時間も前の指示から数えてしまう（サイクル5で一度落とした）。
  - 権限待ち：許可を求めている道具と対象（`Bash: <コマンド>`、`Edit: <ファイル>` など）
  - 質問待ち：Claude が `AskUserQuestion` で出した質問。権限の確認で断って中断したターンでは、断った道具と対象（`Declined: Bash: <コマンド>`）。行が求めているのは「代わりに何をするか」の指示なので、何を断ったかが見えれば attach する前に返す内容を考えられる（そのターンには応答の本文がないことが多く、最後の応答の冒頭では何も出ない）。どれでもなければ最後の応答の冒頭
  - 失敗：エラーの文言（`StopFailure` の `last_assistant_message`、または会話記録の `isApiErrorMessage` の行の本文）。`model_not_found` のような符号は、文言がないときだけ出す。どちらもなければ最後の応答の冒頭。フックの `error` は符号で、会話記録には人向けの文言しかないので、文言に揃えないと、whatnext が起動したかどうかで同じ失敗の一言が変わる
  - それ以外：最後の応答の冒頭
- 一言はフックから取り、フックで取れないときは会話記録から取る（[DESIGN.md](DESIGN.md)「機能ごとの入力の出どころ」）。どちらもなければ出さない。
- 最後の応答の冒頭は、空行、コードの囲み（囲みの中の行を含む）、表の行、区切り線（`---` `***` `___`）を飛ばした最初の行から、見出し・強調・箇条書き・番号・引用の記号と、インラインコードのバッククォートを除いたものである。記号は何の情報も持たず、`---` や `- ` だけの一言では、attach せずに何をしたかが分からない。応答がコードの囲みだけで、飛ばすと何も残らないときは、囲みの中の1行目を出す（レビュー待ちの行に何も出ないのを避ける）。囲みの中を先に出さないのは、中身がコードや出力で要約になっていることがまれなため（サイクル4の終わりに決めた）。要約は作らない。モデルで要約する案は、将来のオプトインの機能として検討する。
- 前のターンの一言は出さない。指示を出してから次の応答が来るまでの行には、稼働中の一言（指示の冒頭）だけが出る。
- 一言は列に揃えず、行の下に字下げした1行で出し、端末の幅で切る。列にすると、狭い端末ではほとんど読めない。
- **作業台でシェル以外のものが動いていれば、一言と `!` の行の下に `⚙ <コマンド行>` を1行で出す。** 複数のペインで動いていれば ` · ` でつなぐ（例：`⚙ npm run e2e · terraform plan`）。コマンド名（`node`）だけでは何を流しているか分からないので、引数を含めたコマンド行を出す。一覧の更新のときに tmux へ問い合わせ、更新の間は変えない。並びには影響しない（段は `--json` だけで決める）。終わったコマンドは出さず、次の更新で行が消える。終了コードや終わった時刻を取るには、利用者のシェルに記録させる仕掛けが要るため。
- **一覧が端末の高さに収まらないときは、スクロールして選んだ行が見えるようにする。** `Last attached` の組と `Up next` の見出しは固定し、ラダーと保留の組だけをスクロールする。選んだ行は窓の中央に置き、収まらないときだけ一覧の直後に `<選んだ行の通し番号>/<総数>` を出す。一覧の下の欄（メッセージ、入力欄、キーの説明）の分は窓から差し引く。窓は最小でも1行を残し、ヘッダを画面から押し出さない。1セッションあたりの行数は一言や入れ子の注記で増えるので、並行が 3〜8 個でも収まらないことがある。
- 色の割り当て、数の表記（`1200k` か `1.2M` か）、パスの略し方（`~` や中央の省略）、`interactive` の行の場所の提示を一行で出すか専用の画面で出すか、といった表示の細部は、この節に書いたこと以外は実装に任せる。サイクルごとに違ってよい。

### 更新と待機時間

- 一覧は、最後の更新から60秒たったとき、更新キーを押したとき、attach から戻ったときに更新する。更新と更新の間は `--json` を読まず、一覧の並びも変えない。
- ヘッダには最後に更新してからの経過時間を出さない。一覧は60秒ごとに自動で更新され、attach している間は一覧が見えないので、経過時間はほぼ常に1分未満になり、得られる情報がなかった（サイクル2で出していた）。
- `--json` を読んでいる間は、60秒ごとの自動の更新でも、一覧の下に `refreshing...` を出す。更新の間は一覧の並びが止まるので、その理由が分かるようにする。
- 更新キーを押したときは、同じ場所に、更新が終わったことを短く示す（`Refreshed.`、2秒で消える）。更新しても一覧の見た目が変わらないことが多く、押したことが伝わらないため。
- **待機時間は悲観的に数える。** 更新の間に新しく今の段に入った行は、前回の更新時刻から待っていたとみなす。誤差は更新の間隔（attach から戻ったときは attach していた時間）以内で、必ず長いほうに振れる。
- 更新と更新の間は、WAITING の数字も最後の更新の時点の値で止め、次の更新まで変えない。表示は実際より最大で更新の間隔だけ短くなり、悲観的に数えるのとは逆向きにずれるが、並び順には効かず、どれに手を付けるかの判断への影響は小さい。更新の間は画面が変わらないほうが単純である（サイクル5の終わりに利用者が判断した。サイクル4は15秒ごとに今の時刻まで進めていた）。
- **待機時間が分からない行（フックも会話記録もなく、起動して最初の更新で見えた行）は `-` と示し、同じ段の先頭に置く。** 不明を0として扱うと、何時間も止まっていたセッションが最下位に沈む。これがこのツールで最悪の失敗である。防ぎたいのは不明を0として沈めることで、表示の記号ではない。
- **attach から戻ったとき（新しく起動したセッションから戻ったときを含む）は、今離脱したセッションを含む組（待ち元を根とする木）を丸ごと、優先度ラダーとは別の組として一覧の先頭に出す。** その組には、前回 attach したセッションであることを見出し（`Last attached`）で示す。位置だけでは初めて使う人に意味が伝わらないため。空行を挟んでその下に、見出し（`Up next`）を付けて優先度ラダーが続く。ラダーの見出しは、先頭の組か保留の組があるときだけ出す（組が1つなら区別する必要がない）。今離脱したセッションはラダーの側には出さない（同じ行を二度出さない）。この組は、段が変わっても、更新を挟んでも、次に attach するまで残る。作業を終えて離脱したセッションを削除するとき、ラダーの中から探さずに済むようにするため。今離脱したセッションが対象外になっていれば（一覧から消えていれば）、この組は出さない。
- 保留中のセッションは、この先頭の組には出さず、保留の組に出す（次節）。
- カーソルは選んでいたセッションに付いていく。起動したときと、選んでいたセッションが一覧から消えたときは、一番上の組の位置を決めた行（実際に手を付ける行）を選ぶ。
- ただし attach から戻ったときは、今離脱したセッションを選ぶ（先頭の組にあっても保留の組にあっても同じ）。次の候補へは `↓` を1回押して移る。以前は今離脱したセッションを飛ばしてラダーの最上位を選んでいたが、作業を終えて離脱した直後にそのセッションを削除したいことがあり、`↓` 1回の手間より、離脱したセッションを探し直す手間のほうが大きかった。この組が出ないとき（対象外になったとき）は、ラダーの最上位の行を選ぶ。User Story 5 の動機は選んでいる最中の入れ替わりなので、attach から戻った瞬間とは衝突しない。
- 対象の行が1件もないときは、そのことをメッセージで示す。
- `--json` の取得に失敗したとき（`claude` が見つからない、出力を解析できないなど）は、エラーの内容を示し、古い一覧は出さない。次の更新で再び読む。

### 保留

- **利用者は、選んだ行を `h`（hold）で保留にできる。** 保留にしたセッションは、優先度ラダーとは別の組として、見出し（`On hold`）を付けて一覧の最下部に出す。組の中の並びは優先度ラダーと同じにする。段の判定は変えないので、STATUS と WAITING の列はふだんどおり出る。
- `h` を押すと、一覧の下に保留の理由の入力欄を出す（`Put <セッション名> on hold. Reason (optional):`）。`Enter` で保留にし、`Esc` で保留せずに閉じる。理由は任意で、空のまま `Enter` を押せば理由なしで保留にする。別の関係者に確認しているといった事情は、数時間たつと本人も忘れるので、書き留める場所を用意する。
- 保留にした直後に、一覧の下に `Put <セッション名> on hold. It comes back when you attach and work on it, or press h on it.` と出し、保留が解ける条件を伝える。解ける条件（attach して作業する）は画面から推測できないので、使い始めの人が保留の行を戻せずに困らないようにする。保留を解いたときは `<セッション名> is back in the list.` と出す。
- 理由は、保留の組の中で、その行のすぐ下に字下げした1行（`↳ <理由>`）で出す。行の末尾に続けると、狭い端末や長い WHERE で切れて見えなくなる。理由のない行には何も足さない。
- 理由は保留が解けたときに消える。理由を直すには、保留を解いてから保留し直す。
- 保留にするかは利用者だけが決め、whatnext は段や状態から自動で保留にしない。別の関係者の確認を待っているといった事情は `--json` からは読めない。
- 保留にしたときは、カーソルを、保留にした行と一緒に保留の組へ移った行（組の根を保留にしたときの待ち先）を飛ばした次の行（なければ前の行）に移す。保留は「今は手を付けない」という判断なので、カーソルが保留の組まで付いていくと、次の候補を選ぶのに戻る手間が増える。
- 保留の行で `h` を押すと、保留を解いて通常の一覧に戻す。カーソルはそのセッションに付いていく。
- **保留のセッションに attach して、作業して戻ると保留が解ける。参照しただけで戻ると保留のまま残る。** 「作業した」は、attach の前後で `--json` の `state`、`status`、`waitingFor` のいずれかが変わったこと、または attach の間に指示が送られたことで判断する。指示が送られたことは、`UserPromptSubmit` のフックが届いたか、フックが届かないセッションでは会話記録に `user` か `assistant` の行が増えたことで分かる。recap（`away_summary`）の行は attach しただけでも書かれうるので数えない。セッションが一覧から消えた（対象外になった）ときも保留を解く。
- 会話記録もないセッション（`--no-session-persistence` で起動したものなど）で、attach して指示を出し、終わるまで attach したまま待ってから戻ると、前後の状態が同じ（例：`done` → `done`）になり、参照しただけとみなされて保留が残る。そのときは `h` で解く。一律に解く案は、参照するたびに保留し直す手間が生じるので採らない。
- **保留と理由は、whatnext を終了しても消えず、次に起動したときに引き継ぐ**（[ADR-0016](adr/0016-persist-holds-and-waits-in-a-state-file.md)）。保留は日をまたいで使われる。whatnext が止まっている間に、そのセッションで作業しても（`claude attach` を直接使うなど）、起動し直したときに保留は解かない。保留が解けるのは、whatnext から attach して作業したときと、`h` を押したときと、セッションが一覧から消えたときだけである。
- 保留中のセッションの段が変わっても（権限待ちになったなど）、保留は自動では解かない。保留の組の中でも STATUS の列の色で見える（サイクル3で、自動で解く案は採らないと決めた）。
- 保留は、優先度が低い、別の関係者の確認が要るなど、利用者の判断だけで決まる「今は手を付けない」に使う。別のセッションの終わりを待つことは、保留ではなく待ち先で表す（次節）。

### 待ち先

- **利用者は、選んだ行（待ち元）に、その行が終わりを待つセッション（待ち先）を結べる。** 使い方の例は、実装したセッションが、そのレビューをするセッションを待つ、大きなタスクを分けた親が子を待つ、あるリポジトリの修正が先に直すべき別リポジトリの修正を待つ、の3つである。1つの待ち元は複数の待ち先を持てる。1つのセッションを待てる待ち元は1つだけで、関係は必ず木になる。失うのは、2つの待ち元が同じ待ち先を待つ場面（例：2つのリポジトリの修正が、共通ライブラリの同じ修正を待つ）で、そのときは片方を保留と理由で表す。
- 待ち先の関係は、結んでから、待ち元か待ち先が削除されるまで（`--json` から行が消えるまで）続く。停止して対象外になっただけでは切れない（削除のときに巻き込めるようにする）。レビューの往復のように手番が入れ替わっても、関係の向きは付け替えない。最初に結んだ関係を保つほうが、組を読み違えない。
- **待ちは状態として持たず、毎回導く。** 待ち元の行がレビュー待ちの段に当たり、待ち先のどれかがまだ終わっていないとき、待ち元を待ちの段（`Waiting`、稼働中の下、停止の上）に置く。待ち先が「終わった」とは、レビュー待ちか停止の段に入ったこと、または一覧に出なくなったこと（対話セッションの終了などで対象外になったか、行が消えた）をいう。待ち先が再び稼働すれば、待ち元は再び待ちの段に入る。往復のたびに利用者が結び直す必要はない。
- 待ち元が自分でも権限待ち、質問待ち、許可待ち、失敗、稼働中のどれかに当たるときは、待ち先を待っていても自分の段に出す。人間の手が要る行を待ちの段に沈めない。
- 待ちの段は放置コストがゼロ（待ち先が進めている）なので、稼働中の下に置く。その下は、利用者が止めた停止の段だけである。保留の組に入れないのは、何を待っているかが行に出ていればノイズにならないため。
- **待ち先は、待ち元の下に入れ子で並べる。** 線（`├ ` `│ ` `└ `）は SESSION の列の中に引き、注記の行にも縦線を引き継ぐ。兄弟どうしはラダーの順に並べる。組（待ち元を根とする木）はラダーの上を組ごと動き、その位置は組の中で最も順位の高い行で決める（段、待機時間が分からないもの、長く待っているもの、名前の順）。こうすると、待ち先が権限待ちになれば組ごと上に来るので、手を付けるべき行が末尾に沈まない。サイクル3の実装の前は、「待ち元が上位に来て『一番上がやるべきもの』という読み方が崩れる」として入れ子を退けていた。しかし、利用者は `↳ for` の注記を入れ子と受け取っていて、注記だけでは関係が見えなかった。組の位置を最上位の行で決めれば、読み方が崩れる問題も起きない。
- 待ち先の名前を待ち元の行に注記（`↳ for`）することはしない。入れ子で関係が見える。
- 待ち先がすべて終わって待ち元が自分の段に戻ったときは、行の下に `↳ <名前> done`（複数なら名前を並べる）を出す。この表示は、その待ち元に attach するか、待ち先が再び稼働して待ち元が待ちの段に入るまで続く。待ちの段の行に `done` を出し続けると事実と食い違う。待ち先が再び終わって待ち元が自分の段に戻れば、また出る。名前は、終わった時点の名前ではなく今の名前で出す（`--bg` のセッションは、ターンを終えると名前が付け直される）。待ち先が終わったあとに待ち元を一覧の中から探し直さずに済むようにする。待ち先を外したことで待ち元が待ちの段から出たときも、残った待ち先はすべて終わっているので、同じく `↳ <名前> done` を出す。待ち先が削除されて（`--json` から行が消えて）関係が切れたときは、`↳ <名前> done` を出さず、出ていれば消える。削除はほとんどが利用者自身の操作で、どのセッションが終わったかを知らせる必要が薄い。関係が切れたあとも名前を覚えておくと、関係とは別の状態を持つことになる。
- **保留と重なったとき**：根を保留にすると、組ごと保留の組に移る。保留は利用者の明示の判断なので、観測から導く待ちより優先する。途中の行を保留にしても組に残り、名前に `(on hold)` を添える。その行は組の位置を決めるときに数えない。保留の組の中でも、`↳ <名前> done` と保留の理由の行は出す。待ち元を連動して保留にはしない（保留は利用者だけが決める。連動させると、待ち先の保留を解いたとき、待ち先の一部だけが保留のとき、複数の待ち元に待たれているときの規則が次々に要る）。
- **待ち先の関係は、whatnext を終了しても消えず、次に起動したときに引き継ぐ**（[ADR-0016](adr/0016-persist-holds-and-waits-in-a-state-file.md)）。待ち先がすべて終わったことを示す `↳ <名前> done` は引き継がず、起動し直したあとは観測から導き直す。組の入れ子で関係は見える。
- 関係が一周する（A が B を待ち、B が A を待つ）と、どちらも待ちの段から出られなくなるので、一周する待ち先は結べない。
- 待ち先の関係を PR から自動で推定する（同じ PR を WHERE に持つ行を組にする）案は採らなかった。レビューするセッションが PR のブランチをチェックアウトするかは Claude に任されていて、当たるかどうかが偶然で決まる。
- 待ち先の出力（レビューの指摘など）を待ち元に渡すことは whatnext ではしない（[ADR-0003](adr/0003-no-input-injection-or-proxy-response.md)）。レビューするセッションに指摘を PR のコメントとして書かせ、待ち元にそれを読ませるなど、受け渡しは whatnext の外で行う。

### Usage の表示

- 一覧のヘッダに、アカウントの Usage を出す。`/usage` が示す枠ごとに、使用率とリセットする時刻を並べる（例：`session 42% (resets 2:09pm) · week (all models) 25% (resets Sep 29 9:59am)`）。リセットが今日なら日付を省く。使用率が50%以上なら黄、80%以上なら赤で示す。
- 目的は、rate limit にいつ当たりそうかを見ることと、新しいセッションのモデルを決める材料にすること。
- 取得するのは、whatnext の起動時、attach から戻ったとき（新しく起動したセッションから戻ったときを含む）、更新キーを押したときに限る。60秒ごとの更新では取らない。Usage は数分で大きく動くものではなく、一覧に戻る時点の値があれば判断に足りる。
- attach から戻ったときと更新キーでは、前回の取得を始めてから60秒たっていなければ取り直さない。取得している最中も取り直さない。起動時は必ず取る。attach から短く戻る操作が続いたときに `claude -p` を立ち上げ続けないためである。起点を「成功した時刻」にしないのは、失敗が続いたときに毎回取り直すことになるため。
- 取得は一覧の更新を待たせず、非同期に行う。取得中は前の値を出したままにする。
- 出る値はアカウント全体のもので、他の端末や claude.ai での利用も含む。セッションごとの内訳は出さない。

### 作業台

仕組みと退けた案は [ADR-0014](adr/0014-workbench-shows-in-a-screen-the-user-opens.md) と [ADR-0010](adr/0010-workbench-lives-inside-whatnext.md) にある。

**作業台は、利用者が端末の別の分割で開く作業台の画面に映す（サイクル7で、popup から改めた）。** 端末を分割し（左右でも上下でもよい。別のタブ、別のウィンドウ、別の端末のアプリでもよい）、そこで `whatnext workbench` を実行すると、その画面が作業台の画面になる。whatnext は端末を操作しない。分割を作る、フォーカスを移す、幅を変える、閉じる、はどれも端末の操作で行う。

```
┌ whatnext の画面 ─────────────────────┬ 作業台の画面 ────────────────────┐
│   変更点は3つです。                   │ $ docker compose up              │
│ ❯                                    │ web-1 | listening on :3000       │
│                                      ├──────────────────────────────────┤
│                                      │ $ pnpm test:e2e                  │
│                                      │ ✓ 42 passed                      │
│ fix-login · ログインの不具合を直して   │                                  │
│ ⚙ docker compose up · pnpm… ^Q^L back│ workbench: fix-login  0:zsh*     │
└──────────────────────────────────────┴──────────────────────────────────┘
```

popup をやめたのは、作業台を開いたまま claude の画面にも入力したいこと、並べて見比べるときに claude の画面の高さを減らしたくないこと、の2つのためである（サイクル6の終わりの利用者の判断）。端末の別々の分割に映すので、次の3つが端末の機能のままで成り立つ。

- 作業台を開いたまま、claude の画面にも作業台にも入力できる。入力は、端末のフォーカスがあるほうに入る。
- 作業台か claude の画面の複数行を端末で選んでコピーしても、もう一方の文字が混ざらない。端末の選択は、端末の分割の中に閉じるためである。tmux の中で左右のペインに分けると、端末の選択が左右をまたぐ。
- 作業台の画面の中でも、`ctrl+q ctrl+l` などの whatnext のキーが効く。作業台の画面も専用の tmux のクライアントなので。

claude の画面の幅は、分割の比率の分だけ減る。一時的に片側を広げたいときは、端末の機能（Ghostty なら分割の拡大 `cmd+shift+enter`）を使う。

- **作業台の画面は任意である。** 開かなくても whatnext はふだんどおり使える。作業台が要るときに開き、要らなくなれば端末の操作で閉じる（Ghostty なら `cmd+d` で分割して開き、`cmd+w` で閉じる）。Ghostty では `ctrl+q ctrl+w` と一覧の `w` で開くこともできる（下の「作業台を作る時機」の項）。閉じても、作業台と、その中で動いているものは残り、`⚙` で見える。次に開くと、元の配置のまま映る。
- **作業台の画面は、whatnext の画面（一覧とセッションの画面を映す端末）が attach しているセッションの作業台を映す。** whatnext の画面でセッションを移ると（`Enter`、`ctrl+q ctrl+j`、`ctrl+q ctrl+l`）、作業台の画面も移った先の作業台に切り替わる。
- **whatnext の画面が一覧を映している間は、作業台の画面はカーソルの行のセッションの作業台を映し、カーソルを動かすと切り替わる。** 一覧で行を選ぶと、そのセッションの作業台で何が動いているかが横に見え、次に何に手を付けるかの材料になる。カーソルを動かしただけでは、作業台を作らない。
- **作業台を作る時機は、利用者が決める。** 作業台の作業ディレクトリは、作った時点のセッションの場所になる。worktree に入る前に作るか後に作るかで場所が変わるので、whatnext は勝手に作らない。作るのは次の3つの操作である。
  - claude の画面か作業台の画面で `ctrl+q ctrl+w`
  - 一覧で `w`（カーソルの行の作業台）
  - 作業台の画面の案内で `Enter`

  作る直前に `--json` を読み直し、その時点のセッションの `cwd` で開く（`ctrl+q ctrl+e` と同じ読み直し方）。止めたセッションでは、`--json` の `cwd` がリポジトリの根に戻っているので、根で開く。すでに作業台があれば作らず、`Workbench already exists for <名前>.` と短く示す。作業台の画面を開いていないときも作り、`Workbench created. Run "whatnext workbench" in a split to see it.` と示す。worktree に入った直後に場所を確定させておき、作業台の画面はあとで開く、という順番も成り立つようにする。

  Ghostty で `ctrl+q ctrl+w` か一覧の `w` を押したときは、作業台の画面まで開いた状態にする。何度押しても同じ形になる（[ADR-0015](adr/0015-ghostty-split-for-workbench-on-ctrl-q-ctrl-w.md)）。
  - 作業台の画面が開いていれば、その分割へフォーカスを移す。分割は増やさない。上の2つの知らせは出さない。
  - 開いていなければ、押した分割を右に分割し、そこで作業台の画面を開いてフォーカスを移す。押したタブにほかの分割（ふだんのシェルなど）があっても、それには触れずに新しく分割する。

  ```
  押す前                       押したあと
  ┌────────────┬───────────┐   ┌────────┬────────┬────────┐
  │ whatnext   │ ~/app $   │   │whatnext│~/app $ │workbnch│ ← フォーカス
  └────────────┴───────────┘   └────────┴────────┴────────┘
  ```

  whatnext が作った分割は、作業台の画面が終わると閉じる。Ghostty でないとき、Ghostty が前面にないとき、Ghostty の操作が許可されていないときは、上の知らせを出すだけにする。初めて押したときに、macOS が Ghostty の操作の許可を求めることがある。
- 作業台の画面が映すセッションに作業台がまだないときは、作業台がないことと、作ったときに開く場所を示す。場所を出すのは、worktree に入ったかどうかを作る前に確かめられるようにするためである。

  ```
  No workbench for fix-login yet.
  Enter: open a shell in ~/ghq/github.com/me/app/.claude/worktrees/fix-login
  ```

- 作業台の最後のシェルを `exit` で抜けると、作業台は消え、作業台の画面には `Workbench closed.` と上の案内が出る。すぐに新しいシェルは作らない。`exit` で作業台を片付けたつもりなのに、新しいシェルが出直して閉じられなくなるのを避ける。作業台の画面ごと閉じたいときは、端末の操作で閉じる。
- **作業台の画面は同時に1つだけ映す。** 2つ目の作業台の画面を開くと（別のウィンドウで打った、うっかり2回打ったなど）、新しいほうが映し、古いほうは作業台から離れてシェルに戻る。tmux は、1つの作業台を大きさの違う2つの画面で映すと、小さいほうに大きさを揃えるため（一覧を1つの端末に限ったのと同じ理由）。
- **1つの作業台の中は、作業台の画面の中で tmux の既定のキーで分割し、ウィンドウを増やす**（`ctrl+q %`、`ctrl+q "`、`ctrl+q c` など）。分割とウィンドウの配置は作業台ごとに持つので、セッション A の作業台は分割なし、セッション B の作業台は `docker compose up` と `pnpm test:e2e` の2つに分割、のように分けて使える。作業台の画面がセッションを移ると、それぞれの配置のまま映る。
- whatnext の画面だけを閉じたときは、作業台の画面はそのまま、最後に映していた作業台を映し続ける。`whatnext` で whatnext の画面を開き直すと、また追従する。作業台だけを使い続けたい場面もあり、残しても害がない。
- whatnext が動いていないときに `whatnext workbench` を実行すると、`whatnext is not running. Start whatnext first.` と示して終了する（終了コード 1）。
- 端末は問わない。whatnext は端末の機能に頼らず、専用の tmux のクライアントを1つ増やすだけなので。例外は、Ghostty で押した `ctrl+q ctrl+w` と一覧の `w` が分割を作ることだけである。確かめるのは Ghostty で行う。
- **キーの起点は `ctrl+q` の1つだけにする。** attach している間は、claude の画面でも作業台の画面でも次のキーが効く。

  ```
  ctrl+q ctrl+l   一覧に戻る
  ctrl+q ctrl+j   一覧に戻らずに、Up next の先頭のセッションへ移る
  ctrl+q ctrl+w   そのセッションの作業台を作る(一覧の `w`)。Ghostty では作業台の画面の分割へ移る
  ctrl+q ctrl+e   外のアプリで見るメニューを出す(「操作」の `e`)
  ctrl+q ctrl+h   一覧に戻り、その行を保留にする(一覧の `h`。保留の理由の入力欄が開く)
  ctrl+q ctrl+x   一覧に戻り、その行を止める(一覧の `Ctrl+X`)。続けてもう一度押すと削除する
  ctrl+q ctrl+n   一覧に戻り、新しいセッションを起動する(一覧の `n`)。いたセッションのリポジトリを候補の先頭に置く
  ctrl+q ctrl+f   一覧に戻り、その行の待ち先のメニューを出す(一覧の `f`)
  ```

  作業台の画面で押したキーは、作業台の画面が映している作業台のセッションを対象にする（`ctrl+q ctrl+l` なら whatnext の画面が一覧に戻り、`ctrl+q ctrl+j` なら whatnext の画面が次のセッションへ移って作業台の画面も追従し、`ctrl+q ctrl+e` ならそのセッションの場所や PR を開く）。
  `ctrl+q ctrl+q` には何も割り当てない。サイクル6までは作業台の popup の出し入れに使っていたが、作業台の画面の開閉は端末の操作になった。
  一覧と attach している間で、同じ操作を同じ文字で使えるようにする（一覧の `e`・`h`・`Ctrl+X`・`n`・`f`・`w` と、`ctrl+q` のあとに ctrl を押したままの同じ文字）。待ち先はサイクル6まで `w` だったが、サイクル7で作業台（**w**orkbench）に `w` を明け渡し、`f`（wait **f**or）に移した。`ctrl+q ctrl+h`・`ctrl+q ctrl+x`・`ctrl+q ctrl+n`・`ctrl+q ctrl+f` は一覧に戻ってから一覧と同じ処理をするので、確認（push していないコミット、作業台で動いているもの、待ち先の巻き込み）も一覧と同じに出る。止めると `claude attach` も終わるので、止めたあとに attach したまま残る形はない。保留の理由の入力欄を `Esc` で閉じると、保留せずに一覧に残り、`Enter` ですぐ元の画面に戻れる。すでに保留の行で `ctrl+q ctrl+h` を押すと、一覧の `h` と同じく保留を解く。`ctrl+q ctrl+n` で候補の先頭をいたセッションのリポジトリにするのは、同じリポジトリで別の作業を始めることが多いため（`f` で待ち先を起動するときと同じ。ただし待ち先の関係は結ばない）。
  `ctrl+q ctrl+j` は、一覧に戻ったときに見える Up next の先頭（組の位置を決めた行）へ、一覧を経由せずに移る。1つ片付けて次に移るとき、`ctrl+q ctrl+l` → `↓` → `Enter` の3手を1手にする。いまいたセッションは一覧に戻ったときと同じく Last attached に入るので、Up next には並ばない。そのため、いたセッションが Up next の先頭でも2番目へ移る。移る先がなければ（Up next が空、attach できる行がない）その画面に留まり、画面の最下行に `No other session in Up next.` を短く示す。続けて押すと、毎回その時点の先頭へ移る（前に移ったところを覚えて巡回はしない。並びが変わっていれば、同じセッションの間を行き来しうる）。移った先が何のセッションかは、概要の行で分かる（次の項目）。
  一覧では `ctrl+q` を無視する。attach している間の癖で押しても何も起きず、`Ctrl+X` の削除の待ち受けも取り消さない。そのため `ctrl+q ctrl+x` を2回続けて押すと、止めてから削除できる。

  作業台の画面では、`ctrl+q` は tmux の prefix として働き、tmux の既定のキー（`c` でウィンドウ、`%` と `"` で分割など）が使える。claude の画面では、ほかの `ctrl+q` の組み合わせは何もしない。`ctrl+q` は、Claude Code、tmux の既定、Ghostty のどれも使っていないキーである。**whatnext の操作は、`ctrl+q` のあとも ctrl を押したままの形にそろえ、キーの説明もこの形で出す（[ADR-0013](adr/0013-whatnext-keys-hold-ctrl-after-ctrl-q.md)）。** 文字だけの形（`ctrl+q x` など）は、作業台の画面では tmux の既定のキーに使う。こうすると「一覧の文字を、ctrl を押したまま `ctrl+q` のあとに押す」の1つの規則で説明でき、tmux とぶつからない。
  - 文字だけの形は、tmux の既定とぶつかり、空きも少ない。tmux 3.7c で prefix の既定の割り当てがない小文字は `a b e g h j k u v y` だけで、`l`（直前のウィンドウ）・`x`（ペインを閉じる）・`n`（次のウィンドウ）・`w`（ウィンドウの選択）・`f`（ウィンドウの検索）はふさがっている。ctrl を押したままの形は、tmux の prefix の既定の割り当てがほとんどない（`C-o`・`C-z` などだけ）。
  - よく使う `ctrl+q ctrl+l` などは ctrl を押したままのほうが押しやすい（サイクル5で `^Q^L` と押して戻らずに混乱した）。
  - 説明の長さは変わらない（`^Q l` も `^Q^L` も4文字）。
  - `ctrl+q l`（文字だけ）は whatnext では扱わない。作業台の画面では tmux の既定（直前のウィンドウ）に返し、claude の画面では何もしない。`ctrl+q ctrl+e`・`ctrl+q ctrl+h`・`ctrl+q ctrl+j` は tmux の既定の割り当てがないので、文字だけでも同じ動作にする（説明には載せない）。
  - 割り当てのない組み合わせは tmux が黙って捨てるので、押し間違えても何も起きない。`ctrl+l` などは `ctrl+q` の直後にしか効かないので、claude とシェルでの本来の意味は変わらない。
- **attach した claude の画面の下に、tmux のステータス行を2行出す。** 上の行（概要の行）に、そのセッションの名前と最初の依頼を出す。下の行の左に作業台の状態を、右にキーの説明を出す。キーの説明は、作業台の有無にかかわらず常に出す。作業台の欄は数秒ごとに描き直す。

  ```
  attach mode keyboard shortcuts · アタッチ中に^Q^Wも使えるようにしたい
  ⚙ npm run e2e              ^Q^L back · ^Q^J next · ^Q^W workbench · ^Q^E external · ^Q^H hold · ^Q^X stop · ^Q^N new · ^Q^F wait
  ```

  - 概要の行は `名前 · 最初の依頼` の形にする。名前は一覧の SESSION の列と同じ。最初の依頼は、会話記録の最初の利用者の指示（`/model` などのコマンドは除く。一覧の `→` と同じ除き方）の1行目で、要約はせず、幅に収まらなければ末尾を `…` で切る。まだ指示がないセッションは名前だけを出す。名前が付いていても最初の依頼を出す。名前が ID のままのセッションでは、最初の依頼が唯一の手がかりになり、名前が付いていても、自分の言葉で書いた依頼のほうが早く思い出せるため。
  - 何のセッションかが画面から分からない場面を減らす。会話の末尾だけでは何の作業かすぐには分からない。とくに `ctrl+q ctrl+j` で移った直後と、長く離れてから画面に戻ったとき。名前と最初の依頼は変わりにくいので、一覧を更新するたび（60秒ごとなど）に置き直す。ただし、依頼のないセッションに attach して最初の依頼を送ったときは、更新を待たずに数秒以内に出す（whatnext が起動したセッションだけ。フックを受けられるため）。更新を待つと最長60秒、名前だけの行が続く（#189 で利用者が選んだ）。名前は次の更新で変わる。
  - 概要の行に出さないもの：リポジトリと worktree は、利用者が Claude Code の statusline で出すものとし、whatnext は出さない（一覧の WHERE の列で分かる）。最新の依頼は、画面の上に実物と recap があるので出さない。STATUS は claude の画面そのものから分かる。
  - 採らなかった形：画面の上端（pane の枠線の行）に出す案は、目がたいてい下の入力欄にあるので見落としやすい。1行のステータス行に詰める案は、キーの説明と概要のどちらも読めなくなる。`ctrl+q ctrl+j` で移ったときだけ数秒出す案は、長く離れて戻ったときに効かない。claude の画面が1行減る費用は、利用者が許容した（サイクル6）。

    ```
    こうはならない(1行に詰める)
    ⚙ npm run dev │ attach mode keyboard sh… │ ^Q^L back · ^Q^J next · ^Q^W wo…
    こうはならない(リポジトリ、最新の依頼、状態を出す)
    [whatnext] attach mode keyboard shortcuts · → 案Aがよさそうです。 · Working · worktree-ctrl-q-ctrl-w
    ```

  下の行の左側(作業台の状態):

  ```
  作業台でシェル以外が動いているとき(複数あれば ` · ` でつなぐ)
  │ ⚙ npm run e2e              ^Q^L back · ^Q^J next · ^Q^W workbench · … │
  作業台はあるが、シェルが待っているだけのとき
  │ ⌂ workbench (shell)        ^Q^L back · ^Q^J next · ^Q^W workbench · … │
  作業台がないとき
  │                            ^Q^L back · ^Q^J next · ^Q^W workbench · … │
  ```

  - 作業台の欄には、動いているコマンドだけを出す。出力の最後の行は出さない。静かで、秘密が出る心配がない。
  - 作業台の画面を開いているかどうかにかかわらず出す。作業台の画面を閉じていても、動いているものが見えるようにする。
  - 一覧には出さない。一覧では、キーは一覧の下のキーの説明に載せる。
  - 左の幅は作業台の画面の分だけ狭くなるので、キーの説明は右端が切れうる。よく使うキーを先に並べ、切れても `^Q^L back · ^Q^J next` が残るようにする。
  - サイクル4では、claude の画面が常に1行減るとして出さないと決めていた。サイクル5で、1行減る費用より、キーを思い出せない（`^Q^L` と押して戻らずに混乱した）・作業台で何が動いているか見えない費用のほうが大きいと利用者が判断して覆した。
  - 退けた形：作業台の出力を複数行の tail で出す（claude の画面が4〜5行減り、一覧の常時表示を退けた理由と同じく気が散る）。出力の最後の1行を出す（書き換わり続けて気が散り、秘密が出うる）。attach した直後の3秒だけキーを出す（作業台の状態が見えない）。
- **作業台の画面の最下行に、作業台のステータス行を1行出す。** 映している作業台のセッション名と、作業台のウィンドウの一覧を出す（`workbench: fix-login  0:zsh* 1:zsh`）。キーの説明は出さない（whatnext の画面に出ている）。作業台がないとき（案内を出しているとき）は、セッション名だけを出す。
- **一覧に戻る経路は2つある。** `ctrl+q ctrl+l` では `claude attach` を残したまま戻り、次の `Enter` では attach し直さずに、すぐ元の画面に戻る。空のプロンプトの ← では Agent View に入ったことを検知して `claude attach` を畳んで戻り、次の `Enter` で attach し直す（少し時間がかかる）。← で戻るので、Agent View から別のセッションに入る操作は使えない。
- `claude attach` がほかの理由で終わったとき（Ctrl+Z、`/exit`、attach の失敗）も一覧に戻り、次の `Enter` で attach し直す。Ctrl+Z は `claude attach` に組み込まれた離脱で、whatnext は挙動を変えないが、一覧に戻る経路としては案内しない（キーの説明にも挙げない）。`ctrl+q ctrl+l` で attach を残したまま戻れれば足りる。claude の画面で Ctrl+Z を握りつぶして何も起きないようにする案は採らなかった。
- 作業台は、セッションごとの tmux のセッション（`sh-<id>`）である。1つのセッションに作業台のウィンドウを複数持てる。
- 作業台で copy mode で遡れる行数は、tmux の既定（2000行）より長くする（20000行）。長いコマンドの出力を遡れるようにする。
- 作業台の中のシェルでは、Ctrl+Z はふだんどおりジョブ停止として効く。
- **attach した claude の画面と作業台の画面で、埋め込みのリンク（OSC 8）をクリックして開ける。** Claude Code や `ls --hyperlink`、`gh` などが出すリンクを、tmux を通さない端末と同じように扱う。リンクを端末に送るのは、xterm 系と Ghostty の端末で動かしているときに限る。OSC 8 を知らない端末では、制御文字が画面に出て崩れうるためである。Claude Code は tmux 3.4 以上の中ではリンクを出す（2.1.284 で確かめた）。
- 作業台と、その中で動いているものは、作業台の画面を閉じても、一覧に戻っても、別のセッションに移っても残る。作業台の画面で映し直すと、元の配置のまま見える。
- **作業台は、whatnext を終了すると閉じる。** 作業台のどこかでシェル以外のものが動いていれば、終了する前に、セッション名とコマンドを並べて英語で確認する（例：`Quit and stop 2 running commands? fix-login: npm run e2e, infra: terraform plan [y/N]`）。`y` なら、作業台と残した `claude attach` をすべて閉じて終了し、`N`（既定）なら閉じない。何も動いていなければ、確認せずに閉じる。空のシェルを閉じて失うのはシェルの履歴と画面の出力だけで、いつも確認を出すと、確認を読まずに `y` を押すようになる。作業台の画面は作業台から離れて、シェルに戻る。Claude のセッション本体は、終了したあとも動き続ける。
- 端末のウィンドウを閉じたときは、whatnext は終了しないので、作業台も動いているものもそのまま残る（「終了と、端末のウィンドウを閉じたとき」の節）。
- **whatnext のプロセスが確認を出せずに終わったとき**（`kill` した、想定外の例外で終わった、異常終了した）は、動いているものを止めない。終わる処理を走らせられれば（シグナルで終わるときも、想定外の例外で終わるときも）、残した `claude attach` と何も動いていない作業台を畳み、動いているものがある作業台だけを残す。次に whatnext を開いたとき、前の tmux サーバが残っていれば、動いているものを並べて引き継ぐかを英語で聞く（例：`2 commands are still running from a previous whatnext: fix-login: npm run e2e, infra: terraform apply. Keep them? [Y/n]`）。`Y`（既定）なら引き継ぎ、`n` なら止めて捨てる。何も動いていない作業台と、残っていた `claude attach` は、聞かずに捨てる。確認の既定は、終了するときも起動し直したときも「何も止めない」側にする。止めることは取り消せない。
- セッションを削除すると、作業台と残した `claude attach` もまとめて閉じる。作業台でシェル以外のものが動いていれば、そのコマンドを示して英語で確認を求め、`N` なら削除しない（セッションは1回目の `Ctrl+X` で止まったまま残る）。作業台だけを残すと、行が消えるので入る手段がなくなる。削除したセッションの作業台を作業台の画面が映していれば、次に映すもの（一覧のカーソルの行の作業台か、その案内）に切り替わる。
- 勧められた `!` のコマンドを作業台に貼る操作は「`!` のコマンドのコピー」にある。
- tmux がなければ、そのことを英語で示して終了する（[ADR-0008](adr/0008-dependencies-and-contact-points-with-tmux.md)）。

### 操作

- **`Enter`（`background` の行）**：一覧を映している端末を、そのセッションの画面に切り替える。画面の中では、専用の tmux サーバの中で `claude attach <id>` が動く（「作業台」の節）。一覧に戻る操作は、`ctrl+q ctrl+l` と空のプロンプトの ← である（「作業台」の節）。`/exit`（入力欄に `exit` とだけ打った場合も）でも一覧に戻り、セッション本体は動き続ける（サイクル5で確かめた）。離脱して一覧に戻ったとき、端末に子の設定（代替画面、マウスの追跡など）が残ってはならず、子が異常終了した場合も同じである。attach している間、キー入力が whatnext と子の両方に届いてはならない。`claude attach` が 0 以外の終了コードで終わったときは、子の出したメッセージを画面に残したまま、キーが押されるのを待ってから一覧に戻る。すぐに描き直すと、attach できなかった理由と対処（`claude respawn` など）が読めない。正常に離脱したときは待たずに戻る。画面の解析や入力の注入はしない（[ADR-0003](adr/0003-no-input-injection-or-proxy-response.md)）。
- **`Enter`（`interactive` の行）**：`id` がなく attach できないので、`cwd` と `pid` を示す。
- **`n`**：作業ディレクトリとモデルを指定し、プロンプトなしで `claude --bg` で起動する。最初の指示は attach した先の Claude Code の入力欄で書く。whatnext はプロンプトを受け取らない（入力欄を作ると Claude Code の入力欄の劣化コピーになり、複数行や貼り付けの扱いを抱え込む）。
  - 作業ディレクトリは候補から選ぶか、`Other...` で自由に入力する。候補は、whatnext を起動したディレクトリ、`--json` の各行の `cwd`、`ghq list` のリポジトリの順に、重複を除いて並べる。worktree に移ったセッションの `cwd` は worktree のパスなので、`git` で元のリポジトリのパスに寄せる。
  - `Other...` で入力したパスが存在しない、またはディレクトリでないときは、入力の場で `Not a directory: <パス>` を出して入力を続けさせる。起動させてから失敗を見せると、一覧に失敗の行が残り、打ち間違いを直す場所が遠くなる。空のまま `Enter` を押すと whatnext を起動したディレクトリで起動し、入力欄にはそのことを `Enter confirm (empty: <起動したディレクトリ>)` と示す。
  - 候補はフルパスではなく末尾のディレクトリ名（リポジトリ名）で表示する。同じ名前の候補が複数あるときだけ、互いを区別できるところまで親のディレクトリを足して表示する（例: `a/foo` と `b/foo`）。絞り込みは表示名とフルパスの両方に対して行い、表示名で当たった候補をフルパスだけで当たった候補より上に並べる。表示名は入力の文字が順に含まれていれば当たるが、フルパスは入力がそのまま続けて含まれるときだけ当たる（長いパスでは、とびとびの一致がほぼどの入力にも成り立ってしまうため）。
  - `ghq` がないとき、または失敗したときは、`ghq` の候補を出さずにそのほかの候補だけで続ける。エラーは示さない。
  - 文字を打つと候補を絞り込む。打った文字を順に含む候補だけを残し、連続して一致する候補を上に置く。`Other...` は絞り込みの対象にせず常に末尾に置き、選ぶと打った文字を入力欄に引き継ぐ。
  - worktree を使うかは聞かず、`claude` の設定（`worktree.bgIsolation`）に任せる。
  - モデルを選んでから claude の画面に入るまでは、起動中の画面（`Starting the session... Ns`）を出し続け、一覧を挟まない。一覧が一瞬見えると、起動に失敗して戻されたように見えて混乱する（サイクル6で直した）。
  - モデルは `default` と `Other...` の2択から選ぶ。最初は `default` を選んでおき、選ぶと `--model` を付けずに `claude` の既定で起動する。`Other...` を選んだときだけモデル名を入力でき、入力した値はそのまま `--model` に渡す。空のままでは起動せず、`Esc` で2択に戻る。自由入力だけにすると、既定で起動したいときにも入力欄を通るので打ち間違いの入口になり、打ち間違えたモデル名は起動後に失敗の段として初めて分かる。モデル名の選択肢は持たない（モデルが入れ替わるたびに whatnext を直さずに済む）。
  - 起動したら、そのセッションにそのまま attach する。プロンプトを書かずに離脱すると、そのセッションは指示を待つ行として質問待ちの段に残る。離脱したあとは `Enter` で attach したときと同じく一覧に戻る。
  - `claude --bg` の応答を待つ間は、新しいセッションの画面に留まり、作業ディレクトリとモデルに加えて、起動中であることと経過秒数を示す。この間のキー入力は受け付けない。一覧に戻すと、入力画面が閉じたことが完了か取り消しに見え、起動に失敗したように感じられるため。
  - 起動の出力から `id` を読み取れなかったときは attach しない。`claude --bg` の出力をその画面に残し、キーが押されるのを待ってから一覧に戻る。
  - Claude Code が信頼していないディレクトリで `claude --bg` に断られたときは、そのディレクトリで対話モードの `claude` を開き、Claude Code 自身の信頼の確認を画面に出す。承認されると、その `claude` を閉じて `claude --bg` で起動し直し、そのまま attach する。断ると（`claude` が終わると）一覧に戻り、`Not trusted: <ディレクトリ>` を示す。新しく作ったリポジトリで `n` が断られ、別の端末で `claude` を開き直す手間をなくす。信頼の確認を whatnext の中で代わりに聞いて Claude Code の設定に書き込むことはしない。確認はディレクトリの中のフックや MCP の設定を読み込む前の安全確認なので、その判断と記録は Claude Code に任せる（何も書き込まない方針 [ADR-0002](adr/0002-no-writes-no-persistent-state.md) とも揃う）。
  - `--name`、`--permission-mode`、`-w` は指定させない。
  - 途中で `Esc` を押すと、1つ前の段階に戻る（`Other...` の入力 → 作業ディレクトリの候補の選択、モデルの選択 → 作業ディレクトリの選択）。作業ディレクトリの選択で押すと一覧に戻る。モデル名の入力の `Esc` で2択に戻るのと揃え、先の段階で選び間違いに気づいたときに最初からやり直さずに済むようにする。
- **`Ctrl+X`（`background` の行）**：確認なしで `claude stop <id>` で止める。2秒以内にもう一度 `Ctrl+X` を押すと `claude rm <id>` で削除し、一覧から消す。止める操作が失敗したときは、`claude stop` の出力を示し、2回目で削除できることを添える（例：`Stop failed: <出力> (Ctrl+X again to delete)`）。止まっていないセッションに止めたと示さないため。2回目で削除することは変えない。Agent View の `Ctrl+X` と同じ挙動にする。
  - 停止の段の行では、1回目の `Ctrl+X` で止める操作をせず、すぐに削除の待ち受けに入る（`Press Ctrl+X again within 2s to delete.`）。止まっているものに `claude stop` を送ると、止める操作の失敗のような紛らわしい表示になりうる。
  - 削除の待ち受け中に `Esc` を押すか、`Ctrl+X` 以外のキー（カーソル移動など）を押すと、待ち受けを取り消す。カーソルを動かしてから2回目を押して、別の行を消すのを防ぐ。
  - **選んでいた行が一覧から消えて、利用者が動かしていないのにカーソルが別の行に移ったときは、その直後の2秒は `Ctrl+X` を受け付けない。** 押されたら、一覧の下に `Ctrl+X ignored: <消えた行のセッション名> left the list and the selection moved.` と示す。行が消える場面は、会話のないセッション（プロンプトなしで起動し、指示を送っていないもの）を止めて `--json` から消えたとき（いつも消えるわけではない）や、whatnext の外で `claude rm` したときである。そのあとの更新で行が消え、カーソルが移る。2秒を過ぎてから押した2回目は、移った先の行への1回目として、確認なしでその行を止めてしまう（稼働中の行なら、ターンが途中で失われる）。黙って受け付けないだけだと、利用者は何も起きないので押し直し、2秒を過ぎた押し直しで同じことが起きる。

    ```
    > review-x       Working     app                     12%      3m
        → テストを直して
      Ctrl+X ignored: fix-login left the list and the selection moved.
    ```

  - 退けた形：止めた行を、削除の待ち受けが切れるまで一覧に残す（待ち受けが切れたあとの更新で行が消えるので、そのあとに遅れて押せば同じことが起きる）。
  - 止めている最中（`claude stop` の応答を待っている間）に押された2回目は、2秒を過ぎていても削除として受け付ける。
  - **止めている間と削除している間は、その行の STATUS に出す。** 1回目の `Ctrl+X` から `claude stop` が終わるまでは `Stopping...` にする。行は薄くしない。止めたあとも一覧に残りうるためである。2回目の `Ctrl+X` を受けた時点から、行が一覧から消えるまでは `Deleting...` にし、行全体（一言などの注記を含む）を薄くする。止め終わるのを待つ間も `Deleting...` にし、一覧の下の `Press Ctrl+X again…` は消す。`claude rm` がロックで断る間は最長で約40秒かかり、以前はその間何も出ず、削除が受け付けられたかが分からなかった。

    ```
    止めている間(1回目の Ctrl+X)
    > fix-login      Stopping...  app fix-login (wt) #12  45%      12m

    削除している間(2回目の Ctrl+X から、行が一覧から消えるまで)
      SESSION        STATUS       WHERE                  CTX  WAITING
    > fix-login      Deleting...  app fix-login (wt) #12  45%      12m   ← 行全体がグレー
        → テストを直しました                                          ← グレー
      refactor-db    Working      app                     12%       3m
    ```

  - 削除している行では、`Enter`、`h`、`f`、`w`、`e`、`Ctrl+X` は効かない。カーソルの移動、更新、終了などは効く。
  - 待ち先を巻き込んで消すときは、巻き込む行も `Deleting...` になる。削除しなかった行（確認に `N` と答えた、断られた）は、すぐに元の表示に戻る。
  - 退けた形：行を薄くし、一覧の下に `Deleting fix-login...` を出すだけにする（注記の行はもともとグレーなので目立たず、意味も伝わりにくい）。行はそのままにし、一覧の下に出すだけにする（ほかのメッセージで上書きされ、どの行を消しているのかが行から離れる）。
  - 止めたプロセスがまだ終わっていないために `claude rm` がロックで断ったときは、プロセスが終わるのを待ってから削除する。利用者から見れば、2回押せば消える挙動のままにする。
  - push していないコミットがあるために `claude rm` が断ったときは、捨ててよいかを英語で聞き（例：`Discard 1 unpushed commit and delete session <id>? [y/N]`）、`y` なら `claude rm` が示した値を `--discard-unpushed` に渡して削除する。コミットは取り消せない形で失われるので、確認を挟む。
  - それ以外の理由で断ったときは、その文言をそのまま示す。
  - Agent View との違い：Agent View の削除は worktree を未コミットの変更ごと消すが、`claude rm` は未コミットの変更がある worktree のセッションを断る（セッションも worktree も残る）。whatnext は「それ以外の理由で断ったとき」の規則どおり断りの文言を示し、セッションは一覧に残る。消すには、利用者が変更をコミットするか捨てるか、Agent View で削除する。未コミットの変更だけを捨てる `claude rm` のオプションはない。
  - **待ち先の巻き込み**：削除する行が待ち先を持つときは、2回目の `Ctrl+X` のあと、その下にある待ち先（待ち先の待ち先も含む）を並べて、一緒に消すかを英語で聞く（例：`Also delete 2 sessions this one was waiting for? (review-x, split-y) [y/N]`）。`y` なら続けて消し、稼働中のものは止めてから消す。`N` なら選んだ行だけを消す。レビューや分割のセッションは待ち元と一緒に不要になることが多いが、`claude rm` は取り消せないので確認を挟む。待ち元が消えなかったとき（未コミットの変更で断られた、push していないコミットや作業台の確認に `N` と答えた）は、待ち先も消さずに残す。`y` は待ち元と一緒に消すことへの同意で、待ち元が残るなら待ち先も要ることが多い。
  - 巻き込んで消すセッションにも、push していないコミットの確認と、未コミットの変更による断りは同じように働く。
  - `interactive` の行では `id` がないので効かない。
- **`h`**（hold）：選んだ行を保留にする。保留の行では保留を解く（「保留」の節）。`background` と `interactive` のどちらの行にも使える。
- **`f`**（wait **f**or）：選んだ行（待ち元）の待ち先を結ぶメニューを一覧の下に出す（「待ち先」の節）。サイクル6までは `w` だった（`w` は作業台に明け渡した）。入口は1つにし、新しいセッションの起動と既存のセッションの選択を同じメニューに並べる。
  - 先頭は `New session`。選ぶと `n` と同じ手順（作業ディレクトリ、モデル）で新しいセッションを起動して attach し、そのセッションを待ち先に結ぶ。起動したセッションが、直後の `--json` の読み直しで見つからなくても（行が出るのが遅れた、読み取りに失敗したなど）、結ぶ予定を持ち続け、`--json` に現れた時点で結ぶ。何も示さずに結ばないと、利用者は結んだつもりのまま、待ち元が `Waiting` にならない理由を探すことになる。作業ディレクトリの候補の先頭は、待ち元のリポジトリにする（worktree なら元のリポジトリに寄せる）。待ち先は新しく起動することが多いので、この経路を先頭に置く。
  - その下に既存のセッションが、一覧と同じ順（ラダーの順）に並ぶ。`--json` の順は利用者から見て規則がなく、すぐ上の一覧と食い違う。各行には、どのセッションかを見分けられるだけの情報を添える（段、リポジトリ名など。何を添えるかと印の形は実装に任せる）。文字を打つと `n` の作業ディレクトリと同じ規則で絞り込める。文字を打つと、先頭の `New session` ではなく、絞り込んで最初に当たった既存のセッションを選ぶ（打った文字は既存のセッションを絞り込むためのもの）。選ぶと待ち先に加わる。すでに待ち先のセッションには印を付け、選ぶと待ち先から外れる。停止などで一覧から外れた待ち先はメニューに並べない。その関係は、待ち元か待ち先が削除されるまで残る（待ち元を削除するときは巻き込みの候補に出る）。
  - 待ち元自身と、選ぶと関係が一周するセッションは並べない。ほかの待ち元の待ち先になっているセッションも並べない（関係を木に保つ）。
  - `Esc` で閉じる。
- **`w`**（workbench）：選んだ行のセッションの作業台を作る（「作業台」の節）。作る場所は、その時点の `--json` の `cwd` である。すでにあれば作らない。
- **`e`**（external）：選んだ行の場所や PR を、whatnext の外のアプリで見るためのメニューを一覧の下に出す（見出しは `Show <セッション名> in:`）。キーの説明に open を使わないのは、`Enter` の attach（セッションを開く）と取り違えるため。`↑↓` と `Enter`、または番号で選び、`Esc` で閉じる。開く先ごとにキーを割り当てると、開く先が増えるたびにキーが尽きるので、入口を1つにする。開く先は、よく使う順に次のように並べ、メニューを出した時点では先頭を選んでおく。
  1. **PR を GitHub で**。
  2. **手元の VS Code**：`cwd` が属するチェックアウトの根を開く。worktree で動いているセッションならその worktree、リポジトリ本体ならリポジトリの根、git でない場所なら `cwd` そのもの。止めたセッションは `--json` の `cwd` がリポジトリの根に戻るので、worktree ではなく根を開く。止まる前に見た worktree のパスを覚えておく案は、whatnext を終了して起動し直すと表示が変わり分かりにくいので採らなかった。`vscode://file/<パス>/?windowId=_blank` を OS の `open` に渡す（`code` コマンドに依存しない）。VS Code のウィンドウがすでにあっても、そのウィンドウを開き直さず新しいウィンドウで開く（その場所をすでに開いているウィンドウがあれば、そのウィンドウが前に出る）。`interactive` の行でも出る。
  3. **PR を vscode.dev で**（`https://vscode.dev/github/<owner>/<repo>/pull/<番号>`）。github.com の PR のときだけ出す。手元にチェックアウトがないときの代わりなので、手元の VS Code より下に置く。
  - PR の選択肢は、WHERE に PR が出ている行でだけ出す。出ていない行（`gh` がない、PR がない、まだ取得中）では、PR がないことをメニューに示す。
  - 開いたら何を開いたかを示し、`open` が失敗したらその出力を示す。
  - **attach している間**：`ctrl+q ctrl+e` で、同じ開く先を tmux のメニューに出す。claude の画面でも作業台の画面でも効く。開く先は、押した時点のセッションの作業ディレクトリから決める。attach している間に claude が worktree に入る（出る）と、一覧が持つ場所は読み直すまで古いので、押したときに `--json` を読み直す（サイクル6で、worktree に入ったあとにリポジトリの根が開いたことから直した）。

    ```
    PR が出ている行
    ┌─ Show feature-x in: ─────────────────┐
    │ (1) Pull request #12 on GitHub       │
    │ (2) VS Code: ~/src/app               │
    │ (3) Pull request #12 on vscode.dev   │
    └──────────────────────────────────────┘
    PR が出ていない行
    ┌─ Show feature-x in: ─────────────────┐
    │ (1) VS Code: ~/src/app               │
    │     No pull request for this session.│  ← グレー、選べない
    └──────────────────────────────────────┘
    ```

    - PR がないことは、選べない行で示す。VS Code だけのメニューにして PR がないことを示さない形は採らなかった。
    - 一覧にまだ出ていないセッション（`n` で起動した直後など）でも PR を取りにいき、`gh` の応答を待ってからメニューを出す。
    - 開いたら何を開いたかを、`open` が失敗したらその出力を、画面の最下行に短く示す。
- 更新や終了に使うキーの割り当ては実装で決める。

### 未確定の前提

- **`pid` のない `blocked` を失敗の段に置くこと。** 「プロセスが異常終了して状態だけ残ったもの」と推測して失敗の段に置いているが、2.1.282 では attach すれば起き直って続けられた。解除コストは「原因の調査」より小さいことになる。段の置き方を変えるかは、使って困るかで判断する。
- **対話セッションを待ち元にしたとき。** 対話セッションはターンを終えると `idle` で対象外になるので、待ちの段にも出ず、待ち先が終わっても `↳ done` の行が出ない。待ちの段はレビュー待ちに当たる行だけを置き換える規則のままにしてあり、困るようなら capture する。
- **whatnext の画面が開いていないときに、作業台の画面で一覧に戻るキーを押したとき。** 作業台の画面で押した `ctrl+q ctrl+l`・`ctrl+q ctrl+h` などは whatnext の画面を一覧に戻して処理するが、whatnext の画面を閉じていると、戻す先の画面がない。何を示すかは決めていない。

#### 一覧と並び

- **1.** 状態の違うセッションが並行して動いているとき、whatnext を起動すると、優先度ラダーの順に1画面の一覧が出る。各行には段、待機時間、セッション名、場所の要約が併記され、待機の理由は段から分からないときだけ添えられる。
- **2.** 一覧は、最後の更新から60秒たったとき、更新キーを押したとき、attach から戻ったときに更新される。ヘッダに最後の更新からの経過時間は出ない。更新している間は、自動の更新でも一覧の下に `refreshing...` が出て、更新キーで更新したときは終わると `Refreshed.` が出る。更新の間に今の段に入った行の待機時間は、前回の更新時刻から数えられる。
- **3.** 起動直後で待機時間が分からない行は `-` と表示され、同じ段の先頭に置かれる。
- **4.** 同じ `sessionId` が二重に出ても1行にまとまり、プロセスが生きている行の状態で段が決まる。`interactive` で `idle` の行は出ない。`stopped` の行は停止の段（末尾）に置かれる。`pid` のない `blocked` は失敗の段（4位）に置かれる。どの規則にも当たらない行（表にない `waitingFor`、`pid` のある `blocked` など）は、生の値を添えて質問待ちの段に置かれる。
- **5.** 更新で行が並び替わっても、カーソルは選んでいたセッションに付いていく。attach から戻ったときは、今離脱したセッションを含む組が `Last attached` の見出しの付いた先頭に出て、カーソルがそこに置かれる。`↓` で優先度ラダーの最上位の行に移る。この組は更新を挟んでも次に attach するまで残り、対象外になったセッションは出ない。
- **10.** 対象の行がないときはメッセージが出る。`--json` の取得に失敗したときはエラーが出て、古い一覧は出ない。
- **24.** 一覧が端末の高さに収まらないとき、カーソルを動かすと、選んだ行が見えるように一覧がスクロールし、一覧の直後に `<通し番号>/<総数>` が示される。`Last attached` の組と `Up next` の見出しはスクロールしない。

#### 一言・待機時間・CTX

- **16.** `n` で起動したセッションは、ターンを1つ終えると CTX の列に値が出る。そのセッションが権限待ちなどで止まると、次の更新で WAITING が止まった時刻から数えられる。whatnext の外で起動したセッションの CTX は `-` と示される。別の端末のウィンドウで whatnext を起動すると、一覧がそのウィンドウに移り、前のウィンドウはシェルに戻る。
- **23.** `n` で起動したセッションに権限の要る指示を出して離脱すると、その行の下に `Bash: <コマンド>` のように許可を求めている対象が出て、セッションの側では権限の確認がふだんどおり出ている。ターンを終えてレビュー待ちの段に入ると、行の下に最後の応答の冒頭が出る。指示を出してすぐに離脱すると、稼働中の行の下に `→ <指示の冒頭>` が出る。whatnext を終了している間にターンを終えても、セッションの画面にフックのエラーは出ない。
- **33.** whatnext の外で `claude --bg` で起動したセッションでも、稼働中の行の下に `→ <指示の冒頭>`、権限待ちの行の下に `Bash: <コマンド>`、レビュー待ちの行の下に最後の応答の冒頭が出る。whatnext を起動した直後の最初の一覧から、止まっているセッションの WAITING は止まった時刻から数えられ、`-` にならない。CTX は `-` と示される。
- **34.** `n` で起動したセッションに指示を出して一覧に戻り、whatnext を終了する。そのセッションがターンを終えてから whatnext を起動し直すと、最初の一覧から、その行の下に最後の応答の冒頭が出て、WAITING はターンを終えた時刻から数えられる。
- **39.** 最後の応答が区切り線や箇条書きで始まっても、一言には記号とバッククォートを除いた最初の中身の行が出る。応答がコードの囲みで始まるときは囲みの後の最初の行が、応答が囲みだけのときは囲みの中の1行目が出る。
- **41.** 受け口のポートを whatnext 以外のプログラムが使っているときに `n` で起動したセッションには、フックと OTel が付かない。その行の一言と待機時間は会話記録から出て、CTX は `-` になる。
- **45.** 権限の確認で `No` を選んでターンが中断したセッションの行の下に、`Declined: <道具>: <対象>` が出る。whatnext の外で起動したセッションでも同じ。

#### attach

- **6.** `background` の行で `Enter` を押すと attach する。空のプロンプトの ← で一覧に戻る。端末に子の設定は残らず、キー入力も二重に届かない。attach が 0 以外の終了コードで終わったときは、子のメッセージが画面に残り、キーを押すと一覧に戻る。
- **7.** `interactive` の行で `Enter` を押すと、attach せずに場所（`cwd`、`pid`）が示される。
- **27.** attach している間は、claude の画面でも作業台の画面でも `ctrl+q ctrl+l` で一覧に戻る。作業台の画面で `ctrl+q l` を押すと、tmux の既定どおり直前のウィンドウに移る。そのあと同じ行で `Enter` を押すと、attach し直さずにすぐ元の画面に戻る。空のプロンプトの ← でも一覧に戻り、このときは次の `Enter` で attach し直す。案内しない Ctrl+Z と `/exit` でも一覧に戻り、whatnext ごと止まることはない。どの経路でも、端末に子の設定は残らない。

#### 作業台

- **25.** `background` の行に `Enter` で attach し、端末を分割して `whatnext workbench` を実行すると、作業台の画面に、そのセッションの作業台がまだないことと、作ったときに開く場所が示される。作業台の画面で `Enter` を押すと、その場所でシェルが開く。claude の画面と作業台の両方に入力でき、入力は端末のフォーカスがあるほうに入る。どちらの複数行を端末で選んでコピーしても、もう一方の文字は混ざらない。
- **26.** 作業台の画面で `ctrl+q %` で分割し、2つの長く動くコマンド（`docker compose up` と `pnpm test:e2e` など）を動かす。そのあと、`ctrl+q ctrl+l` で一覧に戻る → 作業台を分割していない別のセッションに入る（作業台の画面は、分割のないその作業台に切り替わる）→ `ctrl+q ctrl+l` で戻る → 元のセッションに入る、の順に操作しても、2つのコマンドは動き続けていて、分割も元のまま作業台の画面に見える。作業台の画面を端末の操作で閉じ、開き直しても同じ。
- **28.** claude の画面では `ctrl+b` や `ctrl+g` などの claude のキーがふだんどおり効く。作業台のシェルでは Ctrl+Z がジョブ停止として効く。作業台の最後のシェルで `exit` すると、作業台の画面に `Workbench closed.` と作業台を作る案内が出て、新しいシェルはすぐには出ない。`Enter` を押すと新しいシェルが出る。
- **30.** 作業台で `npm run e2e` を動かしたまま一覧に戻ると、次の更新から、その行の下に `⚙ npm run e2e` が出る。コマンドが終わると、次の更新で消える。
- **49.** attach した claude の画面の最下行に、キーの説明が常に出る。その上の行に、そのセッションの名前と最初の依頼が ` · ` でつないで出る（まだ指示がないセッションは名前だけ）。作業台で `npm run e2e` を動かすと、数秒で左側に `⚙ npm run e2e` が出て、終わると `⌂ workbench (shell)` に変わる。作業台の画面を閉じていても出る。一覧には出ない。作業台の画面の最下行には、`workbench: <名前>` と作業台のウィンドウの一覧が出て、キーの説明は出ない。
- **57.** 作業台の画面を開いたまま、whatnext の画面で一覧のカーソルを動かすと、作業台の画面がカーソルの行のセッションの作業台に切り替わる。作業台のないセッションの行では、作業台がないことと開く場所が示され、カーソルを動かしただけでは作業台は作られない。`Enter` で attach すると作業台の画面もそのセッションの作業台に、`ctrl+q ctrl+j` で移ると移った先の作業台に、切り替わる。
- **58.** セッションが worktree に入ったあとに、claude の画面で `ctrl+q ctrl+w` を押すと、その worktree のパスで作業台が作られる。作業台の画面を開いていなければ、`Workbench created. Run "whatnext workbench" in a split to see it.` が示され、あとで作業台の画面を開くとその作業台が映る。すでに作業台があるときに押すと、作られずに `Workbench already exists for <名前>.` が示される。一覧で `w` を押すと、カーソルの行のセッションの作業台が作られる。
- **58a.** Ghostty で、作業台の画面を開かずに claude の画面で `ctrl+q ctrl+w` を押すと、作業台が作られ、その分割が右に分割されて作業台の画面が開き、フォーカスがそこへ移る。左の分割に戻ってもう一度押すと、分割は増えず、フォーカスが作業台の画面の分割へ移るだけになる。押したタブにふだんのシェルの分割があるときも、そのシェルには何も入力されず、右に新しく分割される。whatnext を終了すると、whatnext が作った分割は閉じる。一覧で `w` を押したときも同じように、一覧の分割が右に分割されて作業台の画面が開き、もう一度押すとその分割へ移るだけになる。
- **59.** 作業台の画面を開いたまま、別の端末の分割でもう一度 `whatnext workbench` を実行すると、新しいほうが作業台を映し、前のほうはシェルに戻る。whatnext の画面だけを閉じても、作業台の画面は最後の作業台を映したままで、`whatnext` で開き直すとまた追従する。whatnext が動いていないときに `whatnext workbench` を実行すると、`whatnext is not running. Start whatnext first.` が示され、終了コード 1 で終わる。
- **60.** 作業台の画面で `ctrl+q ctrl+l` を押すと whatnext の画面が一覧に戻り、`ctrl+q ctrl+j` を押すと whatnext の画面が次のセッションへ移って、作業台の画面も追従する。作業台の画面で `ctrl+q ctrl+e` を押すと、作業台の画面が映しているセッションの開く先のメニューが、作業台の画面に出る。作業台の画面で `ctrl+q c` を押すと、tmux の既定どおり作業台に新しいウィンドウができる。

#### 終了と、端末のウィンドウを閉じたとき

- **31.** whatnext を終了する操作をすると、作業台で何かが動いていれば、セッション名とコマンドを並べた英語の確認が出る。`y` を押すか、何も動いていなければ、作業台も残していた attach もすべて閉じて終了する。`N` なら閉じない。Claude のセッションは終了したあとも動き続ける。
- **32.** 作業台で長く動くコマンドを動かし、セッションの画面を見たまま端末のウィンドウを閉じる。whatnext を起動し直すと、同じ一覧に戻り、閉じたときに見ていたセッションが `Last attached` の組に出てカーソルがそこに置かれる。保留と待ち先の関係は残っている。コマンドは動き続けていて、そのセッションに入り、作業台の画面を開くと元の配置で見える。
- **46.** whatnext のプロセスが異常終了したあとに起動し直すと、作業台で動いているコマンドを並べた英語の確認が出る。`Y` ならコマンドは動き続けていて、作業台の画面で元の配置のまま見える。`n` なら止まる。何も動いていなかった作業台は、確認なしに消えている。
- **50.** whatnext を動かしたまま、版の違う whatnext を起動すると、動いている一覧につながり、一覧の下に `whatnext <動いている版> is still running. Quit it to start <起動した版>.` が示される。終了の操作で閉じてから起動すると、起動した版の一覧が出る。

#### 新しいセッションの起動

- **8.** `n` で作業ディレクトリ（候補を絞り込んで選ぶか `Other...` で自由に入力する）、モデル（`default` か、`Other...` で入力した名前）を指定して起動すると、そのセッションに attach して最初の指示を書け、離脱するとそのセッションが一覧に現れている。起動を待つ間は一覧に戻らず、起動中であることと経過秒数が出ている。`ghq` がない環境でも同じ手順で起動できる。`Other...` に存在しないパスを入れると、その場で `Not a directory` と示されて起動しない。
- **47.** Claude Code がまだ信頼していないディレクトリを `n` で選ぶと、Claude Code の信頼の確認が出る。信頼すると、そのまま新しいセッションに attach していて、離脱するとそのセッションが一覧に現れている。断ると一覧に戻り、`Not trusted: <ディレクトリ>` が示される。
- **43.** `n` の途中で `Esc` を押すと、1つ前の段階に戻る（`Other...` の入力 → 作業ディレクトリの候補、モデルの選択 → 作業ディレクトリの選択）。

#### 停止と削除

- **9.** `background` の行で `Ctrl+X` を押すとそのセッションが止まり、2秒以内にもう一度押すと一覧から消える。worktree で動いていたセッションでも、2回押せば消える。push していないコミットがあるときは、捨ててよいかを英語で聞かれ、`y` で消える。未コミットの変更だけがある worktree のセッションでは、`claude rm` の断りの文言が示され、セッションは一覧に残る。1回目の `Ctrl+X` から止め終わるまで、その行の STATUS は `Stopping...` になる。2回目からは行が消えるまで薄い `Deleting...` になり、その行では `h` などが効かない。
- **29.** 作業台を持つセッションを `Ctrl+X` の2回で削除すると、作業台と残していた attach も閉じる。作業台でシェル以外のものが動いていれば、そのコマンドを示す英語の確認が出て、`N` なら削除しない。削除したセッションの作業台を作業台の画面が映していれば、次に映すもの（一覧のカーソルの行の作業台か、その案内）に切り替わる。tmux がない環境で whatnext を起動すると、英語で示して終了する。
- **40.** `Ctrl+X` の1回目で止める操作が失敗すると、`claude stop` の出力と、2回目で削除できることが示される。止めたとは示されない。
- **51.** 選んでいる行のセッションが一覧から消えて（外で `claude rm` した、会話のないセッションを止めて消えた、など）カーソルが別の行に移る。その直後の2秒に `Ctrl+X` を押しても、移った先の行は止まらず、`Ctrl+X ignored: <消えた行のセッション名> left the list and the selection moved.` が示される。

#### 保留

- **15.** `h` を押すと保留の理由の入力欄が出て、`Enter` を押すと選んだ行が最下部の `On hold` の組に移り、カーソルは次の行に移る。理由を入れていれば、その行の下に理由が出る。`Esc` を押すと保留せずに入力欄が閉じる。保留の行で `h` を押すと通常の一覧に戻る。保留の行に attach して何も入力せずに離脱すると、その行は `On hold` の組に残り、カーソルがそこに置かれる。指示を出してすぐに離脱すると、その行は `Last attached` の組に出る。whatnext を終了して起動し直しても、保留と理由はそのまま残る。保留にした直後は、一覧の下に保留が解ける条件（`… It comes back when you attach and work on it, or press h on it.`）が示され、保留を解くと `<名前> is back in the list.` が示される。
- **35.** whatnext の外で起動したセッションを `h` で保留にし、attach して指示を出し、ターンが終わるまで attach したまま待ってから戻ると、保留が解けて `Last attached` の組に出る。attach して何も入力せずに戻ると、保留のまま残る。

#### 待ち先

- **17.** 行 A を選んで `f` を押し、`New session` を選んで作業ディレクトリ（候補の先頭は A のリポジトリ）とモデルを指定すると、新しいセッション B が起動して attach する。離脱すると、B が稼働している間、A は `Waiting` の段になり、B が A の下に入れ子で並ぶ（組は B の段の位置に出る）。
- **18.** B がターンを終えてレビュー待ちの段に入ると、次の更新で A は自分の段に戻り、行の下に `↳ <B> done` と示される。この表示は A に attach するまで続く。B に再び指示を出して B が稼働すると、A は再び `Waiting` の段に出る。`↳ <B> done` は消える。
- **19.** A 自身が権限待ち、質問待ち、失敗のときは、B を待っていても自分の段に出る。
- **20.** `f` のメニューでは、`New session` の下に既存のセッションが並び、文字を打つと絞り込める。既存のセッションを選ぶと A の待ち先に加わり、印の付いた待ち先を選ぶと外れる。待ち先が複数あるときは、全部がレビュー待ちの段に入るか一覧から消えるまで A は `Waiting` のままで、待ち先は A の下に入れ子で並ぶ。一周する関係は結べない。ほかの待ち元の待ち先は、メニューに並ばない。
- **21.** 待ち先を保留にすると、その行は A の組に残り、名前に `(on hold)` が添えられる。A を保留にすると、組ごと `On hold` の組に移る。
- **22.** A で `Ctrl+X` を2回押して削除すると、A の下の待ち先（待ち先の待ち先も含む）を並べて、一緒に消すかを英語で聞かれる。`y` で待ち先も消え、`N` なら A だけが消える。A が消えなかったとき（確認に `N`）は、待ち先も残る。巻き込んで消す待ち先でも、push していないコミットの確認と、未コミットの変更による断りは今と同じに働く。whatnext を終了して起動し直しても、待ち先の関係はそのまま残る。
- **44.** `f` のメニューの既存のセッションは、一覧と同じ順に並ぶ。

#### `!` のコマンドのコピー

- **36・37** は、機能を廃止したので外した（Out of Scope の「`!` のコマンドのコピー」）。

#### Usage

- **13.** 一覧のヘッダに、Usage の枠ごとの使用率とリセットする時刻が出る。attach から戻ると、一覧を待たせずに値が新しくなる。一度も Usage を取れていないときは、Usage だけが出ず、一覧はふだんどおり使える。一度取れたあとで取得に失敗したときは、前の値が出たままになる。

- **56.** attach している間に `ctrl+q ctrl+j` を押すと、一覧を経由せずに、一覧の Up next の先頭のセッションへ移る（claude の画面でも作業台の画面でも）。概要の行は移った先の名前と最初の依頼に変わる。そのあと `ctrl+q ctrl+l` で一覧に戻ると、移った先が Last attached にあり、元のセッションは Up next に並ぶ。続けて `ctrl+q ctrl+j` を押すと、そのときの Up next の先頭へ移る。Up next が空のときは移らず、`No other session in Up next.` が示される。

## Out of Scope

- **コストやトークンのダッシュボード**：Grafana 構成の OSS が十数個あり飽和している。
- **事後の振り返りのサマリやレポート**：競合が多く、リアルタイム性という軸から外れる。
- **セッション内容の再構築やデバッグビュー**：JSONL を解析するツール（claude-hindsight など）が先行しており、情報量でも勝てない。
- **一覧の常時表示**：セッションに入っている間、一覧を横に出し続けること。セッションに集中したいので出さない（利用者の判断）。作業台のために tmux を必須にしたので（[ADR-0010](adr/0010-workbench-lives-inside-whatnext.md)）技術的な障壁はないが、一覧が横にあると気が散る。tmux を使わずに実現するには node-pty と ANSI パーサによる端末多重化の自作が要り、依存の総量が tmux より重い。
- **セッションへの自動介入や自動承認、返信や権限応答の代行、attach せずに一覧の上で権限を許可すること**：[ADR-0003](adr/0003-no-input-injection-or-proxy-response.md) を参照。
- **完了したセッションへの追加の指示を送るキー（`r`）**：追加の指示は attach して送れば足りる。
- **`claude logs` を開くキー**：出力が画面の再描画の制御コードそのもので読める形にならず、中身を見る手段は attach で足りる。
- **一覧に出ない過去のセッション（終了した対話セッション、`rm` したセッション）を再開する機能**：過去のセッションの一覧を機械で読める公式の口がない。会話記録は `--json` に出ているセッションを補うためだけに読み、過去のセッションを探す入口にはしない（[ADR-0011](adr/0011-fill-in-from-transcripts-when-hooks-are-missing.md)）。端末を `claude --resume` のピッカーに渡す案は、再開したセッションが whatnext の子の対話セッションになり、離脱の操作（Ctrl+Z）が attach と食い違う。止めた `background` のセッションは一覧に残り（`done` と `failed` はそのままの段に、それ以外は停止の段に）、`Enter` で再開できる。会話のないもの（プロンプトなしで起動し、指示を送っていないもの）は、止めると `--json` から消えることがあり、消えれば一覧にも残らない。それ以外は、`n` で同じリポジトリに空のセッションを起動し、attach した先で `/resume` を使う。
- **一覧で選んだ行のセッションの画面をプレビューすること**：tmux に `claude attach` を常駐させ、`capture-pane` で画面を一覧の横に出す案。画面を読んで理解する負荷は attach と変わらず、常駐のメモリ（1本あたり約 140MB）がかかる。セッションが今どうなっているかは、フックで取る行の一言で示す（[DESIGN.md](DESIGN.md)「フックの受信」）。画面の文言から段を決めるのは [ADR-0001](adr/0001-read-state-only-from-agents-json.md) に反する。
- **Web UI（ローカルサーバ）**：ブラウザのタブという常駐アプリが一つ増え、ウィンドウを増やさないという動機と衝突する。サイクル6までは「ブラウザでは対話型の Claude Code セッションを開けないので attach が原理的にできない」ことも理由にしていたが、ページに端末部品（xterm.js）を載せ、ローカルのサーバの pty で `claude attach` を動かせば attach はできる（VS Code の端末と同じ仕組み）。サイクル7の開始時には、作業台の画面の構成（[ADR-0014](adr/0014-workbench-shows-in-a-screen-the-user-opens.md)）を利用者が使って、作業台の使い勝手が悪いと判断したときの第一候補として残した。一覧を Web ページとして作り、キーをページが握れるので、端末の組み合わせの制約から自由になる。代わりに、端末部品の描画と日本語入力の品質に頼り、作業台の寿命を持つサーバを自作し、手元のシェルを動かせる口になるローカルのサーバの安全性（起動ごとのトークン、Origin の検査）を引き受ける。
- **独自のセッション管理、外部からの push 型キュー、常駐デーモン、計測ログ**：[ADR-0002](adr/0002-no-writes-no-persistent-state.md) を参照。端末のウィンドウを閉じたあとも whatnext が動き続けるのは、利用者が起動したものが終了していないだけで、常駐デーモンには当たらない（[ADR-0012](adr/0012-list-runs-inside-the-dedicated-tmux-server.md)）。
- **外部の出来事（Slack、CI、レビュー依頼など）の監視を本体で行うこと、常駐するコストの集計の自作**：[ADR-0008](adr/0008-dependencies-and-contact-points-with-tmux.md) を参照。
- **燃焼率の異常の自動検知**：定額プランで空転して失うのは金額ではなく利用枠で、上限に当たらない限り放置コストは小さい。閾値を過去の分布から決めるには蓄積が要り、ADR-0002 に反する。稼働中の行を稼働時間の長い順に末尾へ出せば、長く回り続けている行に気づける。
- **人間の手入力のメモ**：正本がなく、セッションとして起こす根拠もない。保存先が必要になり、個人用 TODO アプリへの変質を招く。
- **クラウドのセッション（claude.ai/code、`--cloud`、routine）を一覧に載せること**：公式の読み取り口がなく（[claude-code-behavior.md](claude-code-behavior.md)）、attach もできない。認証切れで止まる routine の多くは「失敗して終わった」か「起動していない」で、どちらも待機中ではないので段が決まらず、一覧の形に乗らない。非公式の経路（`claude mcp serve` の `RemoteTrigger`）でも、完了・返事待ち・失敗を構造化された値で区別できなかった。`claude agents --json` がクラウドのセッションを返すようになったとき、または Claude Managed Agents（状態と承認待ちを読む公開 API と端末からの attach がある。従量課金）を監視の実行基盤に採るときに再検討する。
- **並行するセッションの数を増やすための機能**：ボトルネックは人間のレビューの帯域なので、目的を詰まっている時間の短縮に限る。
- **セッションの情報（モデル、effort）の列、高価なモデルで定型作業を回していることの検知**：利用枠やコストの監視で、「どれに手を付けるか」を示す役割の外にある。コンテキストの大きさ（CTX）の列は、サイクル2で OTel の受信とともに入れた（[DESIGN.md](DESIGN.md)「OTel の受信」）。コスト（COST）の列も同時に入れたが、サイクル3でやめた。
- **M2 の残り（行内のリンク、端末のタイトルへの待機件数の表示、blocked が発生したときの OS の通知）**：サイクル3で要件から外した。OS の通知は Claude Code のセッション自身が通知するので二重になる。行内のリンク（WHERE の PR 番号を端末のハイパーリンクにする）は、PR を開く用途を `e` のメニューがキー操作で満たしている。端末のタイトルへの表示も、利用者の判断で外した。
- **作業台で終わったコマンドの終了コードや終わった時刻を一覧に出すこと**：取るには利用者のシェルに記録させる仕掛けが要り、利用者の設定に踏み込む。終わったことは `⚙` の行が消えることで分かる（サイクル4で判断）。
- **`n` の `default` の横に既定のモデル名を出すこと**：サイクル3で不要と判断した。
- **端末でない入出力で起動したときに、メッセージを出して終了すること**：whatnext は端末から人が使う道具で、パイプやリダイレクトの先で起動する用途がない。サイクル2にはあったが、サイクル3で扱わないと決めた。
- **ヘッダにセッションの件数（`N sessions`）を出すこと**：並行は 3〜8 個の想定で、一覧を見れば数えられる。サイクル2にはあったが、更新からの経過時間と一緒に消え、サイクル3で出さないと決めた。
- **連続して処理するための並べ替え（同じ段の中で直前と同じリポジトリの行を先にする、読んだだけのレビュー待ちの行を段の中で下げる）**：サイクル3で不要と判断した。リポジトリごとのグループ化と、離脱すると次の候補へ自動で attach する案も、それ以前に退けている（「一番上がやるべきもの」という読み方が崩れる、見ていない間に次へ入る）。
- **保留中に段が上がったら（権限待ちになったなど）保留を自動で解くこと**：サイクル3で採らないと決めた。保留の組の中でも STATUS の列の色で見える範囲でよい。
- **`!` のコマンドのコピー**：セッションが最後の応答で勧めた `! <コマンド>` を、一覧の下に出して `y` でコピーし、attach している間は `ctrl+q ctrl+y` のメニューから選んで作業台の入力欄に貼る機能。サイクル4で入れ、サイクル7のあとに利用者の判断で廃止した（2026-10-02）。作業台の画面を claude の画面の横に並べたので、claude の `/copy` で応答をコピーし、横の作業台で動かせば足りる。
- **外で起動したセッションに、attach のときに OTel を付け直すこと**：同じセッションのまま設定を足す手段がない。`claude respawn` はフラグを取らず、`--resume` に `--settings` を付けると別の ID のコピーが起動して元も残る。コピーで置き換えると行の ID やブランチが変わり、attach が「止めて複製する」という見えない副作用を持つ。得られるのもそのセッションの CTX だけで、対話セッションは対象外のまま。

## Further Notes

### 配布

whatnext を npm に公開し、`npx @masahirompp/whatnext` で呼び出せるようにして、実際に試す（サイクル2で決定）。

- パッケージ名は `@masahirompp/whatnext`、bin の名前は `whatnext` とする。npm の `whatnext` という名前は別人が公開済み（2026-09 時点）なので、スコープ付きの名前にする。`npx` でスコープ付きの名前を呼べば、bin の名前が既存のパッケージと衝突することはない。
- バージョンは `0.1.0` から始める。`0.x` 系で出し、破壊的な変更を入れたら minor を上げる。semver は `0.y.z` を「いつ何が変わってもよい初期開発版」と定めているので、`0.x` であることがアルファ版の表明になる。プレリリース版と dist-tag（`@alpha`）は、安定版の系列が別にあるときの仕組みで、`npx` をタグなしで呼べなくなるので使わない。
- `engines` は `node >=22` とする。サポートが続いている Node の版の下限である。
- パッケージに含めるのは、ビルド後のコード（`dist/`）、README、LICENSE だけにする。
- ライセンスは MIT とする。公開すればコードは誰でも取得できるので、許諾しないまま出すと「公開したのに使えない」状態になる。依存先も、MIT と両立するライセンスのものに限る。
- GitHub のリポジトリは private のまま公開し、`package.json` に `repository` を書かない。npm のページから README の相対リンクが切れることは受け入れる。M1 は撤退判定を通過した（サイクル2）。リポジトリを public にするかは未決で、人間が決める。
- publish は取り消せない外部への公開である。公開したバージョン番号は使い直せず、72時間を過ぎると原則として unpublish できない。そのため、`npm login` と `npm publish --access public` は人間が実行する。実装セッションは、その前に `npm pack --dry-run` で同梱物を示して止まり、公開のあとに `npx` で起動できることを確かめる。
- whatnext は設定を持たず、データは保留と待ち先の関係を書く状態のファイルだけである（[ADR-0016](adr/0016-persist-holds-and-waits-in-a-state-file.md)）。このファイルは読めない版を空として扱い、移行を求めない。そのため、破壊的な変更で利用者に移行を求めるものがない。このため、公開したあともサイクル型の書き直しを続けられる見込みがある。README に「0.x の間は予告なく変わる」と明記する。

### 段階と撤退判定

M1（順位の提示と最小の操作）だけで、順位の提示が実際に役に立つかを判定できる。
役に立たなければ M2 以降は作らない。

撤退判定はサイクルの完了条件とは別に行う。
M1 を1週間使ったあと、利用者本人が定性的に判断する。
提示された順位が自分の直感と一致しない場合、あるいは一致しても結局 `claude agents` を開いている場合は中止する。
順位付けのロジックが機能しない状態で M2 以降の UI に投資すると、完成度に引きずられて使えないツールを使い続けることになる。

目安にする観点は次のとおり。いずれも数値では測らない。

- blocked が発生してから解除するまでの時間が短くなったか。
- 提示された最上位のセッションを実際に選んでいるか。
- `claude agents` を開く回数が減ったか。
- ウィンドウを切り替える回数が減ったか。

**結果（サイクル2の終わり、2026-09-25）**：M1 は撤退判定を通過した。
利用者の判断で、細部の不満はあるが、大枠の使い勝手はよかった。
判定は1週間を待たず、使い始めて2日ほどで行った。
その間に Usage の表示、`e` のメニュー、保留、OTel の受信を足しており、完成度に引きずられずに判定するという上の狙いどおりの条件ではない。
順位の提示が本当に役に立っているかは、以後も上の観点で見続ける。

### CTX の列と OTel の受信（M3）

サイクル2で、コスト（COST）の列を、whatnext が起動したセッションから OTel を直接受ける方式で入れた（[DESIGN.md](DESIGN.md)「OTel の受信」）。試行として入れ、利用者が本採用と判断した。コンテキストの大きさ（CTX）の列と、OTel による待機時間の推定も同じ方式で入れた。当初の設計（利用者が常駐させる外部のメトリクス基盤を属性プラグイン経由で読み、値は並び順に使わない）は採らなかった。COST の列はサイクル3でやめた。CTX があれば足りると利用者が判断した。

### 複数の出どころ（構想）

今は手元の Claude Code 専用だが、クラウドの Claude のセッションや Codex なども一覧に載せる構想がある。サイクル2では、構想として置き、今は作らないと決めた。

- 並び順の考え方（放置コスト ÷ 解除コスト、段、待機時間）は、特定のエージェントに依存しない。依存しているのは、状態の読み方（`claude agents --json`）、行から段を決める規則、操作（`attach` / `stop` / `rm` / `--bg`）の3つである。
- 対応するなら、この3つを「出どころ」の単位で差し替えられるようにする。各出どころは、行（id、段に写した状態、待機の理由、場所、時刻）と、使える操作を返す。ADR-0001 と ADR-0005 は「出どころごとに公式の読み取り口を一つ使う」に書き換えることになる。
- **出どころとして採る基準**：行ごとに、構造化された「待っている／動いている／終わった」の信号を返すこと。文面にしか差が出ない出どころ（routine の実行など）を混ぜると、段の判定を説明できなくなる。
- **有効にする方法**：何を監視するかは利用者が選んで有効にする（既定は `claude agents --json` だけ）。設定ファイルを持たないので、起動時のフラグか環境変数で有効にする。コマンドがあれば自動で有効にする方式は、利用者が選ぶという方針と矛盾する。
- `Enter` の意味（attach、ブラウザで開く、場所を示す）は出どころごとに変わるので、出どころの定義に含める。
- Codex の公式の読み取り口と、`--bg` や attach に当たる仕組みがあるかは未調査。
- **時期**：M1 の撤退判定は通過した（サイクル2）。残る条件は、2つ目の出どころを実際に使うようになること。サイクル3の時点でも、まだ要らないと判断した。サイクル型なので、コードに先回りの抽象は入れない。

### 端末の明け渡しを無くす構成

サイクル5で、一覧を専用の tmux サーバのセッションの中で動かし、`Enter` をクライアントの切り替えにする構成を採った（[ADR-0012](adr/0012-list-runs-inside-the-dedicated-tmux-server.md)）。
サイクル4までの構成では、whatnext が自分の端末を子の `tmux attach` に明け渡しており、Node の内部 API への介入（`cycle-5` のタグの working-with-ink スキル）、`stty` による保存と復元、子が主画面に残す行の後始末が要った。

**確かめること**：次のどれかが、この構成ではどう回避しても満たせないと分かったら、構成は破綻したとみなし、ADR-0010 の構成（明け渡し）に戻すかを利用者が決める。

- attach の最初の Ctrl+Z が効くか、子への端末の応答が一覧に漏れないか、戻ったあとに端末の設定が壊れていないか
- Ctrl+Z と ← で一覧に戻れるか
- Ink の描画、キー入力、貼り付け（kitty キーボード、bracketed paste、色）が、tmux を挟んでも変わらないか
- 利用者の tmux の中で起動したときに問題が出ないか
- 作業台の popup の手触りが今と同じか

**結果（サイクル5）**：5項目とも、満たせないものは見つからなかった。Ink の描画、キー入力、貼り付けと作業台の popup は、利用者がふだんの端末でざっと触って違和感がなかった。kitty キーボードでしか区別できない修飾キー（Shift+Enter など）と複数行の貼り付けは、個別には試していない。困ったら capture する。

**言語を替える案**：言語を替えたい動機は、ほぼ明け渡しにある。この構成が成り立ったので、動機はほぼ消えた。Python（`termios`、Textual の `App.suspend()`）には tmux に代わる成熟した部品がなく（pyte は保守が止まり、ghostty-textual は v0.0.4）、配布と起動でも Node より不利である。Rust（crossterm、alacritty_terminal、portable-pty、tui-term）は単一のバイナリで起動も速いが、作り直す費用が大きい。どの言語でも、作業台を whatnext より長生きさせるには常駐するサーバが要る。この構成が破綻したとき、または whatnext の中で claude の画面を直接描く要件が出たときに再検討し、Rust（ratatui と alacritty_terminal）を第一候補として比べる。`lib/` に最初のモジュールを昇格させる前に判断する。

### 近い道具との違い（サイクル7の開始時）

作業台の形を決めるために端末エミュレータとマルチプレクサを調べた（[ADR-0014](adr/0014-workbench-shows-in-a-screen-the-user-opens.md)）。そのうち2つは、whatnext と目的が重なる。

- **herdr**（tmux のようなマルチプレクサ。Apache-2.0。2026-09 時点で GitHub の星は約4万で、ほぼ毎日公開されている）：背景のサーバが端末を持ち、サイドバーにエージェントごとの状態（working / blocked / done / idle）を出す。状態は、画面の照合と公式のフックから取る。
- **cmux**（Ghostty をもとにした macOS の端末）：縦のタブと、エージェントが待っているときの通知（ペインの枠、未読の印）を持ち、Claude Code のフックを取り込む。

どちらも「並行するエージェントのうち、どれが待っているか」は示すが、次の点は持たない。これが whatnext を作り続ける理由である。

- 放置コストと解除コストによる**順位と、その根拠の表示**。待っているものを並べるだけでは、どれから手を付けるかを利用者が組み立て直すことになる（Problem Statement）。
- 保留と待ち先。
- セッションに紐づき、端末を閉じても残る作業台。
- 段の判定を `--json` の構造化された値だけで行うこと（[ADR-0001](adr/0001-read-state-only-from-agents-json.md)）。画面の照合は Claude Code の見た目が変わると外れうるが、一度でも外した推薦は使われなくなる。

利用者は、どの道具もある程度使ったうえで、「次に何をやるか」の判断には whatnext の一覧に満足しており、不満は作業台の使い勝手にあった（サイクル7の開始時）。撤退判定の観点（「段階と撤退判定」）には、「herdr や cmux の表示で足りていないか」を加えて見続ける。
