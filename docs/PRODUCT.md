# whatnext

## Problem Statement

Claude Code のセッションを同時に 3〜8 個走らせ、セッションどうしで作業を分け合うようになると、`claude agents` の一覧は、どのセッションがどの作業の一部なのかを示さない。
作業の分け方には、実装とレビューの往復、大きなタスクの分割、先に直すべき別リポジトリの修正、オーケストレーションするセッションが起動したセッションがある。
利用者は組の関係を頭の中に持ち続け、待ち先が終わったかを確かめるために一覧を見て回る。
セッションごとにエディタ、GitHub、ターミナルのウィンドウも散らばる。

認知負荷の実体はセッションの数ではなく、組の関係を覚えておくこととウィンドウ間の視線の移動にある。
ボトルネックはエージェントの数ではなく人間のレビューの帯域なので、目的は並行を増やすことではなく、詰まっているセッションが詰まっている時間を短くすることに限る。

## Solution

whatnext は Node で作る端末アプリで、セッションをリポジトリごとの区切りにまとめた一覧を1画面で示す。
Agent View を置き換えるのではなく、その前段に立つ。

一覧は、セッションどうしの依存（利用者が結ぶ待ち先と、プロセスの親子から導く起動された行）を入れ子で示す。組はリポジトリを跨いでも崩さない。
リポジトリごとの区切りの中は、最後に attach した順に並べる。次に何をするかは利用者が自分で選ぶ。

各行には、そのセッションが今どうなっているか（段、段から分からないときは待機の理由）と、場所の要約（リポジトリ、ブランチ、PR）、作ってからの時間を必ず併記する。
段は、タスクの重要度ではなく止まり方の種類で（進めるのに利用者がすること、つまり解除コストで分ける）、人間に重要度を入力させずに決まる。待ちのほかの段は `claude agents --json` の出力だけで決まり、待ちの段は利用者が結んだ待ち先の関係からも導く。
重要度はテレメトリに存在せず、人間に入力させればそれ自体が新しい管理作業になる。

利用者は一覧から行を選んで attach し、離脱すると一覧に戻る。
一覧からは新しいセッションの起動と、セッションの停止と削除もできる。

セッションごとに作業台（そのセッションの作業ディレクトリで開いたシェル）を持ち、端末の別の分割で開いた作業台の画面に、セッションの画面と並べて映せる。
作業台の画面は、いま見ているセッションの作業台に追従する。
sandbox の外で人が動かすコマンドを、どのセッションのためのものかで迷わずに動かせる。
作業台で動かしているものは、一覧に戻っても動き続ける。作業台は whatnext の中にあり、whatnext を終了すると閉じる（動いているものがあれば、終了する前に確認する）。
端末のウィンドウを閉じても whatnext は終了せず、次に起動すると同じ一覧に戻る。

利用者は、あるセッションが別のセッションの終わりを待っていること（待ち先）を示せる。
待ち先は待ち元の下に入れ子で並ぶ。
待ち先がすべて終わると、待ち元は元の段に戻る。
ほかのセッションが起動したセッション（起動された行）は、起動元の下に入れ子で並ぶ。見せるだけで、起動元の段は変えない。
利用者は、セッションに1行のメモを付けられる。

## User Stories

1. （廃止。ラダーのビューをやめた。Out of Scope の「ラダーのビュー」）
2. As a 開発者, I want 各行に段、場所（リポジトリ、ブランチ、PR）、作ってからの時間が出ること、段から分からないときは待機の理由も出ること, so that attach しなくても各セッションが何を求めているか、いつ始めた作業かを見て、次に手を付けるものを選べる。
3. （廃止。ラダーのビューをやめた）
4. （廃止。ラダーのビューをやめた。稼働中のセッションも一覧に出る）
5. As a 開発者, I want 見ている間は一覧の並びが勝手に動かないこと, so that 選ぼうとした行が直前に入れ替わって別のセッションを操作してしまうことがない。
6. As a 開発者, I want 選んだ行で `Enter` を押すとそのセッションに attach し、離脱すると一覧に戻ること, so that ウィンドウを増やさずにセッションを操作できる。
7. As a 開発者, I want attach できない対話セッション（`(tty)` の行）では、その場所（`cwd` と `pid`）が示されること, so that どの端末で止まっているかを探せる。
8. As a 開発者, I want 作業ディレクトリを指定して新しいセッションを起動し、そのまま attach して最初の指示を書けること, so that 一覧から離れずに作業を任せられる。
9. As a 開発者, I want 作業ディレクトリを、いま動いているセッションのリポジトリと手元のリポジトリの一覧から、文字を打って絞り込んで選べること, so that パスを毎回入力せずに済む。
10. As a 開発者, I want Agent View と同じ操作でセッションを止め、続けて一覧から消せること, so that 不要になったセッションを一覧から片付けられる。
11. As a 開発者, I want whatnext を終了してもセッションが動き続けること, so that whatnext を気軽に起動したり終了したりできる。
12. As a 開発者, I want whatnext を経由せずに起動したセッションも一覧に出ること, so that 起動の経路を気にせずに済む。
13. As a 開発者, I want セッションに1行のメモ（誰の返事を待っているか、余裕があるときだけ進める、など）を付けておけること, so that 数時間たっても、そのセッションをどう扱うつもりだったかを attach せずに思い出せる。
14. As a 複数のセッションを組み合わせて一つの作業を進める開発者（実装とレビューの往復、大きなタスクの分割、先に直すべき別リポジトリの修正）, I want あるセッションが別のセッションの終わりを待っていることを一覧に示せ、待ち先が終わると待ち元が戻ってくること, so that 組の関係を覚えておかずに済み、待ち先が終わったあとに待ち元を一覧から探し直さずに済む。
15. As a sandbox の中で Claude Code を動かす開発者, I want セッションの画面と並べて、そのセッションの作業ディレクトリで開いた作業台を映し、両方に入力できること, so that sandbox の中で動かせないコマンド（docker、terraform など）を、どのセッションのためのものかで迷わずに手で動かせる。
16. As a 開発者, I want 作業台で動かしているものが、一覧に戻っても動き続け、戻ると元の配置のまま見え、一覧からも何が動いているかが分かること, so that 長い e2e を流しながら別のセッションの作業ができる。
17. （廃止。Out of Scope の「`!` のコマンドのコピー」）
18. As a 開発者, I want 端末のウィンドウを閉じても、次に起動すればメモや待ち先を含めて同じ一覧に戻ること, so that うっかりウィンドウを閉じても段取りを組み直さずに済み、作業台で動かしているものも止まらない。
19. As a worktree で作業させる開発者, I want 作業台を作る時機を自分で選べること, so that セッションが worktree に入ったあとに、その worktree の場所で作業台を開ける。
20. As a 開発者, I want 作業台の画面を、要るときだけ開き、要らなくなれば閉じられること, so that ふだんは claude の画面を広く使える。
21. As a 次に手を付けるセッションを自分で選ぶ開発者, I want セッションがリポジトリごとにまとまり、まとまりの中ではよく触るものが上に来て、状態が変わっても位置が動かない一覧, so that 続けたい作業をリポジトリの文脈で探せ、記憶した位置がずれない。
22. As a レビュー待ちや稼働中のセッションをいくつも並べる開発者, I want 各行にそのセッションの Goal が出て、選んだ行のダイジェスト（Goal・Progress・Next）と会話リンクが一覧の横に出ること、セッションに入ったあとも同じダイジェストと会話リンクが見えること, so that 一言だけでは見分けられない行を、attach せずに見比べられる。

## Implementation Decisions

観測できる振る舞いを書く。仕組み（技術と依存、機能ごとの入力の出どころ、フック・OTel・会話記録の受け方、確かめ方）は [DESIGN.md](DESIGN.md) にある。

### 全体

- 起動時のオプションは `--help` と、ダイジェストを切る `--no-digest`（「ダイジェスト」の節）だけである。オプトインの機能を有効にする手段も、既定で働く機能を切る手段も、起動時のオプションにし、環境変数にはしない（環境変数は意図しないところへ引き継がれ、`--help` で見つけられない。[ADR-0023](adr/0023-digests-on-by-default.md)）。`--no-digest` は単独で渡すときだけ受け付け、ほかの引数と組めない（`whatnext --no-digest workbench` などは知らないオプションとして扱う）。0.24 までの `--digest` は消し、知らないオプションとして扱う。
- サブコマンドは2つある。作業台の画面を開く `whatnext workbench`（「作業台」の節）と、一覧を開かずにセッションを起動する `whatnext new`（「一覧の外からの起動」の節）である。
- 知らないオプションを渡されたときは、`whatnext: unknown option <引数>` と使い方を標準エラーに出し、終了コード 2 で終わる。無視して起動すると、オプションを打ち間違えたときに、求めた設定にならないまま黙って起動し、利用者は効いたと思い込む（`--no-digest` を打ち間違えると、切ったつもりのセッションが Haiku を呼ぶ）。
- 利用者が明示したオプションが効かないときも、黙って起動しない。ダイジェストを有効にした一覧が動いているときの `whatnext --no-digest` は、その一覧につながずに断り、終了コード 1 で終わる（「ダイジェスト」の節）。理由は、知らないオプションを無視しないのと同じである。
- `--help` は先頭の引数にあるときだけヘルプを出す。`whatnext workbench --help` や `whatnext x --help` は、知らないオプションとして扱う（終了コード 2）。`whatnext new --help` と `whatnext new <ディレクトリ> --help` も同じで、`whatnext: unknown option --help` と使い方を標準エラーに出し、終了コード 2 で終わる。指示が `--help` のセッションは起動しない（使い方を見ようとして、セッションを1つ起動してしまうため）。
- whatnext の中のシェル（作業台）と、claude の Bash で `whatnext` または `whatnext workbench` を起動すると、`whatnext: this shell runs inside whatnext. Run "whatnext" in another split or window of your terminal.` と断り、終了コード 1 で終わる。作業台では、自分自身を入れ子に映すことになるためである。claude の Bash では、そのセッションが whatnext の中で動いているかに関係なく、いつも断る（Bash のシェルに付く `CLAUDECODE=1` で見分ける）。`--bg` のセッションの環境は Claude Code の常駐プロセスのもので、whatnext の中で動いているかを確実には見分けられず、Bash には端末がないので、断って失うものもほとんどない（2026-10-26、利用者の判断。#300）。`whatnext new` は画面を映さないので、作業台のシェルからは断らない。claude の Bash からは、別の文言で断る（「一覧の外からの起動」）。
- 何も書き込まず、永続状態を持たない（[ADR-0002](adr/0002-no-writes-no-persistent-state.md)）。例外は、メモと待ち先の関係を書く状態のファイルだけである（[ADR-0016](adr/0016-persist-holds-and-waits-in-a-state-file.md)）。
- 画面の文言とキーの説明は英語で書く。設計文書は日本語で書く。

### 終了と、端末のウィンドウを閉じたとき

仕組みと退けた案は [ADR-0012](adr/0012-list-runs-inside-the-dedicated-tmux-server.md) にある。

- **端末のウィンドウを閉じても、whatnext は終了しない。** 一覧、作業台（動いているものを含む）、メモ、待ち先の関係は残り、フックも受け続ける。うっかりウィンドウを閉じて段取りを失わないようにする。
- whatnext を起動したとき、終了していない whatnext があれば、新しく動かさずにその一覧に戻る。セッションの画面を見ていたときにウィンドウを閉じたなら、起動し直すと一覧から始まり、そのセッションから戻ったときと同じに扱う（区切りの先頭に上げ、カーソルをそこに置き、一覧を更新する）。起動すれば必ず一覧から始まるほうが、「まず何に手を付けるか」を見る順序に合う。同じ画面には `Enter` 1回で戻れる。
- 別の端末のウィンドウに whatnext が映っているときに起動すると、一覧は新しいウィンドウに移り、前のウィンドウはシェルに戻る。両方に映すと、tmux が小さいほうのウィンドウに大きさを揃えて大きいほうの表示が欠け、片方で attach するともう片方も同じ画面に切り替わる。
- 起動したとき、動いている whatnext の版が起動した版と違えば、動いている一覧につなぎ、一覧の下に `whatnext <動いている版> is still running. Quit it to start <起動した版>.` と示す。端末のウィンドウを閉じても whatnext は終了しないので、`npm i -g` などで更新してから起動しても、つながるのは更新前の版の一覧である。示さないと、利用者には更新が効いていないことが見えない。新しい版を動かすには、終了の操作で閉じてから起動する。

  ```
    SESSION        STATUS      WHERE          CTX      AGE
  > fix-login      Review      app            91k       5m
    ...
    whatnext 0.7.0 is still running. Quit it to start 0.8.0.
  ```

- **終了**は、終了のキーで行う。作業台で動いているものがあれば、終了する前に確認する（「作業台」の節）。終了すると、作業台と残した `claude attach` がすべて消える。メモと待ち先の関係は状態のファイルに残り、次に起動したときに引き継ぐ（「メモ」「依存（待ち先と起動された行）」の節、[ADR-0016](adr/0016-persist-holds-and-waits-in-a-state-file.md)）。Claude のセッション本体は動き続ける。

### 段

段は、セッションがどう止まっているか（または進んでいるか）の種類で、STATUS の列に出る。止まり方によって、セッションを進めるのに利用者がすること（解除コスト）が違うので、段を分ける。段は一覧の並びには使わない（「リポジトリの区切りと並び」）。

| 判定条件 | 段 | 解除コスト |
| --- | --- | --- |
| `waitingFor: "permission prompt"` | 権限待ち | 1キーで許可する |
| `waitingFor: "input needed"`、`state: "working"` かつ `status: "idle"`、およびどの規則にも当たらない行 | 質問待ち | 一文で答える |
| `waitingFor: "sandbox request"` | 許可待ち | 許可するかを選ぶ |
| `state: "failed"`、または `pid` のない `state: "blocked"` | 失敗 | 原因を調べる |
| `state: "done"` | レビュー待ち | 結果を読む |
| `status: "busy"`、または `status` が `idle` でない `state: "working"` | 稼働中 | なし（進んでいる） |
| 行そのものはレビュー待ちに当たり、待ち先のどれかがまだ終わっていない | 待ち | なし（待ち先が進めている） |
| `state: "stopped"` | 停止 | なし（利用者が止めた） |
| `interactive` の `idle` | 対象外 | – |

待ちの段だけは `--json` の行だけでは決まらず、利用者が結んだ待ち先の関係と、待ち先の今の段から導く（「依存（待ち先と起動された行）」）。起動された行は、起動元の段を変えない。

### `--json` の行から段を決める規則

`claude agents --json --all` の行は `kind` によってフィールドの持ち方が違う（Claude Code 2.1.280 での実測）。

| `kind` | `id` | `state` | `status` | `waitingFor` | `pid` |
| --- | --- | --- | --- | --- | --- |
| `background`（稼働中） | あり | あり | `busy` / `waiting` / `idle` | 待機時のみ | あり |
| `background`（プロセスなし） | あり | あり | null | null | null |
| `interactive` | なし | なし | `busy` / `waiting` / `idle` | 待機時のみ | あり |

- **判定は `waitingFor` を最優先にし、`state` は補助に使う。** 対話セッションは `state` を持たないので、`state` だけで判定すると対話セッションの権限待ちを見落とす。
- **重複は `sessionId` で除く。** 停止済みのセッションを別のプロセスが読み込むと、同じ `sessionId` が `background` と `interactive` の二行に出る。重複したときは、`pid` を持つ（プロセスが生きている）行を採る。止めた `background` のセッションを別の端末で開いているときは `interactive` の行が採られ、段はその端末の今の状態で決まり、`Enter` は attach せずに場所を示す。止めたときの古い `state` で段を決めると、別の端末で権限待ちになっているセッションがレビュー待ちに見える。どちらも `pid` を持たないときと、どちらも `pid` を持つときは、`background` の行を採る。`background` の行は attach でき、作業台も持てるので、`Enter` の意味が `--json` の行の順に左右されない。2行とも `pid` を持つ形は、実機では見ていない（止めていない `--bg` のセッションを、別の端末でも開いたときに起こりうる。#265）。
- **`pid` のない `blocked` は失敗の段に置く。** `claude stop` で止めたセッションは `stopped` になるので、`pid` のない `blocked` はプロセスが異常終了して状態だけ残ったものと推測できる。権限待ちの段に置くと、解除できない行が権限の確認を待っているように見える。
- **`state: "working"` かつ `status: "idle"` は質問待ちの段に置く。** 権限の確認で `No` を選ぶとターンが中断され（`Interrupted · What should Claude do instead?`）、この組み合わせのまま次の指示を待つ。`state` だけで稼働中の段に置くと、指示を待っているセッションが進んでいるように見える。
- **`stopped` は停止の段に置き、一覧から除かない。** 止めても `done` と `failed` はそのままの `state` で残るが、`blocked`（権限待ち、質問待ちなど）は `stopped` になる。除くと、止めた結果が行の種類で変わり（レビュー待ちは残り、質問待ちは消える）、`--json` の行がそのまま出るという見込みと食い違う。止めた行が消えてカーソルが別の行に移ると、遅れて押した `Ctrl+X` が別の行を止める。一覧から消したいときは、利用者が削除する。会話のないセッション（プロンプトなしで起動し、指示を送っていないもの）は、止めると `--json` から消えることがあり、消えれば一覧にも残らない（2.1.283 では、消えた観測と `stopped` で残った観測の両方がある。消える条件は未確定）。停止の段の行は、`Enter` で attach すると起き直る（2.1.283）。権限待ちのまま止めた行は、起き直ると権限の確認が消え、そのツールの呼び出しは中断として扱われて「代わりに何をするか」を待つ。そのため質問待ちの段に移り、`Declined:` は出ない。止める前の状態（権限待ち）には戻らない。
- **`interactive` の `idle` は対象外にする。** 対話セッションでは、ターンを終えて入力を待つ状態も、開いているだけの状態も同じ `idle` になる。レビュー待ちに載せると、開いているだけの端末が一覧を埋める。対話セッションは試行錯誤に使い、任せる作業は `claude --bg` で起動する想定なので、止まったときだけ出せば足りる。
- **どの規則にも当たらない行は質問待ちの段に置き、段の表記に生の値を添える。** 表にない `waitingFor`（`"worker request"`、`"dialog open"` を含む）、`pid` があるのに `waitingFor` がない `blocked`、`status: "waiting"` なのに `waitingFor` がない行、未知の `state` などが当たる。添える生の値は、規則に当たらなかった原因の値にする。表にない `waitingFor` ならその値、`pid` のある `blocked` なら `state` の値（`Question (blocked)`。`status` が `waiting` でも `idle` でも同じ）、未知の `state` ならその値である（#265）。止まっているかもしれない行を対象外にすると、不明を0とみなして見落とすのと同じ失敗になる。

`--json` の行の形が変わったときは、この表と規則を合わせて直す。

### 一覧の表示

- 列は SESSION / STATUS / WHERE / CTX / AGE の順に並べる。SESSION を左端に置くのは、待ち先の入れ子の線をその中に引くため。WHERE の幅は表示中の行の最長に合わせ（端末に収まらなければ切り詰める）、数字の列をその後ろにまとめる。AGE は右端に置く。
- **STATUS**：段の英語の表記（`Permission` / `Question` / `Sandbox` / `Failed` / `Review` / `Working` / `Waiting` / `Stopped`）。待機の理由は、段から分からないときだけ括弧で添える（例：`Failed (no process)`、`Question (dialog open)`）。理由のほとんどは段と一対一なので、独立した列にしない。一覧は段で並ばないので、「段」を名乗る見出しは実態と合わない。docs の用語は「段」のままにする（`--json` の `status` と紛れるので、docs で列を指すときは「STATUS の列」と書く）。
- **AGE**：セッションを作ってからの時間。どの作業の行かを思い出す手がかりにする（昨日始めたもの、さっき作ったもの）。会話記録の、時刻を持つ最初の行から数え、会話記録がなければ whatnext が初めて見た時刻から数える（両方あれば早いほう）。段が変わっても、attach しても数え直さない。`--json` の `startedAt` は、`claude -r` で再開すると変わるので使わない。数字を縦にそろえ、最小の単位は分とし、1分未満は `<1m`、以後は `m`、`h`、`d` で示す。日時（`10/25 08:12`）ではなく経った時間にするのは、ぱっと見て読みやすいため（利用者の判断）。
- **SESSION**：セッション名。`interactive` の行にだけ `(tty)` を添える。起動された行には、`(tty)` の代わりに `(sub)` を添える（「依存（待ち先と起動された行）」）。幅は表示中の行の最長に合わせ、48 文字を上限にして、超えた分は末尾を `…` で切る。上限は以前 32 文字だったが、知りたい情報が `…` の先に隠れていた（2026-10-16、利用者の判断）。折り返しはしない。折り返すと行の高さがばらつき、名前の続きと一言の行が見分けにくくなり、入れ子の線も続きの行まで引き延ばす必要がある。端末の幅が足りないときは WHERE を先に詰める。
- **CTX**：今のコンテキストの大きさ（token 数。`36k` のように示す）。本体のターンの最新の要求で送った token 数で、statusline のコンテキストの表示と一致する。サブエージェントや補助の要求は含めない。累計の token 数ではない。
- CTX の列は常に出す。
- CTX が分からないときは `-` と示す。`?` は対応が要る印象を与えるため。
- **WHERE**：場所の要約。リポジトリ名（worktree なら元のリポジトリ名、根より下なら `repo/sub`、git でない場所はパスの末尾）、既定でないブランチ名、worktree なら `(wt)`、PR があれば `#番号 (状態)`（状態は `open` / `draft` / `merged` / `closed` の文字で示し、同じ状態を色でも示す。色だけではどの色が何かをすぐに読めないため）。ブランチと worktree は `git` で取る。PR は `gh` があれば、そのブランチを head に持つ最新の PR を引く。`gh` がない、または認証していないときは PR を出さず、ほかの動作は変えない。一覧は PR を待たずに出し、分かったものから埋める。
- WHERE のブランチは、その `cwd` で今チェックアウトされているブランチであって、セッションが作業したブランチとは限らない。PR も同じ理由でずれうる。`--json` にはセッション固有のブランチを知る口がない。
- `interactive` の行の場所の提示（`Enter`）では、フルパスの `cwd` を出す。
- **各行の下に、そのセッションが今どうなっているかを示す一言を1行で出す。** 段だけでは各行が何をしていて何を求めているかが分からず、確かめるために attach する手間を減らす。段ごとに出すものは次のとおり。
  - 稼働中：今取り組んでいる指示の冒頭（`→ <指示>`）。スラッシュコマンド（スキルの呼び出し、`/review 12` など）で始めたターンは、`/名前 引数` を指示として出す。手元で完結してターンを始めないコマンド（`/model`、`/clear` など）は指示に数えない。数えないと、前の指示の一言が残る。
    - 複数行の貼り付けは、Claude Code がタグ（`<pasted_content id="…">`）で包む（[claude-code-behavior.md](claude-code-behavior.md)「会話記録」）。指示の冒頭は、タグの外に自分の文があればその空でない最初の行、なければ（貼り付けだけの指示）最初の貼り付けの中身の空でない最初の行とする。中身も空の行だけなら、一言は `→` だけになる（指示には数えるので、前の指示の一言は残らない）。タグの行をそのまま出すと、何の指示かが分からない。貼り付けたことを示す印は付けない。フックから取るときも会話記録から取るときも同じ規則にする（#291）。
    - バックグラウンドのタスク（`run_in_background` の Bash、バックグラウンドのサブエージェントなど）の通知で始まったターンは、通知を指示に数えず、一言は前の指示の `→ <前の指示>` のままにする。通知は利用者の指示ではなく、本文（`<task-notification>` で始まる）をそのまま出しても何も伝えない。`<system-reminder>` などのタグで書き始めた行も同じく指示に数えない。フックから取るときも会話記録から取るときも同じ規則にする。通知のターンであることを示す印は付けない（#361）。通知で始まったのも新しいターンなので、前のターンの `Declined:` と最後の応答は出さない。whatnext の外で起動したセッションでも同じ。通知のターンが本文の応答なしで終わったら、一言は何も出さない（#387）。
  - 権限待ち：許可を求めている道具と対象（`Bash: <コマンド>`、`Edit: <ファイル>` など）
  - 質問待ち：Claude が `AskUserQuestion` で出した質問。権限の確認で断って中断したターンでは、断った道具と対象（`Declined: Bash: <コマンド>`）。行が求めているのは「代わりに何をするか」の指示なので、何を断ったかが見えれば attach する前に返す内容を考えられる（そのターンには応答の本文がないことが多く、最後の応答の冒頭では何も出ない）。断ったあともターンが続いたとき（文を添えて断ったときなど）は、`Declined:` を出さない（#387）。どれでもなければ最後の応答の冒頭
  - 失敗：エラーの文言（`StopFailure` の `last_assistant_message`、または会話記録の `isApiErrorMessage` の行の本文）。`model_not_found` のような符号は、文言がないときだけ出す。どちらもなければ最後の応答の冒頭。フックの `error` は符号で、会話記録には人向けの文言しかないので、文言に揃えないと、whatnext が起動したかどうかで同じ失敗の一言が変わる
  - それ以外：最後の応答の冒頭
- 一言はフックから取り、フックで取れないときは会話記録から取る（[DESIGN.md](DESIGN.md)「機能ごとの入力の出どころ」）。どちらもなければ出さない。
- 最後の応答の冒頭は、空行、コードの囲み（囲みの中の行を含む）、表の行、区切り線（`---` `***` `___`）を飛ばした最初の行から、見出し・強調・箇条書き・番号・引用の記号と、インラインコードのバッククォートを除いたものである。記号は何の情報も持たず、`---` や `- ` だけの一言では、attach せずに何をしたかが分からない。応答がコードの囲みだけで、飛ばすと何も残らないときは、囲みの中の1行目を出す（レビュー待ちの行に何も出ないのを避ける）。囲みの中を先に出さないのは、中身がコードや出力で要約になっていることがまれなため。一言は要約しない。モデルで作るダイジェストは、一言の上に足す（「ダイジェスト」の節。`--no-digest` で切れる）。
- 前のターンの一言は出さない。指示を出してから次の応答が来るまでの行には、稼働中の一言（指示の冒頭）だけが出る。
- 一言は列に揃えず、行の下に字下げした1行で出し、端末の幅で切る。列にすると、狭い端末ではほとんど読めない。
- **作業台でシェル以外のものが動いていれば、一言の下に `⚙ <コマンド行>` を1行で出す。** 複数のペインで動いていれば ` · ` でつなぐ（例：`⚙ npm run e2e · terraform plan`）。コマンド名（`node`）だけでは何を流しているか分からないので、引数を含めたコマンド行を出す。パイプでつないだコマンドは ` | ` でつないで全体を出す（例：`⚙ npm run e2e | tee e2e.log`）。一覧の更新のときに tmux へ問い合わせ、更新の間は変えない。段にも並びにも影響しない。終わったコマンドは出さず、次の更新で行が消える。終了コードや終わった時刻を取るには、利用者のシェルに記録させる仕掛けが要るため。
- **一覧が端末の高さに収まらないときは、スクロールして選んだ行が見えるようにする。** 区切りの見出しは固定せず、行と一緒にスクロールする（区切りが多いと、固定した見出しで窓が埋まる）。選んだ行は窓の中央に置き、収まらないときだけ一覧の直後に `<選んだ行の通し番号>/<総数>` を出す。入力欄とメニュー、知らせ、最下部の欄（Usage、キーの説明。キーの説明は折り返した行数）の分は窓から差し引く。行の直下に出した入力欄（メモ）は、最後の行まで窓に入れる。窓は最小でも1行を残し、ヘッダを画面から押し出さない。1セッションあたりの行数は一言や入れ子の注記で増えるので、並行が 3〜8 個でも収まらないことがある。
- **入力欄とメニューは、一覧のすぐ下（1行空けて）に出す。メモの入力欄（`e`）だけは、その行と注記の直下に出す。** 知らせ（`Opened ...`、`refreshing...` など）は、その下にさらに1行空けて出す（入力欄がなければ一覧のすぐ下に1行空けて出す）。Usage とキーの説明は最下部に残す。以前は入力欄もキーの説明のすぐ上（画面の最下部）に出していたが、行が少ないと一覧から離れ、視線の移動が大きく、開いたことに気づかないことがあった（2026-10-16、利用者の判断）。メモはもともと行のすぐ下に出るので、入力欄をその位置に出すと、確定したあとの見え方のまま書ける。メモを直すときは、`↳ <メモ>` の行が入力欄に置き換わる。`n`、`f` などのメニューは長く、行の直下に差し込むと下の行が大きくずれるので、一覧のすぐ下に出す。

  ```
    SESSION                 STATUS   WHERE  CTX      AGE
    cloudflare deployment   Review   app      -      12m
  > fix-login               Review   app    91k       5m
      Note for fix-login: 素材待ち█
      Enter confirm · Esc cancel
    refactor the auth mi…   Working  infra  40k       2m
  ```

  ```
    SESSION                 STATUS   WHERE  CTX      AGE
  > refactor the auth mi…   Working  infra  40k       2m
    fix-login               Review   app    91k       5m

  refactor the auth middleware waits for:  █
  > New session
    fix-login  Review · app
  Type to filter · Enter select · Esc close
  ```

  こうはならない（入力欄を画面の最下部に寄せる。0.17.1 まで）：

  ```
    SESSION                 STATUS   WHERE  CTX      AGE
  > fix-login               Review   app    91k       5m
    refactor the auth mi…   Working  infra  40k       2m




  Note for fix-login: █
  Enter confirm · Esc cancel
  ```

- **キーの説明は、端末の幅に収まるときは1行で出し、収まらないときだけ折り返す。** 文言は削らない。折る位置は区切り（` · `）で、語の途中では折らず、行の末尾にも次の行の頭にも区切りの記号を置かない。幅によっては3行以上になる。1つの項目だけで幅を超える行は、その行を `…` で切る。ダイジェストが既定になって、既定のキーの説明は 130 桁になった。0.24 までは1行に切っていて、130 桁より狭い端末では `q quit` が見えなかった（`--no-digest` の説明は 120 桁で、120 桁より狭い端末では同じに切れていた）。文言を削らず、行を足すと決めた（2026-11-24、利用者の判断）。画面の例（画面の通しで取った画面の下の3行。幅100）：

  ```
  session 42% (resets 2:09pm) · week (all models) 25% (resets Sep 29 9:59am)
  ↑↓ select · Enter attach · n new · ^X stop/delete · e note · f wait for · w/t workbench · v VS Code
  o links · r refresh · q quit
  ```

  こうはならない（1行に切る。0.24 まで）：

  ```
  session 42% (resets 2:09pm) · week (all models) 25% (resets Sep 29 9:59am)
  ↑↓ select · Enter attach · n new · ^X stop/delete · e note · f wait for · w/t workbench · v VS Code…
  ```

  - 折り返した行数だけ、一覧の窓が減る。端末の高さが小さいときは、ヘッダと一覧の1行を残せる行数までにとどめ、残りは最後の行に続けて `…` で切る。
  - 知らせ（操作の結果やエラー）は、キーの説明より優先して見せる。折り返した行数では知らせが収まらない高さでは、キーの説明の行数を収まるところまで減らし（1行は残す）、残りは最後の行に続けて `…` で切る。収まる高さでは、折り返しの形を変えない。1行にしても収まらない高さでは、知らせを下から削る（折り返す前と同じ）。知らせは操作のたびに変わり、見逃すと取り戻せないが、キーの説明は変わらない。
  - メニューや入力欄を開いている間は、キーの説明を出さず、その行数だけ空ける（Usage の位置を変えないため。「Usage の表示」）。端末の高さが小さく、メニューや入力欄の中身（候補、件数、案内の行、確認の問い、メモの入力欄）が収まらないときだけ、空ける行を収まるところまで減らす。1行は残す（折り返す前の、キーの説明の行が空になる形）。このときは Usage が下に動く。中身が切れたまま空行が残るより、動くほうを採る。1行まで減らしても収まらない高さでは、下の欄を下から削る（折り返す前と同じ）。
  - 右の欄が出ているときも、キーの説明は端末の全幅で折り返す。
  - attach している間のキーの説明（claude の画面のステータス行）と、作業台の画面のステータス行は折り返さない（「作業台」の節。tmux のステータス行で、行を足すと claude の画面が狭くなる）。
- 色は常に出す。`NO_COLOR` も端末の種類も見ない。一覧が話す相手は常に専用の tmux（`tmux-256color`）で、状態は色だけでなく文字でも示すので、色が見えない画面でも情報は欠けない（#262）。
- 色の割り当て、数の表記（`1200k` か `1.2M` か）、パスの略し方（`~` や中央の省略）、`interactive` の行の場所の提示を一行で出すか専用の画面で出すか、といった表示の細部は、この節に書いたこと以外は実装に任せる。

### 更新

- 一覧は、最後の更新から60秒たったとき、更新キーを押したとき、attach から戻ったときに更新する。更新と更新の間は `--json` を読まず、一覧の並びも変えない。
- ヘッダには最後に更新してからの経過時間を出さない。一覧は60秒ごとに自動で更新され、attach している間は一覧が見えないので、経過時間はほぼ常に1分未満になり、得られる情報がなかった。
- `--json` を読んでいる間は、60秒ごとの自動の更新でも、一覧の下に `refreshing...` を出す。読み終わるまで段と一言は前の更新のままなので、読み込んでいる最中であることが分かるようにする。
- 更新キーを押したときは、同じ場所に、更新が終わったことを短く示す（`Refreshed.`、2秒で消える）。更新しても一覧の見た目が変わらないことが多く、押したことが伝わらないため。
- 更新と更新の間は、AGE の数字も最後の更新の時点の値で止め、次の更新まで変えない。更新の間は画面が変わらないほうが単純である（利用者の判断）。
- **attach から戻ったとき（新しく起動したセッションから戻ったときを含む）は、今離脱したセッションを区切りの先頭に上げ、カーソルを置く**（「リポジトリの区切りと並び」）。作業を終えて離脱した直後にそのセッションを削除したいことがあり、離脱したセッションを探し直す手間を省く。User Story 5 の動機は選んでいる最中の入れ替わりなので、attach から戻った瞬間とは衝突しない。
- カーソルは選んでいたセッションに付いていく。起動したときと、選んでいたセッションが一覧から消えたときに選ぶ行は、「リポジトリの区切りと並び」の「カーソル」にある。行が消えてカーソルが移った直後の `Ctrl+X` の守りは「操作」にある。
- 対象の行が1件もないときは、そのことをメッセージで示す。
- `--json` の取得に失敗したとき（`claude` が見つからない、出力を解析できないなど）は、エラーの内容を示し、古い一覧は出さない。次の更新で再び読む。

### メモ

- **利用者は、選んだ行に `e`（edit note）で1行のメモを付けられる。** メモは、その行のすぐ下に字下げした1行（`↳ <メモ>`）で出す。行の末尾に続けると、狭い端末や長い WHERE で切れて見えなくなる。段の判定も、区切りの中の位置も変えない。
- 書くのは、誰の返事を待っているか、優先度が低く余裕があるときだけ進める、次に何を確かめるか、といったことである。日をまたぐと、そのセッションをどう扱うつもりだったかを本人も忘れる。
- `e` を押すと、その行と注記の直下にメモの入力欄を出す（`Note for <セッション名>:`）。メモがあれば今のメモを入れて開く。`Enter` で確定し、`Esc` で何も変えずに閉じる。空のまま `Enter` を押すとメモを消す（`Backspace` で消して空にする。`Ctrl+U` で入力欄を空にする操作は、使われなかったのでなくした。2026-11-21、利用者の判断。#289）。付けた、直した、消したことは一覧の下に短く示す（文言は実装に任せる）。メモを直すときは、`↳ <メモ>` の行が入力欄に置き換わる。
- メモは任意で、付けるかは利用者だけが決める。whatnext は段や状態からメモを付けたり消したりしない。attach して作業しても消えない。
- メモを付けても行は動かないので、カーソルはその行に残る。
- **メモは、セッションが `--json` から消えるまで残る**（待ち先の関係と同じ）。対話セッションが `idle` で一覧から外れても、次に一覧に出たときにはメモが残っている。whatnext を終了しても消えず、次に起動したときに引き継ぐ（[ADR-0016](adr/0016-persist-holds-and-waits-in-a-state-file.md)）。
- メモを付けられるのは、人間が始めたセッションだけである。起動された行はカーソルで選べないので、メモを付ける経路がない（「依存（待ち先と起動された行）」）。
- メモはセッションに付いた1行で、セッションと一緒に消える。セッションから離れたメモ、複数行のメモは持たない（Out of Scope の「人間の手入力のメモ」）。
- 保留を書いた古い状態のファイルにある保留の理由は、メモとして読む。理由が空文字の保留（理由なしで保留にしたもの）は、メモなしとして読む。

### 依存（待ち先と起動された行）

一覧のセッションどうしの依存は2種類ある。利用者が結ぶ**待ち先**と、whatnext がプロセスの親子から導く**起動された行**である。どちらも入れ子の木で示すが、意味は混ざらない。待ちの段を決めるのは待ち先だけで、起動された行は見せるだけである。

| | 待ち先 | 起動された行 |
| --- | --- | --- |
| 誰が結ぶか | 利用者（`f`） | whatnext がプロセスの親子から導く |
| 結べる行 | 人間が始めたセッション。待ち元は `background` の行だけ。待ち先は `(tty)` の行でもよい | – |
| 段への影響 | 待ち元を待ちの段に入れる。待ち先がすべて終わると自分の段に戻る | なし。起動元の段を変えない |
| 名前の印 | なし | `(sub)` |
| 削除の巻き込み | 確認して巻き込む（消せない行は確認に並べない） | 巻き込まない |
| 引き継ぎ | 状態のファイルに書く | 書かない。毎回プロセスの親子から導く |

- 1つのセッションの親は1つだけである。待ち先は1つの待ち元にしか結べず、起動された行には待ち先も待ち元も結べない。そのため、2種類の関係を合わせても一覧は木になる。
- 木は根（待ち元、または起動元）のリポジトリの区切りに、組ごと出す（「リポジトリの区切りと並び」）。
- 人間が関係を調整するのは、人間が始めたセッションだけである。起動されたセッションの関係は調整しない。

**待ち先**

- **利用者は、選んだ行（待ち元）に、その行が終わりを待つセッション（待ち先）を結べる。** 使い方の例は、実装したセッションが、そのレビューをするセッションを待つ、大きなタスクを分けた親が子を待つ、あるリポジトリの修正が先に直すべき別リポジトリの修正を待つ、の3つである。リポジトリを跨いで結ぶことはふつうにある。1つの待ち元は複数の待ち先を持てる。1つのセッションを待てる待ち元は1つだけで、関係は必ず木になる。失うのは、2つの待ち元が同じ待ち先を待つ場面（例：2つのリポジトリの修正が、共通ライブラリの同じ修正を待つ）で、そのときは片方をメモで表す。
- **待ち元にできるのは `background` の行だけである。** 対話セッション（`(tty)` の行）は待ち先にはなれるが、待ち元にはなれない。対話セッションはターンを終えると `idle` で一覧から外れるので、待ちの段にならず、待ち元として働かない。結べると、利用者は結んだつもりなのに、待ち元は `Waiting` に出ない。`(tty)` の行で `f` を押すと、待ち先を結べないことを英語で示す。こうすると、待ち元が一覧から外れている状態が起きない。
- 待ち先の関係は、結んでから、待ち元か待ち先が削除されるまで（`--json` から行が消えるまで）続く。停止して対象外になっただけでは切れない（削除のときに巻き込めるようにする）。レビューの往復のように手番が入れ替わっても、関係の向きは付け替えない。最初に結んだ関係を保つほうが、組を読み違えない。
- **待ちは状態として持たず、毎回導く。** 待ち元の行がレビュー待ちの段に当たり、待ち先のどれかがまだ終わっていないとき、待ち元を待ちの段（`Waiting`）にする。待ち先が「終わった」とは、レビュー待ちか停止の段に入ったこと、または一覧に出なくなったこと（対話セッションの終了などで対象外になったか、行が消えた）をいう。待ち先が再び稼働すれば、待ち元は再び待ちの段に入る。往復のたびに利用者が結び直す必要はない。
- 待ち元が自分でも権限待ち、質問待ち、許可待ち、失敗、稼働中のどれかに当たるときは、待ち先を待っていても自分の段に出す。人間の手が要る行を `Waiting` と示すと、待っていればよい行に見える。
- **待ち先は、待ち元の下に入れ子で並べる。** 線（`├ ` `│ ` `└ `）は SESSION の列の中に引き、注記の行にも縦線を引き継ぐ。注記の行では、グレーにするのは注記の文字だけで、縦線は行の線と同じ色のまま出す。縦線までグレーにすると、注記の行で線が途切れて見え、木が読み取りにくくなる。兄弟どうしの並びと、組（待ち元を根とする木）の位置は「リポジトリの区切りと並び」にある。
- 待ち先の名前を待ち元の行に注記（`↳ for`）することはしない。入れ子で関係が見える。
- **待ち先がすべて終わると、待ち元は自分の段（ふつうはレビュー待ち）に戻る。終わったことを知らせる注記は出さない。** 待ちが明けたことは、待ち元の STATUS が `Waiting` から変わることで分かり、どの待ち先が終わったかは入れ子の待ち先の STATUS で分かる。区切りの中の並びは段で変わらないので、待ち元を一覧の中から探し直す必要もない。待ち先を外して待ちが解けたときも、待ち先が削除されて関係が切れたときも同じである。
- 新しく結んだ待ち先がすでに終わっていれば（レビュー待ちや停止の段の行を結んだ）、待ち元は待ちの段に入らない。稼働中の行を結べば入る。
- メモを付けた行は、根でも途中の行でも組に残り、`↳ <メモ>` の行を出す。
- **待ち先の関係は、whatnext を終了しても消えず、次に起動したときに引き継ぐ**（[ADR-0016](adr/0016-persist-holds-and-waits-in-a-state-file.md)）。
- 関係が一周する（A が B を待ち、B が A を待つ）と、どちらも待ちの段から出られなくなるので、一周する待ち先は結べない。
- **状態のファイルから読んだ関係が木にならないとき**（1つの待ち先を2つの待ち元が待つ、一周する、`(tty)` の行が待ち元になっている）は、その関係を結ばれていないものとして読み飛ばす。どれを残すかの規則は、利用者から見て恣意的になる。結ばれていた行が起動された行と分かったときも、その関係を外す。
- 待ち先の関係を PR から自動で推定する（同じ PR を WHERE に持つ行を組にする）案は採らなかった。レビューするセッションが PR のブランチをチェックアウトするかは Claude に任されていて、当たるかどうかが偶然で決まる。
- 待ち先の出力（レビューの指摘など）を待ち元に渡すことは whatnext ではしない（[ADR-0003](adr/0003-no-input-injection-or-proxy-response.md)）。レビューするセッションに指摘を PR のコメントとして書かせ、待ち元にそれを読ませるなど、受け渡しは whatnext の外で行う。

**起動された行**

- **一覧のほかの行が起動した `claude` の行（起動された行）は、起動元の行の下に入れ子で並べる。**
  ほとんどは、スキルやスクリプトが Bash から起動した `claude -p` と、stdio の MCP サーバが起動した `claude -p` である。行の Bash から対話の `claude` を起動したときも同じに扱う。
  これらは `--json` に `interactive` の行として出るが、どの行が起動したかは `--json` にない。
  利用者は MCP やスキルでオーケストレーションをよく行う。起動されたセッションがトップレベルに出ると、起動元から離れて探せなくなる。
- 起動元は、行の `pid` の祖先をたどって最初に当たった、`--json` の別の行である。
  起動された行がさらに起動した行は、もう一段深く並ぶ。
  最初に当たった行が一覧に出ていないとき（開いているだけの対話セッションなど、対象外の行）は、トップレベルに `(sub)` を添えて並ぶ。その先の祖先はたどらない。
  祖先に `--json` の行がないとき（手元のシェルから起動したとき）は、起動された行ではなく、トップレベルに `(tty)` を添えて並ぶ。
  `--bg` で起動したセッションの祖先は Claude Code の常駐プロセスなので、起動された行にならない。セッションの中から `claude --bg` で起動したセッションも、起動元の下に入れ子にしない。非同期で起動して完了を待たないものは、依存ではないと考える（2026-10-26、利用者の判断。#299）。
  祖先から起動元が分からない `interactive` の行は、そのプロセスの環境変数 `MCP_CALLER_PID` も見る。値が `--json` の別の行の `pid` と一致すれば、その行を起動元とする（次の「会話の外で動く MCP サーバ」の項目）。祖先から分かるときは、祖先を優先する。
- 名前には `(tty)` の代わりに `(sub)` を添える。
  線は待ち先と同じものを引くので、利用者が結んだ関係ではないことを示す印が要る。
  起動された行も対話セッション（`interactive`）の行なので、`(tty)` の行と同じく attach も作業台もない。印は1つにしたほうが読みやすいので、`(sub)` が `(tty)` に代わる。

  ```
    SESSION                       STATUS   WHERE        CTX      AGE
  > review-loop-hybrid-skill      Working  skills (wt)  88k       3m
    │ → /review-loop iterate
    └ review-loop-skill-07 (sub)  Working  skills (wt)    -      <1m
  ```

  こうはならない（印を `(tty)` のまま残す）：

  ```
    SESSION                       STATUS   WHERE        CTX      AGE
  > review-loop-hybrid-skill      Working  skills (wt)  88k       3m
    │ → /review-loop iterate
    └ review-loop-skill-07 (tty)  Working  skills (wt)    -      <1m
  ```

- 起動元が一覧に出ていない間のトップレベルの `(sub)` の行は、ふつうのトップレベルの行に `(sub)` を添えるだけにする（2026-10-26、利用者の判断。#280）。開いているだけの対話セッションが起動した `review-loop-07` は、次のように出る（描画の関数で描いた画面）。

  ```
    SESSION               STATUS   WHERE  CTX      AGE
  ── app ─────────────────────────────────────────────────────────
  > add metrics           Review            -       5m
    review-loop-07 (sub)  Working           -      <1m
  ```

  起動元の名前を注記に出す案は採らなかった。こうはならない（上の画面を書き換えたもの）。注記の行が1つ増え、`↳` がメモと紛れる。

  ```
    SESSION               STATUS   WHERE  CTX      AGE
  ── app ─────────────────────────────────────────────────────────
  > add metrics           Review            -       5m
    review-loop-07 (sub)  Working           -      <1m
      ↳ started by scratch (not in the list)
  ```

- **起動された行は見せるだけで、起動元の段を変えない。** 起動された行が動いていても、起動元は待ちの段に入らない。
- **起動された行かどうかは、プロセスの親子だけで決まる。** メモや待ち先には左右されない。起動された行はカーソルで選べないので、`f` でも `e` でも注釈を付けられない。ほかの行の `f` のメニューにも並ばない。
  起動元が一覧に出ていない間も起動された行として扱うので、注釈を付けたあとで `(sub)` に変わる経路はない。
- **起動された行はカーソルで選べない。** `↑` `↓` は区切りの見出しと同じく起動された行を飛ばし、カーソルが自動で移るときも選ばない。起動された行は attach できず、`f` も `e` も `Ctrl+X` も受け付けない行なので、選べても役に立つのは `cwd` と `pid` を示す `Enter` と `v` だけだった。場所は WHERE の列と起動元の行で分かるので、選べなくしても失うものは小さい。選べると、`↓` で降りるたびに手を付けられない行で止まる（2026-10-26、利用者の判断）。
  `<通し番号>/<総数>` にも起動された行は数えない。一覧が端末の高さに収まらないときは、同じ区切りで選んだ行のすぐ下に続く起動された行も、選んだ行と一緒に見えるようにスクロールする。区切りの最初の選べる行を選んでいるときは、その上の見出しと起動された行も見せる。起動された行だけの区切りは、直前の区切りの最後の選べる行（なければ次の区切りの最初の選べる行）を選んでいるときに一緒に見せる。選べない行が画面の外に残って見られなくなるのを防ぐ。全部は窓に収まらないときは、選んだ行（注記とメモの入力欄を含む）を必ず見せ、すぐ下に続く起動された行を収まるだけ見せる。窓の高さを超える数の起動された行が続くときは、見えない分が残る（まれな場面なので、スクロールの手段は設けない）。
  行が更新で起動された行に変わる場面は実機で見ていないが、起こりうるものとして守る。メモの入力中に、その行が起動された行と分かったときは、入力を閉じる（この挙動は利用者の確認待ち。#305）。起動された行にはメモも待ち先も結ばない。一覧から外れただけ（対話セッションが `idle` になった）のときは、入力を開いたまま残す。選んでいた行が起動された行と分かったときは、行が消えたときと同じく隣の行に移る（起動元に移すかは利用者の確認待ち。#305）。
  選べる行がなく、起動された行だけが並ぶとき（起動元が一覧に出ていないトップレベルの `(sub)` の行だけのとき）は、カーソルはどの行にもなく、`<通し番号>/<総数>` も出さない。端末の高さに収まらない分は見られない（まれな場面なので、スクロールの手段は設けない）。
- 起動元を削除するときも、起動された行は巻き込む対象に数えない（`id` がなく、`claude stop` も `claude rm` も受け付けない。対話セッションの待ち先と同じ。「操作」の「待ち先の巻き込み」）。
  whatnext は起動された行のプロセスを止めない。起動元を消したあとも起動された行が動いていれば、祖先に一覧の行がなくなるので、トップレベルに `(tty)` を添えて並び、終われば消える。Claude Code が起動元を止めたときに起動された行も止まるかは、確かめていない。

  ```
    SESSION               STATUS   WHERE    CTX      AGE
  > infra                 Review   repo       -      <1m
    review-loop-07 (tty)  Working  repo       -      <1m
  ```

  こうはならない（起動元がないのに入れ子の線と `(sub)` が残る）：

  ```
    SESSION                 STATUS   WHERE    CTX      AGE
  > infra                   Review   repo       -      <1m
    └ review-loop-07 (sub)  Working  repo       -      <1m
  ```

- 起動された行は起動元の組の中に並ぶ（待ち先と同じく、起動元のリポジトリの区切りに出る）。起動された行には attach できないので、組の位置を動かさない。
- whatnext を終了して起動し直したときは、起動元の関係を引き継がず、プロセスの親子から導き直す。
  起動された行は終わるとプロセスごと消え、`--json` からも消えるので、引き継ぐ必要がない。
- Claude Code の Agent ツールで起動するサブエージェントは、起動元と同じプロセスの中で動くので、`--json` に行として出ない。一覧にも出ない。
- **会話の外で動く MCP サーバ（HTTP、常駐のサーバ）が起動した `claude -p` は、MCP サーバが環境変数 `MCP_CALLER_PID` を渡したときだけ、起動元の下に入れ子で並ぶ。**
  このような行は、祖先に起動元のセッションが出ず、`--json` にも親を示す値がない。利用者はこの形でオーケストレーションを日常的に行っていて、トップレベルに出ると起動元から離れて探せない。
  そこで、ツールを呼んだ MCP クライアントの pid を、MCP サーバに起動する子の環境変数 `MCP_CALLER_PID` で渡してもらう。利用者の側の改修は2つある（設定の例は README に載せる）。
  - MCP の設定に `headersHelper` を足し、ヘッダ `X-MCP-Caller-Pid` に `$PPID` を入れて返す。`headersHelper` は Claude Code が接続のたびに実行するコマンドで（公式の仕組み）、その `$PPID` は呼んだセッションの `claude` の pid になる。
  - MCP サーバで、`claude -p` を起動するときに、その要求のヘッダ `X-MCP-Caller-Pid` の値を、子の環境変数 `MCP_CALLER_PID` に入れる。
  名前は whatnext 専用にせず、「ツールを呼んだ MCP クライアントの pid」という中身を表す汎用の名前にした（2026-10-26、利用者の判断）。whatnext はこの値を「一覧の行の `pid` と一致すれば、その行が起動元」とだけ解釈する。
  渡されないとき、値が一覧のどの行の `pid` とも一致しないときは、今までどおりトップレベルに普通の行（`(tty)`）として出る。MCP サーバ、セッション、whatnext が同じマシンにあることが前提である（pid はマシンの中でしか意味を持たない）。
  推定（ツールを呼んだ時刻と行が現れた時刻の突き合わせ）で関係を決めることはしない。外れうる入れ子は、利用者が信用できなくなる。

### リポジトリの区切りと並び

- **一覧は、セッションをリポジトリごとの区切りにまとめ、区切りの中を最後に attach した順に並べる。** 次に何をするかは利用者が自分で選ぶ。リポジトリでまとめると探しやすくなるかは、まだ使って確かめていない。

**区切りの単位と並び**

- 区切りの単位は、`cwd` が属する git のリポジトリの根である。根より下で動くセッション（monorepo の下位のディレクトリなど）も同じ区切りに入る。worktree で動くセッションは、元のリポジトリの区切りに入る。git でない場所は、パスごとに区切る。末尾の名前が同じでも、場所が違えば別の区切りにする。場所が違えば作業も違うことが多い（2026-10-25、利用者の判断）。
- worktree を裸のリポジトリの横に並べる構成（`foo/.bare` に本体を置き、`foo/main` や `foo/feature` に worktree を置く）では、根を裸のリポジトリの親のディレクトリ（`foo`）とし、見出しもその名前にする。
- submodule の中で動くセッションは、親のリポジトリの区切りに入り、WHERE に submodule のパスを残す（根より下で動くセッションと同じ扱い）。submodule で作業するのは、たいてい親の作業の一部で、別の区切りにすると同じ作業が2つの区切りに割れる（2026-10-26、利用者の判断）。WHERE には submodule のパスとブランチを出し、submodule であることを示す印は付けない（2026-10-26、利用者の判断。#281）。`app` の `vendor/lib` が submodule で、その中のブランチが `bump-deps` のとき、次のように出る（描画の関数で描いた画面）。

  ```
    SESSION        STATUS   WHERE                 CTX      AGE
  ── app ─────────────────────────────────────────────────────────
  > bump lib deps  Working  vendor/lib bump-deps    -       1m
    fix-login      Review                           -       5m

  ── lib ─────────────────────────────────────────────────────────
    lib itself     Review                           -       1h
  ```

  submodule であることを `(sm)` で示す案は採らなかった。こうはならない（上の画面を書き換えたもの）。

  ```
    SESSION        STATUS   WHERE                      CTX      AGE
  ── app ─────────────────────────────────────────────────────────
  > bump lib deps  Working  vendor/lib (sm) bump-deps    -       1m
    fix-login      Review                                -       5m
  ```

- 区切りの見出しは、リポジトリのディレクトリ名（git でない場所はパスの末尾）である。同じ名前の区切りが2つ以上あるとき（ghq の `github.com/a/foo` と `github.com/b/foo` など）だけ、区別できるところまで親のディレクトリ名を足して `a/foo` と `b/foo` にする（`n` の作業ディレクトリの候補と同じ）。
- 区切りは、見出しの、人の読み方の順（大文字と小文字を区別せず、日本語も読みに近い順。`localeCompare`）に並べる。文字の符号の順では `Zeta` が `alpha` より前に来る（2026-10-26、利用者の判断）。区切りの位置は、セッションの状態で動かない。
- **区切りの中は、whatnext から最後に attach した時刻の新しい順に並べる。** よく触るセッションが上に来る。`n` や `f` の `New session` で起動して、そのまま attach したときも数える。whatnext の外で `claude attach` したときは、whatnext からは見えないので数えない。メモを直す、待ち先を結ぶ、作業台を作るといった操作は数えない。数えると、メモを直しただけで行が上がり、利用者を驚かせる。
- 一度も attach していないセッションは、そのセッションが一覧に初めて出た時刻（初めて見た時刻）を、attach した時刻の代わりに使う。`--json` には出ていても対象外だった対話セッションが、権限待ちなどで後から一覧に出たときも、そのときに区切りの先頭に出る（2026-10-25、利用者の判断）。外で起動したセッションや、外部 watcher が起こしたセッションは、見えたときに区切りの先頭に出る。時刻が同じ行（初めて起動したときは、全部の行の初めて見た時刻が同じになる）は、名前の、見出しと同じ人の読み方の順に並べる。
- 並べ直すのは、attach から戻った直後である。行が動くのは、利用者が attach したセッションと、新しく見えたセッションだけになる。段が変わっても、並びは変わらない。
- attach した時刻と初めて見た時刻は状態のファイルに書き、whatnext を終了しても引き継ぐ。引き継がないと、起動し直すたびに並びが変わる。セッションが `--json` から消えたら、どちらの時刻も消す（待ち先の関係とメモと同じ。一覧から外れただけでは消さない）。
- 待ち先の組（待ち元を根とする木）は崩さず、根のリポジトリの区切りに組ごと出す。待ち先が別のリポジトリで動いていても、その区切りには出さない（同じ行を二度出さない）。組の位置は、根の時刻（attach した時刻、なければ初めて見た時刻）と、組の中の行に attach した時刻のうち、最も新しいもので決める。待ち先の初めて見た時刻は数えない。こうすると、`e` でメモを付けても、一度も attach していない待ち先を `f` で結んでも、組は動かない（2026-10-25、利用者の判断）。根より後に attach したことのある待ち先を結んだときは、その時刻まで組が上がる。兄弟は、attach した時刻（なければ初めて見た時刻）の新しい順に並べる。

**見た目**

- 区切りの見出しを1行で出し、その下に行を並べる。区切りと区切りの間は1行あける。見出しの行はカーソルで選べず、`↑` と `↓` は見出しを飛ばす（起動された行も飛ばす。「依存（待ち先と起動された行）」）。
- 見出しは左端から `── <名前> ───…` と出し、罫線を端末の幅いっぱいまで伸ばす。名前は太字、罫線はグレーにする。セッションの行と同じ字下げで太字にするだけでは、見出しがセッション名と見分けにくかった（2026-10-25、利用者の判断）。罫線なら、色が見えない画面（端末の設定で色を描かないとき、`capture-pane` で文字だけを取ったとき）でも形で見分けられる。
- WHERE からは、区切りと同じリポジトリ名を除き、ブランチ、`(wt)`、PR だけを出す（根より下で動くセッションは `sub` を残す。monorepo のどこで動いているかが分からなくなるため。2026-10-25、利用者の判断）。待ち先が別のリポジトリで動いているときは、その行の WHERE にリポジトリ名を出す。見出しと同じ名前を行ごとに繰り返すと、WHERE の幅を取るだけで情報がない。
- 今離脱したセッションの組を、一覧の先頭に別の組（`Last attached`）として出すことはしない。今離脱したセッションは自分の区切りの先頭に上がり、カーソルもそこに付く。先頭の組を別に出すと、同じセッションが先頭の組と区切りのどちらにいるかが毎回変わる。
- メモを付けた行も、自分の区切りの中で同じ規則で並べる。`↳ <メモ>` の行を出す（「メモ」）。
- 一覧が端末の高さに収まらないときのスクロールは、「一覧の表示」の規則による。区切りの見出しは固定せず、行と一緒にスクロールする。区切りが多いと、固定した見出しで窓が埋まる。`<通し番号>/<総数>` には見出しの行を数えない。
- STATUS、CTX、AGE の列、一言、`⚙` は、「一覧の表示」「依存（待ち先と起動された行）」のとおりに出す。

  ```
    SESSION                   STATUS     WHERE                 CTX      AGE
  ── app ──────────────────────────────────────────────────────────────────
  > fix-login                 Review     fix-login #12 (open)  91k       5m
    ├ review fix-login        Working    fix-login (wt)        40k       2m
    └ bump shared lib         Stopped    lib                     -       1h
    add metrics               Working                          12k      <1m
    alpha                     Review                            8k       3h
      ↳ waiting for Bob's API change

  ── infra ────────────────────────────────────────────────────────────────
    refactor the auth mi…     Permission auth-mw               22k       9m

  Usage 5h 42% · 7d 18%
  ↑↓ select · Enter attach · e note · f wait for · ...
  ```

  こうはならない（見出しを付けず、リポジトリ名の順に並べるだけ。区切りが見えない）：

  ```
    SESSION                   STATUS     WHERE                     CTX      AGE
  > fix-login                 Review     app fix-login #12 (open)  91k       5m
    add metrics               Working    app                       12k      <1m
    refactor the auth mi…     Permission infra auth-mw             22k       9m
  ```

  こうはならない（見出しをセッションの行と同じ字下げで太字にするだけ。色が見えないと、見出しとセッション名の区別が付かない）：

  ```
    SESSION                   STATUS     WHERE                 CTX      AGE
    app
  > fix-login                 Review     fix-login #12 (open)  91k       5m
    add metrics               Working                          12k      <1m
  ```

  こうはならない（見出しに件数と段の内訳を出す。権限待ちを目立たせるのは、区切りの中を状態で並べないこととかみ合わない）：

  ```
    app  3 · 1 Permission
  ```

**カーソル**

- 起動したときは、最も新しく attach したセッションを選ぶ。先頭の区切りの先頭の行は、リポジトリ名の順で決まるだけで、意味がない。
- attach から戻ったときは、今離脱したセッションを選ぶ（「更新」）。
- `e` でメモを付けても、行は動かないので、カーソルはその行に残る。
- 選んでいたセッションが一覧から消えたときは、同じ区切りの次の行を選ぶ。なければ前の行を選び、区切りが空になったら隣の区切りの行を選ぶ。起動された行は選ばない（「依存（待ち先と起動された行）」）。

### ダイジェスト

仕組みは [DESIGN.md](DESIGN.md)「ダイジェストの mod」「ダイジェストの受信」、判断は [ADR-0022](adr/0022-ship-a-digest-mod-for-launched-sessions.md)（mod を配ること。#325）と [ADR-0023](adr/0023-digests-on-by-default.md)（既定で有効にすること。#381）にある。

- **既定で働き、`whatnext --no-digest` で起動すると切れる。** 引数なしの `whatnext` で起動すると、`n` で起動したセッションは、ターンの終わりごとに Haiku を1回呼んで利用枠を使う。切る手段を残すのは、利用枠を断れるようにするためと、mod の API（Claude Code の早期公開版）が変わって mod が壊れたときの逃げ道にするためである。既定で有効にするのは、オプトインでは `--digest` を付け忘れて開いた一覧から起動したセッションに、あとからダイジェストを付けられないためである（2026-11-23、利用者の判断。#381）。
- Haiku を呼ぶのは、ダイジェストを有効にして起動した whatnext がダイジェストを受けているときだけである。whatnext を終了したとき、`--no-digest` で起動し直したとき、受け口のポートを別のもの（ほかのプログラムや、別のポートで動く whatnext）が使っているときは、mod を付けたセッションもターンの終わりに Haiku を呼ばず、何も送らない（会話リンクは今までどおり拾い、セッションの中のペインに出す）。引数なしで起動し直せば、次のターンの終わりからまた呼んで送る（2026-11-21、利用者の判断。#325）。受け手がいても利用者が見る機会がないとき（別のセッションに attach しているときなど）は、呼ぶ（そこまで判定するかと、人が attach して見ているときは受け手がいなくても呼んでペインを生かすかは、#328 で決める）。`--no-digest` で起動した whatnext は、この節のどれも行わない（`n` で起動するセッションに mod を付けず、Goal の行も右の欄も出さず、`o` も効かない。ダイジェストが届いても捨てる）。例外は `whatnext new` で、`--no-digest` の一覧が動いていても、起動するセッションに mod を付ける。その mod も、`--no-digest` の一覧が動いている間は Haiku を呼ばない（「一覧の外からの起動」）。
- ダイジェストを有効にして起動した whatnext は、`n` で起動するセッションに、whatnext が配るダイジェストの mod を付ける。受け口を開けていないとき（シナリオ 41）は付けない（フックと同じ）。`whatnext new` で起動するセッションには、一覧が動いているか、ダイジェストが有効かに関係なく付ける（受け口のポートをほかのプログラムが使っているときを除く。「一覧の外からの起動」）。mod は、ターンの終わりにダイジェスト（Goal・Progress・Next）を作り、会話リンク（会話に出た issue、PR、コミット、URL など）を拾い、セッションの中のペインに出し、whatnext に送る。
- 動いている一覧のダイジェストの有無は、つなぐときの引数で変わらない。変えるには、一覧を終了して開き直す。
  - **ダイジェストを有効にして動いている一覧があるときに `whatnext --no-digest` を実行すると、その一覧につながずに、標準エラーに `whatnext: a whatnext with digests is already running. Quit it first (run whatnext without --no-digest, then press q), then run whatnext --no-digest.` と出して、終了コード 1 で終わる。** 動いている一覧と、それを映している画面には何も起きない。黙ってつなぐと、利用者は切ったつもりのまま `n` でセッションを起動し、そのセッションには mod が付いて、ターンごとに Haiku を呼ぶ（「全体」の、知らないオプションを無視しない理由と同じ）。文言は、別の whatnext が受け口を使っているときの `… Quit it first, then run whatnext again.` に揃えた。つないで一覧の下に知らせる形にしないのは、`--no-digest` を求めた人の前にダイジェストが有効な一覧を開くと、知らせを読む前に `n` を押せるためである（2026-11-24、利用者の判断。#381）。
  - `--no-digest` で動いている一覧に `whatnext` でつなぐと、一覧は今のまま動き、違いを示さない。ダイジェストが切れている一覧は `--no-digest` を自分で付けて開いたもので、付け忘れを知らせる相手がほぼいないためである（2026-11-24、利用者の判断。#381）。`--no-digest` で動いている一覧に `whatnext --no-digest` でつなぐときも、今までどおりつながる。
  - 0.24 の一覧が動いているときも同じに扱う。`--digest` で起動した 0.24 の一覧には `whatnext --no-digest` でつながず、`--digest` なしの 0.24 の一覧（ダイジェストを出さない）にはつながる。
- **各行の一言の上に、ダイジェストの Goal を1行で出す（`◎ <Goal>`）。** 注記の並びは、Goal → 一言 → `⚙` → `↳ メモ` である。記号で始めるのは、`→` `⚙` `↳` と揃え、画面の文言を英語に保つため（`Goal` という言葉のラベルは付けない）。一言は、どの段でも今のまま残す。
- **端末の幅が 120 桁以上なら、一覧の右に欄（46 桁）を出し、カーソルの行のダイジェスト（Goal・Progress・Next）と会話リンクを出す。** 見出しは `Goal` `Progress` `Next` `Links` で（`Status` は STATUS の列と紛れるので `Progress`）、値は利用者の指示の言語（日本語か英語）で出す。値は欄の幅で折り返し、会話リンクは新しいものから5件まで出して、残りは `+<件数> more` と数だけ出す。欄の高さに収まらない分は切り、最後の行を `…` にする。120 桁より狭いときは右の欄を出さず、Goal の行だけを出す。最下部の欄（Usage、キーの説明）は全幅のまま出す。一覧の下の入力欄・メニュー・知らせと、メモの入力欄は、左の幅に収まらなければ全幅で出し、右の欄はその上で止める（確認の問いの `[y/N]` のような末尾を切らないため）。幅の境目（120 桁）と体裁（値の折り返し、会話リンクは5件と `+<件数> more`、収まらなければ `…`）は、2026-11-21 に利用者が決めた（#325）。
- ダイジェストのない行（外で起動したセッション、`(tty)` の行、起動された行、最初のターンが終わる前の行）にカーソルがあるときも、右の欄は出したままにし、`No digest yet. Digests come from sessions started with n, when a turn ends.` を出す。会話リンクだけが届いている行では、その下に `Links` も出す（2026-11-21、利用者の判断。#325）。
- **ダイジェストが有効なのに受け口を開けなかったとき（シナリオ 41）は、右の欄の `No digest yet. …` の代わりに、ダイジェストが届かない理由を出す。** 例：`Digests are off: port 14318 is used by another program.`（ポートは実際の値。別の whatnext が使っていれば `… is used by another whatnext.`、開けなかっただけなら `Digests are off: could not open port <ポート>.`）。`◎` の行と右の欄、`o` はそのまま出す。シナリオ 41 の「エラーを示さない」の例外である。右の欄はダイジェストを出すための欄で、黙って出さないと、ダイジェストが届かない理由が分からない（2026-11-21、利用者の判断。#325。既定で有効にしても変えない。2026-11-24、#381）。`--no-digest` のときは右の欄がなく、理由も出さない。
- **稼働中の行は、次のダイジェストが届くまで、前に届いたダイジェストを出したままにする。** 「前のターンの一言は出さない」の対象にしない。今の指示は `→ <指示>` の一言が示す。
- ダイジェストは一覧の更新のとき（「更新」の節）に新しくなり、更新と更新の間は変えない。段にも並びにも使わない。
- **右の欄の `Links` の各行は、埋め込みのリンク（OSC 8）で描き、クリックで開ける**（Ghostty では cmd+クリック）。リンクを端末に送る条件は、attach した claude の画面と同じである（「attach」の節の、埋め込みのリンクの項）。開く先は、whatnext が受けたときに検査した `http://` か `https://` の URL だけである（2026-11-21、利用者の判断。#325）。
- **`o` で、カーソルの行の会話リンクを選んで開く**（`open` で既定のブラウザに渡す）。会話リンクのない行では `No links for <名前>.` を示す。ダイジェストが有効なときだけ効き、キーの説明にも `o links` を足す。会話リンクは、右の欄のクリック（OSC 8）と `o` のメニューの両方で開ける（2026-11-21、利用者の判断。#325）。
- セッションの中では、mod のペイン（題は `Digest`）に同じ見出しで同じダイジェストと会話リンクを出す。ペインはセッションが始まると開く。Claude Code は、頼まれずに開いたペインを端末が 144 桁以上（一度手で開けば 110 桁以上）のときだけ出す。`/wn-digest` で開ける（自動で開くことは、2026-11-21 に利用者が決めた。#325）。ペインは会話リンクを新しいものから8件まで出し、残りは `+<件数> more` と数だけ出す。右の欄の5件より多いのは、ペインが縦に長い dock で、会話リンクに使える高さがあるからである。右の欄は一覧と同じ高さを Goal・Progress・Next と分け合うので、5件にとどめる。
- ダイジェストは、前のダイジェスト、利用者の指示（最新の10件）、最後の応答から作る。ターンの途中の応答は入れない（2026-11-21、利用者の判断。#325）。
- whatnext を終了して起動し直すと、次のダイジェストが届くまで出ない（ダイジェストと会話リンクはメモリにだけ持つ）。セッションが `--json` から消えたら、そのダイジェストと会話リンクは捨てる。受け口にはローカルのどのプロセスからも送れるので、表示の前に制御文字を落とす。
- ダイジェストが届くのは、whatnext が起動したセッション（一覧の `n`、`whatnext new`）だけである。1回で終わる `claude -p` には出ない（ダイジェストを作る前にプロセスが終わる）。
- 一言とダイジェストの Next のどちらを出すか（#329）と、whatnext が受けていなくても、attach して見ているセッションではダイジェストを作るか（#328）は、別の issue で決める。

### Usage の表示

- キーの説明のすぐ上の行に、アカウントの Usage を出す。`/usage` が示す枠ごとに、使用率とリセットする時刻を並べる（例：`session 42% (resets 2:09pm) · week (all models) 25% (resets Sep 29 9:59am)`）。リセットが今日なら日付を省く。使用率が50%以上なら黄、80%以上なら赤で示す。
- 0.18.0 の前は一覧のヘッダ（列の見出しの上）に出していた。一覧を見るときに最初に目に入る位置を、毎回は要らない Usage が取っていたので、下に移した（2026-10-16、利用者の判断）。知らせ（`Deleted ...` など）は一覧の近くに出す（「一覧の表示」の入力欄の項目）。メニューを開いている間はキーの説明の行が空になるが、Usage の位置は変えない（キーの説明が折り返して複数行のときは、その行数だけ空ける。端末の高さが小さく、メニューや入力欄の中身が収まらないときだけ、空ける行を1行まで減らし、Usage はその分だけ下に動く。「一覧の表示」のキーの説明の項目）。

  ```
    SESSION                 STATUS   WHERE  CTX      AGE
  > fix-login               Review   app    91k       5m
    refactor the auth mi…   Working  infra  40k       2m


  Deleted old-session.


  session 42% (resets 2:09pm) · week (all models) 25% (resets Sep 29 9:59am)
  ↑↓ select · Enter attach · n new · ^X stop/delete · e note · f wait for · …
  ```
- 目的は、rate limit にいつ当たりそうかを見ること。
- 取得するのは、whatnext の起動時、attach から戻ったとき（新しく起動したセッションから戻ったときを含む）、更新キーを押したときに限る。60秒ごとの更新では取らない。Usage は数分で大きく動くものではなく、一覧に戻る時点の値があれば判断に足りる。
- attach から戻ったときと更新キーでは、前回の取得を始めてから60秒たっていなければ取り直さない。取得している最中も取り直さない。起動時は必ず取る。attach から短く戻る操作が続いたときに `claude -p` を立ち上げ続けないためである。起点を「成功した時刻」にしないのは、失敗が続いたときに毎回取り直すことになるため。
- 取得は一覧の更新を待たせず、非同期に行う。取得中は前の値を出したままにする。
- 出る値はアカウント全体のもので、他の端末や claude.ai での利用も含む。セッションごとの内訳は出さない。

### 作業台

仕組みと退けた案は [ADR-0014](adr/0014-workbench-shows-in-a-screen-the-user-opens.md) と [ADR-0010](adr/0010-workbench-lives-inside-whatnext.md) にある。

**作業台は、利用者が端末の別の分割で開く作業台の画面に映す。** 端末を分割し（左右でも上下でもよい。別のタブ、別のウィンドウ、別の端末のアプリでもよい）、そこで `whatnext workbench` を実行すると、その画面が作業台の画面になる。whatnext は端末を操作しない。分割を作る、フォーカスを移す、幅を変える、閉じる、はどれも端末の操作で行う。

```
┌ whatnext の画面 ─────────────────────┬ 作業台の画面 ────────────────────┐
│   変更点は3つです。                   │ $ docker compose up              │
│ ❯                                    │ web-1 | listening on :3000       │
│                                      ├──────────────────────────────────┤
│                                      │ $ pnpm test:e2e                  │
│                                      │ ✓ 42 passed                      │
│ fix-login · ログインの不具合を直して   │                                  │
│ ⚙ docker compose up · pnpm… ^Q^L back│ workbench: fix-login  0:zsh*  · ^│
└──────────────────────────────────────┴──────────────────────────────────┘
```

popup をやめたのは、作業台を開いたまま claude の画面にも入力したいこと、並べて見比べるときに claude の画面の高さを減らしたくないこと、の2つのためである（利用者の判断）。端末の別々の分割に映すので、次の3つが端末の機能のままで成り立つ。

- 作業台を開いたまま、claude の画面にも作業台にも入力できる。入力は、端末のフォーカスがあるほうに入る。
- 作業台か claude の画面の複数行を端末で選んでコピーしても、もう一方の文字が混ざらない。端末の選択は、端末の分割の中に閉じるためである。tmux の中で左右のペインに分けると、端末の選択が左右をまたぐ。
- **作業台の画面では、ホイールで作業台の出力をさかのぼれる。** テストやサーバの出力を流す場所なので、流れた出力を読み返せないと使えない。さかのぼれるのは tmux の履歴（2万行）で、端末のスクロールバックではない。いちばん下まで戻すと、ふだんの入力に戻る。
  - 作業台の画面でドラッグすると、tmux の選択になり、離したときにコピーされる。選択は作業台のペインの中に閉じるので、claude の画面の文字は混ざらない。端末の選択にしたいときは、Ghostty なら `shift` を押しながらドラッグする。
  - claude の画面と一覧のマウスの扱いは変えない。
- 作業台の画面の中でも、`ctrl+q ctrl+l` などの whatnext のキーが効く。作業台の画面も専用の tmux のクライアントなので。

claude の画面の幅は、分割の比率の分だけ減る。一時的に片側を広げたいときは、端末の機能（Ghostty なら分割の拡大 `cmd+shift+enter`）を使う。

- **作業台の画面は任意である。** 開かなくても whatnext はふだんどおり使える。作業台が要るときに開き、要らなくなれば端末の操作で閉じる（Ghostty なら `cmd+d` で分割して開き、`cmd+w` で閉じる）。Ghostty では `ctrl+q ctrl+w` と一覧の `w` で分割に、`ctrl+q ctrl+t` と一覧の `t` でタブに開くこともできる（下の「作業台を作る時機」の項）。閉じても、作業台と、その中で動いているものは残り、`⚙` で見える。次に開くと、元の配置のまま映る。
- **作業台の画面は、whatnext の画面（一覧とセッションの画面を映す端末）が attach しているセッションの作業台を映す。** whatnext の画面でセッションを移ると（`Enter`、`ctrl+q ctrl+l`）、作業台の画面も移った先の作業台に切り替わる。
- **whatnext の画面が一覧を映している間は、作業台の画面はカーソルの行のセッションの作業台を映し、カーソルを動かすと切り替わる。** 一覧で行を選ぶと、そのセッションの作業台で何が動いているかが横に見え、次に何に手を付けるかの材料になる。カーソルを動かしただけでは、作業台を作らない。
- **作業台を作る時機は、利用者が決める。** 作業台の作業ディレクトリは、作った時点のセッションの場所になる。worktree に入る前に作るか後に作るかで場所が変わるので、whatnext は勝手に作らない。作るのは次の3つの操作である。
  - claude の画面か作業台の画面で `ctrl+q ctrl+w` か `ctrl+q ctrl+t`
  - 一覧で `w` か `t`（カーソルの行の作業台）
  - 作業台の画面の案内で `Enter`

  作る直前に `--json` を読み直し、その時点のセッションの `cwd` で開く（`ctrl+q ctrl+v` と同じ読み直し方）。止めたセッションでは、`--json` の `cwd` がリポジトリの根に戻っているので、根で開く。すでに作業台があれば作らず、`Workbench already exists for <名前>.` と短く示す。作業台の画面を開いていないときも作り、`Workbench created. Run "whatnext workbench" in a split to see it.` と示す。worktree に入った直後に場所を確定させておき、作業台の画面はあとで開く、という順番も成り立つようにする。

  Ghostty で `ctrl+q ctrl+w` か一覧の `w` を押したときは、作業台の画面まで開いた状態にする。何度押しても同じ形になる（[ADR-0015](adr/0015-ghostty-split-for-workbench-on-ctrl-q-ctrl-w.md)）。
  - 作業台の画面が開いていれば、その分割へフォーカスを移す。分割は増やさない。上の2つの知らせは出さない。
  - 開いていなければ、押した分割を右に分割し、そこで作業台の画面を開いてフォーカスを移す。押したタブにほかの分割（ふだんのシェルなど）があっても、それには触れずに新しく分割する。

  ```
  押す前                       押したあと
  ┌────────────┬───────────┐   ┌────────┬────────┬────────┐
  │ whatnext   │ ~/app $   │   │whatnext│~/app $ │workbnch│ ← フォーカス
  └────────────┴───────────┘   └────────┴────────┴────────┘
  ```

  Ghostty で `ctrl+q ctrl+t` か一覧の `t` を押したときは、分割の代わりに、押したウィンドウに新しいタブを開いて作業台の画面を映す（分割すると claude の画面が半分の幅になるので、claude の画面を広く保ちたいときに使う。2026-11-17）。
  - 作業台の画面が開いていれば、`w` と同じく、それを映している分割かタブへフォーカスを移す。タブは増やさない。分割で開いた作業台の画面をタブに移すことはしない（移したいときは、作業台の画面を閉じてから押す）。
  - 開いていなければ、新しいタブで作業台の画面を開いてフォーカスを移す。押したタブは分割せず、そこにあるほかの分割にも触れない。claude の画面と作業台の画面は、どちらもウィンドウの幅をそのまま使う。

  ```
  押す前                         押したあと
  ┌──────────────────────────┐   ┌────────────┬─────────────┐
  │ [whatnext]               │   │  whatnext  │ [workbench] │ ← タブ
  ├──────────────────────────┤   ├────────────┴─────────────┤
  │ claude の画面            │   │ 作業台の画面             │ ← フォーカス
  └──────────────────────────┘   └──────────────────────────┘
  ```

  claude の画面へは、端末のタブの操作で戻る（Ghostty なら `cmd+shift+[`）。Ghostty でないときの `t` と `ctrl+q ctrl+t` は、`w` と `ctrl+q ctrl+w` と同じに働く（作業台を作り、知らせを出す）。

  whatnext が作った分割とタブは、作業台の画面が終わると閉じる。Ghostty でないとき、Ghostty が前面にないとき、Ghostty の操作が許可されていないときは、上の知らせを出すだけにする。初めて押したときに、macOS が Ghostty の操作の許可を求めることがある。
- 作業台の画面が映すセッションに作業台がまだないときは、作業台がないことと、作ったときに開く場所を示す。場所を出すのは、worktree に入ったかどうかを作る前に確かめられるようにするためである。

  ```
  No workbench for fix-login yet.
  Enter: open a shell in ~/ghq/github.com/me/app/.claude/worktrees/fix-login
  ```

- 作業台の最後のシェルを `exit` で抜けると、作業台は消え、作業台の画面には `Workbench closed.` と上の案内が出る。すぐに新しいシェルは作らない。`exit` で作業台を片付けたつもりなのに、新しいシェルが出直して閉じられなくなるのを避ける。作業台の画面ごと閉じたいときは、端末の操作で閉じる。
- **作業台の画面は同時に1つだけ映す。** 2つ目の作業台の画面を開くと（別のウィンドウで打った、うっかり2回打ったなど）、新しいほうが映し、古いほうは作業台から離れてシェルに戻る。tmux は、1つの作業台を大きさの違う2つの画面で映すと、小さいほうに大きさを揃えるため（一覧を1つの端末に限ったのと同じ理由）。
- **1つの作業台の中は、作業台の画面の中で tmux の既定のキーで分割し、ウィンドウを増やす**（`ctrl+q %`、`ctrl+q "`、`ctrl+q c` など）。分割とウィンドウの配置は作業台ごとに持つので、セッション A の作業台は分割なし、セッション B の作業台は `docker compose up` と `pnpm test:e2e` の2つに分割、のように分けて使える。作業台の画面がセッションを移ると、それぞれの配置のまま映る。
- whatnext の画面だけを閉じたときは、作業台の画面はそのまま、最後に映していた作業台を映し続ける。`whatnext` で whatnext の画面を開き直すと、また追従する。作業台だけを使い続けたい場面もあり、残しても害がない。
- whatnext が動いていないときに `whatnext workbench` を実行すると、`whatnext is not running. Start whatnext first.` と示して終了する（終了コード 1）。
- whatnext は動いているのに作業台の画面につなげなかったときは、`whatnext: could not open the workbench screen (tmux session "wbguide").` と示して終了する（終了コード 1）。tmux のエラー（`can't find session` など）も消さずに残す。案内を作れなかったときは `whatnext: could not create the workbench guide (tmux session "wbguide").` と示して終了する（終了コード 1）。
- whatnext が Ghostty に作った分割とタブでは、`whatnext workbench` が上のどれかで失敗したら（whatnext が動いていないときも）、`Press any key to close.` と示してキーを待ってから閉じる。待たないと分割やタブごと閉じて、エラーが読めない。
- 作業台の画面の案内は、何かの理由で落ちても、whatnext を起動し直さずに出直す。案内が出ないせいで作業台の画面が開かない、ということはない。ただし、起動してすぐ落ちることが続くとき（出直してから1分以内にまた落ちることが、5回続いたとき）は出直すのをやめ、作業台の画面には案内の代わりに落ちたときの出力が残る。whatnext を起動し直すと、また出直す。
- 端末は問わない。whatnext は端末の機能に頼らず、専用の tmux のクライアントを1つ増やすだけなので。例外は、Ghostty で押した `ctrl+q ctrl+w` と一覧の `w` が分割を、`ctrl+q ctrl+t` と一覧の `t` がタブを作ることだけである。確かめるのは Ghostty で行う。
- **キーの起点は `ctrl+q` の1つだけにする。** attach している間は、claude の画面でも作業台の画面でも次のキーが効く。

  ```
  ctrl+q ctrl+l   一覧に戻る
  ctrl+q ctrl+w   そのセッションの作業台を作る(一覧の `w`)。Ghostty では作業台の画面の分割へ移る
  ctrl+q ctrl+t   そのセッションの作業台を作る(一覧の `t`)。Ghostty では作業台の画面のタブへ移る
  ctrl+q ctrl+v   一覧に戻らずに、そのセッションの場所を VS Code で開く(一覧の `v`)
  ctrl+q ctrl+e   一覧に戻り、その行のメモの入力欄を開く(一覧の `e`)
  ctrl+q ctrl+x   一覧に戻り、その行を止める(一覧の `Ctrl+X`)。続けてもう一度押すと削除する
  ctrl+q ctrl+n   一覧に戻り、新しいセッションを起動する(一覧の `n`)。いたセッションのリポジトリを候補の先頭に置く
  ctrl+q ctrl+f   一覧に戻り、その行の待ち先のメニューを出す(一覧の `f`)
  ```

  作業台の画面で押したキーは、作業台の画面が映している作業台のセッションを対象にする（`ctrl+q ctrl+l` なら whatnext の画面が一覧に戻り、`ctrl+q ctrl+v` ならそのセッションの場所を VS Code で開く）。

  Ghostty で、作業台の画面で一覧に戻るキー（`ctrl+q ctrl+l`・`ctrl+e`・`ctrl+x`・`ctrl+n`・`ctrl+f`）を押すと、フォーカスを whatnext の画面へ移す。whatnext の画面が隣の分割にあっても、別のタブや別のウィンドウにあっても移す。メモの入力欄や削除の確認を開いたまま、続けて打った文字が作業台のシェルに入るのを避けるためである（2026-11-17）。Ghostty でない端末では、フォーカスは動かない。

  whatnext の画面を閉じているときに、作業台の画面で一覧に戻るキー（`ctrl+q ctrl+l`・`ctrl+e`・`ctrl+x`・`ctrl+n`・`ctrl+f`）を押すと、何もせず、作業台の画面の最下行に `The list is not open. Run "whatnext" to open it.` を3秒示す。一覧を開くのは利用者である。

  対話セッション（`(tty)` の行）は `id` を持たないので、作業台を持たない。一覧のカーソルがその行にあるとき、作業台の画面には `<名前> is an interactive session. It has no workbench.` を示し（`Enter` は効かない）、一覧の `w` と `t` は同じ文言を一覧の下に示して何もしない。
  `ctrl+q ctrl+q` には何も割り当てない。作業台の画面の開閉は端末の操作で行う。
  一覧と attach している間で、同じ操作を同じ文字で使えるようにする（一覧の `v`・`e`・`Ctrl+X`・`n`・`f`・`w`・`t` と、`ctrl+q` のあとに ctrl を押したままの同じ文字）。作業台（**w**orkbench）は `w`、待ち先（wait **f**or）は `f` である。`ctrl+q ctrl+e`・`ctrl+q ctrl+x`・`ctrl+q ctrl+n`・`ctrl+q ctrl+f` は一覧に戻ってから一覧と同じ処理をするので、確認（push していないコミット、作業台で動いているもの、待ち先の巻き込み）も一覧と同じに出る。止めると `claude attach` も終わるので、止めたあとに attach したまま残る形はない。メモの入力欄を `Esc` で閉じると、メモを変えずに一覧に残り、`Enter` ですぐ元の画面に戻れる。メモのある行で `ctrl+q ctrl+e` を押すと、一覧の `e` と同じく今のメモの入った入力欄が開く。`ctrl+q ctrl+n` は、一覧の `n` と同じく候補の先頭をいたセッションのリポジトリにする。`--json` を読めずにエラーを出している間も同じにする（一覧の `n` と違い、利用者は直前までそのセッションにいたので、どのセッションかを知っている）。
  一覧では `ctrl+q` を無視する。attach している間の癖で押しても何も起きず、`Ctrl+X` の削除の待ち受けも取り消さない。そのため `ctrl+q ctrl+x` を2回続けて押すと、止めてから削除できる。

  作業台の画面では、`ctrl+q` は tmux の prefix として働き、tmux の既定のキー（`c` でウィンドウ、`%` と `"` で分割など）が使える。claude の画面では、ほかの `ctrl+q` の組み合わせは何もしない。`ctrl+q` は、Claude Code、tmux の既定、Ghostty のどれも使っていないキーである。**whatnext の操作は、`ctrl+q` のあとも ctrl を押したままの形にそろえ、キーの説明もこの形で出す（[ADR-0013](adr/0013-whatnext-keys-hold-ctrl-after-ctrl-q.md)）。** 文字だけの形（`ctrl+q x` など）は、作業台の画面では tmux の既定のキーに使う。こうすると「一覧の文字を、ctrl を押したまま `ctrl+q` のあとに押す」の1つの規則で説明でき、tmux とぶつからない。
  - 文字だけの形は、tmux の既定とぶつかり、空きも少ない。tmux 3.7c で prefix の既定の割り当てがない小文字は `a b e g h j k u v y` だけで、`l`（直前のウィンドウ）・`x`（ペインを閉じる）・`n`（次のウィンドウ）・`w`（ウィンドウの選択）・`f`（ウィンドウの検索）はふさがっている。ctrl を押したままの形は、tmux の prefix の既定の割り当てがほとんどない（`C-o`・`C-z` などだけ）。
  - よく使う `ctrl+q ctrl+l` などは ctrl を押したままのほうが押しやすい（文字だけの形だったときは、`^Q^L` と押して戻らずに混乱した）。
  - 説明の長さは変わらない（`^Q l` も `^Q^L` も4文字）。
  - `ctrl+q l`（文字だけ）は whatnext では扱わない。作業台の画面では tmux の既定（直前のウィンドウ）に返し、claude の画面では何もしない。`ctrl+q ctrl+v`・`ctrl+q ctrl+e` は tmux の既定の割り当てがないので、文字だけでも同じ動作にする（説明には載せない）。
  - 割り当てのない組み合わせは tmux が黙って捨てるので、押し間違えても何も起きない。`ctrl+l` などは `ctrl+q` の直後にしか効かないので、claude とシェルでの本来の意味は変わらない。
- **attach した claude の画面の下に、tmux のステータス行を1行出す。** 左に作業台の状態を、右にキーの説明を出す。キーの説明は、作業台の有無にかかわらず常に出す。作業台の欄は数秒ごとに描き直す。画面の例（画面の通しで、作業台がないときに取った画面。幅120）：

  ```
  fake claude attached to a0000000
  ❯
                                           ^Q^L back · ^Q^W workbench · ^Q^T tab · ^Q^V VS Code · ^Q^E note · ^Q^X stop ·…
  ```

  - 名前と最初の依頼は出さない。0.21.0 までは、キーの説明の上にもう1行（概要の行）を足し、`名前 · 最初の依頼` を出していた。何のセッションかは、利用者が Claude Code の statusline（ccstatusline）で出すことにして、whatnext は出さない（2026-11-16、利用者の判断）。消したぶん、claude の画面が1行広くなる。
  - リポジトリ、worktree、最新の依頼、STATUS も出さない。リポジトリと worktree は statusline で、最新の依頼は画面の上の実物と recap で、STATUS は claude の画面そのもので分かる。
  - 採らなかった形：画面の上端（pane の枠線の行）に出す案は、目がたいてい下の入力欄にあるので見落としやすい。attach した直後だけ数秒出す案は、長く離れて戻ったときに効かない。

    ```
    こうはならない(概要の行を足して2行にする。0.21.0 まで)
    alpha · ログインの不具合を直して
                                             ^Q^L back · ^Q^W workbench · ^Q^T tab · ^Q^V VS Code · ^Q^E note · ^Q^X stop ·…
    ```

  左側(作業台の状態):

  ```
  作業台でシェル以外が動いているとき(複数あれば ` · ` でつなぐ)
  │ ⚙ npm run e2e          ^Q^L back · ^Q^W workbench · ^Q^T tab · ^Q… │
  作業台はあるが、シェルが待っているだけのとき
  │ ⌂ workbench (shell)    ^Q^L back · ^Q^W workbench · ^Q^T tab · ^Q… │
  作業台がないとき
  │                        ^Q^L back · ^Q^W workbench · ^Q^T tab · ^Q… │
  ```

  - 作業台の欄には、動いているコマンドだけを出す。出力の最後の行は出さない。静かで、秘密が出る心配がない。
  - 作業台の画面を開いているかどうかにかかわらず出す。作業台の画面を閉じていても、動いているものが見えるようにする。
  - 一覧には出さない。一覧の下のキーの説明には一覧のキーだけを載せ、attach している間のキーは載せない（attach している間は、claude の画面のステータス行に常に出ている）。
  - 左の幅は作業台の画面の分だけ狭くなるので、キーの説明は右端が切れうる。よく使うキーを先に並べ、切れても `^Q^L back · ^Q^W workbench` が残るようにする。
  - claude の画面は常に1行減る。1行減る費用より、キーを思い出せない（`^Q^L` と押して戻らずに混乱した）・作業台で何が動いているか見えない費用のほうが大きいと利用者が判断した。
  - 退けた形：作業台の出力を複数行の tail で出す（claude の画面が4〜5行減り、一覧の常時表示を退けた理由と同じく気が散る）。出力の最後の1行を出す（書き換わり続けて気が散り、秘密が出うる）。attach した直後の3秒だけキーを出す（作業台の状態が見えない）。
- **作業台の画面の最下行に、作業台のステータス行を1行出す。** 映している作業台のセッション名と、作業台のウィンドウの一覧と、分割とウィンドウのキーを出す（`workbench: fix-login  0:zsh* 1:zsh  · ^Q% split │ · ^Q" split ─ · ^Qc window`）。作業台がないとき（案内を出しているとき）は、セッション名だけを出す。
  - キーは、tmux の既定のキーのうち、左右の分割（`^Q%`、境目が `│`）、上下の分割（`^Q"`、境目が `─`）、新しいウィンドウ（`^Qc`）の3つだけを出す。whatnext の画面には whatnext のキーしか出ていないので、1つのシェルで足りなくなったときに、作業台の中を分けられることが分からなかった（2026-10-28、利用者の判断）。
  - キーはウィンドウの一覧のあとに続け、右寄せにしない。作業台の画面は狭いことが多く、右寄せにすると左から欠けて、いちばん使う `^Q%` が先に消える。続けると右から欠けるので、`^Q%` が最後まで残る。ウィンドウを増やすほどキーは右へ押し出される。
  - こうはならない（キーを右寄せにする。幅60の作業台の画面で取った画面）：

    ```
    workbench: fix-login  0:zsh* 1:zsh  ^Q" split ─ · ^Qc window
    ```
  - 狭いときも文言を短い形に切り替えず、欠けるのに任せる（2026-10-28、利用者の判断）。名前が `fix-login` でウィンドウが1つなら、幅がおよそ41を下回ると `^Q% split` が欠け、幅34では `^Q` しか残らない。短い形にしても幅34では同じで、書式が複雑になるわりに得るものが少ない。名前が長いときやウィンドウが多いときは、もっと広い幅から欠ける。
  - こうはならない（狭いときは短い形に切り替える。名前が `fix-login`、ウィンドウが1つ、幅60の作業台の画面で取った画面）：

    ```
    workbench: fix-login  0:zsh*  · ^Q% │ ^Q" ─ ^Qc
    ```
- **一覧に戻る経路は2つある。** `ctrl+q ctrl+l` では `claude attach` を残したまま戻り、次の `Enter` では attach し直さずに、すぐ元の画面に戻る。空のプロンプトの ← では Agent View に入ったことを検知して `claude attach` を畳んで戻り、次の `Enter` で attach し直す（少し時間がかかる）。← で戻るので、Agent View から別のセッションに入る操作は使えない。
- `claude attach` がほかの理由で終わったとき（Ctrl+Z、`/exit`、attach の失敗）も一覧に戻り、次の `Enter` で attach し直す。Ctrl+Z は `claude attach` に組み込まれた離脱で、whatnext は挙動を変えないが、一覧に戻る経路としては案内しない（キーの説明にも挙げない）。`ctrl+q ctrl+l` で attach を残したまま戻れれば足りる。claude の画面で Ctrl+Z を握りつぶして何も起きないようにする案は採らなかった。一覧に戻すのは、そのセッションを映している画面だけにする。`ctrl+q ctrl+l` で残した `claude attach` が、止めたり消したりしたことで裏で終わっても、別のセッションに入っている画面は動かさない（#374）。
- 作業台は、セッションごとの tmux のセッション（`sh-<id>`）である。1つのセッションに作業台のウィンドウを複数持てる。
- 作業台で copy mode で遡れる行数は、tmux の既定（2000行）より長くする（20000行）。長いコマンドの出力を遡れるようにする。
- 作業台の中のシェルでは、Ctrl+Z はふだんどおりジョブ停止として効く。
- **attach した claude の画面と作業台の画面で、埋め込みのリンク（OSC 8）をクリックして開ける。** Claude Code や `ls --hyperlink`、`gh` などが出すリンクを、tmux を通さない端末と同じように扱う。リンクを端末に送るのは、xterm 系と Ghostty の端末で動かしているときに限る。OSC 8 を知らない端末では、制御文字が画面に出て崩れうるためである。Claude Code は tmux 3.4 以上の中ではリンクを出す（2.1.284 で確かめた）。
- 作業台と、その中で動いているものは、作業台の画面を閉じても、一覧に戻っても、別のセッションに移っても残る。作業台の画面で映し直すと、元の配置のまま見える。
- **作業台は、whatnext を終了すると閉じる。** 作業台のどこかでシェル以外のものが動いていれば、終了する前に、セッション名とコマンドを並べて英語で確認する（例：`Quit and stop 2 running commands? fix-login: npm run e2e, infra: terraform plan [y/N]`）。`y` なら、作業台と残した `claude attach` をすべて閉じて終了し、`N`（既定）なら閉じない。何も動いていなければ、確認せずに閉じる。空のシェルを閉じて失うのはシェルの履歴と画面の出力だけで、いつも確認を出すと、確認を読まずに `y` を押すようになる。作業台の画面は作業台から離れて、シェルに戻る。Claude のセッション本体は、終了したあとも動き続ける。
- 端末のウィンドウを閉じたときは、whatnext は終了しないので、作業台も動いているものもそのまま残る（「終了と、端末のウィンドウを閉じたとき」の節）。
- **whatnext のプロセスが確認を出せずに終わったとき**（`kill` した、想定外の例外で終わった、異常終了した）は、動いているものを止めない。終わる処理を走らせられれば（シグナルで終わるときも、想定外の例外で終わるときも）、残した `claude attach` と何も動いていない作業台を畳み、動いているものがある作業台だけを残す。次に whatnext を開いたとき、前の tmux サーバが残っていれば、動いているものを並べて引き継ぐかを英語で聞く（例：`2 commands are still running from a previous whatnext: fix-login: npm run e2e, infra: terraform apply. Keep them? [Y/n]`）。`Y`（既定）なら引き継ぎ、作業台の画面のステータス行などは今の版の形に入れ直す（前の版で作った作業台にも、分割とウィンドウのキーが出る。2026-10-28、利用者の判断）。`n` なら止めて捨てる。何も動いていない作業台と、残っていた `claude attach` は、聞かずに捨てる。確認の既定は、終了するときも起動し直したときも「何も止めない」側にする。止めることは取り消せない。
- セッションを削除すると、作業台と残した `claude attach` もまとめて閉じる。作業台でシェル以外のものが動いていれば、そのコマンドを示して英語で確認を求め、`N` なら削除しない（セッションは1回目の `Ctrl+X` で止まったまま残る）。作業台だけを残すと、行が消えるので入る手段がなくなる。削除したセッションの作業台を作業台の画面が映していれば、次に映すもの（一覧のカーソルの行の作業台か、その案内）に切り替わる。
- 勧められた `!` のコマンドを作業台に貼る操作は「`!` のコマンドのコピー」にある。
- tmux がなければ、そのことを英語で示して終了する（[ADR-0008](adr/0008-dependencies-and-contact-points-with-tmux.md)）。
- tmux が 3.5 より古ければ、`whatnext: tmux 3.4 is too old. whatnext needs tmux 3.5 or newer. Update tmux and try again.`（`tmux 3.4` は `tmux -V` の出力）と示し、終了コード 1 で終わる。古い tmux では、起動はできても、attach から一覧に戻るキーや作業台が黙って効かない（tmux 3.4 で確かめた。[DESIGN.md](DESIGN.md)「一覧と作業台の仕組み」）。3.5 は、動くことを確かめた最も古い版（3.5a）に合わせた（3.5a と 3.6a では 3.4 で壊れる2点が起きず、画面の通しも通った。2026-11-22、#337）。Ubuntu 22.04/24.04 と Debian 12 の tmux（3.2a〜3.4）は断られる。版を読み取れない表記（`tmux master` など）は断らない（2026-11-21、利用者の判断）。

### 操作

- **`Enter`（`background` の行）**：一覧を映している端末を、そのセッションの画面に切り替える。画面の中では、専用の tmux サーバの中で `claude attach <id>` が動く（「作業台」の節）。一覧に戻る操作は、`ctrl+q ctrl+l` と空のプロンプトの ← である（「作業台」の節）。`/exit`（入力欄に `exit` とだけ打った場合も）でも一覧に戻り、セッション本体は動き続ける。離脱して一覧に戻ったとき、端末に子の設定（代替画面、マウスの追跡など）が残ってはならず、子が異常終了した場合も同じである。attach している間、キー入力が whatnext と子の両方に届いてはならない。`claude attach` が 0 以外の終了コードで終わったときは、子の出したメッセージを画面に残したまま、キーが押されるのを待ってから一覧に戻る。すぐに描き直すと、attach できなかった理由と対処（`claude respawn` など）が読めない。正常に離脱したときは待たずに戻る。画面の解析や入力の注入はしない（[ADR-0003](adr/0003-no-input-injection-or-proxy-response.md)）。
- **`Enter`（`interactive` の行）**：`id` がなく attach できないので、`cwd` と `pid` を示す。
- **`n`**：作業ディレクトリを指定し、プロンプトなしで `claude --bg` で起動する。モデルは選ばせず、`--model` を付けずに `claude` の既定で起動する。最初の指示は attach した先の Claude Code の入力欄で書く。whatnext はプロンプトを受け取らない（入力欄を作ると Claude Code の入力欄の劣化コピーになり、複数行や貼り付けの扱いを抱え込む）。
  - 作業ディレクトリは候補から選ぶか、`Other...` で自由に入力する。候補は、カーソルのあるセッションのリポジトリ（git でない場所ならその場所）、whatnext を起動したディレクトリ、`--json` の各行の `cwd`、`ghq list` のリポジトリの順に、重複を除いて並べる。カーソルのあるセッションのリポジトリを先頭に置くのは、同じリポジトリで別の作業を始めることが多いため（`f` の `New session` で待ち元のリポジトリを先頭に置くのと同じ。ただし待ち先の関係は結ばない。2026-11-02、利用者の判断）。行がないときと、`--json` を読めずにエラーを出している間は、whatnext を起動したディレクトリが先頭になる。エラーの間は行が画面に出ていないので、見えない行のリポジトリを先頭にしない。worktree に移ったセッションの `cwd` は worktree のパスなので、`git` で元のリポジトリのパスに寄せる。
  - `Other...` で入力したパスが存在しない、またはディレクトリでないときは、入力の場で `Not a directory: <パス>` を出して入力を続けさせる。起動させてから失敗を見せると、一覧に失敗の行が残り、打ち間違いを直す場所が遠くなる。受け付けるのは絶対パスと `~` で始まるパスだけで、相対パス（`../app` など）も同じく `Not a directory: <パス>` で断る。どこを基準に解いたかが画面から分からず、意図しない場所で起動しうるため。空のまま `Enter` を押すと whatnext を起動したディレクトリで起動し、入力欄にはそのことを `Enter start (empty: <起動したディレクトリ>)` と示す（`Enter` ですぐ起動するので、候補のヒントの `Enter start` と揃える）。
  - 候補はフルパスではなく末尾のディレクトリ名（リポジトリ名）で表示する。同じ名前の候補が複数あるときだけ、互いを区別できるところまで親のディレクトリを足して表示する（例: `a/foo` と `b/foo`）。絞り込みは表示名とフルパスの両方に対して行い、表示名で当たった候補をフルパスだけで当たった候補より上に並べる。表示名は入力の文字が順に含まれていれば当たるが、フルパスは入力がそのまま続けて含まれるときだけ当たる（長いパスでは、とびとびの一致がほぼどの入力にも成り立ってしまうため）。
  - `ghq` がないとき、または失敗したときは、`ghq` の候補を出さずにそのほかの候補だけで続ける。エラーは示さない。
  - 文字を打つと候補を絞り込む。打った文字を順に含む候補だけを残し、連続して一致する候補を上に置く。`Other...` は絞り込みの対象にせず常に末尾に置き、選ぶと打った文字を入力欄に引き継ぐ。
  - worktree を使うかは聞かず、`claude` の設定（`worktree.bgIsolation`）に任せる。
  - 候補で `Enter` を押すか、`Other...` の入力で `Enter` を押すと、確かめの段を挟まずにすぐ起動する。候補の下のヒントは `Type to filter · Enter start · Esc close` とし、`Enter` で起動することを示す（`f` の待ち先のメニューは起動しないので `Enter select` のまま）。
  - 候補を出したあとに `ghq` の候補が届いて並びが変わっても、カーソルは見ていた候補に残す。`Enter` ですぐ起動するので、カーソルの下の候補が入れ替わると、確かめた候補と違う場所で起動する。選び間違えたときは、起動した先から一覧に戻り、`Ctrl+X` で止めて消す（起動中の画面と attach した先に作業ディレクトリが見える）。
  - 作業ディレクトリを決めてから claude の画面に入るまでは、起動中の画面（`Starting the session... Ns`）を出し続け、一覧を挟まない。一覧が一瞬見えると、起動に失敗して戻されたように見えて混乱する。
  - 起動したら、そのセッションにそのまま attach する。プロンプトを書かずに離脱すると、そのセッションは指示を待つ行として質問待ちの段に残る。離脱したあとは `Enter` で attach したときと同じく一覧に戻る。
  - `claude --bg` の応答を待つ間は、新しいセッションの画面に留まり、作業ディレクトリに加えて、起動中であることと経過秒数を示す。この間のキー入力は受け付けない。一覧に戻すと、入力画面が閉じたことが完了か取り消しに見え、起動に失敗したように感じられるため。
  - 起動の出力から `id` を読み取れなかったときは attach しない。`claude --bg` の出力をその画面に残し、キーが押されるのを待ってから一覧に戻る。`claude` を起動できなかったとき（PATH にないなど）は、出力の前にその理由（例：`claude not found on PATH (ENOENT)`）も残す。`Ctrl+X` の停止と `open` の失敗の知らせも、出力がなければ起動できなかった理由を出す（#320）。
  - Claude Code が信頼していないディレクトリで `claude --bg` に断られたときは、そのディレクトリで対話モードの `claude` を開き、Claude Code 自身の信頼の確認を画面に出す。承認されると、その `claude` を閉じて `claude --bg` で起動し直し、そのまま attach する。断ると（`claude` が終わると）一覧に戻り、`Not trusted: <ディレクトリ>` を示す。新しく作ったリポジトリで `n` が断られ、別の端末で `claude` を開き直す手間をなくす。信頼の確認を whatnext の中で代わりに聞いて Claude Code の設定に書き込むことはしない。確認はディレクトリの中のフックや MCP の設定を読み込む前の安全確認なので、その判断と記録は Claude Code に任せる（何も書き込まない方針 [ADR-0002](adr/0002-no-writes-no-persistent-state.md) とも揃う）。
  - `--name`、`--permission-mode`、`-w` は指定させない。
  - `Other...` の入力で `Esc` を押すと、作業ディレクトリの候補の選択に戻る。候補の選択で押すと一覧に戻る。入力の途中で候補から選べばよいと気づいたときに、最初からやり直さずに済むようにする。
- **`Ctrl+X`（`background` の行）**：確認なしで `claude stop <id>` で止める。2秒以内にもう一度 `Ctrl+X` を押すと `claude rm <id>` で削除し、一覧から消す。止める操作が失敗したときは、`claude stop` の出力を示し、2回目で削除できることを添える（例：`Stop failed: <出力> (Ctrl+X again to delete)`）。止まっていないセッションに止めたと示さないため。2回目で削除することは変えない。Agent View の `Ctrl+X` と同じ挙動にする。
  - 停止の段の行では、1回目の `Ctrl+X` で止める操作をせず、すぐに削除の待ち受けに入る（`Press Ctrl+X again within 2s to delete.`）。止まっているものに `claude stop` を送ると、止める操作の失敗のような紛らわしい表示になりうる。
  - 削除の待ち受け中に `Esc` を押すか、`Ctrl+X` 以外のキー（カーソル移動など）を押すと、待ち受けを取り消す。カーソルを動かしてから2回目を押して、別の行を消すのを防ぐ。
  - **選んでいた行が一覧から消えて、利用者が動かしていないのにカーソルが別の行に移ったときは、その直後の2秒は `Ctrl+X` を受け付けない。** 押されたら、一覧の下に `Ctrl+X ignored: <消えた行のセッション名> left the list and the selection moved.` と示す。選んでいた行が残っていても、更新で起動された行と分かって選べなくなったときは同じに守り、`Ctrl+X ignored: <名前> turned out to be started by another session and the selection moved.` と示す（#305）。行が消える場面は、会話のないセッション（プロンプトなしで起動し、指示を送っていないもの）を止めて `--json` から消えたとき（いつも消えるわけではない）や、whatnext の外で `claude rm` したときである。そのあとの更新で行が消え、カーソルが移る。2秒を過ぎてから押した2回目は、移った先の行への1回目として、確認なしでその行を止めてしまう（稼働中の行なら、ターンが途中で失われる）。黙って受け付けないだけだと、利用者は何も起きないので押し直し、2秒を過ぎた押し直しで同じことが起きる。

    ```
    > review-x       Working     app                     12%      3m
        → テストを直して
      Ctrl+X ignored: fix-login left the list and the selection moved.
    ```

  - 退けた形：止めた行を、削除の待ち受けが切れるまで一覧に残す（待ち受けが切れたあとの更新で行が消えるので、そのあとに遅れて押せば同じことが起きる）。
  - 止めている最中（`claude stop` の応答を待っている間）に押された2回目は、2秒を過ぎていても削除として受け付ける。
  - **止めている間と削除している間は、その行の STATUS に出す。** 1回目の `Ctrl+X` から `claude stop` が終わるまでは `Stopping...` にする。行は薄くしない。止めたあとも一覧に残りうるためである。2回目の `Ctrl+X` を受けた時点から、行が一覧から消えるまでは `Deleting...` にし、行全体（一言などの注記を含む）を薄くする。止め終わるのを待つ間も `Deleting...` にし、一覧の下の `Press Ctrl+X again…` は消す。`claude rm` がロックで断る間は最長で約40秒かかり、以前はその間何も出ず、削除が受け付けられたかが分からなかった。

    ```
    止めている間(1回目の Ctrl+X)
    > fix-login      Stopping...  app fix-login (wt) #12  45%      12m

    削除している間(2回目の Ctrl+X から、行が一覧から消えるまで)
      SESSION        STATUS       WHERE                  CTX      AGE
    > fix-login      Deleting...  app fix-login (wt) #12  45%      12m   ← 行全体がグレー
        → テストを直しました                                          ← グレー
      refactor-db    Working      app                     12%       3m
    ```

  - 削除している行では、`Enter`、`e`、`f`、`w`、`t`、`v`、`Ctrl+X` は効かない。カーソルの移動、更新、終了などは効く。
  - 待ち先を巻き込んで消すときは、巻き込む行も `Deleting...` になる。削除しなかった行（確認に `N` と答えた、断られた）は、すぐに元の表示に戻る。
  - 退けた形：行を薄くし、一覧の下に `Deleting fix-login...` を出すだけにする（注記の行はもともとグレーなので目立たず、意味も伝わりにくい）。行はそのままにし、一覧の下に出すだけにする（ほかのメッセージで上書きされ、どの行を消しているのかが行から離れる）。
  - 止めたプロセスがまだ終わっていないために `claude rm` がロックで断ったときは、プロセスが終わるのを待ってから削除する。利用者から見れば、2回押せば消える挙動のままにする。
  - push していないコミットがあるために `claude rm` が断ったときは、捨ててよいかを英語で聞き（例：`Discard 1 unpushed commit and delete session <id>? [y/N]`）、`y` なら `claude rm` が示した値を `--discard-unpushed` に渡して削除する。コミットは取り消せない形で失われるので、確認を挟む。
  - それ以外の理由で断ったときは、その文言をそのまま示す。
  - Agent View との違い：Agent View の削除は worktree を未コミットの変更ごと消すが、`claude rm` は未コミットの変更がある worktree のセッションを断る（セッションも worktree も残る）。whatnext は「それ以外の理由で断ったとき」の規則どおり断りの文言を示し、セッションは一覧に残る。消すには、利用者が変更をコミットするか捨てるか、Agent View で削除する。未コミットの変更だけを捨てる `claude rm` のオプションはない。
  - **待ち先の巻き込み**：削除する行が待ち先を持つときは、2回目の `Ctrl+X` のあと、その下にある待ち先（待ち先の待ち先も含む）を並べて、一緒に消すかを英語で聞く（例：`Also delete 2 sessions this one was waiting for? (review-x, split-y) [y/N]`）。`y` なら続けて消し、稼働中のものは止めてから消す。`N` なら選んだ行だけを消す。レビューや分割のセッションは待ち元と一緒に不要になることが多いが、`claude rm` は取り消せないので確認を挟む。待ち元が消えなかったとき（未コミットの変更で断られた、push していないコミットや作業台の確認に `N` と答えた）は、待ち先も消さずに残す。`y` は待ち元と一緒に消すことへの同意で、待ち元が残るなら待ち先も要ることが多い。対話セッション（`(tty)` の行）と起動された行は `claude rm` が受け付けず消せないので、並べない。並べると、`y` と答えても消えない行が出る。その下に消せる待ち先がいれば、それは並べる。
  - 巻き込んで消すセッションにも、push していないコミットの確認と、未コミットの変更による断りは同じように働く。
  - `interactive` の行では `id` がないので効かない。
- **`e`**（edit note）：選んだ行のメモを付ける、直す、消す（「メモ」の節）。`background` と `interactive` のどちらの行にも使える。起動された行は選べないので、付けられない（「依存（待ち先と起動された行）」）。
- **`f`**（wait **f**or）：選んだ行（待ち元）の待ち先を結ぶメニューを一覧の下に出す（「依存（待ち先と起動された行）」）。`(tty)` の行では断る（待ち元にできるのは `background` の行だけ。起動された行は選べない）。入口は1つにし、新しいセッションの起動と既存のセッションの選択を同じメニューに並べる。
  - 先頭は `New session`。選ぶと `n` と同じ手順（作業ディレクトリ）で新しいセッションを起動して attach し、そのセッションを待ち先に結ぶ。起動したセッションが、直後の `--json` の読み直しで見つからなくても（行が出るのが遅れた、読み取りに失敗したなど）、結ぶ予定を持ち続け、`--json` に現れた時点で結ぶ。何も示さずに結ばないと、利用者は結んだつもりのまま、待ち元が `Waiting` にならない理由を探すことになる。作業ディレクトリの候補の先頭は、待ち元のリポジトリにする（worktree なら元のリポジトリに寄せる）。待ち先は新しく起動することが多いので、この経路を先頭に置く。
  - その下に既存のセッションが、一覧と同じ順に並ぶ（区切りの順と区切りの中の順。区切りの見出しは出さない）。`--json` の順は利用者から見て規則がなく、すぐ上の一覧と食い違う。各行には、どのセッションかを見分けられるだけの情報を添える（段、リポジトリ名など。何を添えるかと印の形は実装に任せる）。文字を打つと `n` の作業ディレクトリと同じ規則で絞り込める。文字を打つと、先頭の `New session` ではなく、絞り込んで最初に当たった既存のセッションを選ぶ（打った文字は既存のセッションを絞り込むためのもの）。選ぶと待ち先に加わる。すでに待ち先のセッションには印を付け、選ぶと待ち先から外れる。選ぶたびにメニューを閉じ、一覧の下に `<待ち元> now waits for <待ち先>.`（外したときは `<待ち元> no longer waits for <待ち先>.`）と示す。待ち元がすぐに `Waiting` の段に入り、入れ子が見える。複数を結ぶときは `f` を押し直す（開いたままにして印を付け外しする案は、結んだ結果がメニューを閉じるまで見えにくいので採らなかった。2026-11-21、利用者の判断。#283）。停止などで一覧から外れた待ち先はメニューに並べない。その関係は、待ち元か待ち先が削除されるまで残る（待ち元を削除するときは巻き込みの候補に出る）。
  - 待ち元自身と、選ぶと関係が一周するセッションは並べない。ほかの待ち元の待ち先になっているセッションも並べない（関係を木に保つ）。
  - `Esc` で閉じる。
- **`w`**（workbench）：選んだ行のセッションの作業台を作る（「作業台」の節）。作る場所は、その時点の `--json` の `cwd` である。すでにあれば作らない。
- **`t`**（tab）：`w` と同じく作業台を作る。違いは Ghostty で作業台の画面を開く場所だけで、`w` は右の分割に、`t` は新しいタブに開く（「作業台」の節）。一覧の下のキーの説明では、`w/t workbench` とまとめて示す。
- **`v`**（VS Code）：選んだ行の場所を、手元の VS Code で開く。メニューは出さず、押すとすぐ開く。`cwd` が属するチェックアウトの根を開く。worktree で動いているセッションならその worktree、リポジトリ本体ならリポジトリの根、git でない場所なら `cwd` そのもの。止めたセッションは `--json` の `cwd` がリポジトリの根に戻るので、worktree ではなく根を開く。止まる前に見た worktree のパスを覚えておく案は、whatnext を終了して起動し直すと表示が変わり分かりにくいので採らなかった。`vscode://file/<パス>/?windowId=_blank` を OS の `open` に渡す（`code` コマンドに依存しない）。VS Code のウィンドウがすでにあっても、そのウィンドウを開き直さず新しいウィンドウで開く（その場所をすでに開いているウィンドウがあれば、そのウィンドウが前に出る）。`interactive` の行でも効く。
  - 開いたら一覧の下に `Opened <場所> in VS Code.` と示し、`open` が失敗したらその出力を示す。
  - 押したときに `--json` を読み直して場所を決める。attach している間に claude が worktree に入る（出る）と、一覧が持つ場所は読み直すまで古いため（読み直さないと、worktree に入ったあとにリポジトリの根が開く）。
  - **attach している間**：`ctrl+q ctrl+v` で同じく VS Code で開く。一覧には戻らず、押した画面（claude の画面か作業台の画面）の最下行に何を開いたかを短く示す。作業台の画面で押したときは、その作業台のセッションの場所を開く。`e` や `f` は作業の切れ目に使うので一覧に戻ってよいが、VS Code は作業の途中で開きたいことが多い。
  - 0.17.1 までは、`e`（external）で、PR を GitHub で開く、手元の VS Code、PR を vscode.dev で開く、のメニューを出していた（attach している間は tmux のメニュー）。使ってみると手元の VS Code ばかり使い、PR の URL はたいていセッションの会話の中に出ているので、PR を開く選択肢はなくし、キーも `v` に改めた（2026-10-16、利用者の判断）。WHERE の列の PR の表示は残す。
- 更新や終了に使うキーの割り当ては実装で決める。

### 一覧の外からの起動

判断は [ADR-0024](adr/0024-start-sessions-from-outside-the-list.md)、仕組みは [DESIGN.md](DESIGN.md)「一覧の外からの起動」にある。

- **`whatnext new <ディレクトリかリポジトリ名> <指示>` は、一覧を開かずに、指示を渡したセッションを `--bg` で起動し、その `id`（8 文字）を標準出力に1行で出して、終了コード 0 で終わる。** attach はしない。起動したセッションは、あとで一覧で拾う。Raycast の script のような端末のない場所から、端末を開いて `n` を押さずに、セッションに仕事を投げるために置く（2026-11-23、利用者の判断。#358）。
- 端末がなくても動く（標準入力も tty も要らない）。tmux も使わない。`claude` は `PATH` から探すので、呼ぶ側の `PATH` に `claude` が要る。
- 呼ぶ側の `PATH` に tmux が無くても、ダイジェストは出る。mod は tmux で一覧に「受けているか」を問うので、`whatnext new` は tmux の実行ファイルを探し、絶対パスで mod に渡す。`PATH` に無ければ、よくある置き場所（`/opt/homebrew/bin`、`/usr/local/bin`、`/usr/bin`、`/opt/local/bin`）も探す。ランチャーの `PATH` は短く、tmux の置き場所を含まないことが多いためである。どこにも見つからないときは、起動はして（終了コード 0、`id` も出す）、標準エラーに `whatnext: tmux not found on PATH. Started the session, but its digest shows in the list only if the session can run tmux.` を出す。付けるものは起動時に固定なので、黙って起動すると、ダイジェストが出ない理由を利用者があとから知る手段がない。
- 一覧が動いているのに、呼ぶ側の `TMUX_TMPDIR` が一覧を開いた端末のものと違うときも、起動はして（終了コード 0、`id` も出す）、標準エラーに `whatnext: the list is running, but its tmux socket is not at <パス>. Started the session, but its digest will not show in the list. Check that TMUX_TMPDIR here matches the list's terminal.` を出す。mod は、`TMUX_TMPDIR` から決まる場所の tmux のソケットで一覧に「受けているか」を問うので、場所が違うと一覧を見つけられず、そのセッションのダイジェストは出ない（フックと OTel は届くので、一言と CTX は出る）。tmux が見つからないときと同じ理由で、黙って起動しない。一覧が動いていないときは、ソケットがまだ無いのが普通なので、確かめない。
- 指示は必須で、1つの引数で渡す（空白を含むなら、呼ぶ側が引用符で囲む）。`--help` だけの指示は受けない（「全体」）。ディレクトリかリポジトリ名の前後の空白は切る（`n` の入力と同じ）。指示のないセッションは、attach して指示を書くまで何もしないので、投げて放置する用途に合わない。
- **起動したセッションには、`n` で起動したセッションと同じもの（フック、OTel、ダイジェストの mod）を付ける。** 何を付けるかは、起動のたびに受け口のポートを確かめて決める。

  | 受け口のポート | 付けるもの | 一覧での見え方 |
  |---|---|---|
  | 一覧が動いている | フック、OTel、mod | `n` で起動したセッションと同じ（一言、CTX、ダイジェスト）。`--no-digest` の一覧では、ダイジェストは出ない |
  | 誰も使っていない（一覧が動いていない） | フック、OTel、mod | あとで一覧を開くと、行と一言が出る（一言は会話記録で補う）。一覧が動いていない間に終わったターンの CTX とダイジェストは出ない（CTX は `-`）。どちらも、一覧を開いたあとの次のターンから出る |
  | ほかのプログラムが使っている | なし | 外で起動したセッションと同じ（一言は会話記録で補い、CTX は `-`）。標準エラーに `whatnext: port <ポート> is used by another program. Started the session without hooks, so the list shows no context size or digest for it.` を出す。起動はするので、終了コードは 0 で、`id` も出す |

  - 一覧が動いていないときに断らないのは、一覧を止めている間に投げる場面が多いためである。フックは受け手がいなくても失敗せず、セッションの画面にも何も出ない（[DESIGN.md](DESIGN.md)「フックの受信」）。一覧を裏で起こすことと、会話記録で CTX を補うことはしない（2026-11-24、利用者の判断）。
  - ほかのプログラムがポートを使っているときに付けないのは、`n` と同じ理由である。付けると、そのセッションは生きている間、指示と最後の応答の全文を、そのプログラムに送り続ける。
  - 「ほかのプログラムが使っている」と決める前に、ポートをもう一度確かめる。動いている一覧の応答が1回遅れただけで、何も付けずに起動しないためである（付けるものは起動時に固定で、あとから付け直せない）。2回とも一覧の応答でなければ、ほかのプログラムとみなす。
- **mod は、動いている一覧が `--no-digest` かどうかを見ずに付ける。** `--no-digest` の一覧はダイジェストを受けていないので、mod は Haiku を呼ばない（「ダイジェスト」の節）。その一覧を終了して引数なしで開き直せば、次のターンの終わりからダイジェストが出る。`whatnext new` に、mod を付けずに起動する手段は置かない。mod が壊れたときは、素の `claude --bg -- <指示>` で起動する（2026-11-25、利用者の判断）。
- 作業ディレクトリは、次の順で決める（2026-11-23、利用者の判断）。
  1. 引数が既存のディレクトリなら、それを使う。先頭の `~` を展開し、相対パスは呼んだ場所から解く。
  2. そうでなければ、`ghq list -p` のパスのうち、末尾が引数に一致するものを探す（`name`、`owner/name`、`github.com/owner/name`。パスの区切りの単位で比べるので、`oo` は `foo` に当たらない）。`/`、`~`、`./`、`../` で始まる引数と、`.`、`..` はパスとして扱い、リポジトリ名としては探さない。`~user` もパスとして扱うが、展開はしないので、ディレクトリでないと断る。
  3. 1件ならそこで起動する。`n` の候補と違い、一覧に出ているセッションのリポジトリは候補にしない（一覧の外からは見えないため）。
- 次のときは、標準エラーに理由を出して終了コード 1 で終わり、セッションを起動しない。標準出力には何も出さない。
  - 引数が2つでない、または空のとき：`whatnext: new needs a directory or a repository name, and a prompt.` と、使い方の1行（`Usage: whatnext new <directory|repository> <prompt>`）。知らないオプションの終了コード 2 と分けるのは、`new` までは打てているためである。
  - パスとして書いた引数がディレクトリでないとき：`whatnext: Not a directory: <引数>`。
  - リポジトリ名が `ghq list -p` のどれにも一致しないとき：`whatnext: No such repository: <名前>`。
  - 2件以上に一致するとき：`whatnext: Ambiguous: <名前>` に続けて、候補のパスを1行に1つ、2桁の字下げで出す。`owner/name` で絞って呼び直せる。
  - ghq が無い、または失敗したときに名前を渡されたとき：`whatnext: Not a directory: <引数> (repository names need ghq, and "ghq list -p" failed)`。このときはパスだけを受ける。
  - Claude Code が信頼していないディレクトリのとき：`whatnext: Not trusted: <ディレクトリ>. Run claude there once and accept the trust prompt.`。端末がないので、`n` のように信頼の確認を出せない。
  - claude の Bash から呼んだとき（`CLAUDECODE=1`）：`whatnext: whatnext new cannot run inside a Claude Code session. Run it from a shell or a script.`。sandbox の中では claude が claude を起動できないので、claude のセッションを窓口にする使い方は支えない（2026-11-22、利用者の判断）。
  - `claude --bg` が `id` を返さなかったとき、`claude` を起動できなかったとき：`whatnext: claude --bg did not start a session:` に続けて、claude の出力（`n` の失敗の画面と同じ行）。
- whatnext 自身は、ネットワークの口を開かない。スマホなどの外から起動したいときは、届く口を whatnext の外に置き、そこからこのコマンドを呼ぶ（2026-11-22、利用者の判断。#360）。

### 未確定の前提

- **`pid` のない `blocked` を失敗の段に置くこと。** 「プロセスが異常終了して状態だけ残ったもの」と推測して失敗の段に置いているが、2.1.282 では attach すれば起き直って続けられた。解除コストは「原因を調べる」より小さいことになり、STATUS の `Failed (no process)` は、調べる必要があるように読める。段の表記を変えるかは、使って困るかで判断する。

#### 新しいセッションの起動

- **8.** `n` で作業ディレクトリ（候補を絞り込んで選ぶか `Other...` で自由に入力する）を指定して起動すると、そのセッションに attach して最初の指示を書け、離脱するとそのセッションが一覧に現れている。起動を待つ間は一覧に戻らず、起動中であることと経過秒数が出ている。`ghq` がない環境でも同じ手順で起動できる。`Other...` に存在しないパスを入れると、その場で `Not a directory` と示されて起動しない。一覧でカーソルを別のリポジトリの行に置いて `n` を押すと、候補の先頭はそのリポジトリになる。
- **47.** Claude Code がまだ信頼していないディレクトリを `n` で選ぶと、Claude Code の信頼の確認が出る。信頼すると、そのまま新しいセッションに attach していて、離脱するとそのセッションが一覧に現れている。断ると一覧に戻り、`Not trusted: <ディレクトリ>` が示される。
- **43.** `n` の `Other...` の入力で `Esc` を押すと、作業ディレクトリの候補の選択に戻る。

#### 停止と削除

- **9.** `background` の行で `Ctrl+X` を押すとそのセッションが止まり、2秒以内にもう一度押すと一覧から消える。worktree で動いていたセッションでも、2回押せば消える。push していないコミットがあるときは、捨ててよいかを英語で聞かれ、`y` で消える。未コミットの変更だけがある worktree のセッションでは、`claude rm` の断りの文言が示され、セッションは一覧に残る。1回目の `Ctrl+X` から止め終わるまで、その行の STATUS は `Stopping...` になる。2回目からは行が消えるまで薄い `Deleting...` になり、その行では `e` などが効かない。前に入ったセッションを止めたり消したりしている間に別のセッションに入っても、止め終わったときや消し終わったときに一覧に戻されない。
- **29.** 作業台を持つセッションを `Ctrl+X` の2回で削除すると、作業台と残していた attach も閉じる。作業台でシェル以外のものが動いていれば、そのコマンドを示す英語の確認が出て、`N` なら削除しない。削除したセッションの作業台を作業台の画面が映していれば、次に映すもの（一覧のカーソルの行の作業台か、その案内）に切り替わる。tmux がない環境で whatnext を起動すると、英語で示して終了する。
- **40.** `Ctrl+X` の1回目で止める操作が失敗すると、`claude stop` の出力と、2回目で削除できることが示される。止めたとは示されない。
- **51.** 選んでいる行のセッションが一覧から消えて（外で `claude rm` した、会話のないセッションを止めて消えた、など）カーソルが別の行に移る。その直後の2秒に `Ctrl+X` を押しても、移った先の行は止まらず、`Ctrl+X ignored: <消えた行のセッション名> left the list and the selection moved.` が示される。

#### メモ

- **15.** `e` を押すと選んだ行の直下にメモの入力欄が出て、文字を書いて `Enter` を押すと、その行の下に `↳ <メモ>` が出る。行は動かず、カーソルはその行に残り、名前に印は付かない。`Esc` を押すとメモを付けずに入力欄が閉じる。メモのある行で `e` を押すと今のメモの入った入力欄が出て、書き換えて `Enter` を押すとメモが変わり、`Backspace` で空にして `Enter` を押すとメモが消える。メモのある行に attach して離脱しても、メモは残る。whatnext を終了して起動し直しても、メモはそのまま残る。対話セッションにメモを付け、そのセッションが `idle` で一覧から外れたあと再び一覧に出ても、メモは残っている。保留を書いた古い状態のファイルにある保留の理由は、メモとして出る。
- **35.** （廃止。保留をメモに改めた）

#### 待ち先

- **17.** 行 A を選んで `f` を押し、`New session` を選んで作業ディレクトリ（候補の先頭は A のリポジトリ）を指定すると、新しいセッション B が起動して attach する。離脱すると、B が稼働している間、A は `Waiting` の段になり、B が A の下に入れ子で並ぶ。
- **18.** B がターンを終えてレビュー待ちの段に入ると、次の更新で A は自分の段に戻る（STATUS が `Waiting` から `Review` に変わる）。A の行の下に、B が終わったことを知らせる注記は出ない。B に再び指示を出して B が稼働すると、A は再び `Waiting` の段に出る。
- **19.** A 自身が権限待ち、質問待ち、許可待ち、失敗、稼働中のときは、B を待っていても自分の段に出る。
- **20.** `f` のメニューでは、`New session` の下に既存のセッションが並び、文字を打つと絞り込める。既存のセッションを選ぶと A の待ち先に加わり、印の付いた待ち先を選ぶと外れる。待ち先が複数あるときは、全部がレビュー待ちか停止の段に入るか一覧から消えるまで A は `Waiting` のままで、待ち先は A の下に入れ子で並ぶ。一周する関係は結べない。ほかの待ち元の待ち先は、メニューに並ばない。
- **21.** 待ち先にメモを付けると、その行は A の組に残り、下に `↳ <メモ>` が出る。A にメモを付けても、組は区切りの中の同じ位置に残る。
- **22.** A で `Ctrl+X` を2回押して削除すると、A の下の待ち先（待ち先の待ち先も含む）を並べて、一緒に消すかを英語で聞かれる。`y` で待ち先も消え、`N` なら A だけが消える。A が消えなかったとき（確認に `N`）は、待ち先も残る。巻き込んで消す待ち先でも、push していないコミットの確認と、未コミットの変更による断りは今と同じに働く。whatnext を終了して起動し直しても、待ち先の関係はそのまま残る。対話セッション（`(tty)` の行）の待ち先は消せないので、確認には並ばない。待ち先が対話セッションだけなら、確認なしで A だけが消える。
- **44.** `f` のメニューの既存のセッションは、一覧と同じ順に並ぶ。

#### リポジトリの区切りと並び

- **61.** 一覧では、セッションがリポジトリごとの区切りにまとまって、見出しの文字列の順に並ぶ。区切りの間は1行あき、見出しの行はカーソルで選べない。worktree で動くセッションと、リポジトリの根より下で動くセッションは、元のリポジトリの区切りに入る。WHERE には、区切りと違うリポジトリのときだけリポジトリ名が出る。
- **62.** 行 A に attach して戻ると、A が区切りの先頭に上がり、カーソルが A に付く。A の段が変わっても、次に別の行に attach するまで並びは変わらない。外で起動したセッションは、見えたときに区切りの先頭に出る。
- **63.** ディレクトリ名が同じリポジトリが2つあると、見出しは `a/foo` と `b/foo` になる。git でない場所は、パスごとの区切りになり、末尾の名前が同じでも場所が違えば別の区切りになる。
- **64.** 待ち元 A（リポジトリ `app`）が待ち先 B（リポジトリ `lib`）を待っているとき、B は `app` の区切りの中で A の下に入れ子で並び、`lib` の区切りには出ない。B の WHERE には `lib` が出る。B に attach して戻ると、A と B の組が `app` の区切りの先頭に上がる。
- **65.** `e` でメモを付けると、行は区切りの中の同じ位置に残り、下に `↳ <メモ>` が出て、カーソルはその行に残る。
- **66.** whatnext を終了して起動し直すと、区切りの中の並びも終了する前と同じになる。カーソルは最も新しく attach したセッションにある。
- **75.** `.bare` 型の worktree の構成（`foo/.bare` に本体を置き、`foo/main` や `foo/feature` に worktree を置く）で動くセッションは、見出しが `foo` の区切りに入る。submodule の中で動くセッションは、親のリポジトリの区切りに入り、WHERE に submodule のパスが出る。
- **76.** 区切りの見出しは、大文字と小文字を区別しない、人の読み方の順に並ぶ（`alpha` が `Zeta` より前）。初めて起動したときのように、初めて見た時刻が同じ行どうしも、名前の同じ順に並ぶ。

#### 起動された行

- **67.** 行 P のセッションがスキルや MCP サーバを通して `claude -p` を起動すると、次の更新で、その行が P の下に入れ子で並び、名前に `(sub)` が添えられる。その行がさらに `claude -p` を起動すると、もう一段深く並ぶ。手元のシェルから起動した `claude -p` は、トップレベルに `(tty)` を添えて並ぶ。
- **68.** P が起動した行が稼働していても、P の段は変わらない。P がレビュー待ちに当たれば（`--json` が `done` を返す）、`Waiting` ではなくレビュー待ちの段に出る。
- **69.** ほかの行の `f` のメニューに、起動された行は並ばない。P で `Ctrl+X` を2回押して削除するとき、起動された行を一緒に消すかは聞かれない。P が消えたあとも起動された行が動いていれば、トップレベルに `(tty)` を添えて並ぶ。
- **70.** P を選んで `↓` を押すと、P の下に入れ子で並ぶ起動された行（2段の入れ子を含む）を飛ばして、その次の行に移る。`↑` でも起動された行には止まらず、カーソルは起動された行に乗らない。
- **71.** 開いているだけの対話セッション Q（一覧に出ていない）が `claude -p` を起動すると、その行はトップレベルに `(sub)` を添えて並び、カーソルで選べない。ほかに選べる行がなければ、カーソルはどの行にもなく、`f` も `e` も何もしない。Q が稼働して一覧に出ると、その行は Q の下に入れ子で並ぶ。
- **72.** `(tty)` の行で `f` を押すと、待ち先を結べないことが英語で示される。`(tty)` の行は、ほかの行の `f` のメニューに並び、待ち先として結べる（#263）。
- **73.** 待ち先がすべて終わってレビュー待ちの段にいる A に、`f` で新しく C を結ぶ。C が稼働していれば、A は `Waiting` の段に入る。C がすでにレビュー待ちの段なら、A は自分の段のままである。
- **74.** 状態のファイルに、1つの待ち先を2つの待ち元が待つ関係、一周する関係、`(tty)` の行を待ち元にした関係があると、whatnext を起動したとき、それらの行は結ばれていないものとして一覧に出る（入れ子にならず、`Waiting` にもならない）。起動しただけでは、ファイルのそれらの関係は書き換わらない（初めて見た時刻などは書く。関係を書き換えるのは、利用者がメモか待ち先を変えたときだけ）。別のセッションが一覧から消えても、それらの関係は残る。
- **77.** `headersHelper` で `X-MCP-Caller-Pid` を返す設定にした HTTP の MCP サーバを、2つのセッション P と R から同時に使う。サーバがヘッダの値を `MCP_CALLER_PID` にして `claude -p` を起動すると、P が呼んで起動した行は P の下に、R が呼んで起動した行は R の下に、`(sub)` を添えて入れ子で並ぶ。`MCP_CALLER_PID` を渡さないサーバが起動した行は、トップレベルに `(tty)` を添えて並ぶ。

#### ダイジェスト

- **80.** `whatnext` を引数なしで起動し、`n` で起動したセッションがターンを終えると、次の更新から、その行の一言の上に `◎ <Goal>` が出る。稼働中になっても、次のダイジェストが届くまで同じ Goal が出たままになる。
- **81.** 端末が 120 桁以上なら、一覧の右の欄に、カーソルの行の `Goal` `Progress` `Next` と `Links` が出る。カーソルを動かすと、右の欄がその行の中身に替わる。ダイジェストのない行では `No digest yet.` が出る（会話リンクが届いていれば、その下に `Links` も出る）。xterm 系と Ghostty の端末では、`Links` の行をクリック（Ghostty では cmd+クリック）するとブラウザで開く。120 桁より狭いと右の欄は出ず、Goal の行だけが出る。
- **82.** `whatnext --no-digest` で起動すると、ダイジェストが届いても Goal の行も右の欄も出ず、`n` で起動するセッションに mod は付かない。引数なしで起動した whatnext の `n` で起動したセッションは、whatnext を終了するか `--no-digest` で起動し直すと、ターンの終わりに Haiku を呼ばず、何も送らない。引数なしで起動し直すと、次のターンの終わりからまた届く。`--no-digest` で動いている一覧に `whatnext` でつないでも、一覧は今のまま動き、何も示されない（逆向きは 88）。
- **83.** 引数なしで起動した whatnext の `n` で起動したセッションに attach すると、セッションの中のペイン（`Digest`）に、一覧と同じ見出しでダイジェストと会話リンクが出る。`/wn-digest` でペインを開ける。
- **84.** 一覧で `o` を押すと、カーソルの行の会話リンクが並び、選んで `Enter` を押すとブラウザで開き、何を開いたかが一覧の下に出る。会話リンクのない行では `No links for <名前>.` が出る。

- **94.** 存在しないディレクトリや、候補にないリポジトリ名を渡すと、理由が標準エラーに出て終了コード 1 で終わり、セッションは起動しない。名前が2つ以上のリポジトリに一致すると、候補のパスが出て終了コード 1 で終わる。指示を渡さないと、使い方が出て終了コード 1 で終わる。信頼していないディレクトリを渡すと、`Not trusted` が出て終了コード 1 で終わる。

## Out of Scope

- **コストやトークンのダッシュボード**：Grafana 構成の OSS が十数個あり飽和している。
- **事後の振り返りのサマリやレポート**：競合が多く、リアルタイム性という軸から外れる。ダイジェスト（「ダイジェスト」の節）は、今どこまで進んだかを並んだ行の間で見比べるためのもので、これには当たらない。
- **工程のタイムライン**（session-timeline の、工程ごとに区切った縦の表示）：利用者が見ていたのはまとめとリンクで、工程はたまにしか見なかった。区間ごとの Haiku の呼び出しを全セッションで払うことになる。まとめとリンクだけを、ダイジェストと会話リンクとして引き継いだ（#325、masahirompp/skills#63）。必要になったら改めて考える。
- **セッション内容の再構築やデバッグビュー**：JSONL を解析するツール（claude-hindsight など）が先行しており、情報量でも勝てない。
- **一覧の常時表示**：セッションに入っている間、一覧を横に出し続けること。セッションに集中したいので出さない（利用者の判断）。作業台のために tmux を必須にしたので（[ADR-0010](adr/0010-workbench-lives-inside-whatnext.md)）技術的な障壁はないが、一覧が横にあると気が散る。tmux を使わずに実現するには node-pty と ANSI パーサによる端末多重化の自作が要り、依存の総量が tmux より重い。
- **セッションへの自動介入や自動承認、返信や権限応答の代行、attach せずに一覧の上で権限を許可すること**：[ADR-0003](adr/0003-no-input-injection-or-proxy-response.md) を参照。
- **完了したセッションへの追加の指示を送るキー（`r`）**：追加の指示は attach して送れば足りる。
- **`claude logs` を開くキー**：出力が画面の再描画の制御コードそのもので読める形にならず、中身を見る手段は attach で足りる。
- **一覧に出ない過去のセッション（終了した対話セッション、`rm` したセッション）を再開する機能**：過去のセッションの一覧を機械で読める公式の口がない。会話記録は `--json` に出ているセッションを補うためだけに読み、過去のセッションを探す入口にはしない（[ADR-0011](adr/0011-fill-in-from-transcripts-when-hooks-are-missing.md)）。端末を `claude --resume` のピッカーに渡す案は、再開したセッションが whatnext の子の対話セッションになり、離脱の操作（Ctrl+Z）が attach と食い違う。止めた `background` のセッションは一覧に残り（`done` と `failed` はそのままの段に、それ以外は停止の段に）、`Enter` で再開できる。会話のないもの（プロンプトなしで起動し、指示を送っていないもの）は、止めると `--json` から消えることがあり、消えれば一覧にも残らない。それ以外は、`n` で同じリポジトリに空のセッションを起動し、attach した先で `/resume` を使う。
- **一覧で選んだ行のセッションの画面をプレビューすること**：tmux に `claude attach` を常駐させ、`capture-pane` で画面を一覧の横に出す案。画面を読んで理解する負荷は attach と変わらず、常駐のメモリ（1本あたり約 140MB）がかかる。セッションが今どうなっているかは、フックで取る行の一言で示す（[DESIGN.md](DESIGN.md)「フックの受信」）。画面の文言から段を決めるのは [ADR-0001](adr/0001-read-state-only-from-agents-json.md) に反する。
- **対話セッション（`(tty)` の行）の中身を whatnext から覗く機能**：`claude attach` も `claude logs` も対話セッションには使えない。`claude --resume <sessionId> --fork-session` の複製を、キーを絞った画面で開けば、その時点までの会話を Claude Code の描き方で見られることを確かめ、一度実装した。しかし、それが必要になる場面をもう少し見極めるため、入れないことにした（2026-10-21、利用者の判断）。`Enter` は引き続き `cwd` と `pid` を示すだけにする。再検討するときの材料（会話記録を自前で描く案、OSS、`/export`、複製の安全の補強に `--safe-mode --permission-mode plan`）は #227 と #228、[claude-code-behavior.md](claude-code-behavior.md)「対話セッションの複製」にある。`claude -p` で動いているセッションも、動いている間はこの行として出る。
- **Web UI（ローカルサーバ）**：ブラウザのタブという常駐アプリが一つ増え、ウィンドウを増やさないという動機と衝突する。ページに端末部品（xterm.js）を載せ、ローカルのサーバの pty で `claude attach` を動かせば attach はできる（VS Code の端末と同じ仕組み）ので、attach できないことは理由にならない。作業台の画面の構成（[ADR-0014](adr/0014-workbench-shows-in-a-screen-the-user-opens.md)）の使い勝手が足りないと分かったときの、代わりの第一候補として残す。一覧を Web ページとして作り、キーをページが握れるので、端末の組み合わせの制約から自由になる。代わりに、端末部品の描画と日本語入力の品質に頼り、作業台の寿命を持つサーバを自作し、手元のシェルを動かせる口になるローカルのサーバの安全性（起動ごとのトークン、Origin の検査）を引き受ける。
- **独自のセッション管理、外部からの push 型キュー、常駐デーモン、計測ログ**：[ADR-0002](adr/0002-no-writes-no-persistent-state.md) を参照。端末のウィンドウを閉じたあとも whatnext が動き続けるのは、利用者が起動したものが終了していないだけで、常駐デーモンには当たらない（[ADR-0012](adr/0012-list-runs-inside-the-dedicated-tmux-server.md)）。
- **外部の出来事（Slack、CI、レビュー依頼など）の監視を本体で行うこと、常駐するコストの集計の自作**：[ADR-0008](adr/0008-dependencies-and-contact-points-with-tmux.md) を参照。
- **燃焼率の異常の自動検知**：定額プランで空転して失うのは金額ではなく利用枠で、上限に当たらない限り失うものは小さい。閾値を過去の分布から決めるには蓄積が要り、ADR-0002 に反する。
- **セッションから離れた、人間の手入力のメモ**：正本がなく、セッションとして起こす根拠もない。保存先が必要になり、個人用 TODO アプリへの変質を招く。セッションに付く1行のメモ（「メモ」の節）は持つ。メモはセッションと一緒に消え、セッションから離れたメモ、複数行のメモ、メモの一覧や検索は持たない。個人用 TODO アプリへの変質を防ぐ線を、ここに引く。
- **クラウドのセッション（claude.ai/code、`--cloud`、routine）を一覧に載せること**：公式の読み取り口がなく（[claude-code-behavior.md](claude-code-behavior.md)）、attach もできない。認証切れで止まる routine の多くは「失敗して終わった」か「起動していない」で、どちらも待機中ではないので段が決まらず、一覧の形に乗らない。非公式の経路（`claude mcp serve` の `RemoteTrigger`）でも、完了・返事待ち・失敗を構造化された値で区別できなかった。`claude agents --json` がクラウドのセッションを返すようになったとき、または Claude Managed Agents（状態と承認待ちを読む公開 API と端末からの attach がある。従量課金）を監視の実行基盤に採るときに再検討する。
- **並行するセッションの数を増やすための機能**：ボトルネックは人間のレビューの帯域なので、目的を詰まっている時間の短縮に限る。
- **セッションの情報（モデル、effort）の列、高価なモデルで定型作業を回していることの検知**：利用枠やコストの監視で、「どれに手を付けるか」を示す役割の外にある。コンテキストの大きさ（CTX）の列は出す（[DESIGN.md](DESIGN.md)「OTel の受信」）。コスト（COST）の列は、一度入れたがやめた。
- **一覧に戻らずに次のセッションへ移るキー（`ctrl+q ctrl+j`）**：attach している間に、一覧を経由せずに、ラダーのビューの `Up next` の先頭のセッションへ移るキー。一度入れたが、利用者の判断でやめた（2026-10-25）。次に何をするかは利用者が自分で選ぶほうがコンテキストを切り替えやすく、使っていなかった。リポジトリの区切りでは「次」が決まらないことも理由にした。区切りの中の次の行へ移すと、移った行が区切りの先頭に上がるので、2つのセッションの間を行き来するだけになる。
- **行内のリンク、端末のタイトルへの待機件数の表示、blocked が発生したときの OS の通知**：OS の通知は Claude Code のセッション自身が通知するので二重になる。行内のリンク（WHERE の PR 番号を端末のハイパーリンクにする）は、PR を開く用途を `e` のメニューがキー操作で満たしている。端末のタイトルへの表示も、利用者の判断で外した。
- **作業台で終わったコマンドの終了コードや終わった時刻を一覧に出すこと**：取るには利用者のシェルに記録させる仕掛けが要り、利用者の設定に踏み込む。終わったことは `⚙` の行が消えることで分かる。
- **`n` でモデルを選ぶこと**：一度入れたが、やめた（2026-11-04、利用者の判断）。`default` と `Other...`（モデル名を入力して `--model` に渡す）の2択を出していたが、`default` 以外を選んだことが一度もなく、起動のたびに `Enter` を1回余分に押させるだけだった。別のモデルで動かしたいときは、attach した先の Claude Code の `/model` で切り替える。`default` の横に既定のモデル名を出すことも、不要と判断した。
- **端末でない入出力で一覧（`whatnext`）と作業台の画面（`whatnext workbench`）を起動したときに、メッセージを出して終了すること**：一覧と作業台の画面は端末から人が使うもので、パイプやリダイレクトの先で起動する用途がない。`whatnext new` はこの項に当たらず、端末のない場所から呼ぶために置いている（「一覧の外からの起動」）。
- **`whatnext new` に足さないもの**：起動するセッションの名前（`--name`）と待ち先の指定、`--json` の出力、mod を付けずに起動する手段、一覧が動いていないときに一覧を裏で起こすこと。使う場面がまだない（2026-11-23、利用者の判断。#358）。スマホなどの外から届く口は、whatnext の中には置かない（#360）。
- **ヘッダにセッションの件数（`N sessions`）を出すこと**：並行は 3〜8 個の想定で、一覧を見れば数えられる。
- **連続して処理するための並べ替え（同じ段の中で直前と同じリポジトリの行を先にする、読んだだけのレビュー待ちの行を段の中で下げる）**：不要と判断した。離脱すると次の候補へ自動で attach する案も退けた（見ていない間に次へ入る）。
- **ラダーのビュー**：一覧を優先度ラダーの順（段、待機時間が分からない行、長く待っている順、名前の順）に並べ、`Last attached`・`Up next`・`On hold` の組を出すビュー。以前の一覧の形で、リポジトリのビューと `g` で切り替えていたが、利用者の判断でやめた（2026-10-25、#271）。使ってみて並べ替えに意味が薄かった。更新や attach から戻ったときに行の位置が変わって探し直すことになり、一番上の行が自分の選びたいものと違い、次の行は自分で選んでいた（#232）。2つのビューがあると、依存（待ち先と起動された行）の規則をビューごとに書くことになり（組の位置、組の位置に保留や起動された行を数えるか、先頭と保留の組）、仕様が縛られることも理由にした。段の判定（STATUS の列）は残す。
- **保留中に段が上がったら（権限待ちになったなど）保留を自動で解くこと**：採らないと決めた。保留の組の中でも STATUS の列の色で見える範囲でよい。保留はメモに改めたので、今は当たらない。メモも段や状態から自動では消さない。
- **保留のセッションに attach して作業したら保留を自動で解くこと**：以前はあった（attach の前後の `--json` の差と、届いた指示で判定した）。利用者が使って、やめた（2026-10-06）。優先度が低くて余裕があるときだけ進めるセッションを少し進めるたびに、保留が解けて `Up next` に出るのが煩わしかった。保留はメモに改めた（「メモ」の節）。
- **`!` のコマンドのコピー**：セッションが最後の応答で勧めた `! <コマンド>` を、一覧の下に出して `y` でコピーし、attach している間は `ctrl+q ctrl+y` のメニューから選んで作業台の入力欄に貼る機能。一度入れたが、利用者の判断で廃止した（2026-10-02）。作業台の画面を claude の画面の横に並べたので、claude の `/copy` で応答をコピーし、横の作業台で動かせば足りる。
- **外で起動したセッションに、attach のときに OTel を付け直すこと**：同じセッションのまま設定を足す手段がない。`claude respawn` はフラグを取らず、`--resume` に `--settings` を付けると別の ID のコピーが起動して元も残る。コピーで置き換えると行の ID やブランチが変わり、attach が「止めて複製する」という見えない副作用を持つ。得られるのもそのセッションの CTX だけで、対話セッションは対象外のまま。

## Further Notes

### 配布

whatnext を npm に公開し、`npx @masahirompp/whatnext` で呼び出せるようにして、実際に試す。

- パッケージ名は `@masahirompp/whatnext`、bin の名前は `whatnext` とする。npm の `whatnext` という名前は別人が公開済み（2026-09 時点）なので、スコープ付きの名前にする。`npx` でスコープ付きの名前を呼べば、bin の名前が既存のパッケージと衝突することはない。
- バージョンは `0.1.0` から始める。`0.x` 系で出し、破壊的な変更を入れたら minor を上げる。semver は `0.y.z` を「いつ何が変わってもよい初期開発版」と定めているので、`0.x` であることがアルファ版の表明になる。プレリリース版と dist-tag（`@alpha`）は、安定版の系列が別にあるときの仕組みで、`npx` をタグなしで呼べなくなるので使わない。
- `engines` は `node >=22` とする。サポートが続いている Node の版の下限である。
- パッケージに含めるのは、ビルド後のコード（`dist/`）、ダイジェストの mod（`mod/` のうち実行に要るもの）、README、LICENSE だけにする。
- ライセンスは MIT とする。公開すればコードは誰でも取得できるので、許諾しないまま出すと「公開したのに使えない」状態になる。依存先も、MIT と両立するライセンスのものに限る。
- GitHub のリポジトリは public にし、`package.json` の `repository`・`homepage`・`bugs` に書く。npm のページからリポジトリと issue に辿れ、README の相対リンクも GitHub のファイルを指す。
- publish は取り消せない外部への公開である。公開したバージョン番号は使い直せず、72時間を過ぎると原則として unpublish できない。そのため、公開は保守者の承認を最後の一押しにする。
  - タグ `v<版>` を push すると、CI が npm の stage に置く。保守者が 2FA で承認するまで公開されない。承認の前に、stage に置いた tarball を取り出して中身を確かめられる。
  - タグのコミットが main のマージのコミット(main の first-parent の鎖の上のコミット)でないとき、タグの版が `package.json` の `version` と違うときは、CI は stage に置かずに止まる。
  - CI は npm の trusted publisher(OIDC)で stage に置き、公開に使うトークンを持たない。公開した版には provenance(どのリポジトリのどのコミットから、どの workflow で作ったかの証明)が付く。
  - 実装セッションは、承認の前に、stage の tarball と同じタグから手元で作った tarball を比べて示し、公開のあとに `npx` で起動できることを確かめる。手順は releasing-whatnext スキルに置く。
- whatnext は設定を持たず、データはメモと待ち先の関係を書く状態のファイルだけである（[ADR-0016](adr/0016-persist-holds-and-waits-in-a-state-file.md)）。このファイルは読めない版を空として扱い、移行を求めない。そのため、破壊的な変更で利用者に移行を求めるものがない。README に「0.x の間は予告なく変わる」と明記する。
- 名前は whatnext のまま変えない。ラダーのビュー（「次に何をやるか」を順位で示す一覧）はやめたが、パッケージ名と bin の名前も含めて変えない（2026-10-25、利用者の判断。#272）。

### 複数の出どころ（構想）

今は手元の Claude Code 専用だが、クラウドの Claude のセッションや Codex なども一覧に載せる構想がある。構想として置き、今は作らない。

- 段の考え方は、特定のエージェントに依存しない。依存しているのは、状態の読み方（`claude agents --json`）、行から段を決める規則、操作（`attach` / `stop` / `rm` / `--bg`）の3つである。
- 対応するなら、この3つを「出どころ」の単位で差し替えられるようにする。各出どころは、行（id、段に写した状態、待機の理由、場所、時刻）と、使える操作を返す。ADR-0001 と ADR-0005 は「出どころごとに公式の読み取り口を一つ使う」に書き換えることになる。
- **出どころとして採る基準**：行ごとに、構造化された「待っている／動いている／終わった」の信号を返すこと。文面にしか差が出ない出どころ（routine の実行など）を混ぜると、段の判定を説明できなくなる。
- **有効にする方法**：何を監視するかは利用者が選んで有効にする（既定は `claude agents --json` だけ）。設定ファイルを持たないので、起動時のフラグか環境変数で有効にする。コマンドがあれば自動で有効にする方式は、利用者が選ぶという方針と矛盾する。
- `Enter` の意味（attach、ブラウザで開く、場所を示す）は出どころごとに変わるので、出どころの定義に含める。
- Codex の公式の読み取り口と、`--bg` や attach に当たる仕組みがあるかは未調査。
- **時期**：2つ目の出どころを実際に使うようになったら考える。それまでは、コードに先回りの抽象は入れない。

### 近い道具との違い（2026-09 時点）

作業台の形を決めるために端末エミュレータとマルチプレクサを調べた（[ADR-0014](adr/0014-workbench-shows-in-a-screen-the-user-opens.md)）。そのうち2つは、whatnext と目的が重なる。

- **herdr**（tmux のようなマルチプレクサ。Apache-2.0。2026-09 時点で GitHub の星は約4万で、ほぼ毎日公開されている）：背景のサーバが端末を持ち、サイドバーにエージェントごとの状態（working / blocked / done / idle）を出す。状態は、画面の照合と公式のフックから取る。
- **cmux**（Ghostty をもとにした macOS の端末）：縦のタブと、エージェントが待っているときの通知（ペインの枠、未読の印）を持ち、Claude Code のフックを取り込む。

どちらも「並行するエージェントのうち、どれが待っているか」は示すが、次の点は持たない。これが whatnext を作り続ける理由である。

- **2種類の依存（利用者が結ぶ待ち先と、プロセスの親子から導く起動された行）を、リポジトリを跨いで組めること。** 利用者はリポジトリを跨ぐ待ち先を日に数回結び、オーケストレーションも日常的に行う（2026-10-26）。
- セッションに付くメモ。
- セッションに紐づき、端末を閉じても残る作業台。
- 段の判定を `--json` の構造化された値だけで行うこと（[ADR-0001](adr/0001-read-state-only-from-agents-json.md)）。画面の照合は Claude Code の見た目が変わると外れうるが、一度でも外した推薦は使われなくなる。

利用者は、どの道具もある程度使ったうえで、「次に何をやるか」の判断には whatnext の一覧に満足しており、不満は作業台の使い勝手にあった。herdr や cmux の表示で足りるようになっていないかは、見続ける。
