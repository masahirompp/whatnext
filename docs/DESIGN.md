# whatnext の設計

whatnext を**どう実現するか**（仕組み）を書く。**何を実現するか**（利用者から観測できる振る舞い、受け入れシナリオ、Out of Scope）は [PRODUCT.md](PRODUCT.md) にある。
境界は CLAUDE.md の自律判断の層1（内部設計）と層2（観測可能な挙動）で引く。PRODUCT.md の側を変えるには人間の判断が要り、このファイルの側は AI が変えて `decision-log` の issue に残す。
2つのファイルの間は、節の番号ではなく見出しの名前で参照する。

## 技術と依存

- Node で作る。描画とキー入力は自前で行い、Ink は使わない（「描画とキー入力」）。
- 本体が依存するコマンドは `claude`、`git`、`tmux` だけで（tmux は作業台のために必須。専用のサーバで使い、利用者の設定には触れない）、URL やエディタを開くときに OS の `open` を、起動したセッションのフックが値を送るときに `curl` を、作業台で動いているもののコマンド行を引くときと、起動された行の起動元を引くとき（プロセス表と、会話の外の MCP サーバが起動した行の環境変数 `MCP_CALLER_PID`）に `ps` を使う（[ADR-0008](adr/0008-dependencies-and-contact-points-with-tmux.md)、[ADR-0019](adr/0019-derive-spawned-rows-from-the-process-table.md)）。任意の依存として、作業ディレクトリの候補を増やすためだけに `ghq` を、行に PR を出し、その PR を開くためだけに `gh` を、あれば使う。
- 段を決める状態は `claude agents --json --all` からだけ読む（[ADR-0001](adr/0001-read-state-only-from-agents-json.md)）。アカウントの Usage はセッションの状態ではないので、別に `claude -p "/usage"` から読む（[PRODUCT.md](PRODUCT.md)「Usage の表示」を参照）。
- whatnext が起動したセッションからは、フックのイベントと OTel も受ける（「フックの受信」「OTel の受信」と [ADR-0009](adr/0009-receive-hooks-and-otel-from-launched-sessions.md) を参照）。フックで取れない値は、Claude Code がセッションごとに残す会話記録から補う（「会話記録の読み取り」と [ADR-0011](adr/0011-fill-in-from-transcripts-when-hooks-are-missing.md) を参照）。フック、OTel、会話記録の値は、行の一言と列の表示（CTX、AGE の起点）にだけ使い、段の判定には使わない。どの機能をどの入力から取るかは「機能ごとの入力の出どころ」にまとめる。
- `--digest` で起動したときだけ、`n` で起動するセッションに、whatnext が配るダイジェストの mod（関数フックのプラグイン。Claude Code の早期公開版の API）を `--plugin-dir` で付け、ダイジェストと会話リンクを受ける（「ダイジェストの mod」「ダイジェストの受信」と [ADR-0022](adr/0022-ship-a-digest-mod-for-launched-sessions.md)）。依存するコマンドは増えない。

## モジュールの境界

コードを次の7つのモジュールに分ける。
境界は、テストで偽物を差し込む場所に合わせる。外部（`claude`、`git`、`gh`、`tmux`、`open`、`ps`、時計、ファイル）に触れるのは入力、状態のファイル、tmux、cli の4つだけにし、段と並び、画面の組み立て、操作は、外部を引数で受け取る。
こうすると、判定と組み立ては固定データで単体として確かめられ、外部に触れる部分は偽の claude や専用の tmux で通しとして確かめられる（「確かめ方」）。

依存は cli → 操作 → (段と並び、画面の組み立て、入力、状態のファイル、tmux) の一方向にし、矢印の先から元を参照しない。
段と並びと画面の組み立ては、ほかのモジュールに依存しない。

| モジュール | 受け取るもの | 返すもの、行うこと |
|---|---|---|
| 段と並び | `--json` の行、メモと待ち先の関係、起動された行と起動元の関係、触った時刻（attach した時刻、なければ初めて見た時刻）と attach した時刻、区切り（元のリポジトリの根）、補う値（一言、CTX）、作った時刻、今の時刻 | 段の判定と、行の並び（リポジトリの区切りと、待ち先と起動された行の入れ子）。純粋な関数 |
| 入力 | `claude agents --json --all`、フックと OTel の受け口、会話記録、`claude -p "/usage"`、`git` と `gh`、`ps` のプロセス表 | 1回の更新の観測をまとめたもの（行、補う値、場所、Usage、pid から親の pid を引く表）。取得の失敗は観測の一部として返す |
| 状態のファイル | メモと待ち先の関係、attach した時刻と初めて見た時刻 | `state.json` の読み書き（「状態のファイルに書くもの」） |
| 画面の組み立て | 並んだ行、カーソル、スクロールの位置、端末の幅と高さ、下に出す知らせ | 画面に書く文字列（幅の計算、切り詰め、色）。純粋な関数 |
| 操作 | キー入力、tmux からの知らせ、更新の結果、時刻 | 一覧の状態の遷移（カーソルの追従、メニュー、入力欄、`Ctrl+X` の2回押し、確認）と、外部に頼む作業（attach、起動、停止、削除、作業台の操作）の指示 |
| tmux | 操作からの指示 | 専用のサーバ、attach、作業台と作業台の画面、キーの割り当て、ステータス行、Ghostty の分割とタブ（「一覧と作業台の仕組み」「作業台の画面の仕組み」） |
| cli | 引数、環境変数 | 起動の振り分け（一覧、`whatnext workbench`、`--help`、知らないオプション）、2つ目の起動と版の違いの扱い |

入力（起動元の導き方と場所の問い合わせを除く）、tmux（attach している間のキーの表を除く）、段の判定、文字の幅と色は `lib/` に置く（[ADR-0021](adr/0021-promote-leaf-modules-to-lib.md)。契約は [lib/](lib/README.md)）。`lib/` は契約を通して使う。置き場所は次のとおり。

| モジュール | 置き場所 |
|---|---|
| 段と並び | `src/model/`（待ちの段 `waits.ts`、区切りと木と並び `layout.ts`、`f` のメニューと削除の巻き込み `relations.ts`、カーソル `cursor.ts`） |
| 入力 | `lib/input/` と `src/input/`（起動元の導き方 `spawners.ts`、場所の問い合わせ `where.ts`、1回の更新の観測 `observe.ts`、ダイジェストの受け取り `digest.ts`） |
| 状態のファイル | `src/state/` |
| 画面の組み立て | `src/screen/` |
| 操作 | `src/ops/`（一覧の状態の遷移と外部に頼む作業 `app.ts`、口 `ports.ts`、attach している間のキーの表 `keys.ts`、cli と共有する名前 `names.ts`、候補の絞り込み `filter.ts`） |
| tmux | `lib/tmux/` |
| cli | `src/cli.ts` と `src/cli/`（ランチャー `launch.ts`、一覧の役 `list.ts`、`whatnext workbench` `workbench.ts`、案内のプログラム `guide.ts`） |

- ダイジェストの mod（`mod/`）は、この7つのモジュールの外にある。Claude Code の中の別の実行環境で動き、whatnext のコードを import せず、whatnext も mod のコードを import しない。接点は、mod の置き場所（`src/cli/env.ts` の `modDir`）と、受け口に送る本文の形（「ダイジェストの受信」）だけである。
- 段と並びと画面の組み立ては、昇格した部品（`lib/text`）のほかに依存しない。操作は cli に依存しない。専用サーバのオプションの名前（`@wn_main_tty` など）と案内の中身の形は、cli と操作の両方が使うので、操作の側（`src/ops/names.ts`）に置き、cli が import する。
- 作業台の制御（作業台を作る、作業台の画面の追従、案内、Ghostty の分割とタブの呼び出し）は、一覧の状態と同じ `src/ops/app.ts` にある。どちらも、カーソルと whatnext の画面が映しているものから決まるため、分けると状態を二重に持つことになる。
- 案内のプログラムは、何を出すかを専用サーバのオプション `@wn_guide`（JSON）から読む。一覧の役が書き、案内のプログラムは 0.3 秒ごとに読み直す（#275）。一覧から案内にシグナルで知らせることはしない。案内の pid をオプションに置くと、案内が終わったあとにその pid が別のプロセスに使い回されたとき、SIGUSR2 でそのプロセスを終わらせうるため（#312）。案内のプログラムは `WHATNEXT_ROLE=guide` で起動する（利用者向けのサブコマンドを増やさないため）。

- 段と並びと画面の組み立ては、受け取る行の型を自分で宣言し、ほかのモジュールの型を import しない。操作が、入力の返す行と段と並びの返す組を、画面の組み立ての行の形に移し替える。
- 外部のコマンドを動かす小さな口（`lib/input/exec.ts` の `run`）は入力に置き、tmux と cli も使う。tmux から入力への依存はこの口だけである。
- 操作は外部に頼む作業を `src/ops/ports.ts` の口（`Ports`）越しに頼む。cli が本物を差し込み、テストは偽の claude と専用の tmux で通しとして確かめる。
- attach している間のキーの表は一覧の側に置き、tmux の設定に引数で渡す。操作が一覧に戻ってから処理する頼みごとの列挙にも使う。
- 作業台の画面の案内を描くプログラム（`src/cli/guide.ts`）は、案内のセッションの中で動く起動の口なので cli に置く。

テストから外部を差し替える口は、環境変数（`WHATNEXT_TMUX_SOCKET`、`WHATNEXT_PORT`（mod には `WHATNEXT_DIGEST_PORT` で渡る）、`XDG_STATE_HOME`、`CLAUDE_CONFIG_DIR`、偽のコマンドを前に置いた `PATH`）にする。
`WHATNEXT_DEBUG_LOG` があるときだけ、一覧のプロセスは attach、異常終了などの出来事をそのファイルに書く。テストが失敗の原因を追うための口で、利用者の環境では何も書かない（[ADR-0016](adr/0016-persist-holds-and-waits-in-a-state-file.md) の状態のファイルのほかに書かない方針を保つ）。
利用者の whatnext と同じマシンでテストを流しても、互いに触れないようにするため。
一覧の自動の更新の間隔と、Usage を取り直す最短の間隔（どちらも既定は 60 秒）は、`WHATNEXT_REFRESH_MS` と `WHATNEXT_USAGE_MIN_MS`（ミリ秒）で短くできる。画面の通しが 60 秒を実時間で待たないための口で、起動引数や `--help` には出さない。数でない値と 0 以下の値は既定にする。起動の口が読み、一覧のペインに渡し、一覧が操作に `Ports` で渡す（#348）。

境界は実装の中で見直してよい。見直したら、この節を直し、`decision-log` の issue に残す。

## 描画とキー入力

一覧は、画面の描画もキー入力の解釈も自前で行い、Ink（React の端末 UI）を使わない。
一覧が話す相手の端末は常に専用の tmux（`tmux-256color`）なので、端末ごとの違いを吸収する価値が小さい。
落ちてもペインごと消えるので、終わるときに端末を戻す処理も要らない。
行の配列（列の幅、切り詰め、スクロールの窓）はもともと自前で作っていて、React と Yoga の役目はほとんどなかった。
外すと依存と罠が減る。実行時の依存パッケージは 40 から 8 に減った。メモリの差は小さい（Node 24.16.0 の RSS。利用者のセッション5件の一覧を出して15〜35秒後、各1回の観測で、Ink を使った一覧は約 147MB、Ink を外した一覧は約 126MB。約 21MB の差に対して、大半は Ink と React 以外（会話記録の読み取りなど）が占める）。
実装の罠は working-with-the-terminal スキルにある。

- **描画**：行の配列を文字列にし、画面全体を1回の `write` で、同期出力（`\e[?2026h` … `\e[?2026l`）で囲んで書き直す。消してから描くのではなく、左上から上書きし、各行の末尾を `\e[K` で、残りの行を `\e[J` で消す。tmux は同期出力をペインの単位で扱うので、描きかけの画面は見えない。
- **大きさの変化**：SIGWINCH を受けて描き直す。ヘッダを含むすべての行を端末の幅で切る。1行でも幅を超えると tmux が折り返し、画面全体が1行上にずれる。
- **キー入力**：Node 標準の `readline.emitKeypressEvents(stdin, {escapeCodeTimeout: 30})` で受ける（第2引数に interface の代わりに素のオブジェクトを渡す、くだけた渡し方）。既定では Esc 単独のキーが 500ms 遅れるが、この設定で約 30ms になる。
- **貼り付け**：bracketed paste（`\e[?2004h`）を有効にし、`paste-start` と `paste-end` の間に届いた文字をためて、1回の入力として扱う。中身は1文字ずつ `keypress` で届く。
- **kitty 形式（CSI-u）**：解釈しない。専用サーバは `extended-keys on` だが、tmux はアプリが求めたときだけ CSI-u を送り、求めなければ従来の形で送る（`Ctrl+X` は `\x18` で届いた）。一覧は Shift+Enter のような、CSI-u でしか区別できないキーを使わない。
- **1行の入力欄**：文字を足すことと、Backspace で書記素を1つ消すことだけで足りる。
- **続けて届いたキー**：1つの塊で届いた複数のキーも、`keypress` が1つずつ順に出す。状態はふつうの変数に持つので、前のキーでの変更を次のキーが読める。描画は `setImmediate` でまとめ、キーの数だけ描かない。

### 退けた案と予備

- **Ink を使い続ける**：上に書いた理由で外した。外すための条件（Esc が遅れない、貼り付けが1回で届く、日本語を入れて Backspace で消せる、`↓` を押しっぱなしにしても行き過ぎない、大きさを変えると描き直す、ちらつかない）は、外す前の試作で6つとも満たした。ちらつきは利用者が目で見て確かめた。試作は `proto/cycle-6-no-ink` タグにある。
- **`@earendil-works/pi-tui` の `StdinBuffer` と `keys`**（pi のコーディングエージェントの TUI。MIT。旧名 `@mariozechner/pi-tui`）：予備。貼り付けを1回で出し、分かれて届いた制御列をつなぎ、Esc は約 14ms、kitty 形式も解釈した。ただしパッケージは TUI 全体（2.8MB、ネイティブのモジュールを含む）で、`exports` がなく、版の進みも速い（4か月で 0.73 → 0.87、scope も変わった）。Node 標準で困ったとき（CSI-u が届く、貼り付けに不具合が出る）に、2つのファイル（約1500行、外部に依存しない）を MIT の表示付きで写して使う。
- **`kitty-keyboard`**：採らない。貼り付けを扱わず、ゲーム向け（keyup と押しっぱなしの追跡）である。

## 機能ごとの入力の出どころ

凡例：主＝主に使う、補＝主から取れないときに使う、補2＝補からも取れないときに使う。

- フックと OTel は、whatnext が `n` で起動したセッションにだけ届く。外で起動したセッションと対話セッションでは補から取り、補のない行（CTX）は `-` にする。
- 補を使うのは、項目ごとに「今のターンのフックの値がないとき」である。セッション単位で切り替えると、ターンの途中で whatnext を終了して起動し直したときに、稼働中の一言が次のターンまで出なくなる。
- 「今のターン」の境は、フックの指示（`UserPromptSubmit`）の時刻で引く。フックの値は、その時刻以降のものだけを今のターンとみなす。会話記録の値は、その指示の行の時刻がフックの指示の時刻の2秒前以降のときだけ使う。フックの時刻は whatnext が受け取った時刻、会話記録の時刻は行の `timestamp` なので、同じ指示でも少しずれる。許容を広げると、すぐに次の指示を送ったときに前のターンの値が混ざり、PRODUCT.md「一覧の表示」の「前のターンの一言は出さない」に反する。フックの指示がない行（外で起動したセッションなど）は、会話記録の最後の指示を今のターンの始まりとする（#267）。タスクの通知など、指示でない `prompt` の `UserPromptSubmit` も、その時刻を境にする。指示には数えないので一言は前の指示のままだが、通知で始まったのも新しいターンで、前のターンの質問や断った権限を今のターンの値として出さない（#361）。会話記録も通知の行を指示に数えないので、会話記録の最後の指示は境より前の行になり、2秒の許容に入らない。フックが通知の `UserPromptSubmit` を受けたターンでは、会話記録の値を使わない。フックの値がない行（外で起動したセッション、whatnext を起動し直した直後）では、会話記録の読み取りが同じ境を引く。ターンを始めた通知の行（`turnOrigin` が `task_notification`）で、指示は前のまま残し、前のターンの断った道具、質問、失敗、最後の応答を消す。通知のターンが本文の応答なしで終われば、一言は何も出ない。記録にだけ残ってターンを始めなかった通知の行（`queueTranscriptOnly: true`）は境にしない。境にすると、ターンが始まっていないのに、返し終えた応答の一言が消える（#387）。
- 会話記録で「断った」とみなすのは、`is_error` が `true` で、本文が `The user doesn't want to proceed with this tool use.` で始まる文字列の `tool_result` だけである。文言を含むかどうかで見ると、その文言が書かれたファイルを読んだ結果にも当たり、中断していないターンに `Declined:` が出る（#387。行の形は claude-code-behavior.md「会話記録」）。
- 権限待ちの一言と `Declined:` の「対象」は、道具の入力の `command`、`file_path`、`notebook_path`、`path`、`url`、`pattern`、`query`、`skill`、`description`、`prompt` の順に、最初の空でない文字列を取る。どれもなければ入力の最初の文字列の値を取り、それもなければ道具の名前だけを出す。MCP の道具などは決めた項目を持たないが、何かしらの値が見えれば、attach する前に何を求めているかの手がかりになる（#266）。
- 1つの行に主が2つあるときは、どちらかが当たれば成り立つ。

## 起動元の引き方

起動された行の起動元を OS のプロセス表から導く判断は [ADR-0019](adr/0019-derive-spawned-rows-from-the-process-table.md) にある。

- 更新のたびに `ps -A -o pid=,ppid=` を1回動かしてプロセス表を読む（読めなければ空の表として扱う）。`pid` を持つ各行について親をたどり、最初に当たった `--json` の別の行を起動元とする。表の読み取りは昇格した入力の部品（`lib/input/procs.ts` の `readParents`）にある。起動元の導き方は `src/input/spawners.ts` にある。
- `background` の行は起動された行にしない。祖先は Claude Code の常駐プロセスで、今の Claude Code ではほかの行に当たらない。当たったとしても、起動された行として扱うと、attach と削除の扱いが食い違う。
- 前回の関係を持ち越す場面が2つある。持ち越すのはメモリの中の表だけで、状態のファイルには書かない。
  - 表に `pid` がない行（`--json` と `ps` を読む間に終わった行、表が読めなかった回の行）は、起動元がまだ行に残っていれば持ち越す。持ち越さないと、その1回だけ起動された行がトップレベルに出て、入れ子がちらつく。
  - 祖先をたどっても行に当たらない行は、起動元の行がこの回の `--json` でまだ `pid` を持っていれば持ち越す。読む間に起動元のプロセスが終わったときは、次の回に起動元の行の `pid` が消えるので、そこで終わる（止めた起動元の下に残り続けない）。間のシェルだけが終わって親が pid 1 に付け替わったときは、起動元が動いている間は持ち越し続ける。その行を起動したのは起動元なので、入れ子のままにする。
  - 表が読めなかった回に初めて出た行は、前回の関係がないので、その回だけトップレベルに出る。
- 祖先をたどっても行に当たらない `interactive` の行は、そのプロセスの環境変数 `MCP_CALLER_PID` を読む。値が `--json` の別の行の `pid` と一致すれば、その行を起動元とする（会話の外で動く MCP サーバが起動した行。PRODUCT.md「依存（待ち先と起動された行）」、#273）。祖先から分かる行は読まない。
  - 環境変数は `ps -E -ww -o pid=,command= -p <pid>,…` で、該当する行の pid だけをまとめて1回読む（macOS では、同じ利用者のプロセスなら読めることを確かめた。Linux なら `/proc/<pid>/environ`）。`ps -E` の出力はコマンド行と環境変数が空白でつながるので、` MCP_CALLER_PID=<数字>` の語を探す。プロンプトの文字列に同じ語が入っていると取り違えうるが、一致する `--json` の行がなければ使わないので、外れても入れ子が1つ増えるだけで、利用者の操作には効かない。
  - 読めなかった、値がない、一致しないときは、今までどおりトップレベルに `(tty)` で出す。読んだ値は、その行が `--json` から消えるまでメモリに持ち、毎回は読み直さない（環境変数はプロセスの生きている間に変わらない）。
  - 値を入れるのは利用者の MCP サーバで、値の出どころは MCP の設定の `headersHelper` の `$PPID` である。`headersHelper` は Claude Code がセッションの接続のたびに実行し、`$PPID` はそのセッションの `claude` の pid（`--bg` なら `claude bg-spare`）で、`--json` の `pid` と一致した（2.1.310。#273）。
- 最初に当たった行が一覧に出ていない（対象外の）ときも、起動された行として扱い、トップレベルに `(sub)` を添えて出す。その先の祖先はたどらない。起動元が一覧に出れば、その下に入る。
- 起動元の関係は、段と並びの中で入れ子を導くためだけに使い、待ちの段には使わない（PRODUCT.md「依存（待ち先と起動された行）」）。
- 起動された行には待ち先もメモも結ばない（起動された行はカーソルで選べないので、`f` も `e` も届かない。`f` のメニューにも並べない）。待ち先は1つの待ち元にしか結べないので、2種類の関係を合わせても、各行の親は1つだけになり、一覧は木になる。起動された行と分かった行に結ばれた関係（状態のファイルから読んだもの、起動元が分かる前に結んだもの）は外す。注釈を付けた行を起動された行にしない例外は置かない（#254）。
- カーソルは起動された行に置かない。`↑` `↓` で動く並び、起動したときの行、行が消えたときに選ぶ隣の行のどれも、起動された行を除いた並びから選ぶ。選んでいた行が更新で起動された行に変わったときも、消えたときと同じに隣の行へ移る。画面の組み立てでは、画面の各行を、それを見せる役の選べる行に付ける（区切りの中では直前の選べる行、区切りの頭はその区切りの最初の選べる行、選べる行のない区切りは直前の区切りの最後の選べる行、なければ次の区切りの最初の選べる行）。選んだ行に付く範囲を、窓に収まるときだけまとめて入れる。収まらないときは選んだ行の塊を優先する。`<通し番号>/<総数>` には起動された行を数えず、選べる行がなければ出さない。
- `--json` の値から段を決める規則には使わない。起動された行は段を変えないので、[ADR-0001](adr/0001-read-state-only-from-agents-json.md) の「状態は `--json` からだけ読む」は変わらない。
- 作業台の `⚙` も `ps -A` を読むが（tmux のモジュール）、まとめない。モジュールの境界をまたいで表を渡す口が要り、`ps` 1回の費用は小さい。
- stdio の MCP サーバは起動元の `claude` の子プロセスなので、祖先をたどれば拾える（[claude-code-behavior.md](claude-code-behavior.md)「起動された `claude -p` のプロセスの祖先」）。HTTP で待ち受ける MCP サーバや、常駐のデーモンを経由する起動は、祖先に起動元が出ないので拾えない。これらは、上の `MCP_CALLER_PID` があるときだけ引ける。

## AGE の起点の取り方

- `--json` の `startedAt` は、`claude -r` で再開すると更新され、`claude stop` でも少しずれるので、作った時刻の代わりにならない。会話記録の、`timestamp` を持つ最初の行の時刻を作った時刻とする（`lib/input` の `createdAt`。先頭の数行には時刻のない行（`mode`、`permission-mode` など）が来ることがある）。会話記録がまだなければ、状態のファイルにある初めて見た時刻で補う。両方あるときは早いほうを採る。開いてしばらく指示を送らなかった対話セッションのように、会話記録が初めて見たあとにできることがあり、会話記録の時刻を優先すると、会話記録ができた更新で AGE が縮む。作った時刻は変わらないので、一度読めたら読み直さない。

## Usage の取得

- 取得には `claude -p "/usage" --no-session-persistence --output-format json` を使う。モデルを呼ばないので rate limit を消費しない。`--no-session-persistence` を付けないと、呼ぶたびに会話ファイルが残る。プロジェクトの設定や hook を拾わないよう、一時ディレクトリで実行する。
- `/usage` の結果は人間向けの文字列なので、`Current <枠>: <N>% used · resets <時刻>` の行を読む。取得に失敗したとき、または読める行が1つもないときは、前に取れた値を出したままにする。一度も取れていなければ Usage を出さない。エラーは示さず、一覧のほかの動作は変えない。

## フックの受信

- `n` で起動するセッションには、`--settings` の `hooks` で、`UserPromptSubmit`、`Stop`、`StopFailure`、`PermissionRequest`、`PreToolUse`（`AskUserQuestion` だけ）のフックを付ける。受け口を開けていないときは付けない（「OTel の受信」）。利用者自身の設定にあるフックは上書きされず、併せて動く（[claude-code-behavior.md](claude-code-behavior.md)）。
- フックの種類は `command` にし、コマンドは `curl -s -m 1 -o /dev/null --data-binary @- http://127.0.0.1:14318/v1/hooks; exit 0` とする。フックの入力を OTel と同じ受け口に送り、送れなくても何も出力せずに終了コード 0 で終わる。こうすると、whatnext を終了している間もセッションの画面にエラーが出ず、`PermissionRequest` に許可や拒否の判断を返すこともない（[ADR-0003](adr/0003-no-input-injection-or-proxy-response.md)）。コマンドに whatnext の置き場所を書き込まないので、whatnext を入れ直しても、それ以前に起動したセッションのフックはそのまま届く。
- `http` のフックは使わない。受け口が閉じていると、セッションの画面に `Stop hook error: connect ECONNREFUSED` を出す。sandbox のプロキシや組織の設定（`allowedHttpHookUrls`）の影響も受ける。
- 受けた値はメモリにだけ持つ（[ADR-0002](adr/0002-no-writes-no-persistent-state.md)）。whatnext を終了している間に発火したフックは失われる。端末のウィンドウを閉じているだけなら、受け口は開いたままで失われない。起動し直した直後の一言は、会話記録で補う（「会話記録の読み取り」）。
- 受けた値の使い道は、行の一言である。
- 中断したターン（権限の確認で `No` を選んだときなど）では `Stop` が発火しない。その行の一言は会話記録で補う。

## OTel の受信

- `n` で起動するセッションには、`--settings` の `env` で OTel の設定を付ける。送信先は、whatnext が `127.0.0.1` で開く受け口にする。metrics は受けない（COST の列のためだけに受けていた）。起動したシェルの環境変数は `--bg` のセッションに届かないので、`--settings` を使う（[claude-code-behavior.md](claude-code-behavior.md)）。
- whatnext は起動している間だけ受け口を開き、受けた値はメモリにだけ持つ（[ADR-0002](adr/0002-no-writes-no-persistent-state.md)）。常駐する保存先やメトリクス基盤は置かない。
- 受け口のポートは `127.0.0.1:14318` に固定する。利用者が既存のコレクタを既定の 4318 で動かしていてもぶつからないようにする。**whatnext は同時に1つだけ動かす。** 専用の tmux サーバに一覧がすでにあれば、新しく動かさずにその一覧につなぐ（「一覧と作業台の仕組み」）。それでも受け口を別の whatnext（サーバ名の違う版など）が開いているときは、そのことを英語で示して終了する（終了コード 1）。2つ目の whatnext は受け口を開けず、一言も出さずに黙って動くことになるため。別の whatnext かどうかは、受け口に `GET /v1/whatnext` を送って確かめる。応答は `{"app":"whatnext"}` とし、受ける側は素の文字列の応答も whatnext とみなす。版の違う whatnext が動いていても、二重起動を正しく判定するため。whatnext 以外のプログラムがポートを使っているときは、受け口を開かずに動き、`n` で起動するセッションにもフックと OTel を付けない。付けると、そのセッションは生きている間ずっと、指示と最後の応答の全文を、ポートを使っている別のプログラムに送り続ける。こうして起動したセッションは、外で起動したセッションと同じ扱いになり（一言と待機時間は会話記録で補い、CTX は `-`）、あとで whatnext が受け口を開けても変わらない。エラーは示さない。例外は `--digest` で起動したときで、一覧の右の欄の「ダイジェストがない」の文言の代わりに理由（`Digests are off: port <ポート> is used by another program.` など）を出す（「ダイジェストの受信」）。
- 受けた値の使い道は、CTX の列だけである。
- OTel は常に受け、オプトインにはしない。受け口をフックと共用しているので、オプトインにしても減る仕組みがなく、起動時のオプションが1つ増えるだけになる。
- whatnext を終了して起動し直した直後は、CTX は次のターンまで空欄になる（logs は再送されない）。
- whatnext の外で起動したセッションと対話セッションは OTel を送らないので、CTX は `-` になる。User Story 12 のうち、この列だけは例外になる。会話記録の `message.usage` で補う案は採らない（[ADR-0011](adr/0011-fill-in-from-transcripts-when-hooks-are-missing.md)）。空欄が困るようになったら、利用者が `~/.claude/settings.json` の `env` に自分で OTel の設定を書く経路を検討する。これは「書き換えを求める別ツールも前提にしない」（[ADR-0002](adr/0002-no-writes-no-persistent-state.md)）を「利用者が任意で設定すれば値が出る」に緩める判断になる。この経路で `--bg` に届くかは未確認（[claude-code-behavior.md](claude-code-behavior.md)）。

## ダイジェストの mod

判断は [ADR-0022](adr/0022-ship-a-digest-mod-for-launched-sessions.md) にある。観測できる振る舞いは [PRODUCT.md](PRODUCT.md)「ダイジェスト（`--digest`）」にある。

- mod はリポジトリの根の `mod/` にあり、`.claude-plugin/plugin.json`、`hooks/hooks.json`、`hooks/register.tsx`（イベントとペイン）、`hooks/digest.ts`（ダイジェストを作る指示と、送る本文）、`hooks/links.ts`（会話リンクを拾う規則）、`types/index.d.ts`（`$.state` の型）からなる。`.tsx` のまま npm の配布物に入れる（`package.json` の `files`）。
- 付け方：`--digest` で起動した一覧は、受け口を開けたときだけ、`n` の `claude --bg` に `--plugin-dir <パッケージの根>/mod` を足し、`--settings` の `env` に `WHATNEXT_DIGEST_PORT=<受け口のポート>` を足す（`launchSettings` の JSON に、`src/` の側で足す）。mod はこの変数を `$.env.get` で読み、なければ 14318 に送る（受け手の確かめに使う `WHATNEXT_DIGEST_TMUX` と `WHATNEXT_DIGEST_SOCKET` も同じく足す。下の「受け手の確かめ」）。`--digest` の有無は、起動の口が一覧のペインに `WHATNEXT_DIGEST=1` で渡し、一覧が専用サーバのオプション `@wn_digest` に置く。動いている一覧につなぐ `whatnext --digest` は、`@wn_digest` がなければ `@wn_digest_wanted` を置き、一覧が知らせを出す。
- ダイジェスト：`turn.complete`（本体のループだけ。サブエージェントは除く）で、前のダイジェスト、利用者の指示（`$.session.messages` の利用者の行から、GLOSSARY.md の **指示** に当たるものだけを採る。最新の10件。`hooks/digest.ts` の `instructionsOf`）、最後の応答（中断などで応答でなく終わったターンは空）を Haiku に渡し、`{"goal", "progress", "next"}` の JSON を受ける（`$.model.complete`、`effort: low`、45 秒で打ち切る）。書く言語は mod が指示から決め、入力の末尾の `## Language` で名指しする（`hooks/digest.ts` の `languageOf`）。かなを含む指示は日本語、文字がすべてラテン文字の指示は英語とし（コード、URL、スラッシュコマンドの名前は数えない）、渡す指示の多いほうを採り、同数なら新しいほうを採る。どちらでもなければ「指示と同じ言語。日本語なら日本語、英語なら英語」と例つきで頼む。前のダイジェストが別の言語なら訳させる。「the language the user writes in」とだけ頼んでいたときは、英語の指示に Haiku がロシア語で返した（実機、2026-11-21）。直したあと、英語の指示に応答が日本語で返ったセッションでも、ダイジェストは英語で届いた（2.1.330、2026-11-21、1回）。指示に当たらない行は、2.1.330 の `$.session.messages()` で観測した形で除く。道具の結果を持つ行、中断の印（本文がちょうど `[Request interrupted by user]` か `[Request interrupted by user for tool use]`）、手元で完結するコマンドの行（`<command-name>` で始まる。`/model`、`/compact`）とその出力（`<local-command-` で始まる）、compact の要約（`This session is being continued from a previous conversation that ran out of context.` で始まる）。Claude Code が利用者の役で書くほかの行も、lib の `instructionText`（会話記録の側）と同じ形で除く。バックグラウンドのタスクの通知（`<task-notification>` で始まる）、`<system-reminder>`、`!` のシェルの行とその出力（`<bash-input>` `<bash-stdout>` `<bash-stderr>`）、手元のコマンドの出力の前の `Caveat: The messages below were generated by the user while running local commands` である。0.24.0 では通知を除いておらず、日本語の指示1件のセッションで、英語の通知2件が多数決に勝ってダイジェストが英語になった（会話記録で確かめた。2.1.330、2026-11-22）。ターンを始めるスラッシュコマンドの行は `<command-message>` で始まり、`<command-name>` と `<command-args>` から `/名前 引数` を作る。mod が登録したコマンド（`wn-digest`）は会話記録では `system` の `local_command` で、`$.session.messages()` に出ない。どれも公開された形ではないので、Claude Code を更新したら見直す（checking-claude-cli）。ターンの終わりは待たせない。前の呼び出しより後に頼んだ呼び出しがあれば、前の答えは捨てる。読めなかったときは前のダイジェストを残す。
- 会話リンク：session-timeline 0.5.0 の `links.ts` と規則を移した（会話の言葉と、値が URL そのものの道具の引数から拾う。道具の出力とファイルに書く中身からは拾わない。GitHub の issue、PR、コミットは番号で1件にまとめる。Markdown のリンクの文言を名前に使う）。`turn.start`、`turn.step`、`tool.call`、`turn.complete` で拾い、`session.start` で会話の履歴から拾い直す（再開したセッション）。新しく言われたものを先に、40 件まで持つ。
- 受け手の確かめ：`turn.complete` で Haiku を呼ぶ前に、`--digest` の whatnext がダイジェストを受けているかを確かめ、受けていなければ呼ばずに何も送らない（会話リンクは拾ってペインに出す）。確かめ方は、whatnext の専用サーバの一覧のセッション `list` のオプション `@wn_digest_port`（`DIGEST_LIVE`。セッションのオプション）を `$.process.run` の `tmux -S <ソケット> show-options -t =list: -qv @wn_digest_port` で読み、値が mod の送り先のポートと同じなら受けているとみなす。一覧は、`--digest` で受け口を開けて mod を付けるときだけ、このオプションに受け口のポートを置く。whatnext を終了するとサーバごと消え、`--digest` なしで起動し直すとオプションがなく、別のポートで受けているとポートが違うので、どれも呼ばない。サーバ全体のオプションにしないのは、一覧が異常終了したとき（シグナル、SIGKILL）に、作業台で動いているもののためにサーバが残るから。一覧のセッションは一覧のプロセスと一緒に消えるので、どの終わり方でも受けていないと読める。tmux を動かせない、時間切れ（5 秒）なども呼ばない側に倒す。`--settings` の `env` に、`WHATNEXT_DIGEST_TMUX`（一覧の `PATH` で見つけた tmux の絶対パス。`claude --bg` のセッションの `PATH` に tmux があるとは限らない）と `WHATNEXT_DIGEST_SOCKET`（専用サーバのソケットの絶対パス。`#{socket_path}`。`TMUX_TMPDIR` の違いに左右されない）を足す。ソケットの変数がなければ `-L whatnext`、tmux の変数がなければ `tmux` を使う。
  - 受け口に「受けているか」を答える口を足す案は採らなかった。lib の受け口（`openReceiver`、`probe`）の応答は lib が決め、`src/` の `DigestHookStore` は本文を受けるだけで応答を変えられないので、lib の契約を変えることになる。一覧のセッションのオプションは一覧（`src/`）が置けて、版の違う whatnext が同じソケット名で起動し直しても読める。一覧のセッションは一覧のプロセスと一緒に消えるので、異常終了しても古い値は残らない。
  - 確かめたこと（2.1.330、tmux 3.8、2026-11-21、1回）：実際の `claude --bg --plugin-dir <mod>` で、専用サーバがないとき（`tmux` が 1 で終わる）、サーバはあるがオプションがないとき、オプションのポートが違うときは、デバッグのログに `$.model.complete` がなく、受け口に何も届かなかった。オプションに送り先のポートを置くと、次のターンの終わりに Haiku を呼び（約 1 秒）、ダイジェストと会話リンクが届いた。`$.process.run` の tmux は約 6ms で終わった。
- 送る：ダイジェストを作ったあと（作れなかったときも）、`$.http.fetch` で受け口の `/v1/hooks` に POST する（「ダイジェストの受信」）。送れなくても何も出さない。
- ペイン：`session.start` で `$.ui.open({id: 'whatnext-digest', title: 'Digest', columns: 46})` を呼ぶ。Claude Code は、頼まれずに開いたペインを端末が 144 桁以上（一度手で開けば 110 桁以上）のときだけ置き、110 桁以上なら右の dock、それより狭いと Claude Code の入力欄の上に置く（2.1.329 で確かめた。位置を指定する引数はない）。`/wn-digest` で開ける（`wn-` を付けるのは、組み込みのコマンドやほかの mod のコマンドとぶつけないため。`/recap` は組み込みにある）。見出しは一覧の右の欄と同じ `Goal` `Progress` `Next` `Links` で、会話リンクは8件まで出して押すと開く。
- 書き方の罠（2.1.329）：`$` を渡す関数はファイルの先頭で宣言しないと `claude plugin validate` が通らない。`tool.call` と `command.run` の hook には `.catch` が要る（付けないと validate が警告する）。mod の値は `$.state`（そのセッションの）に持ち、読み直したあとも残る。
- テスト：`mod/tests/*.test.tsx` を `npm run test:mod`（`claude plugin validate mod` と `claude plugin test mod`）で流す。Claude Code の振る舞いは、テストの `on` の hook が代わりに答える。型の確かめは、plugin-authoring スキルの型の宣言を含めた tsconfig を mod の外に置いて `tsc -p` で行う（Claude Code が mod を読み込むと、書ける置き場所の mod に `.claude-plugin/types/` と `tsconfig.json` を書く。`.gitignore` で外す）。
- 確かめたこと（2.1.329、2026-11-20）：`claude --bg --plugin-dir <mod>` で mod が動き、ターンの終わりから約 0.8 秒でダイジェストが受け口に届いた。作業場所の外の、読み取りだけのパスでも読み込めた。信頼していない作業場所では `--bg` が起動を断る（今の `n` の信頼の流れのまま）。ほかの mod のペインがあると、タブで並び、そちらが前に出たままのことがある。`◎` は tmux でも `string-width` でも1桁だった（`→` と同じ）。
- 確かめたこと（whatnext を通した通し、2.1.329、2026-11-21、1回）：`whatnext --digest` の `n` で起動したセッションに mod が付き、`--settings` の `env` で渡した `WHATNEXT_DIGEST_PORT` を mod が読み、送ったダイジェストの `session_id` が `--json` の `sessionId` と一致して、一覧の `◎` の行と右の欄に出た。権限の確認で断って中断したターンでは、ダイジェストを作らずに会話リンクだけが届いた。端末 150 桁では、mod のペインが右の dock に出たが、利用者の session-timeline のペインとタブで並び、session-timeline が前に出たままだった。開いているペインに `/wn-digest` を打っても、前には出なかった。

## ダイジェストの受信

- mod は、今の受け口（`127.0.0.1:<ポート>`）の `/v1/hooks` に、フックと同じ口で次の本文を送る。`{"hook_event_name": "WhatnextDigest", "session_id": <sessionId>, "digest": {"goal", "progress", "next"} | null, "links": [{"label", "href"}, …]}`。`digest` が `null` なのは、まだ一度もダイジェストを作れていないときである。作れなかった回は、前のダイジェストをそのまま送る。`links` は新しいものから20件まで。この形は版の違う whatnext と mod の間の契約なので、変えるときは両方を読める形にする。`WhatnextDigest` は、ダイジェストの mod（`whatnext-digest`）が送る本文であることを表す名前で、中身はダイジェストと会話リンクを別の項目に並べる（会話リンクはダイジェストの一部ではない）。
- lib の受け口（`openReceiver`）は、`/v1/hooks` の本文を `HookStore.receiveHook` に渡す。一覧は `HookStore` を継いだ `DigestHookStore`（`src/input/digest.ts`）を渡し、`hook_event_name` が `WhatnextDigest` の本文だけを手前で抜き取り、ほかは lib に渡す。lib の受け口と契約は変えない。別の口（`/v1/digest`）を足す案は、lib を直すことになるので採らなかった。
- 受けた値はメモリにだけ持つ（[ADR-0002](adr/0002-no-writes-no-persistent-state.md)）。セッションごとに最後に受けたものだけを持ち、`digest` が `null` の回は前のダイジェストを残して会話リンクだけを替える。`--json` から消えたセッションの値は、フックの値と同じく更新のたびに捨てる（`forget`）。
- `--digest` で起動して受け口を開けなかったとき（`probe` が `free` でない、または `openReceiver` が `null`）は、一覧の起動（`src/cli/list.ts` の `digestOffText`）が理由の文言を作り、`Ports.digestOff` で一覧に渡す。右の欄は、ダイジェストのない行の文言の代わりにこれを出す。文言は `probe` の答えで分ける（`other`：`is used by another program`、`whatnext`：`is used by another whatnext`、`free` なのに開けなかった：`could not open port`）。受け口を開けなければ mod を付けず、ダイジェストは届かないので、どの行でも理由が出る。シナリオ 41 の「エラーを示さない」の、`--digest` のときだけの例外である（PRODUCT.md「ダイジェスト（`--digest`）」）。
- `--digest` なしで起動した一覧は、ダイジェストの本文を捨てる（前に `--digest` で起動した whatnext の mod を付けたセッションが送ってきても、出さない）。
- 受け口にはローカルのどのプロセスからも送れるので、受けたときに制御文字（改行とタブを含む）を除き、長さを切る（Goal 200 字、Progress 400 字、Next 300 字、会話リンクの名前 200 字）。会話リンクは `http://` か `https://` で始まり空白を含まないものだけを受ける（`o` で `open` に渡すため）。
- 一覧は、受けた値を更新のとき（`Observer.observe`）に写し取り、更新と更新の間は変えない（一言と同じ）。段にも並びにも使わない。
- 右の欄の描画は画面の組み立て（`src/screen/screen.ts` の `render` と `sideLines`）が行う。端末の幅が 120 桁以上のとき、一覧を `幅 - 49` 桁で組み立て、右に ` │ ` と 46 桁の欄を並べる。最下部の欄は全幅のまま出す。メモの入力欄と一覧の下の欄（入力欄・メニュー・知らせ）は全幅で切り、どれかの行が左の幅を超えるときは、その欄（前の空行を含む）から下に右の欄を並べない。収まる欄の横には今までどおり右の欄を並べる（60秒ごとの `refreshing...` で右の欄が縮まないように）。折り返しは表示幅で数え、英数字の語の途中では折らず（語の頭で折る）、句読点と閉じ括弧を行の頭に置かない。
- 右の欄の `Links` の行は、名前を欄の幅で切ってから、埋め込みのリンク（OSC 8。`ESC ]8;;<URL> ESC \ <名前> ESC ]8;; ESC \`）で囲む（`src/screen/screen.ts` の `hyperlink`）。幅を数えたり切ったりするのは囲む前の文字列で、囲んだあとの行は数えない（`string-width` は OSC 8 を 0 桁に数えるが、lib の `stripAnsi` は OSC 8 を除かない）。URL は受け口で検査したもの（`http://` か `https://` で始まり空白を含まない。制御文字は受けたときに除いてある）で、描くときも、制御文字や空白を含むもの、http(s) でないものは囲まずに名前だけを出す。`o` のメニューは残す。
- 外側の端末に OSC 8 を送るかは、attach した claude の画面と同じく tmux が決める（「一覧と作業台の仕組み」の `terminal-features`）。一覧は端末の種類を見ずに常に囲む。tmux は送るとき、リンクに `id=tmux<n>` を足す。確かめたこと（tmux 3.8、2026-11-21）：問い合わせに答えない pty（`script`）で attach すると、`TERM` が `xterm-256color` と `xterm-ghostty` のクライアントには OSC 8 が届き、`vt220` と `screen` には届かず名前だけが出た。外側が tmux のとき（画面の通しのテスト）は、`TERM=screen` でも、tmux が問い合わせの応答から外側を tmux と知って `hyperlinks` を付け、送った。PRODUCT.md の「xterm 系と Ghostty に限る」は `terminal-features` で入れる範囲で、tmux が応答から機能を知る端末には、それ以外にも送る。

## 会話記録の読み取り

- フックで取れない一言と、AGE の起点を、Claude Code がセッションごとに残す会話記録（`~/.claude/projects/*/<sessionId>.jsonl`）から取る（[ADR-0011](adr/0011-fill-in-from-transcripts-when-hooks-are-missing.md)）。どの機能で補うかは「機能ごとの入力の出どころ」にある。
- 会話記録は `--json` に出ているセッションについてだけ、`sessionId` でファイルを探して読む。フォルダ名は `cwd` から組み立てない（worktree の中で動いたセッションは、worktree のパスに対応するフォルダに記録が残る）。`CLAUDE_CONFIG_DIR` が設定されていれば、`~/.claude` の代わりにそこを探す。
- 読むのは一覧を更新するとき（起動時、60秒ごと、更新キー、attach から戻ったとき）だけである。ファイルは数 MB になるので、前に読んだときから更新時刻が変わったファイルだけを、末尾から必要な分だけ読む。
- 読み取りに失敗したとき（ファイルがない、形式が読めない）は、補わずに続ける。エラーは示さない。段と並びは会話記録に左右されない。
- 会話記録は読むだけで、書き込まない。
- 読んだ値はメモリにだけ持つ。
- 依存する項目と実測した形式は [claude-code-behavior.md](claude-code-behavior.md) にある。

## 場所の問い合わせ

- git でない場所の区切りの根は、`cwd` の実パスにする。`/tmp/x` と `/private/tmp/x` のように同じ場所を別の書き方で持つ行を、別の区切りに分けないため（リポジトリの根は `git` が実パスで返す）。
- `gh` は、既定でないブランチを持つ行についてだけ、チェックアウトの根で `gh pr list --head <ブランチ> --state all --limit 1` を引く。一覧の更新を待たせず、同じブランチは60秒に1回まで引き直す。`gh` がないか認証していないと分かったら、それ以降は引かない。

### 失敗したとき

- `git` の問い合わせが失敗すると、場所はリポジトリでない場所として返る。前回リポジトリだった場所がそう返ったときは、1回だけ前回の場所を使う。続けて2回そう返ったら、本当にリポジトリでなくなった（worktree を消したなど）とみなす。一度の失敗で、WHERE とリポジトリの区切りが入れ替わらないようにする。

## 状態のファイルに書くもの

- メモと待ち先の関係を、`${XDG_STATE_HOME:-~/.local/state}/whatnext/state.json` に書き、起動し直しても引き継ぐ（[ADR-0016](adr/0016-persist-holds-and-waits-in-a-state-file.md)）。リポジトリの区切りの中の並びのために、セッションごとの whatnext から最後に attach した時刻と、whatnext が初めて見た時刻も書く（[ADR-0018](adr/0018-persist-view-and-attach-times-in-the-state-file.md)）。ほかの値はメモリにだけ持つ。
- `version` は 3 である。版 3 で、保留の `holds` をメモの `notes` に改め、ビューの `view` を書かなくした（ラダーのビューをやめ、ビューが1つになったため。ADR-0018 の「見直す条件」）。`version` が 1 と 2 のファイルは、`holds` の理由をメモとして読み（空文字はメモなし）、待ち先の関係と時刻（2 だけ）を読み、`view` は読み捨てる。版を上げるたびに注釈を失うと、ADR-0016 で引き継ぐと決めたものが消えるため。1〜3 のほかの版、壊れたファイル、ないファイルは、空として読む。読めなかった（ないのではなく、壊れているか知らない版の）ファイルは、利用者がメモか待ち先を変えるまで置き換えない。時刻だけで置き換えると、新しい版のファイルにあった注釈が、操作なしに消えるため。 版 1 と 2 の `holds` の値は、文字列ならそれを、`reason` の文字列を持つオブジェクトならその `reason` を、メモとして読む（#276）。
- attach した時刻は、`claude attach` を始めたときと、一覧に戻ったときに書く。戻ったときにも書くのは、attach している間に新しく見えたセッションより、離脱したセッションを上に置くため（PRODUCT.md「リポジトリの区切りと並び」）。初めて見た時刻は、一覧に初めて出たとき（`--json` に出ていて対象外でないとき）に書く。`--json` から消えたセッションの時刻は、待ち先の関係と同じく更新のたびに外す（一覧から外れただけでは外さない）。
- 形は `{"version": 3, "notes": {<sessionId>: <メモ>}, "waits": {<待ち元の sessionId>: [<待ち先の sessionId>, …]}, "seen": {<sessionId>: {"first": <ミリ秒>, "attached"?: <ミリ秒>}}}` である。
- 読んだ関係が木にならないとき（1つの待ち先を2つの待ち元が待つ、一周する、`(tty)` の行や起動された行が待ち元になっている、起動された行が待ち先になっている）は、段と並びでその関係を結ばれていないものとして扱う（PRODUCT.md「依存（待ち先と起動された行）」）。読み込んだだけではファイルを書き換えず、利用者がメモか待ち先を変えたときに、扱った関係だけを書いて置き換える。`(tty)` かどうか、起動された行かどうかは `--json` とプロセス表を読むまで分からないので、ファイルを読む時点では判定しない。
- 一覧のプロセスが起動したときに読む。書くのは、並べ直したとき、メモや待ち先を変えたとき、attach した時刻を書いたときで、そのたびに中身を作り、前に書いたものと違うときだけ書く。中身を作るのは軽い（件数はセッションの数ほど）ので、変わったかどうかを呼ぶ側で判断しない。一時ファイル（`state.json.<pid>.tmp`）に書いてから `rename` で置き換える。書けなかったときは一覧を止めず、次に変わったときにまた書く。
- `--json` から消えたセッションの関係とメモは、更新のたびにメモリから外し、続く描き直しでファイルからも消える。一覧から外れただけ（対象外になった）では外さない。`--json` を読めなかった更新ではメモリを触らないので、ファイルも変わらない。
- `WHATNEXT_TMUX_SOCKET` が既定の `whatnext` でないときは、ファイルを `state-<ソケット名>.json` に分ける。確かめるために横で動かす whatnext が、利用者のファイルを書き換えないようにする。
- 一覧のプロセスは、専用の tmux サーバに1つだけ動く（同じソケット名で `whatnext` をもう一度起動すると、動いている一覧につなぐ）。同じファイルを2つのプロセスが書き合うことはない。

## 一覧と作業台の仕組み

仕組みと退けた案は [ADR-0012](adr/0012-list-runs-inside-the-dedicated-tmux-server.md) と [ADR-0010](adr/0010-workbench-lives-inside-whatnext.md) にある。この節の「クライアント」は、とくに断らなければ whatnext の画面（一覧とセッションの画面を映す端末）のクライアントを指す。作業台の画面のクライアントは「作業台の画面の仕組み」にある。

- 一覧は、専用の tmux サーバ（`tmux -L <名前> -f /dev/null`、`TMUX` は外す）のセッション `list` の中で動く。tmux の設定は、起動してから一覧のプロセスが `source-file -`（標準入力）で流し込む。設定に一覧の pid とスクリプトのパスが要り、一覧のプロセスが起動し直すたび（異常終了のあと）に入れ直すため。`whatnext` を実行すると、`list` があればそこにつなぎ、なければ作ってつなぐ。別のクライアントがつながっていれば離す。
- 例外として、`terminal-features`（外側の端末の機能。色の `RGB` と、リンクの `hyperlinks`）は、サーバを作る `new-session` と同じ呼び出しで入れる。tmux はクライアントの端末の機能を attach した時点の値で決め、あとで変えても、つながっているクライアントには効かない。一覧が設定を流し込むより先にクライアントが attach するので、一覧から入れると最初のクライアントに効かなかった（attach 済みの Ghostty のクライアントに `hyperlinks` が付かないことで分かった）。`hyperlinks` がないと、tmux はペインの中の OSC 8 のリンクを外側の端末に送らない。
- `list` につなぐ前に、動いている一覧の版を確かめ、起動した版と違えば、一覧にそのことを示させる（[PRODUCT.md](PRODUCT.md)「終了と、端末のウィンドウを閉じたとき」）。tmux のキーとフックが呼ぶスクリプトは、動いている一覧と同じ版のものにする。同じ場所に入れ直す更新ではスクリプトだけが新しい版に置き換わり、古い一覧と新しいスクリプトが混ざって動くため。版の確かめ方と、スクリプトを版ごとに分けるやり方は実装に任せる。
- `Enter` はクライアントをセッション `<id>`（中で `claude attach <id>` が動く）に切り替え、`ctrl+q ctrl+l` と ← は `list` に切り替える。`claude attach` が終わったとき（Ctrl+Z、`/exit`、失敗）も `list` に戻す。戻すのは、そのセッションを映しているクライアントだけにする（`list-clients -t =<id>` で選び、`switch-client -c` で切り替える）。`-c` なしの `switch-client` は、映しているクライアントがないとき、別のセッションを見ているクライアントを動かす。`ctrl+q ctrl+l` で残した `claude attach` が、止めたり消したりして裏で終わると、別のセッションに入っていた画面が一覧に戻されていた（#374）。一覧は端末を手放さないので、`stty` による保存と復元や Node の内部 API への介入は使わない。
- 端末のウィンドウを閉じるとクライアントが離れるだけで、`list` の中の whatnext は動き続ける。クライアントが `<id>` を見ていたときに離れたなら、次につながったときに `list` に切り替え、そのセッションから戻ったときと同じに扱う。
- tmux は利用者から隠す。ステータス行は、attach した claude の画面のセッションと、作業台の画面にだけ出す（[PRODUCT.md](PRODUCT.md)「作業台」）。作業台の欄は、tmux が数秒ごとに作業台のペインの子のプロセスを `ps` で引いて描く。
- 専用サーバでは `focus-events` を有効にし、端末のフォーカスのイベントを中のアプリに渡す。whatnext を挟まないときと同じに届けるため（[ADR-0010](adr/0010-workbench-lives-inside-whatnext.md) が tmux に求める「claude の画面の忠実な中継」）。Claude Code が何に使うかは確かめていない。
- 専用サーバは `allow-passthrough on` にする。Claude Code は tmux の中では、通知（iTerm2 の OSC 9、kitty の OSC 99、Ghostty の OSC 777）、進み具合の表示（OSC 9;4）、タブの状態、背景色の問い合わせを tmux の passthrough（`ESC Ptmux; … ESC \`）で包んで送り、tmux はこれを on のときだけ外側の端末に通す（Claude Code 2.1.310、tmux 3.8 で確かめた。#268）。端末の中に画像を出す機能も、passthrough がないと使えない。off だと、whatnext を挟んだときだけこれらが失われ、ADR-0010 が tmux に求める「claude の画面の忠実な中継」に反する。`all`（見えていないペインからも通す）にはしない。以前、理由なく off になっていたことがある。通知が実際に出る場面は再現できていないので、利用者の通知が届くようになったかは確かめていない。
- 専用サーバは `set-clipboard on` にする。作業台の画面のドラッグのコピーと、claude の `/copy` を外側の端末のクリップボードに届けるため（`/copy` が tmux の中から届くことは確かめていない）。
- `n` の信頼の確認は、クライアントをセッション `trust-<乱数>`（中で対話モードの `claude` が動く）に切り替えて出す。一覧は `~/.claude.json`（`CLAUDE_CONFIG_DIR` があればその下）を 0.5 秒ごとに読む。そのディレクトリの `hasTrustDialogAccepted` が `true` になったら、クライアントを `list` に戻してから `trust-<乱数>` を畳み、`claude --bg` をやり直す。断って `claude` が終わったときは、ペインのコマンドがクライアントを `list` に戻す。`detach-on-destroy on` なので、クライアントが見ているセッションを先に畳むと、端末ごと離れてしまう。
- 一覧の役として動くのは、`WHATNEXT_ROLE=list` があり、かつ自分のペイン（`TMUX_PANE`）が専用サーバのセッション `list` にあるときだけにする。whatnext の中で動くシェル（作業台、attach したセッションの Bash）はこの環境変数を引き継ぐ。変数だけで判断すると、そこから起動した whatnext が一覧として動き、利用者のサーバの設定を入れ直して、残した attach を畳んでしまう（実際に起きた）。
- tmux から一覧への知らせ（キーと、`client-session-changed`、`client-attached`、`client-detached`、`session-closed`、← の `pane-title-changed` のフック）は、小さな sh を `run-shell -b` で呼び、一覧のプロセスに SIGUSR2 を送るだけにする。一覧は知らせを受けたら `list-clients` を問い合わせて、戻った・入った・端末が閉じた、を自分で判断する。頼みごと（`ctrl+q ctrl+f` など、一覧に戻ってから処理するキー）は tmux のオプションに書いてから知らせる。受け口のポート（HTTP）を使わないのは、ポートを別のプログラムが使っているとき（シナリオ 41）にもキーが効くようにするため。SIGUSR1 は Node の inspector が使うので避ける。 この sh は tmux のオプションに置き、`show -gv` で読んで動かす。tmux 3.4 は、値の中の `$p` や `${s#sh-}` を `\$p`、`\${s#sh-}` にして返すので、sh が壊れて知らせが届かない（`extended-keys-format` のオプションもない）。そのため、起動の口は `tmux -V` を読み、3.5 より古ければ断る（[PRODUCT.md](PRODUCT.md)「作業台」、シナリオ 87）。3.5a と 3.6a はどちらの壊れもなく、値をそのまま返す（2026-11-22、macOS で観測。#337）。
- 残した `claude attach` は、1本あたり約 140MB のメモリを使う。本数に上限は設けず、そのセッションを止めたとき、削除したとき、whatnext を終了したときに畳む。
- attach している間のキーは、1か所の表から、tmux の割り当て、一覧に戻ってから処理する頼みごとの列挙、キーの説明（claude の画面のステータス行）を作る。表がなかったときは、キーを1つ足すのに6か所を手で触り、頼みごとの列挙の足し忘れで、キーが一覧に戻るだけで効かなかった。

## 作業台の画面の仕組み

仕組みと退けた案は [ADR-0014](adr/0014-workbench-shows-in-a-screen-the-user-opens.md) にある。

- 作業台の画面は、専用の tmux サーバの2つ目のクライアントである。`whatnext workbench` は、専用サーバの一覧が動いていることを確かめてから、専用サーバにクライアントとしてつなぐ。一覧は、どのクライアントが whatnext の画面で、どれが作業台の画面かを見分ける（見分け方は実装に任せる。クライアントの名前や tty、つなぐときに立てる印など）。一覧のクライアントを1つに限るのと同じく、作業台の画面のクライアントも1つに限り、新しくつながったら古いほうを離す。
- 作業台の画面は、whatnext の画面が映すものに合わせて `switch-client -c <作業台の画面のクライアント> -t <セッション>` で切り替える。whatnext の画面が `<id>` なら `sh-<id>`、`list` ならカーソルの行の `sh-<id>`、作業台がなければ案内を出すセッションに切り替える。案内のセッションは、作業台がないことと作ったときの場所を描き、`Enter` で作業台を作る頼みごとを一覧に渡す小さなプログラムを動かす（作り方は実装に任せる）。
- 作業台を作るとき（`ctrl+q ctrl+w`、一覧の `w`、案内の `Enter`）は、`--json` を読み直してそのセッションの `cwd` を取り、`new-session -d -s sh-<id> -c <cwd>` で作る。`ctrl+q ctrl+v` の読み直しと同じ取り方である。
- Ghostty で押した `ctrl+q ctrl+w` と一覧の `w`、`ctrl+q ctrl+t` と一覧の `t` は、作業台を作ったあと（あれば作らずに）、`osascript` で Ghostty の AppleScript を呼ぶ（[ADR-0015](adr/0015-ghostty-split-for-workbench-on-ctrl-q-ctrl-w.md)）。押したクライアント（一覧の `w` と `t` では whatnext の画面のクライアント）の `client_termname` が `ghostty` を含むときだけ呼ぶ。
  - 作業台の画面のクライアントがつながっていれば、名前（端末のタイトル）が `whatnext workbench` の Ghostty の端末を全部のタブから探して `focus` する。`focus` は、その端末のあるタブに切り替える（1.4.0 で確かめた）。どのキーで押しても、開いている作業台の画面へ移るだけで、分割とタブの間を移し替えない。タイトルは、作業台のセッション（`sh-<id>` と案内のセッション）だけで `set-titles on` にして出す。whatnext の画面のタイトルには触れない。`whatnext workbench` は終わるときに OSC 2 でタイトルを消し、古いタイトルの分割へ移らないようにする。
  - つながっていなければ、Ghostty が前面にあることを確かめ、前面のウィンドウの選ばれたタブの `focused terminal`（押した分割）を `split ... direction right` で分割する。新しい分割はいつものシェルで開き、`initial input` で ` exec <node> <cli.js> workbench` を打ち込む。`WHATNEXT_TMUX_SOCKET` と `WHATNEXT_PORT` は `environment variables` で渡す。`exec` にするので、作業台の画面が終わるとシェルごと終わり、分割が閉じる。
  - 作業台の画面で一覧に戻るキーを押したときは、whatnext の画面のクライアントの tty（`client_tty`）と同じ `tty` を持つ Ghostty の端末を探して `focus` する。Ghostty の端末の `tty` は 1.4.0 の辞書にある（1.3.1 では取れなかった）。whatnext の画面にはタイトルを付けないので、名前ではなく tty で見分ける。失敗しても何も示さず、一覧に戻る処理は続ける。
  - `t` と `ctrl+q ctrl+t` は、分割の代わりに `new tab in front window` で前面のウィンドウにタブを足す。打ち込む文字列と環境変数は分割と同じで、作業台の画面が終わるとタブが閉じ、Ghostty は隣のタブを選ぶ。
- 作業台の最後のシェルが終わって `sh-<id>` が消えるときは、作業台の画面のクライアントを先に案内のセッションへ切り替えておく。`detach-on-destroy on` なので、クライアントが見ているセッションが先に消えると、作業台の画面ごと離れてしまう（working-with-tmux スキル）。消えるセッション自身の `detach-on-destroy` が使われるので、セッションが消えてからでは間に合わない。専用サーバ全体を `remain-on-exit on` にし、`pane-died` のフックでペインが終わった時点で処理する（ほかに生きているペインがあれば閉じ、最後なら作業台の画面を案内に切り替えてからセッションを畳む）。一覧を通さないので、一覧が落ちていても動く。whatnext が作るほかのウィンドウ（`claude attach`、一覧）は `remain-on-exit off` にする。
- 案内のプログラムのペインが終わったとき（案内のプログラムが落ちたとき）は、`pane-died` のフックがセッションを畳まずにペインを起動し直す。畳むと、案内のセッションがなくなり、`whatnext workbench` がつなげず、作業台の画面を案内へ切り替えることもできなくなる（全体を `remain-on-exit on` にしていても、`pane-died` で畳めば残らない）。起動し直すのは、一覧か `whatnext workbench` が印（`@wn_guide_pane`）を付けた案内のプログラムのペインだけで、利用者が案内のセッションで分割したペインは閉じる。ただし、それがセッションの最後の生きたペインなら、閉じずに死んだまま残す（閉じると案内のセッションが消え、作業台の画面ごと離れるため）。一覧が案内を足したあとに片付ける。起動してすぐ終わるときに回り続けないよう、前の起動し直しから60秒以内に続けて終わった回を数え、続けて5回起動し直したあとにまた終わったら、死んだペインのまま残す。畳むと一覧が作り直して数え直しになり、回り続けるため。死んだペインは作業台の画面に最後の出力を映すので、落ちた理由も見える。終わったときの画面の末尾（30行）を `@wn_guide_died` に残す。案内のプログラムがなぜ終わることがあるのかは、まだ分かっていない（#311。`@wn_guide_died` はその手がかりを残すため）。
- 案内のプログラムのペインがなければ（案内のセッションを手で畳んだとき、案内のセッションで分割して案内のペインだけを閉じたときなど）、一覧が自分の版の案内で作り直す（`src/ops/guide-session.ts` の `ensureGuide`）。案内のペインは、セッションの名前ではなく印で見分ける。セッションがあっても、案内のペインがあるとは限らないため。セッションがあって案内のペインがなければ、新しいウィンドウで案内を動かし、映すウィンドウをそこへ移す。利用者が案内のセッションで分割して動かしているものは止めない。そのあと、死んだまま残った印のないペインを片付ける。印は、案内を動かすのと同じ1回の tmux の呼び出しで付ける。分けると、すぐ終わる案内が印の付く前に `pane-died` で閉じられ、作り直しが回り続ける。一覧が終わる途中と、一覧のセッションがないときは作らない（`new-session` は、サーバがなければ設定のないサーバを立ち上げてしまう）。確かめるのは、tmux からの知らせのたび（案内のセッションが消えると `session-closed` で届く）と、作業台の画面を案内へ切り替える前（追従と、作業台を畳む前）である。作業台の画面がつながったまま案内が消えると、切り替えが黙って失敗し、古い作業台を映し続けたり、最後のシェルを抜けたときに作業台の画面ごと離れたりするため。作業台の最後のシェルが終わったときの `pane-died` の後始末は一覧を通さないので、案内のセッションが消えてから一覧が作り直すまでの間か、一覧が落ちている間に最後のシェルを抜けると、作業台の画面ごと離れる（`whatnext workbench` を打ち直せば戻る）。作り直した案内には名前（`@wn_name`）がないので、一覧は同じ中身でも名前と中身を書き直す。案内の中身（`@wn_guide`）はサーバ全体のオプションなので、作り直した案内のプログラムもそのまま読める。作業台の画面のクライアントがつながったという知らせでも追従する。`whatnext workbench` がつなぐ前に送る知らせで作業台の画面の tty の変化を使い切ると、つながったあとに作業台へ切り替わらないため。`whatnext workbench` は、つなぐ前に案内のペインがなければ一覧に SIGUSR2 で知らせ、2秒待つ。それでもなければ（案内を作り直さない古い版の一覧）、自分で作る。案内は一覧と同じ版で動かしたいので、一覧に作らせるのを先にする。
- 一覧は起動したとき、前からある案内のセッション（異常終了のあと）の案内を、一覧の版で動かし直して数え直させる（`startGuide`）。前の版のまま動いていたり、起動し直しをやめて死んだまま残っていたり、印のない前の版のものだったりするため。
- `whatnext workbench` は、tmux の attach が 0 以外で終わり、かつ一覧がまだあるときは、つなげなかったとして、行を消さずに理由を標準エラーに出す（tmux の `can't find session` などのメッセージも残る）。whatnext の終了でサーバごと閉じたときも tmux は 0 以外で終わるので、一覧があるかで見分ける。シグナルで終わったとき（tmux のクライアントが止められた）は、つながったあとなので失敗にしない。Ghostty の分割かタブから起動したとき（一覧が `WHATNEXT_WORKBENCH_SPLIT=1` を渡す。名前は分割だけだったころのまま）は、`exec` で動いていて終わると分割やタブごと閉じるので、失敗したらキーを待ってから終わる。
- Ghostty の分割とタブに打ち込む文字列の `exec` は、`splitWorkbench` と `tabWorkbench` だけが付ける（lib の契約）。一覧が渡すコマンド（`workbenchCommand`）には付けない。両方が付けると ` exec exec <node> ...` になり、zsh では動くが bash では `exec: exec: not found` で失敗する（#311）。
- 打ち込む文字列がシェルでそのまま動くことは、単体テスト（`test/unit/ghostty-split.test.ts`）では bash と sh で動かして確かめる。zsh（macOS での利用者のシェル）では、実機の通しのシナリオ 58a/58b（`test/real/ghostty.test.ts`）が本物の Ghostty に打ち込んで確かめる。単体テストを zsh のない環境でも回すため。
- 作業台の画面で押した `ctrl+q` のキーは、押したクライアントが作業台の画面であることと、映している `sh-<id>` から対象のセッションを決める。`ctrl+q ctrl+l` などの「whatnext の画面を一覧に戻す」キーは、作業台の画面ではなく whatnext の画面のクライアントを切り替える。短い知らせ（`display-message`）は、押したクライアントに出す。`ctrl+q ctrl+v`（VS Code で開く）は一覧に戻らず、結果をこの知らせで示す。tmux のメニュー（`display-menu`）は使わない。
- `sh-<id>` と案内のセッションだけ、tmux の `mouse` を on にする（`mouse` はセッションごとの設定）。off のままだと、tmux のクライアントは代替画面で描くので、端末（Ghostty）はホイールを ↑↓ のキーに変えて送り、作業台の出力ではなくシェルの入力履歴が動く。on にすると、ホイールで tmux のコピーモードに入って履歴をさかのぼり、ドラッグの選択は tmux が持ち、離すとコピーする（`set-clipboard on` で端末のクリップボードに届く）。一覧と claude の画面のセッションは off のままにする。
- 作業台の画面にフォーカスが移ったとき（`client-focus-in`）、案内の場所を `--json` から読み直す。claude が worktree に入ったあと、作る前に場所を確かめられるようにする。
- 作業台の画面のステータス行は `sh-<id>` と案内のセッションにだけ出し、1行にする。claude の画面のステータス行（これも1行）とは別の書式にする。書式とキーの文言は lib の `workbenchStatusFormat` が持つ（`status-format` は strftime を通るので、`%` は `%%` と書く）。
- 異常終了のあとに `Y` で引き継いだ作業台には、`cleanupLeftovers` から `refreshWorkbenches` を呼び、名前を除くオプションを今の版の値で入れ直す。上書きするだけなので、作業台に置くオプションを減らす版では、減らしたものが引き継いだ作業台に残る。
- 端末の分割の大きさは、クライアントごとに tmux が扱う。作業台の画面が映すウィンドウは作業台の画面の大きさに合う。whatnext の画面と作業台の画面が同じセッションを映すことはないので、大きさの取り合いは起きない。

### 確かめたこと

- **claude の画面の幅の変化は問題にならない**（claude 2.1.284、tmux 3.7c）。`claude attach` は代替画面で描くので、分割と解除を繰り返してもスクロールバックに描き直しが積もらない。狭めると折り返して描き直し、戻すと元の画面に戻る。ただし利用者の statusline は、広げた直後も狭い幅で切った形のまま残り、statusline の次の再実行で直る。作業台の画面を開閉すると、whatnext の画面の幅が変わるので、同じことが起きる。
- **Ghostty の既定のキー**（1.3.1）：`cmd+d` で右に分割、`cmd+shift+d` で下に分割、`cmd+w` で分割を閉じる、`cmd+[` と `cmd+]` で前後の分割へ、`cmd+opt+矢印` でその方向の分割へ、`cmd+ctrl+矢印` で境界を動かす、`cmd+shift+enter` で分割の拡大、`cmd+shift+[` と `cmd+shift+]` で前後のタブへ、`cmd+数字` でその番号のタブへ。作業台の画面の開閉、フォーカス、幅は、これらで足りる。
- **Ghostty の AppleScript**（1.3.1）：tmux サーバから起動した `osascript` でも Ghostty を操作できる（利用者の環境では許可済みだった）。`split` の `with configuration` で `command` を渡すと、`wait after command` を false にしても、コマンドが終わったあと `Process exited. Press any key to close the terminal.` を出して分割が残る。`initial input` で `exec` を打ち込めば、終わると分割が閉じる。分割がどの tty か、シェルの入力待ちかどうかは取れない。分割の見分けには `name`（端末のタイトル）と `id` を使う。`split` には比率や大きさの引数がない。`new tab ... with configuration` は `split` と同じ設定を受け、できたタブは選ばれた状態になる（1.4.0 で確かめた）。

- **クライアントの見分け**（tmux 3.7c）：whatnext の画面と作業台の画面が、それぞれ自分の端末の tty（`tty` の出力は `#{client_tty}` と同じ形）を専用サーバのオプションに置いて見分けた。端末を閉じて開き直すと同じ tty が使い回されるので、つないだ側は、もう一方の印が自分と同じ tty なら消す。閉じて開き直したとき、2つ目の作業台の画面をつないだとき、whatnext の画面だけを閉じたときで、取り違えなかった。
- **カーソルを速く動かしたとき**：60ms 待ってまとめ、切り替えを1本の鎖で順に行うと、`Down` を3回続けても最後の行の作業台に落ち着いた。

## 未確定の前提

- **実物の `claude attach` が 0 以外で終わったときの振る舞い。** シナリオ 6 は、attach だけ失敗する偽の claude で確かめた。実物で起こす手順がない。
- **会話記録を読むときの時機。** 最後の応答の行は、Stop のフックの約2秒前に書かれていた（行の `timestamp` による。ファイルに書かれた時刻そのものは測っていない）。`--json` が `done` になるのは Stop のあとと見られるので、`done` を観測してから読めば、最後の応答は書き終わっている見込みが高い。実機で確かめた範囲では、1つ前のターンの一言が出たことはなかった。書き終わる前に読んだとしても、更新時刻が変わったファイルは次の更新で読み直すので、ずれは更新の間隔以内に収まる。
- **会話記録で補う値の細部。** 会話記録が途中で別のファイルに移る場合（`continued-in` の行を1件見た）は確かめていない。

## 確かめ方

シナリオ（[PRODUCT.md](PRODUCT.md)「受け入れシナリオ」）は、次の4つの層のどれかで確かめる。
テストは外から観測できる振る舞いだけを対象にする。

| 層 | 実行 | 中身 |
|---|---|---|
| 単体 | `npm test` | 段と並び、画面の組み立て、入力の読み取り(会話記録、フック、OTel、Usage)、状態のファイル、候補の表示名と絞り込み、引数を、固定データで確かめる |
| 画面の通し | `npm run test:e2e` | 専用の tmux、偽の claude、偽の `open` で whatnext を起動し、send-keys で操作して capture-pane で画面を読む |

| 手動 | 利用者 | マウスでの選択とコピーにもう一方の文字が混ざらないこと（25、25a）、ホイールで作業台の出力をさかのぼれること（25a） |

- GitHub Actions(`.github/workflows/ci.yml`)が、main への push と pull request ごとに、Node 22 と 24 で build、`npm run check`、`npm test` を流す。`test:e2e` は別のジョブ(`e2e`)で、Node 24 で流す。tmux 3.5 以上が要り、ランナーの Ubuntu の tmux(3.4)では断られるので、下限の版(3.5a)をソースから組み、版とランナーの Ubuntu の版(`ImageOS`)をキーにキャッシュして使う。組んだ tmux はライブラリを動的に引くので、Ubuntu の版が上がるとキャッシュが外れて組み直す(#354)。tmux の版を指定して手動でも流せる(`workflow_dispatch` の入力 `tmux`。3.5a で落ちたときに、3.8 などと比べて版の差か Linux と macOS の差かを切り分ける)。最新の版の tmux での `test:e2e` は CI では流さず、手元(macOS、Homebrew の tmux)で流す。CI に最新の版を書くと、上げ忘れで古くなるため(#337)。`test:mod` と `test:real` は claude が要るので手元で流す。
- 公開(PRODUCT.md「配布」)は、`.github/workflows/publish.yml` がタグ `v<版>` の push で行う。タグのコミットが `origin/main` の first-parent の鎖に載るか(`git rev-list --first-parent origin/main` にあるか。祖先かどうかだけを見ると、マージで取り込んだ PR のブランチの途中のコミットも通る)と、タグの版が `package.json` の `version` と一致するかを確かめ、build、`npm run check`、`npm test` を通したあとに `npm stage publish` する。npmjs.com の trusted publisher にこのファイル名を登録しているので、名前を変えたら登録も直す。判定の shell は自動のテストを持たず、変えたときは、手元の一時のリポジトリで、main のマージのコミット、main にないコミット、版の違うタグ、main に取り込まれたブランチの途中のコミットの4通りに当てて確かめる。手順は releasing-whatnext スキル。
- `npm test` はコミットごとに流す。`test:e2e` は、tmux、操作、作業台に触れたコミットで流す。`test:real` は、実機の claude との接点に触れた変更を PR に出す前と、claude を更新したあとに流す。
- `test:real` は、テスト用の一時ディレクトリ（信頼の確認を済ませたもの）、tmux のソケット、受け口のポート、状態のファイルを使い、利用者が使っている whatnext とそのセッションには触れない。起動したセッションは、終わったら `claude rm` で消す。Ghostty のシナリオは、前面に新しいウィンドウを開いて操作し、終わったら閉じる。
- 実機の応答の揺れで安定しないシナリオは、issue に起票して確かめ方を決め直す。
- 実機の通しのセッションは、利用者の `~/.claude/settings.json` の権限モードを引き継ぐ。利用者の既定が `auto` だと権限の確認が出ず、権限待ちのシナリオ（23、33、45）が成り立たない。テストの作業ディレクトリに `.claude/settings.local.json` を書き、`permissions.defaultMode` を `default` に固定する（プロジェクトの設定は利用者の設定より優先される）。
- 同じファイルに `model` を書き、`n` で起動するセッションを haiku にする（`n` はモデルを選ばない）。環境変数（`ANTHROPIC_MODEL`）で渡すと、whatnext が起こしたデーモンを通して作業場所の外のセッションにまで残りうる。`n` で起動するシナリオ（23、34、41）は、どれも応答のあとに会話記録のモデル名を確かめ、haiku と確かめられなければ以後の `n` のシナリオを止める。作業場所の `settings.local.json` の `model` は `claude --bg` のセッションに効き、優先順位は `--model` > 環境の `ANTHROPIC_MODEL` > `settings.local.json` である（2026-11-23、claude 2.1.330、#368。条件ごとの結果は claude-code-behavior.md「起動（`--bg`）」）。環境の `ANTHROPIC_MODEL` は、`--settings` の `env` と、`claude --bg` を呼んだシェルの環境で見た（呼んだ側の値は起動要求の許可リストで届く。2.1.331）。利用者のシェルの `ANTHROPIC_MODEL` はテストの環境から外す（`real-harness.ts` の `UNSET`）。これで、テストが起動するプロセスから起動要求に載る値は外せる。外せないのはデーモンの環境である。デーモンは、それを起こしたプロセスの環境を持ち続け、すべての `--bg` のセッションに渡す（#363 で見たデーモンには、一覧のプロセスの `WHATNEXT_*` が入っていた）。すでに動いているデーモンがこの変数を持っていると、値が haiku 以外ならモデル名の確かめで止まるが、haiku なら確かめは通り、設定が効いたかを見分けられない。それでも whatnext の不具合は隠れず、失うのは Claude Code の設定の解決の確かめだけなので、デーモンの環境を見て警告する段は持たない（#368）。確かめで止まったときは、デーモンの環境を `ps -E -ww -p <claude daemon run の pid>` で見て `ANTHROPIC_MODEL` を探す（失敗のメッセージにも出す）。実機の通しが `ANTHROPIC_MODEL=haiku` を付けて起動していたのは 2026-11-04 の約30分（a537ba2 から 45c3325 まで）だけである。
- 実機の通しの一覧には、利用者の本物のセッションも並ぶ。確かめるのはテストのセッションの行と、その組の中だけにする。画面全体に対して確かめると、利用者のセッション（CTX が `-` のレビュー待ちなど）や、その時に動いているものの `(sub)` の行に当たって落ちる。
- 実機の通しは、ほかに何も流さずに実行する。review-loop のように `claude -p` を起動するものを並行して流すと、行が増え、並びも変わる。流す前に、テストのセッション（`wn-real-…`）の権限の確認に答えないよう利用者に伝える。利用者が自分の画面から許可すると、権限待ちを確かめるテストが落ちる。 Ghostty のシナリオは、利用者が自分の端末から、ほかの操作をせずに流す。AI がバックグラウンドのセッションから流し、利用者がほかのウィンドウで作業していたときは、作業台の分割ができずに時間切れで3回続けて落ち、利用者の端末から単独で流すと通った（Ghostty が前面にないか、そのセッションに Ghostty の操作の許可がないためと見られる。原因は確かめていない。#298）。
- 外で起動した権限待ちのセッションの WAITING が、最初の一覧で一度だけ `-` になった（33、45。単独で流し直すと通った）。原因は確かめていない（#253）。WAITING の列を AGE に替えたので、この観察は今の画面には当たらない。

`test:e2e` はファイルを並行に流す(ワーカーの数は vitest の既定)。テストごとに一時ディレクトリ、tmux のソケット、受け口のポートを分けるので、ファイルどうしで共有するものはない。受け口のポートは `harness.ts` の `freePort` が空きを確かめてから一覧に渡すので、一覧が bind するまでの間に、別のワーカーが同じ番号を選びうる。そこで 14500〜15899 を 8 つの区画に分け、ワーカーの番号(`VITEST_POOL_ID`)で区画を決めて、その中から選ぶ。ワーカーが 8 を超えたら区画を共有する。`test:real` はファイルを直列に流す。並行に流すと、ほかのファイルが起動したセッションが一覧の行に加わるため(「確かめ方」の、実機の通しはほかに何も流さずに実行するのと同じ理由)。

画面は、確かめる欄が描き終わった形になるまで `waitFor` で待ってから読む。欄の一部の行(入力欄など)だけを待つと、ほかの行がまだ前の形のことがある。`n` の欄では、入力欄は `zq█` なのに、絞り込む前の候補が残った画面を読んで落ちた(#373。描きかけの画面を capture-pane が読んだのかは確かめていない)。ghq の候補も後から届く。そのため `n` の欄は、期待する候補の行がそろうまで待つ(`ops.test.ts` の `waitDirs`)。

### シナリオごとの作り方

- シナリオ 1、4（段の判定と行の判定）は、`--json` の出力を模した固定データで確かめる。待ちのほかの段は `--json` の行だけで決まる判定なので、固定データでも実機と同じ保証が得られる。`pid` のない `blocked` は実機で意図して作るのが難しい。`"sandbox request"` は checking-claude-cli スキルの手順で作れる。`failed` は、存在しないモデル名で `--bg` を起動すれば作れる。

## 外部 watcher（別ツール）の設計の要点

外部の出来事を監視し、必要なときにセッションを起こす別ツール。監視先ごとに作ってよい。
whatnext の側で必要な要件は、人間が起動したセッションを前提にしないこと（機械生成の `name` や `cwd` で壊れないこと）だけである。

- **起こす価値があるものだけ起こす。** セッションは利用枠を使う。flaky なテストの失敗や、見ればすぐ分かるレビュー依頼まで起こさない。この選別の良し悪しが外部 watcher の品質になる。
- **出来事が解消したら片付ける。** CI が再実行で通った、別の人がレビューを済ませた、といった場合は、外部 watcher が解消を検知して `claude stop` する。
- **同じ出来事で二度起こさない。** `--name` に出来事の識別子（Slack ならメッセージの `ts`、CI なら `ci-<repo>-<runId>` など）を埋め、起動の前に `--json --all` で同じ名前を探す。セッション一覧そのものが着手済みの台帳になる。`claude -r` でコピーが作られると `--name` が引き継がれず重複排除が崩れるので、新規の起動だけを行う。
- **plan mode で起動する。** セッションは調査だけを行い、計画を出して止まる。承認の対象が「外部の出来事についての推測」から「具体的な変更計画」に変わり、判定を誤って起動してもコードは書かれない。却下は `claude stop` で行う。未確定の前提として、計画の承認待ちで `waitingFor` に何が出るかがある。`"permission prompt"` と出るなら権限待ちの段に入るが、実際には計画を読む必要があり解除コストは大きいので、別の段に置く判定が要る。
- **プロンプトインジェクションを防ぐ。** Slack のメッセージ、PR のコメント、CI のログは信頼できない入力である。本文はデータとして囲み指示として解釈させない、対象を限る（Slack なら DM と特定のチャンネル、送信者のホワイトリスト）、`--permission-mode plan` を強制して `auto` と `bypassPermissions` を使わない、worktree の分離（`--bg` の既定）を切らない、を最低限の防御とする。
- **routine（クラウド）で作るときの制約。** routine には permission mode の選択がなく、plan mode を強制できない。含めたコネクタへの書き込みも承認なしで行われるので、コネクタを読み取りに必要なものに絞る。止まったものは whatnext に出せないので、プロンプトで「必要なコネクタや GitHub が使えなければ `PushNotification` で知らせて止まる」と書かせる（通知をタップするとそのセッションが開く）。起動しなかった実行（GitHub の接続切れ、一時停止、上限）と通知の手前で落ちた実行は拾えないので、`/schedule` で routine の状態を確かめて補う。GitHub トリガーは pull request と release だけで、CI の失敗には直接反応しない。
