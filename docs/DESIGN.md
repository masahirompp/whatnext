# whatnext の設計

<!-- last updated: cycle 9 -->

whatnext を**どう実現するか**（仕組み）を書く。**何を実現するか**（利用者から観測できる振る舞い、受け入れシナリオ、Out of Scope）は [PRODUCT.md](PRODUCT.md) にある。
境界は CLAUDE.md の自律判断の層1（内部設計）と層2（観測可能な挙動）で引く。PRODUCT.md の側を変えるには人間の判断が要り、このファイルの側は AI が変えて `decision-log` の issue に残す。
2つのファイルの間は、節の番号ではなく見出しの名前で参照する。

## 技術と依存

- Node で作る。描画とキー入力は自前で行い、Ink は使わない（「描画とキー入力」）。
- 本体が依存するコマンドは `claude`、`git`、`tmux` だけで（tmux は作業台のために必須。専用のサーバで使い、利用者の設定には触れない）、URL やエディタを開くときに OS の `open` を、起動したセッションのフックが値を送るときに `curl` を、作業台で動いているもののコマンド行を引くときと、起動された行の起動元を引くとき（プロセス表と、会話の外の MCP サーバが起動した行の環境変数 `MCP_CALLER_PID`）に `ps` を使う（[ADR-0008](adr/0008-dependencies-and-contact-points-with-tmux.md)、[ADR-0019](adr/0019-derive-spawned-rows-from-the-process-table.md)）。任意の依存として、作業ディレクトリの候補を増やすためだけに `ghq` を、行に PR を出し、その PR を開くためだけに `gh` を、あれば使う。
- 段を決める状態は `claude agents --json --all` からだけ読む（[ADR-0001](adr/0001-read-state-only-from-agents-json.md)）。アカウントの Usage はセッションの状態ではないので、別に `claude -p "/usage"` から読む（[PRODUCT.md](PRODUCT.md)「Usage の表示」を参照）。
- whatnext が起動したセッションからは、フックのイベントと OTel も受ける（「フックの受信」「OTel の受信」と [ADR-0009](adr/0009-receive-hooks-and-otel-from-launched-sessions.md) を参照）。フックで取れない値は、Claude Code がセッションごとに残す会話記録から補う（「会話記録の読み取り」と [ADR-0011](adr/0011-fill-in-from-transcripts-when-hooks-are-missing.md) を参照）。フック、OTel、会話記録の値は、行の一言、列の表示、待機時間の推定にだけ使い、段の判定には使わない。どの機能をどの入力から取るかは「機能ごとの入力の出どころ」にまとめる。

## モジュールの境界

コードを次の7つのモジュールに分ける。
境界は、テストで偽物を差し込む場所に合わせる。外部（`claude`、`git`、`gh`、`tmux`、`open`、`ps`、時計、ファイル）に触れるのは入力、状態のファイル、tmux、cli の4つだけにし、段と並び、画面の組み立て、操作は、外部を引数で受け取る。
こうすると、判定と組み立ては固定データで単体として確かめられ、外部に触れる部分は偽の claude や専用の tmux で通しとして確かめられる（「確かめ方」）。

依存は cli → 操作 → (段と並び、画面の組み立て、入力、状態のファイル、tmux) の一方向にし、矢印の先から元を参照しない。
段と並びと画面の組み立ては、ほかのモジュールに依存しない。

| モジュール | 受け取るもの | 返すもの、行うこと |
|---|---|---|
| 段と並び | `--json` の行、メモと待ち先の関係、起動された行と起動元の関係、触った時刻（attach した時刻、なければ初めて見た時刻）と attach した時刻、区切り（元のリポジトリの根）、補う値（一言、待機時間の起点、CTX）、今の時刻 | 段の判定と、行の並び（リポジトリの区切りと、待ち先と起動された行の入れ子）。純粋な関数 |
| 入力 | `claude agents --json --all`、フックと OTel の受け口、会話記録、`claude -p "/usage"`、`git` と `gh`、`ps` のプロセス表 | 1回の更新の観測をまとめたもの（行、補う値、場所、Usage、pid から親の pid を引く表）。取得の失敗は観測の一部として返す |
| 状態のファイル | メモと待ち先の関係、attach した時刻と初めて見た時刻 | `state.json` の読み書き（「状態のファイルに書くもの」） |
| 画面の組み立て | 並んだ行、カーソル、スクロールの位置、端末の幅と高さ、下に出す知らせ | 画面に書く文字列（幅の計算、切り詰め、色）。純粋な関数 |
| 操作 | キー入力、tmux からの知らせ、更新の結果、時刻 | 一覧の状態の遷移（カーソルの追従、メニュー、入力欄、`Ctrl+X` の2回押し、確認）と、外部に頼む作業（attach、起動、停止、削除、作業台の操作）の指示 |
| tmux | 操作からの指示 | 専用のサーバ、attach、作業台と作業台の画面、キーの割り当て、ステータス行、Ghostty の分割（「一覧と作業台の仕組み」「作業台の画面の仕組み」） |
| cli | 引数、環境変数 | 起動の振り分け（一覧、`whatnext workbench`、`--help`、知らないオプション）、2つ目の起動と版の違いの扱い |

サイクル8の cycle-end で、入力（起動元の導き方と場所の問い合わせを除く）、tmux（attach している間のキーの表を除く）、段の判定、文字の幅と色を `lib/` に昇格した（[ADR-0021](adr/0021-promote-leaf-modules-to-lib.md)。契約は [lib/](lib/README.md)）。`lib/` は書き直さず、契約を通して使う。ほかのモジュールはサイクル9で書き直す。サイクル8の置き場所は、段と並びが `src/ladder/`、状態のファイルが `src/state/`、画面の組み立てが `src/screen/`、操作が `src/ops/`、cli が `src/cli.ts` と `src/cli/` だった。

- 段と並びと画面の組み立ては、受け取る行の型を自分で宣言し、ほかのモジュールの型を import しない。操作が、入力の返す行と段と並びの返す組を、画面の組み立ての行の形に移し替える。
- 外部のコマンドを動かす小さな口（`lib/input/exec.ts` の `run`）は入力に置き、tmux と cli も使う。tmux から入力への依存はこの口だけである。
- 操作は外部に頼む作業を `src/ops/ports.ts` の口（`Ports`）越しに頼む。cli が本物を差し込み、テストは偽の claude と専用の tmux で通しとして確かめる。
- attach している間のキーの表は一覧の側に置き、tmux の設定に引数で渡す。操作が一覧に戻ってから処理する頼みごとの列挙にも使う。
- 作業台の画面の案内を描くプログラム（`src/cli/guide.ts`）は、案内のセッションの中で動く起動の口なので cli に置く。

テストから外部を差し替える口は、環境変数（`WHATNEXT_TMUX_SOCKET`、`WHATNEXT_PORT`、`XDG_STATE_HOME`、`CLAUDE_CONFIG_DIR`、偽のコマンドを前に置いた `PATH`）にする。
`WHATNEXT_DEBUG_LOG` があるときだけ、一覧のプロセスは attach、異常終了などの出来事をそのファイルに書く。テストが失敗の原因を追うための口で、利用者の環境では何も書かない（[ADR-0016](adr/0016-persist-holds-and-waits-in-a-state-file.md) の状態のファイルのほかに書かない方針を保つ）。
利用者の whatnext と同じマシンでテストを流しても、互いに触れないようにするため。

境界は実装の中で見直してよい。見直したら、この節を直し、`decision-log` の issue に残す。

## 描画とキー入力

一覧は、画面の描画もキー入力の解釈も自前で行い、Ink（React の端末 UI）を使わない。
一覧が話す相手の端末は常に専用の tmux（`tmux-256color`）なので、端末ごとの違いを吸収する価値が小さい。
落ちてもペインごと消えるので、終わるときに端末を戻す処理も要らない。
行の配列（列の幅、切り詰め、スクロールの窓）はもともと自前で作っていて、React と Yoga の役目はほとんどなかった。
外すと依存と罠が減る。実行時の依存パッケージは 40 から 8 に減った。メモリの差は小さい（Node 24.16.0 の RSS。利用者のセッション5件の一覧を出して15〜35秒後、各1回の観測で、Ink を使ったサイクル5の一覧は約 147MB、Ink を外したサイクル6の一覧は約 126MB。約 21MB の差に対して、大半は Ink と React 以外（会話記録の読み取りなど）が占める）。
実装の罠は working-with-the-terminal スキルにある。

- **描画**：行の配列を文字列にし、画面全体を1回の `write` で、同期出力（`\e[?2026h` … `\e[?2026l`）で囲んで書き直す。消してから描くのではなく、左上から上書きし、各行の末尾を `\e[K` で、残りの行を `\e[J` で消す。tmux は同期出力をペインの単位で扱うので、描きかけの画面は見えない。
- **大きさの変化**：SIGWINCH を受けて描き直す。ヘッダを含むすべての行を端末の幅で切る。1行でも幅を超えると tmux が折り返し、画面全体が1行上にずれる。
- **キー入力**：Node 標準の `readline.emitKeypressEvents(stdin, {escapeCodeTimeout: 30})` で受ける（第2引数に interface の代わりに素のオブジェクトを渡す、くだけた渡し方）。既定では Esc 単独のキーが 500ms 遅れるが、この設定で約 30ms になる。
- **貼り付け**：bracketed paste（`\e[?2004h`）を有効にし、`paste-start` と `paste-end` の間に届いた文字をためて、1回の入力として扱う。中身は1文字ずつ `keypress` で届く。
- **kitty 形式（CSI-u）**：解釈しない。専用サーバは `extended-keys on` だが、tmux はアプリが求めたときだけ CSI-u を送り、求めなければ従来の形で送る（`Ctrl+X` は `\x18` で届いた）。一覧は Shift+Enter のような、CSI-u でしか区別できないキーを使わない。
- **1行の入力欄**：文字を足すことと、Backspace で書記素を1つ消すことだけで足りる。
- **続けて届いたキー**：1つの塊で届いた複数のキーも、`keypress` が1つずつ順に出す。状態はふつうの変数に持つので、前のキーでの変更を次のキーが読める。描画は `setImmediate` でまとめ、キーの数だけ描かない。

### 退けた案と予備

- **Ink を使い続ける**：上に書いた理由で外した。外すための撤退の条件（Esc が遅れない、貼り付けが1回で届く、日本語を入れて Backspace で消せる、`↓` を押しっぱなしにしても行き過ぎない、大きさを変えると描き直す、ちらつかない）は、サイクル6の開始時の試作で6つとも満たした。ちらつきは利用者が目で見て確かめた。試作は `proto/cycle-6-no-ink` タグにある。
- **`@earendil-works/pi-tui` の `StdinBuffer` と `keys`**（pi のコーディングエージェントの TUI。MIT。旧名 `@mariozechner/pi-tui`）：予備。貼り付けを1回で出し、分かれて届いた制御列をつなぎ、Esc は約 14ms、kitty 形式も解釈した。ただしパッケージは TUI 全体（2.8MB、ネイティブのモジュールを含む）で、`exports` がなく、版の進みも速い（4か月で 0.73 → 0.87、scope も変わった）。Node 標準で困ったとき（CSI-u が届く、貼り付けに不具合が出る）に、2つのファイル（約1500行、外部に依存しない）を MIT の表示付きで写して使う。
- **`kitty-keyboard`**：採らない。貼り付けを扱わず、ゲーム向け（keyup と押しっぱなしの追跡）である。

## 機能ごとの入力の出どころ

凡例：主＝主に使う、補＝主から取れないときに使う、補2＝補からも取れないときに使う。

- フックと OTel は、whatnext が `n` で起動したセッションにだけ届く。外で起動したセッションと対話セッションでは補から取り、補のない行（CTX）は `-` にする。
- 補を使うのは、項目ごとに「今のターンのフックの値がないとき」である。セッション単位で切り替えると、ターンの途中で whatnext を終了して起動し直したときに、稼働中の一言が次のターンまで出なくなる。
- 「今のターン」の境は、フックの指示（`UserPromptSubmit`）の時刻で引く。フックの値は、その時刻以降のものだけを今のターンとみなす。会話記録の値は、その指示の行の時刻がフックの指示の時刻の2秒前以降のときだけ使う。フックの時刻は whatnext が受け取った時刻、会話記録の時刻は行の `timestamp` なので、同じ指示でも少しずれる。許容を広げると、すぐに次の指示を送ったときに前のターンの値が混ざり、PRODUCT.md「一覧の表示」の「前のターンの一言は出さない」に反する。フックの指示がない行（外で起動したセッションなど）は、会話記録の最後の指示を今のターンの始まりとする（サイクル8の終わりに決めた。#267）。
- 権限待ちの一言と `Declined:` の「対象」は、道具の入力の `command`、`file_path`、`notebook_path`、`path`、`url`、`pattern`、`query`、`skill`、`description`、`prompt` の順に、最初の空でない文字列を取る。どれもなければ入力の最初の文字列の値を取り、それもなければ道具の名前だけを出す。MCP の道具などは決めた項目を持たないが、何かしらの値が見えれば、attach する前に何を求めているかの手がかりになる（サイクル8の終わりに決めた。#266）。
- 1つの行に主が2つあるときは、どちらかが当たれば成り立つ。

| 機能（使い道） | `--json` | フック | 会話記録 | その他 |

## 起動元の引き方

起動された行の起動元を OS のプロセス表から導く判断は [ADR-0019](adr/0019-derive-spawned-rows-from-the-process-table.md) にある。

- 更新のたびに `ps -A -o pid=,ppid=` を1回動かしてプロセス表を読む（読めなければ空の表として扱う）。`pid` を持つ各行について親をたどり、最初に当たった `--json` の別の行を起動元とする。表の読み取りは昇格した入力の部品（`lib/input/procs.ts` の `readParents`）にある。起動元の導き方はサイクル8では `src/input/spawners.ts` にあり、サイクル9で書き直す。
- `background` の行は起動された行にしない。祖先は Claude Code の常駐プロセスで、今の Claude Code ではほかの行に当たらない。当たったとしても、起動された行として扱うと、attach と削除の扱いが食い違う。
- 前回の関係を持ち越す場面が2つある。持ち越すのはメモリの中の表だけで、状態のファイルには書かない。
  - 表に `pid` がない行（`--json` と `ps` を読む間に終わった行、表が読めなかった回の行）は、起動元がまだ行に残っていれば持ち越す。持ち越さないと、その1回だけ起動された行がトップレベルに出て、入れ子がちらつく。
  - 祖先をたどっても行に当たらない行は、起動元の行がこの回の `--json` でまだ `pid` を持っていれば持ち越す。読む間に起動元のプロセスが終わったときは、次の回に起動元の行の `pid` が消えるので、そこで終わる（止めた起動元の下に残り続けない）。間のシェルだけが終わって親が pid 1 に付け替わったときは、起動元が動いている間は持ち越し続ける。その行を起動したのは起動元なので、入れ子のままにする。
  - 表が読めなかった回に初めて出た行は、前回の関係がないので、その回だけトップレベルに出る。
- 祖先をたどっても行に当たらない `interactive` の行は、そのプロセスの環境変数 `MCP_CALLER_PID` を読む。値が `--json` の別の行の `pid` と一致すれば、その行を起動元とする（会話の外で動く MCP サーバが起動した行。PRODUCT.md「依存（待ち先と起動された行）」、#273）。祖先から分かる行は読まない。
  - 環境変数は `ps -E -ww -o pid=,command= -p <pid>,…` で、該当する行の pid だけをまとめて1回読む（macOS では、同じ利用者のプロセスなら読めることを確かめた。Linux なら `/proc/<pid>/environ`）。`ps -E` の出力はコマンド行と環境変数が空白でつながるので、` MCP_CALLER_PID=<数字>` の語を探す。プロンプトの文字列に同じ語が入っていると取り違えうるが、一致する `--json` の行がなければ使わないので、外れても入れ子が1つ増えるだけで、利用者の操作には効かない。
  - 読めなかった、値がない、一致しないときは、今までどおりトップレベルに `(tty)` で出す。読んだ値は、その行が `--json` から消えるまでメモリに持ち、毎回は読み直さない（環境変数はプロセスの生きている間に変わらない）。
  - 値を入れるのは利用者の MCP サーバで、値の出どころは MCP の設定の `headersHelper` の `$PPID` である。`headersHelper` は Claude Code がセッションの接続のたびに実行し、`$PPID` はそのセッションの `claude` の pid（`--bg` なら `claude bg-spare`）で、`--json` の `pid` と一致した（2.1.310。#273）。
- 最初に当たった行が一覧に出ていない（対象外の）ときも、起動された行として扱い、トップレベルに `(sub)` を添えて出す。その先の祖先はたどらない。起動元が一覧に出れば、その下に入る。
- 起動元の関係は、段と並びの中で入れ子を導くためだけに使い、待ちの段と `↳ <名前> done` には使わない（PRODUCT.md「依存（待ち先と起動された行）」）。サイクル8までは待ち先の関係に辺として足し、同じ規則で待ちの段を導いていたが、サイクル9で外した。
- 起動された行には待ち先もメモも結ばない（`f` と `e` を断る。`f` のメニューにも並べない）。待ち先は1つの待ち元にしか結べないので、2種類の関係を合わせても、各行の親は1つだけになり、一覧は木になる。起動された行と分かった行に結ばれた関係（状態のファイルから読んだもの、起動元が分かる前に結んだもの）は外す。サイクル8は、注釈を付けた行を起動された行にしない例外を置いていたが（#254）、サイクル9ではやめた。
- カーソルを置く行に、起動された行を選ばない。起動された行は attach も `f` も `e` も断るので、選ぶと手を付けられない行に乗る。当てはまるのは、行が消えたときに選ぶ同じ区切りの隣の行である。
- 選んでいた起動された行が消えたときは、並べ直す前の組で起動元を近い順にたどり、新しい一覧に残っていて、新しい並びで起動された行でない最初の行に移る。たどるのは、起動された行でない最初の祖先（大本の起動元）までで、その上の待ち元には移らない。2段の入れ子の中間の起動元は、残っていても起動された行なので飛ばし、大本の起動元へ戻る。大本の起動元が消えて中間の起動元がトップレベルの行になったときは、そこに移る。
- `--json` の値から段を決める規則には使わない。起動された行は段を変えないので、[ADR-0001](adr/0001-read-state-only-from-agents-json.md) の「状態は `--json` からだけ読む」は変わらない。
- 作業台の `⚙` も `ps -A` を読むが（tmux のモジュール）、まとめない。モジュールの境界をまたいで表を渡す口が要り、`ps` 1回の費用は小さい。
- stdio の MCP サーバは起動元の `claude` の子プロセスなので、祖先をたどれば拾える（[claude-code-behavior.md](claude-code-behavior.md)「起動された `claude -p` のプロセスの祖先」）。HTTP で待ち受ける MCP サーバや、常駐のデーモンを経由する起動は、祖先に起動元が出ないので拾えない。これらは、上の `MCP_CALLER_PID` があるときだけ引ける。

## 待機時間の取り方

- `--json` には「いつ今の状態になったか」がなく、`startedAt` は `claude -r` で再開すると更新されるので、待機時間の代わりにならない。待機時間は、フックのイベントの時刻から、なければ会話記録の行の時刻から取る（「機能ごとの入力の出どころ」）。どちらもなければ whatnext の観測から推定する。

## Usage の取得

- 取得には `claude -p "/usage" --no-session-persistence --output-format json` を使う。モデルを呼ばないので rate limit を消費しない。`--no-session-persistence` を付けないと、呼ぶたびに会話ファイルが残る。プロジェクトの設定や hook を拾わないよう、一時ディレクトリで実行する。
- `/usage` の結果は人間向けの文字列なので、`Current <枠>: <N>% used · resets <時刻>` の行を読む。取得に失敗したとき、または読める行が1つもないときは、前に取れた値を出したままにする。一度も取れていなければ Usage を出さない。エラーは示さず、一覧のほかの動作は変えない。

## フックの受信

- `n` で起動するセッションには、`--settings` の `hooks` で、`UserPromptSubmit`、`Stop`、`StopFailure`、`PermissionRequest`、`PreToolUse`（`AskUserQuestion` だけ）のフックを付ける。受け口を開けていないときは付けない（「OTel の受信」）。利用者自身の設定にあるフックは上書きされず、併せて動く（[claude-code-behavior.md](claude-code-behavior.md)）。
- フックの種類は `command` にし、コマンドは `curl -s -m 1 -o /dev/null --data-binary @- http://127.0.0.1:14318/v1/hooks; exit 0` とする。フックの入力を OTel と同じ受け口に送り、送れなくても何も出力せずに終了コード 0 で終わる。こうすると、whatnext を終了している間もセッションの画面にエラーが出ず、`PermissionRequest` に許可や拒否の判断を返すこともない（[ADR-0003](adr/0003-no-input-injection-or-proxy-response.md)）。コマンドに whatnext の置き場所を書き込まないので、whatnext を入れ直しても、それ以前に起動したセッションのフックはそのまま届く。
- `http` のフックは使わない。受け口が閉じていると、セッションの画面に `Stop hook error: connect ECONNREFUSED` を出す。sandbox のプロキシや組織の設定（`allowedHttpHookUrls`）の影響も受ける。
- 受けた値はメモリにだけ持つ（[ADR-0002](adr/0002-no-writes-no-persistent-state.md)）。whatnext を終了している間に発火したフックは失われる。端末のウィンドウを閉じているだけなら、受け口は開いたままで失われない。起動し直した直後の一言と待機時間は、会話記録で補う（「会話記録の読み取り」）。
- 受けた値の使い道は、行の一言と待機時間の推定の2つである。
- **待機時間の推定**：稼働中の行では、最後の `UserPromptSubmit` の時刻を稼働を始めた時刻とする。それ以外の行では、最後の `Stop`、`StopFailure`、`PermissionRequest`、`AskUserQuestion` の時刻を「今の段に入った時刻」とみなす。ただし、それより新しい指示があれば使わない（前のターンの時刻になるため）。フックは段が変わる瞬間に発火するので、観測による悲観的な推定より正確である。フックの時刻は段を決め直すとき（起動時、60秒ごと、更新キー、attach のあと）にだけ反映し、更新の間に並びは変わらない。
- 中断したターン（権限の確認で `No` を選んだときなど）では `Stop` が発火しない。その行の一言と待機時間は会話記録で補う。

## OTel の受信

- `n` で起動するセッションには、`--settings` の `env` で OTel の設定を付ける。送信先は、whatnext が `127.0.0.1` で開く受け口にする。metrics は受けない（COST の列のためだけに受けていた）。起動したシェルの環境変数は `--bg` のセッションに届かないので、`--settings` を使う（[claude-code-behavior.md](claude-code-behavior.md)）。
- whatnext は起動している間だけ受け口を開き、受けた値はメモリにだけ持つ（[ADR-0002](adr/0002-no-writes-no-persistent-state.md)）。常駐する保存先やメトリクス基盤は置かない。
- 受け口のポートは `127.0.0.1:14318` に固定する。利用者が既存のコレクタを既定の 4318 で動かしていてもぶつからないようにする。**whatnext は同時に1つだけ動かす。** 専用の tmux サーバに一覧がすでにあれば、新しく動かさずにその一覧につなぐ（「一覧と作業台の仕組み」）。それでも受け口を別の whatnext（サーバ名の違う版など）が開いているときは、そのことを英語で示して終了する（終了コード 1）。2つ目の whatnext は受け口を開けず、一言も待機時間も出さずに黙って動くことになるため。別の whatnext かどうかは、受け口に `GET /v1/whatnext` を送って確かめる。応答は `{"app":"whatnext"}` とし、受ける側は素の文字列の応答も whatnext とみなす。版の違う whatnext（サイクルごとに書き直したもの）が動いていても、二重起動を正しく判定するため。whatnext 以外のプログラムがポートを使っているときは、受け口を開かずに動き、`n` で起動するセッションにもフックと OTel を付けない。付けると、そのセッションは生きている間ずっと、指示と最後の応答の全文を、ポートを使っている別のプログラムに送り続ける。こうして起動したセッションは、外で起動したセッションと同じ扱いになり（一言と待機時間は会話記録で補い、CTX は `-`）、あとで whatnext が受け口を開けても変わらない。エラーは示さない。
- 受けた値の使い道は、CTX の列だけである。待機時間の推定にはフックを使う（「フックの受信」）。
- OTel は常に受け、オプトインにはしない。受け口をフックと共用しているので、オプトインにしても減る仕組みがなく、起動時のオプションが1つ増えるだけになる。
- whatnext を終了して起動し直した直後は、CTX は次のターンまで空欄になる（logs は再送されない）。
- whatnext の外で起動したセッションと対話セッションは OTel を送らないので、CTX は `-` になる。User Story 12 のうち、この列だけは例外になる。会話記録の `message.usage` で補う案は採らない（[ADR-0011](adr/0011-fill-in-from-transcripts-when-hooks-are-missing.md)）。空欄が困るようになったら、利用者が `~/.claude/settings.json` の `env` に自分で OTel の設定を書く経路を検討する。これは「書き換えを求める別ツールも前提にしない」（[ADR-0002](adr/0002-no-writes-no-persistent-state.md)）を「利用者が任意で設定すれば値が出る」に緩める判断になる。この経路で `--bg` に届くかは未確認（[claude-code-behavior.md](claude-code-behavior.md)）。

## 会話記録の読み取り

- フックで取れない一言と待機時間を、Claude Code がセッションごとに残す会話記録（`~/.claude/projects/*/<sessionId>.jsonl`）から取る（[ADR-0011](adr/0011-fill-in-from-transcripts-when-hooks-are-missing.md)）。どの機能で補うかは「機能ごとの入力の出どころ」にある。
- 会話記録は `--json` に出ているセッションについてだけ、`sessionId` でファイルを探して読む。フォルダ名は `cwd` から組み立てない（worktree の中で動いたセッションは、worktree のパスに対応するフォルダに記録が残る）。`CLAUDE_CONFIG_DIR` が設定されていれば、`~/.claude` の代わりにそこを探す。
- 読むのは一覧を更新するとき（起動時、60秒ごと、更新キー、attach から戻ったとき）だけである。ファイルは数 MB になるので、前に読んだときから更新時刻が変わったファイルだけを、末尾から必要な分だけ読む。
- 概要の行の最初の依頼だけは、先頭から読む（最大 2 MB）。一度見つけたら変わらないので覚えておき、読み直さない。まだ見つからないセッションは、ファイルが伸びたときだけ読み直す。`UserPromptSubmit` のフックを受けたとき、そのセッションの最初の依頼がまだなければ、会話記録を読み直して置き直す。指示の行がフックより少し遅れて書かれることがあるので、見つかるまで数回（約10秒まで）読み直す。このときは、ファイルの置き場所も前回の読み取りも覚えた値を使わずに探し直す（会話記録のファイルは最初の依頼を送るまでないので、「ない」を覚えると見つけられない）。置く先のセッション `<id>` は `sessionId` の先頭 8 文字から決め、`--json` を読み直さない（起動した直後のセッションは、一覧の行にまだないため）。フックの `prompt` の値をそのまま使わないのは、コマンドなどを除く規則を会話記録の読み方の1か所にそろえるため。起動した直後のセッションは一覧の行がまだないので、attach するときに名前だけを置く。一覧はこの値と名前を、claude の画面のセッションの tmux のオプションに置き、ステータス行の書式が幅に合わせて切って描く。tmux は値の中の `#` を書式として読むので、`##` にして置く。
- 読み取りに失敗したとき（ファイルがない、形式が読めない）は、補わずに続ける。エラーは示さない。段と並びは会話記録に左右されない。
- 会話記録は読むだけで、書き込まない。
- 読んだ値はメモリにだけ持つ。
- 依存する項目と実測した形式は [claude-code-behavior.md](claude-code-behavior.md) にある。

## 場所の問い合わせが失敗したとき

- `git` の問い合わせが失敗すると、場所はリポジトリでない場所として返る。前回リポジトリだった場所がそう返ったときは、1回だけ前回の場所を使う。続けて2回そう返ったら、本当にリポジトリでなくなった（worktree を消したなど）とみなす。一度の失敗で、WHERE とリポジトリの区切りが入れ替わらないようにする。

## 状態のファイルに書くもの

- メモと待ち先の関係を、`${XDG_STATE_HOME:-~/.local/state}/whatnext/state.json` に書き、起動し直しても引き継ぐ（[ADR-0016](adr/0016-persist-holds-and-waits-in-a-state-file.md)）。リポジトリの区切りの中の並びのために、セッションごとの whatnext から最後に attach した時刻と、whatnext が初めて見た時刻も書く（[ADR-0018](adr/0018-persist-view-and-attach-times-in-the-state-file.md)）。ほかの値はメモリにだけ持つ。
- サイクル9では `version` を 3 にし、保留の `holds` をメモの `notes` に改め、ビューの `view` を書かない（ラダーのビューをやめ、ビューが1つになったため。ADR-0018 の「見直す条件」）。`version` が 1 と 2 のファイルは、`holds` の理由をメモとして読み（空文字はメモなし）、待ち先の関係と時刻（2 だけ）を読み、`view` は読み捨てる。版を上げるたびに注釈を失うと、ADR-0016 で引き継ぐと決めたものが消えるため。1〜3 のほかの版、壊れたファイル、ないファイルは、空として読む。読めなかった（ないのではなく、壊れているか知らない版の）ファイルは、利用者がメモか待ち先を変えるまで置き換えない。時刻だけで置き換えると、新しい版のファイルにあった注釈が、操作なしに消えるため。
- attach した時刻は、`claude attach` を始めたときと、一覧に戻ったときに書く。戻ったときにも書くのは、attach している間に新しく見えたセッションより、離脱したセッションを上に置くため（PRODUCT.md「リポジトリの区切りと並び」）。初めて見た時刻は、一覧に初めて出たとき（`--json` に出ていて対象外でないとき）に書く。`--json` から消えたセッションの時刻は、待ち先の関係と同じく更新のたびに外す（一覧から外れただけでは外さない）。
- 形は `{"version": 3, "notes": {<sessionId>: <メモ>}, "waits": {<待ち元の sessionId>: [<待ち先の sessionId>, …]}, "seen": {<sessionId>: {"first": <ミリ秒>, "attached"?: <ミリ秒>}}}` である。
- 読んだ関係が木にならないとき（1つの待ち先を2つの待ち元が待つ、一周する、`(tty)` の行や起動された行が待ち元になっている、起動された行が待ち先になっている）は、段と並びでその関係を結ばれていないものとして扱う（PRODUCT.md「依存（待ち先と起動された行）」）。読み込んだだけではファイルを書き換えず、利用者がメモか待ち先を変えたときに、扱った関係だけを書いて置き換える。`(tty)` かどうか、起動された行かどうかは `--json` とプロセス表を読むまで分からないので、ファイルを読む時点では判定しない。
- 一覧のプロセスが起動したときに読む。書くのは、並べ直したとき、メモや待ち先を変えたとき、attach した時刻を書いたときで、そのたびに中身を作り、前に書いたものと違うときだけ書く。中身を作るのは軽い（件数はセッションの数ほど）ので、変わったかどうかを呼ぶ側で判断しない。一時ファイル（`state.json.<pid>.tmp`）に書いてから `rename` で置き換える。書けなかったときは一覧を止めず、次に変わったときにまた書く。
- `--json` から消えたセッションの関係とメモは、更新のたびにメモリから外し、続く描き直しでファイルからも消える。一覧から外れただけ（対象外になった）では外さない。`--json` を読めなかった更新ではメモリを触らないので、ファイルも変わらない。
- `WHATNEXT_TMUX_SOCKET` が既定の `whatnext` でないときは、ファイルを `state-<ソケット名>.json` に分ける。確かめるために横で動かす whatnext が、利用者のファイルを書き換えないようにする。
- 一覧のプロセスは、専用の tmux サーバに1つだけ動く（同じソケット名で `whatnext` をもう一度起動すると、動いている一覧につなぐ）。同じファイルを2つのプロセスが書き合うことはない。

## 一覧と作業台の仕組み

仕組みと退けた案は [ADR-0012](adr/0012-list-runs-inside-the-dedicated-tmux-server.md) と [ADR-0010](adr/0010-workbench-lives-inside-whatnext.md) にある。この節の「クライアント」は、とくに断らなければ whatnext の画面（一覧とセッションの画面を映す端末）のクライアントを指す。作業台の画面のクライアントは「作業台の画面の仕組み」にある。

- 一覧は、専用の tmux サーバ（`tmux -L <名前> -f /dev/null`、`TMUX` は外す）のセッション `list` の中で動く。tmux の設定は、起動してから一覧のプロセスが `source-file -`（標準入力）で流し込む。設定に一覧の pid とスクリプトのパスが要り、一覧のプロセスが起動し直すたび（異常終了のあと）に入れ直すため。`whatnext` を実行すると、`list` があればそこにつなぎ、なければ作ってつなぐ。別のクライアントがつながっていれば離す。
- 例外として、`terminal-features`（外側の端末の機能。色の `RGB` と、リンクの `hyperlinks`）は、サーバを作る `new-session` と同じ呼び出しで入れる。tmux はクライアントの端末の機能を attach した時点の値で決め、あとで変えても、つながっているクライアントには効かない。一覧が設定を流し込むより先にクライアントが attach するので、一覧から入れると最初のクライアントに効かなかった（サイクル6で、attach 済みの Ghostty のクライアントに `hyperlinks` が付かないことで分かった）。`hyperlinks` がないと、tmux はペインの中の OSC 8 のリンクを外側の端末に送らない。
- `list` につなぐ前に、動いている一覧の版を確かめ、起動した版と違えば、一覧にそのことを示させる（[PRODUCT.md](PRODUCT.md)「終了と、端末のウィンドウを閉じたとき」）。tmux のキーとフックが呼ぶスクリプトは、動いている一覧と同じ版のものにする。同じ場所に入れ直す更新ではスクリプトだけが新しい版に置き換わり、古い一覧と新しいスクリプトが混ざって動くため。版の確かめ方と、スクリプトを版ごとに分けるやり方は実装に任せる。
- `Enter` はクライアントをセッション `<id>`（中で `claude attach <id>` が動く）に切り替え、`ctrl+q ctrl+l` と ← は `list` に切り替える。`claude attach` が終わったとき（Ctrl+Z、`/exit`、失敗）も `list` に戻す。一覧は端末を手放さないので、`stty` による保存と復元や Node の内部 API への介入は使わない。
- 端末のウィンドウを閉じるとクライアントが離れるだけで、`list` の中の whatnext は動き続ける。クライアントが `<id>` を見ていたときに離れたなら、次につながったときに `list` に切り替え、そのセッションから戻ったときと同じに扱う。
- tmux は利用者から隠す。ステータス行は、attach した claude の画面のセッションと、作業台の画面にだけ出す（[PRODUCT.md](PRODUCT.md)「作業台」）。作業台の欄は、tmux が数秒ごとに作業台のペインの子のプロセスを `ps` で引いて描く。
- 専用サーバでは `focus-events` を有効にし、端末のフォーカスのイベントを中のアプリに渡す。whatnext を挟まないときと同じに届けるため（[ADR-0010](adr/0010-workbench-lives-inside-whatnext.md) が tmux に求める「claude の画面の忠実な中継」）。Claude Code が何に使うかは確かめていない。
- 専用サーバは `allow-passthrough on` にする。Claude Code は tmux の中では、通知（iTerm2 の OSC 9、kitty の OSC 99、Ghostty の OSC 777）、進み具合の表示（OSC 9;4）、タブの状態、背景色の問い合わせを tmux の passthrough（`ESC Ptmux; … ESC \`）で包んで送り、tmux はこれを on のときだけ外側の端末に通す（Claude Code 2.1.310、tmux 3.8 で確かめた。#268）。端末の中に画像を出す機能も、passthrough がないと使えない。off だと、whatnext を挟んだときだけこれらが失われ、ADR-0010 が tmux に求める「claude の画面の忠実な中継」に反する。`all`（見えていないペインからも通す）にはしない。サイクル4〜7は on で、サイクル8は理由なく外れていた。通知が実際に出る場面は再現できていないので、利用者の通知が届くようになったかは確かめていない。
- 専用サーバは `set-clipboard on` にする。作業台の画面のドラッグのコピーと、claude の `/copy` を外側の端末のクリップボードに届けるため（`/copy` が tmux の中から届くことは確かめていない）。
- `n` の信頼の確認は、クライアントをセッション `trust-<乱数>`（中で対話モードの `claude` が動く）に切り替えて出す。一覧は `~/.claude.json`（`CLAUDE_CONFIG_DIR` があればその下）を 0.5 秒ごとに読む。そのディレクトリの `hasTrustDialogAccepted` が `true` になったら、クライアントを `list` に戻してから `trust-<乱数>` を畳み、`claude --bg` をやり直す。断って `claude` が終わったときは、ペインのコマンドがクライアントを `list` に戻す。`detach-on-destroy on` なので、クライアントが見ているセッションを先に畳むと、端末ごと離れてしまう。
- 一覧の役として動くのは、`WHATNEXT_ROLE=list` があり、かつ自分のペイン（`TMUX_PANE`）が専用サーバのセッション `list` にあるときだけにする。whatnext の中で動くシェル（作業台、attach したセッションの Bash）はこの環境変数を引き継ぐ。変数だけで判断すると、そこから起動した whatnext が一覧として動き、利用者のサーバの設定を入れ直して、残した attach を畳んでしまう（サイクル6で実際に起きた）。
- tmux から一覧への知らせ（キーと、`client-session-changed`、`client-attached`、`client-detached`、`session-closed`、← の `pane-title-changed` のフック）は、小さな sh を `run-shell -b` で呼び、一覧のプロセスに SIGUSR2 を送るだけにする。一覧は知らせを受けたら `list-clients` を問い合わせて、戻った・入った・端末が閉じた、を自分で判断する。頼みごと（`ctrl+q ctrl+f` など、一覧に戻ってから処理するキー）は tmux のオプションに書いてから知らせる。受け口のポート（HTTP）を使わないのは、ポートを別のプログラムが使っているとき（シナリオ 41）にもキーが効くようにするため。SIGUSR1 は Node の inspector が使うので避ける。
- 残した `claude attach` は、1本あたり約 140MB のメモリを使う。本数に上限は設けず、そのセッションを止めたとき、削除したとき、whatnext を終了したときに畳む。
- attach している間のキーは、1か所の表から、tmux の割り当て、一覧に戻ってから処理する頼みごとの列挙、キーの説明（claude の画面のステータス行）を作る。サイクル6ではキーを1つ足すのに6か所を手で触り、頼みごとの列挙の足し忘れで、キーが一覧に戻るだけで効かなかった。

## 作業台の画面の仕組み

仕組みと退けた案は [ADR-0014](adr/0014-workbench-shows-in-a-screen-the-user-opens.md) にある。サイクル7で実装して確かめた（[PRODUCT.md](PRODUCT.md)「受け入れシナリオ」のサイクル7の完了条件）。

- 作業台の画面は、専用の tmux サーバの2つ目のクライアントである。`whatnext workbench` は、専用サーバの一覧が動いていることを確かめてから、専用サーバにクライアントとしてつなぐ。一覧は、どのクライアントが whatnext の画面で、どれが作業台の画面かを見分ける（見分け方は実装に任せる。クライアントの名前や tty、つなぐときに立てる印など）。一覧のクライアントを1つに限るのと同じく、作業台の画面のクライアントも1つに限り、新しくつながったら古いほうを離す。
- 作業台の画面は、whatnext の画面が映すものに合わせて `switch-client -c <作業台の画面のクライアント> -t <セッション>` で切り替える。whatnext の画面が `<id>` なら `sh-<id>`、`list` ならカーソルの行の `sh-<id>`、作業台がなければ案内を出すセッションに切り替える。案内のセッションは、作業台がないことと作ったときの場所を描き、`Enter` で作業台を作る頼みごとを一覧に渡す小さなプログラムを動かす（作り方は実装に任せる）。
- 作業台を作るとき（`ctrl+q ctrl+w`、一覧の `w`、案内の `Enter`）は、`--json` を読み直してそのセッションの `cwd` を取り、`new-session -d -s sh-<id> -c <cwd>` で作る。`ctrl+q ctrl+v` の読み直しと同じ取り方である。
- Ghostty で押した `ctrl+q ctrl+w` と一覧の `w` は、作業台を作ったあと（あれば作らずに）、`osascript` で Ghostty の AppleScript を呼ぶ（[ADR-0015](adr/0015-ghostty-split-for-workbench-on-ctrl-q-ctrl-w.md)）。押したクライアント（一覧の `w` では whatnext の画面のクライアント）の `client_termname` が `ghostty` を含むときだけ呼ぶ。
  - 作業台の画面のクライアントがつながっていれば、名前（端末のタイトル）が `whatnext workbench` の Ghostty の分割を探して `focus` する。タイトルは、作業台のセッション（`sh-<id>` と案内のセッション）だけで `set-titles on` にして出す。whatnext の画面のタイトルには触れない。`whatnext workbench` は終わるときに OSC 2 でタイトルを消し、古いタイトルの分割へ移らないようにする。
  - つながっていなければ、Ghostty が前面にあることを確かめ、前面のウィンドウの選ばれたタブの `focused terminal`（押した分割）を `split ... direction right` で分割する。新しい分割はいつものシェルで開き、`initial input` で ` exec <node> <cli.js> workbench` を打ち込む。`WHATNEXT_TMUX_SOCKET` と `WHATNEXT_PORT` は `environment variables` で渡す。`exec` にするので、作業台の画面が終わるとシェルごと終わり、分割が閉じる。
- 作業台の最後のシェルが終わって `sh-<id>` が消えるときは、作業台の画面のクライアントを先に案内のセッションへ切り替えておく。`detach-on-destroy on` なので、クライアントが見ているセッションが先に消えると、作業台の画面ごと離れてしまう（working-with-tmux スキル）。消えるセッション自身の `detach-on-destroy` が使われるので、セッションが消えてからでは間に合わない。専用サーバ全体を `remain-on-exit on` にし、`pane-died` のフックでペインが終わった時点で処理する（ほかに生きているペインがあれば閉じ、最後なら作業台の画面を案内に切り替えてからセッションを畳む）。一覧を通さないので、一覧が落ちていても動く。whatnext が作るほかのウィンドウ（`claude attach`、一覧）は `remain-on-exit off` にする。
- 作業台の画面で押した `ctrl+q` のキーは、押したクライアントが作業台の画面であることと、映している `sh-<id>` から対象のセッションを決める。`ctrl+q ctrl+l` などの「whatnext の画面を一覧に戻す」キーは、作業台の画面ではなく whatnext の画面のクライアントを切り替える。短い知らせ（`display-message`）は、押したクライアントに出す。`ctrl+q ctrl+v`（VS Code で開く）は一覧に戻らず、結果をこの知らせで示す。tmux のメニュー（`display-menu`）は使わない。
- `sh-<id>` と案内のセッションだけ、tmux の `mouse` を on にする（`mouse` はセッションごとの設定）。off のままだと、tmux のクライアントは代替画面で描くので、端末（Ghostty）はホイールを ↑↓ のキーに変えて送り、作業台の出力ではなくシェルの入力履歴が動く。on にすると、ホイールで tmux のコピーモードに入って履歴をさかのぼり、ドラッグの選択は tmux が持ち、離すとコピーする（`set-clipboard on` で端末のクリップボードに届く）。一覧と claude の画面のセッションは off のままにする。
- 作業台の画面にフォーカスが移ったとき（`client-focus-in`）、案内の場所を `--json` から読み直す。claude が worktree に入ったあと、作る前に場所を確かめられるようにする。
- 作業台の画面のステータス行は `sh-<id>` と案内のセッションにだけ出し、1行にする。whatnext の画面のステータス行（2行）とは別の書式にする。
- 端末の分割の大きさは、クライアントごとに tmux が扱う。作業台の画面が映すウィンドウは作業台の画面の大きさに合う。whatnext の画面と作業台の画面が同じセッションを映すことはないので、大きさの取り合いは起きない。

### 確かめたこと（サイクル6、サイクル7）

- **claude の画面の幅の変化は問題にならない**（claude 2.1.284、tmux 3.7c）。`claude attach` は代替画面で描くので、分割と解除を繰り返してもスクロールバックに描き直しが積もらない。狭めると折り返して描き直し、戻すと元の画面に戻る。ただし利用者の statusline は、広げた直後も狭い幅で切った形のまま残り、statusline の次の再実行で直る。作業台の画面を開閉すると、whatnext の画面の幅が変わるので、同じことが起きる。
- **Ghostty の既定のキー**（1.3.1）：`cmd+d` で右に分割、`cmd+shift+d` で下に分割、`cmd+w` で分割を閉じる、`cmd+[` と `cmd+]` で前後の分割へ、`cmd+opt+矢印` でその方向の分割へ、`cmd+ctrl+矢印` で境界を動かす、`cmd+shift+enter` で分割の拡大。作業台の画面の開閉、フォーカス、幅は、これらで足りる。
- **Ghostty の AppleScript**（1.3.1）：tmux サーバから起動した `osascript` でも Ghostty を操作できる（利用者の環境では許可済みだった）。`split` の `with configuration` で `command` を渡すと、`wait after command` を false にしても、コマンドが終わったあと `Process exited. Press any key to close the terminal.` を出して分割が残る。`initial input` で `exec` を打ち込めば、終わると分割が閉じる。分割がどの tty か、シェルの入力待ちかどうかは取れない。分割の見分けには `name`（端末のタイトル）と `id` を使う。

- **クライアントの見分け**（サイクル7、tmux 3.7c）：whatnext の画面と作業台の画面が、それぞれ自分の端末の tty（`tty` の出力は `#{client_tty}` と同じ形）を専用サーバのオプションに置いて見分けた。端末を閉じて開き直すと同じ tty が使い回されるので、つないだ側は、もう一方の印が自分と同じ tty なら消す。閉じて開き直したとき、2つ目の作業台の画面をつないだとき、whatnext の画面だけを閉じたときで、取り違えなかった。
- **カーソルを速く動かしたとき**（サイクル7）：60ms 待ってまとめ、切り替えを1本の鎖で順に行うと、`Down` を3回続けても最後の行の作業台に落ち着いた。

## 確かめ方

シナリオは、次の4つの層のどれかで確かめる（[PRODUCT.md](PRODUCT.md)「サイクル9の完了条件」）。
テストは外から観測できる振る舞いだけを対象にする。

| 層 | 実行 | 中身 |
|---|---|---|
| 単体 | `npm test` | 段と並び、画面の組み立て、入力の読み取り(会話記録、フック、OTel、Usage)、状態のファイル、候補の表示名と絞り込み、引数を、固定データで確かめる |
| 画面の通し | `npm run test:e2e` | 専用の tmux、偽の claude、偽の `open` で whatnext を起動し、send-keys で操作して capture-pane で画面を読む |
| 実機の通し | `npm run test:real` | 実機の claude（haiku）で起動したセッションを使う。Ghostty の分割は AppleScript で操作する。スクリプトにして何度でも流せるようにする |
| 手動 | 利用者 | マウスでの選択とコピーにもう一方の文字が混ざらないこと（25、25a）、ホイールで作業台の出力をさかのぼれること（25a）、サイクル7の whatnext より悪くなっていないことの判断 |

- `npm test` はコミットごとに流す。`test:e2e` は、tmux、操作、作業台に触れたコミットで流す。`test:real` は、完了条件を判定する前と claude を更新したあとに流す。
- `test:real` は、テスト用の一時ディレクトリ（信頼の確認を済ませたもの）、tmux のソケット、受け口のポート、状態のファイルを使い、利用者が使っている whatnext とそのセッションには触れない。起動したセッションは、終わったら `claude rm` で消す。Ghostty のシナリオは、前面に新しいウィンドウを開いて操作し、終わったら閉じる。
- 実機の応答の揺れで安定しないシナリオは、issue に起票して確かめ方を決め直す。
- 実機の通しのセッションは、利用者の `~/.claude/settings.json` の権限モードを引き継ぐ。利用者の既定が `auto` だと権限の確認が出ず、権限待ちのシナリオ（23、33、45）が成り立たない。テストの作業ディレクトリに `.claude/settings.local.json` を書き、`permissions.defaultMode` を `default` に固定する（プロジェクトの設定は利用者の設定より優先される）。
- 実機の通しの一覧には、利用者の本物のセッションも並ぶ。確かめるのはテストのセッションの行と、その組の中だけにする。画面全体に対して確かめると、利用者のセッション（CTX が `-` のレビュー待ちなど）や、その時に動いているものの `(sub)` の行に当たって落ちる。
- 実機の通しは、ほかに何も流さずに実行する。review-loop のように `claude -p` を起動するものを並行して流すと、行が増え、並びも変わる。流す前に、テストのセッション（`wn-real-…`）の権限の確認に答えないよう利用者に伝える。利用者が自分の画面から許可すると、権限待ちを確かめるテストが落ちる。

## 外部 watcher（別ツール）の設計の要点

外部の出来事を監視し、必要なときにセッションを起こす別ツール。監視先ごとに作ってよい。
whatnext の側で必要な要件は、人間が起動したセッションを前提にしないこと（機械生成の `name` や `cwd` で壊れないこと）だけである。

- **起こす価値があるものだけ起こす。** セッションは利用枠を使う。flaky なテストの失敗や、見ればすぐ分かるレビュー依頼まで起こさない。この選別の良し悪しが外部 watcher の品質になる。
- **出来事が解消したら片付ける。** CI が再実行で通った、別の人がレビューを済ませた、といった場合は、外部 watcher が解消を検知して `claude stop` する。
- **同じ出来事で二度起こさない。** `--name` に出来事の識別子（Slack ならメッセージの `ts`、CI なら `ci-<repo>-<runId>` など）を埋め、起動の前に `--json --all` で同じ名前を探す。セッション一覧そのものが着手済みの台帳になる。`claude -r` でコピーが作られると `--name` が引き継がれず重複排除が崩れるので、新規の起動だけを行う。
- **plan mode で起動する。** セッションは調査だけを行い、計画を出して止まる。承認の対象が「外部の出来事についての推測」から「具体的な変更計画」に変わり、判定を誤って起動してもコードは書かれない。却下は `claude stop` で行う。未確定の前提として、計画の承認待ちで `waitingFor` に何が出るかがある。`"permission prompt"` と出るなら権限待ちの段に入るが、実際には計画を読む必要があり解除コストは大きいので、別の段に置く判定が要る。
- **プロンプトインジェクションを防ぐ。** Slack のメッセージ、PR のコメント、CI のログは信頼できない入力である。本文はデータとして囲み指示として解釈させない、対象を限る（Slack なら DM と特定のチャンネル、送信者のホワイトリスト）、`--permission-mode plan` を強制して `auto` と `bypassPermissions` を使わない、worktree の分離（`--bg` の既定）を切らない、を最低限の防御とする。
- **routine（クラウド）で作るときの制約。** routine には permission mode の選択がなく、plan mode を強制できない。含めたコネクタへの書き込みも承認なしで行われるので、コネクタを読み取りに必要なものに絞る。止まったものは whatnext に出せないので、プロンプトで「必要なコネクタや GitHub が使えなければ `PushNotification` で知らせて止まる」と書かせる（通知をタップするとそのセッションが開く）。起動しなかった実行（GitHub の接続切れ、一時停止、上限）と通知の手前で落ちた実行は拾えないので、`/schedule` で routine の状態を確かめて補う。GitHub トリガーは pull request と release だけで、CI の失敗には直接反応しない。
